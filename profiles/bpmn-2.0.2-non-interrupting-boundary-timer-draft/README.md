# BPMN 2.0.2 non-interrupting boundary Timer draft profile

This standards profile selects one User Task carrying one non-interrupting Timer Boundary Event with an exact `PT1S` duration. The Activity and its deadline are armed atomically, the Activity's own completion withdraws the deadline and follows its normal outgoing flow, and a fired deadline spawns a concurrent branch along the boundary output **while the host Activity stays active and independently completable**. Each branch reaches its own follow-on User Task, so the spawn is visible at the public observation boundary as two open tasks where an interrupting implementation publishes one.

The [profile artifact](profile.json) names BPMN 2.0.2 Clause 10.5.4, Clause 10.5.6, Clause 13.2, Clause 13.5.3, Table 10.91, and Table 10.92 as normative authority: Clause 10.5.4 for the Boundary Event attribute tables, Table 10.91 for the attributes themselves, Table 10.92 for the legal `cancelActivity` values per trigger whose Timer row reads `True/false`, Clause 10.5.6 for the continuing-Activity behavior granted to a lexical *false*, Clause 13.5.3 for the handling order and its non-interrupting arm, and Clause 13.2 for the quiescent Process completion the two concurrent branches must reach. Relationships `CIB-AGR-0001` and `CIB-OP-0001` govern only the reused User Task interaction boundary: its lifecycle, and the mapping of semantic task identity with stale-command refusal. No CIB Boundary Event or non-interrupting compatibility claim is selected, and the mechanism is vendor-neutral.

Admission is the exact inverse of the [interrupting sibling profile](../bpmn-2.0.2-activity-boundary-timer-draft/README.md), and that inversion is load-bearing rather than stylistic. `cancelActivity` must name *false*, which its `xs:boolean` lexemes `false` and `0` both do. An omitted attribute and a lexical `true` are rejected, because the XSD and CMOF default resolves omission to `true` and interrupting behavior is the sibling's proposition. Lexical `1` is rejected before parsing under its own diagnostic: it is the one valid lexeme the pinned parser inverts, so admitting it would give this profile a source that means *interrupting*. Both profiles pin the same checked-node multiset and disjoint interruption dispositions, so neither profile's source is admissible to the other and a source cannot acquire the wrong interruption semantics by matching a shape they share.

One consequence of the non-interrupting arm is recorded as an exclusion rather than solved. Table 10.91 states that an uncancelled Activity can run multiple handler instances concurrently. This profile admits only the `timeDuration` form, so exactly one handler instance is reachable and repetition is out of scope; that is a bound on the admitted source, not a claim about non-interrupting boundaries generally.

Two admitted freedoms are deliberate and recorded as exclusions. Admission pins that the deadline resolves to a unique same-scope User Task host, and it does not pin which None End Event each branch reaches, which is semantically inert because the canonical observation exposes no terminal element identity.

The exact account, evidence boundary, and exclusions belong to the [non-interrupting boundary Timer capsule](../../docs/capsules/NON-INTERRUPTING-BOUNDARY-TIMER-SPEC.md). Status remains `draft`; the profile makes no claim about interrupting boundaries, other host Activity types, other boundary trigger types, more than one boundary per Activity, other Timer expressions, repeated firing, concurrent handler instances, general cancellation, CIB compatibility, A12 adoption, BPMN Process Execution Conformance, or production history compatibility.
