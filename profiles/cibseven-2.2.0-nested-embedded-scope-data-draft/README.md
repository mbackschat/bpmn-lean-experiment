# Nested embedded scope data draft profile

The [profile artifact](profile.json) selects the [nested embedded scope data specification](../../docs/capsules/NESTED-EMBEDDED-SCOPE-DATA-SPEC.md): ordinary embedded Sub-Processes up to definition depth three, each optionally declaring scope locals through `camunda:inputOutput`, with User Tasks and mapped Service Tasks on each serial path. Every surface uses the `SingletonBusinessItem` domain with the 1,024-byte root-String bound.

A read resolves to the nearest frame on the scope chain that declares the name, otherwise the Process; a write updates that owner and never creates a local. A User Task completion patch may name only frame-declared names on its chain and is capped at 16,384 canonical UTF-8 bytes. The [Call variable mapping specification](../../docs/capsules/CALL-VARIABLE-MAPPING-SPEC.md) adds one Call Activity on the caller's root path to a second in-document Process of one to three User Tasks: `camunda:in` copies caller values into the called-root frame, which stands in for the called instance's Process store and never resolves to caller data, and `camunda:out` writes the called values back from the Call's position at normal return. Stage B of the [repeated, nested and concurrent Calls specification](../../docs/capsules/REPEATED-NESTED-CONCURRENT-CALLS-SPEC.md) admits a second Call of the same Process and lets either Call sit in a Sub-Process body at depth one or two, where its inputs read and its outputs write along that Sub-Process's chain. The [CIB relationships](../../docs/CIB-BPMN-RELATION-REGISTER.md) classify the name-based scope account as an extension; hosting capacity, public registration and independent Closure are separate claims, and the capsule owns current acceptance.

The [concurrent structured scope data specification](../../docs/capsules/CONCURRENT-STRUCTURED-SCOPE-DATA-SPEC.md) additionally admits paired Parallel forks and joins inside Sub-Process bodies, never into a merge, with every model carrying its source overlay; the [root Parallel forks account](../../docs/capsules/ROOT-PARALLEL-FORKS-SPEC.md) admits them in the Process root body as well, in a model that holds no Call in that body. A Program with such a fork runs the concurrent account it shares with the embedded completion profile: each concurrently live Sub-Process occurrence owns its own frame of structured values, an effect's arguments are the snapshot taken when it is armed, branch outputs publish when their Sub-Process completes, and up to two mapped Calls of one Process may sit on the branches, each with its own called-root frame. Programs without a fork keep the serial account unchanged.

The [scope re-entry account](../../docs/capsules/SCOPE-REENTRY-SPEC.md) additionally admits Exclusive Gateways in the Process root body of a model without a fork: Choices with one or more Simple Boolean v1 conditions, tested in XML declaration order, and a default, and pass-through Merges, so a cycle may re-enter an earlier Sub-Process or mapped Call when a User or Service Task outside the called Process separates it. The [Exclusive choice arity account](../../docs/capsules/EXCLUSIVE-CHOICE-ARITY-SPEC.md) widened those Choices from exactly two conditions; no admission rule bounds their count, so a very wide Choice is bounded only by the 192 KiB `semanticProcessProgramBytes` Workflow-argument check at Start, which refuses its Program before the Workflow is created with an untyped error, not a typed capacity failure. Each re-entry is a fresh activation with fresh locals and next-ordinal task and effect occurrences, Process values written earlier survive, a command addressed to an earlier activation is rejected unchanged, and a model with root-body Exclusive Gateways whose automatic burst from Start or any resumption exceeds eight steps is refused at admission. A serial model has no such rule: one whose completion closure exceeds eight steps is admitted, and that completion rolls back on every attempt. A Program with root-body Exclusive Gateways offers no single bounded journey, so it gets only the Start capacity envelope's Program-level and reserved effect-result checks: a run whose values outgrow a hosted budget ends with a typed capacity failure rather than a Start refusal, and the number of iterations is bounded only by the existing aggregate continuation and Run bounds.

The [pass-through Task account](../../docs/capsules/PASS-THROUGH-TASK-SPEC.md) additionally admits a plain Task or Manual Task with only an id and a name, one incoming and one unconditioned, non-default outgoing flow, on a serial path of the root or a Sub-Process body or in a re-entry root graph (`CIB-EXT-0022`). It passes the token on at once and publishes one occurrence that starts and ends in that step, a fresh one on each re-entry; the checked graph keeps its source kind, and the Program carries it as a one-input exclusive merge. A serial model holding one is admitted only when its longest automatic burst stays within eight steps, so the serial rule above is unchanged for models without one. The [pass-through branch account](../../docs/capsules/PASS-THROUGH-PARALLEL-BRANCHES-SPEC.md) extends this to Parallel branches of the root and of every Sub-Process body: a branch that reaches its fork's join may hold only such Tasks, and a model holding one stays within eight steps per automatic burst, while a branch of a terminal fork must reach a User or Service Task before its End and a Call never follows only such Tasks from its body's Start. Pass-through Tasks in called Processes, under a fork with several incoming flows, with both several incoming and several outgoing flows, or with asynchronous continuations, mappings, listeners or boundaries are refused.

The [terminal forks account](../../docs/capsules/TERMINAL-FORKS-SPEC.md) additionally admits root terminal forks, so the root may hold several None Ends, and terminal branches in the root and Sub-Process bodies that reach their End without a User or Service Task: through pass-through Tasks, None Throws, a nested fork whose branches do the same, or directly. Each End consumes only its own token, and a scope completes only once no token, task or child scope remains (`CIB-EXT-0022`). The [data-declaring terminal branches account](../../docs/capsules/DATA-DECLARING-TERMINAL-BRANCHES-SPEC.md) admits such branches whether or not a Sub-Process declares scope-local data, an End committing beside a declared Sub-Process entry through a proved pair law; a branch that reaches its fork's join still needs work or a pass vertex.

The [None End fan-in account](../../docs/capsules/NONE-END-FAN-IN-SPEC.md) additionally admits a None End of a re-entry root graph with several incoming Sequence Flows, from a Choice, a Merge, a Task, a Sub-Process or a Call: each arriving token ends there on its own, never waiting for another flow, and the Process completes once no token remains (`CIB-AGR-0015`). The root keeps one None End element; fan-in at Activities, at Ends in Sub-Process bodies or called Processes, and in a model that forks stays refused.

The [None Throw account](../../docs/capsules/NONE-INTERMEDIATE-THROW-SPEC.md) additionally admits an Intermediate Throw Event without an EventDefinition, with only an id and a name and one incoming and one outgoing flow, wherever a pass-through Task is admitted (`CIB-AGR-0016`). It passes the token on at once and publishes one occurrence that starts and ends in that step, a fresh one on each re-entry; the checked graph keeps it as its own Event node, the Program carries it as a one-input exclusive merge, and every other profile refuses it. None Throws that both merge and split, with asynchronous continuations or listeners, in called Processes, and every throw trigger stay refused.

The [pass-through implicit split and merge account](../../docs/capsules/PASS-THROUGH-IMPLICIT-SPLIT-MERGE-SPEC.md) additionally admits such a Task or None Throw with several incoming flows in the Process root of a re-entry graph, where each arriving token passes it once on its own as a many-input exclusive merge, or with several unconditioned outgoing flows wherever a Parallel fork of that arity is admitted, where one activation puts a token on each as a fork with the node as origin (`CIB-AGR-0019`). Never both at once; every other profile keeps one incoming and one outgoing flow.

The [Activity host account](../../docs/capsules/ACTIVITY-HOST-FLOW-LISTS-SPEC.md) additionally admits a User Task without data, boundary or Multi-Instance variants, or a Service or Send Task without a BPMN Error route, with several incoming flows and one outgoing flow in the Process root of a re-entry graph: each arriving token starts one fresh occurrence of the Task in one step, with no step or position for the merge (`CIB-AGR-0020`). Such a Task lowers to one Activity host over its incoming flows, which waits and publishes exactly as the legacy Task. Merging Tasks under a fork, in a body or with several outgoing flows stay refused.

The [scope host account](../../docs/capsules/SCOPE-HOST-FLOW-LISTS-SPEC.md) additionally admits a root None Start, the None Start of an ordinary embedded Sub-Process body, and an ordinary embedded Sub-Process with one incoming flow, each with two or more unconditioned, non-default outgoing flows, outside every fork region of its scope and its ancestors: the Start's start or the Sub-Process's entry or completion puts a token on every outgoing flow in its one step, with no step or occurrence for the split (`CIB-AGR-0022`). Such a Start lowers to a `process` host, a Sub-Process whose body Start splits to a `subProcess` host and a splitting Sub-Process's completion to a scope exit, each publishing exactly as the legacy initiation, entry or completion. Conditional or default flows, merges at Starts and Sub-Processes, splitting Calls and called-Process Starts, and splits inside fork regions stay refused.

The [Link Events account](../../docs/capsules/LINK-EVENTS-SPEC.md) additionally admits single-source Link pairs: a throw and a catch of one `linkEventDefinition` name in one scope of the executed Process, the throw with one incoming flow and the catch with one unconditioned outgoing flow (`CIB-AGR-0018`). Both languages contract each pair to the Sequence Flow it replaces before admission and lowering, so a Link model is admitted, lowered and run exactly as its explicit-flow twin and publishes no occurrence or wait for a Link Event, while the checked artifact keeps the Link nodes. Several throws of one name are admitted only where their catch leads to such a merging Task; chains, `source` or `target` references, asynchronous or listened Link Events, Links outside the executed Process and every other profile stay refused.

The [single-scope models account](../../docs/capsules/SINGLE-SCOPE-MODELS-SPEC.md) additionally admits a Process without an embedded Sub-Process, with its root alone or beside a called Process, in every form the accounts above admit with one: the root is their only body, and its Process data comes from the Start bindings and Service outputs. The embedded completion profile, the only other profile reaching these analyses, keeps requiring a Sub-Process or a Call.

The [Send Task account](../../docs/capsules/SEND-TASK-SPEC.md) additionally admits a Send Task performed by a handler the source overlay binds through `camunda:delegateExpression`, with `camunda:asyncBefore` and input parameters, wherever a mapped Service Task is admitted (`CIB-EXT-0023`). It executes as that Service Task's effect, with an empty result, since the profile admits no output on a Send Task; no Message, Message Flow, `messageRef` or `operationRef` is read, and every CIB implementation other than the delegate expression is refused. No other profile admits a Send Task.

The [Exclusive Choice without a default account](../../docs/capsules/EXCLUSIVE-CHOICE-WITHOUT-DEFAULT-SPEC.md) additionally admits a diverging Exclusive Gateway with no default and two or more conditional outgoing Sequence Flows, wherever a Choice with a default is admitted and no effect result reaches it within its command (`CIB-INT-0003`). The first true condition in declaration order is taken; when none holds, the command that reached the Choice rolls back and leaves the state before it, so a Start creates no instance and a User Task completion leaves its task open. A model in which a Service or Send Task result could reach such a Choice within one command is refused, because CIB turns that no-match into a retried job and an incident.

The [Inclusive regions specification](../../docs/capsules/INCLUSIVE-GATEWAY-REGIONS-SPEC.md) additionally admits structured Inclusive regions in the Process root body: a diverging Inclusive Gateway with two or more outputs paired with one converging Inclusive Gateway that has one input per output, where each non-default output carries one Simple Boolean v1 condition or none, an absent condition is always true (`CIB-INT-0005`), a split without a default has an unconditioned output and a split with a default has none. Every true output is taken, the default only when none is, and the join fires when every selected branch has arrived (`CIB-AGR-0017`). Branches hold the root body content a fork admits, nested Parallel regions included, and reach a User Task, Service Task or Sub-Process before any join or End. An Inclusive Gateway in a Sub-Process or called body, on a branch of another Inclusive region or beside one on a sibling branch of a fork, beside a Choice, a cycle or a Call Activity, or in a pass-through, unpaired or unstructured region is refused.

Capacity: a serial Program keeps the Start capacity envelope and its refusals before Workflow creation. A Program with a fork gets only the envelope's Program-level checks, the 256-byte hosting identity bound and the reserved effect-result checks; its hosted budgets are enforced at runtime, so a run whose structured values outgrow a budget ends with a typed capacity failure rather than a Start refusal. One full-allowance value copied into two frames and two effect snapshots already approaches the 64 KiB committed-state budget, and only the retained models are measured clear of the untyped retained Run trace path.
