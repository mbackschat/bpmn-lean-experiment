# Nested embedded scope data draft profile

The [profile artifact](profile.json) selects the [nested embedded scope data specification](../../docs/capsules/NESTED-EMBEDDED-SCOPE-DATA-SPEC.md): serial ordinary embedded Sub-Processes up to definition depth three, each optionally declaring scope locals through `camunda:inputOutput`, with User Tasks and mapped Service Tasks on each serial path. Every surface uses the `SingletonBusinessItem` domain with the 1,024-byte root-String bound.

A read resolves to the nearest frame on the scope chain that declares the name, otherwise the Process; a write updates that owner and never creates a local. A User Task completion patch may name only frame-declared names on its chain and is capped at 16,384 canonical UTF-8 bytes. The [Call variable mapping specification](../../docs/capsules/CALL-VARIABLE-MAPPING-SPEC.md) adds one Call Activity on the caller's root path to a second in-document Process of one to three User Tasks: `camunda:in` copies caller values into the called-root frame, which stands in for the called instance's Process store and never resolves to caller data, and `camunda:out` writes the called values back from the Call's position at normal return. Stage B of the [repeated, nested and concurrent Calls specification](../../docs/capsules/REPEATED-NESTED-CONCURRENT-CALLS-SPEC.md) admits a second Call of the same Process and lets either Call sit in a Sub-Process body at depth one or two, where its inputs read and its outputs write along that Sub-Process's chain. The [CIB relationships](../../docs/CIB-BPMN-RELATION-REGISTER.md) classify the name-based scope account as an extension; hosting capacity, public registration and independent Closure are separate claims, and the capsule owns current acceptance.
