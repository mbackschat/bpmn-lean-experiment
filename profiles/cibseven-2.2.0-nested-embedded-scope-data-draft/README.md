# Nested embedded scope data draft profile

The [profile artifact](profile.json) selects the [nested embedded scope data specification](../../docs/capsules/NESTED-EMBEDDED-SCOPE-DATA-SPEC.md): ordinary embedded Sub-Processes up to definition depth three, each optionally declaring scope locals through `camunda:inputOutput`, with User Tasks and mapped Service Tasks on each serial path. Every surface uses the `SingletonBusinessItem` domain with the 1,024-byte root-String bound.

A read resolves to the nearest frame on the scope chain that declares the name, otherwise the Process; a write updates that owner and never creates a local. A User Task completion patch may name only frame-declared names on its chain and is capped at 16,384 canonical UTF-8 bytes. The [Call variable mapping specification](../../docs/capsules/CALL-VARIABLE-MAPPING-SPEC.md) adds one Call Activity on the caller's root path to a second in-document Process of one to three User Tasks: `camunda:in` copies caller values into the called-root frame, which stands in for the called instance's Process store and never resolves to caller data, and `camunda:out` writes the called values back from the Call's position at normal return. Stage B of the [repeated, nested and concurrent Calls specification](../../docs/capsules/REPEATED-NESTED-CONCURRENT-CALLS-SPEC.md) admits a second Call of the same Process and lets either Call sit in a Sub-Process body at depth one or two, where its inputs read and its outputs write along that Sub-Process's chain. The [CIB relationships](../../docs/CIB-BPMN-RELATION-REGISTER.md) classify the name-based scope account as an extension; hosting capacity, public registration and independent Closure are separate claims, and the capsule owns current acceptance.

The [concurrent structured scope data specification](../../docs/capsules/CONCURRENT-STRUCTURED-SCOPE-DATA-SPEC.md) additionally admits paired Parallel forks and joins inside Sub-Process bodies, never into a merge, with every model carrying its source overlay; the [root Parallel forks account](../../docs/capsules/ROOT-PARALLEL-FORKS-PROPOSAL.md) admits them in the Process root body as well, in a model that holds no Call in that body. A Program with such a fork runs the concurrent account it shares with the embedded completion profile: each concurrently live Sub-Process occurrence owns its own frame of structured values, an effect's arguments are the snapshot taken when it is armed, branch outputs publish when their Sub-Process completes, and up to two mapped Calls of one Process may sit on the branches, each with its own called-root frame. Programs without a fork keep the serial account unchanged.

The [scope re-entry account](../../docs/capsules/SCOPE-REENTRY-SPEC.md) additionally admits Exclusive Gateways in the Process root body of a model without a fork: Choices with two Simple Boolean v1 conditions and a default, and pass-through Merges, so a cycle may re-enter an earlier Sub-Process or mapped Call when a User or Service Task outside the called Process separates it. Each re-entry is a fresh activation with fresh locals and next-ordinal task and effect occurrences, Process values written earlier survive, a command addressed to an earlier activation is rejected unchanged, and a model with root-body Exclusive Gateways whose automatic burst from Start or any resumption exceeds eight steps is refused at admission. A serial model has no such rule: one whose completion closure exceeds eight steps is admitted, and that completion rolls back on every attempt. A Program with root-body Exclusive Gateways offers no single bounded journey, so it gets only the Start capacity envelope's Program-level and reserved effect-result checks: a run whose values outgrow a hosted budget ends with a typed capacity failure rather than a Start refusal, and the number of iterations is bounded only by the existing aggregate continuation and Run bounds.

The [pass-through Task account](../../docs/capsules/PASS-THROUGH-TASK-SPEC.md) additionally admits a plain Task or Manual Task with only an id and a name, one incoming and one unconditioned, non-default outgoing flow, on a serial path of the root or a Sub-Process body or in a re-entry root graph (`CIB-EXT-0022`). It passes the token on at once and publishes one occurrence that starts and ends in that step, a fresh one on each re-entry; the checked graph keeps its source kind, and the Program carries it as a one-input exclusive merge. A serial model holding one is admitted only when its longest automatic burst stays within eight steps, so the serial rule above is unchanged for models without one. Pass-through Tasks on Parallel branches, in called Processes, with several flows or with asynchronous continuations, mappings, listeners or boundaries are refused.

Capacity: a serial Program keeps the Start capacity envelope and its refusals before Workflow creation. A Program with a fork gets only the envelope's Program-level checks, the 256-byte hosting identity bound and the reserved effect-result checks; its hosted budgets are enforced at runtime, so a run whose structured values outgrow a budget ends with a typed capacity failure rather than a Start refusal. One full-allowance value copied into two frames and two effect snapshots already approaches the 64 KiB committed-state budget, and only the retained models are measured clear of the untyped retained Run trace path.
