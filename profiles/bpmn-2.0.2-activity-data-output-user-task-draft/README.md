# BPMN 2.0.2 Activity data-output User Task draft profile

This standards profile selects one private executable Process whose single User Task declares one required scalar `DataOutput`, one empty `InputSet`, one `OutputSet` referencing exactly that output, and one direct `DataOutputAssociation` into one Process-owned `Property`. The task activates on its incoming control token alone, and an accepted completion fills the declared output and executes the association in the same transition.

The [profile artifact](profile.json) names BPMN 2.0.2 Clause 10.4.1 for Property lifetime and output Data Association execution after the Activity's work, Clause 10.4.2 for the data interface, Clause 13.3.2 for User Task completion, and Clause 13.3.7 for the task's data requirements, together with Tables 10.57, 10.58, 10.59, 10.61, 10.62, and 10.64 for the Activity data interface. Relationships `CIB-AGR-0001` and `CIB-OP-0001` govern only the reused User Task lifecycle and occurrence-identity mapping. This profile selects no CIB Data Association behavior.

Process Start admits exactly the empty payload. That emptiness is the profile's own separating fact rather than an omission: a declared `OutputSet` constrains completion and never entry, so the task must become active in a Process with no data at all, which is exactly the state in which the sibling data-input profile creates nothing.

User Task completion admits exactly one submitted value, named by the exact `DataOutput` id, whose value is a String or explicit null. A submission that names anything else, omits the output, or adds a second name is refused with exact state preservation, because this `OutputSet` declares one required member and an Activity may not complete without making it available. Accepted completion fills the Activity-owned output, writes the value into the Process `Property` the association names, and disposes the task, its Activity record, and its Activity-local data together.

Routing is decided by the association rather than by the submitted name. The registered model gives the `DataOutput` and its target `Property` deliberately different ids, so an implementation that merged them would satisfy every routed expectation by coincidence.

The exact account, evidence boundary, and reopen conditions belong to the [Activity data-output mediation specification](../../docs/capsules/ACTIVITY-DATA-OUTPUT-MEDIATION-SPEC.md). Status remains `draft`; the profile makes no claim about data inputs, input mediation, an Activity carrying both directions, further outputs or OutputSets, optional or while-executing outputs, `OutputSet`/`InputSet` pairing, Assignments, transformations, expressions, `ItemDefinition`, Data Objects, Data Stores, collection or nested values, mutation while the Activity is active, another Activity or Task type, Boundary Events, looping, Multi-Instance, Sub-Process scope, Call Activity mappings, forms, authorization, CIB Data Association compatibility, production history compatibility, or BPMN Process Execution Conformance.
