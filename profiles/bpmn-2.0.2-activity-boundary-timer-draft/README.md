# BPMN 2.0.2 interrupting Activity boundary Timer draft profile

This standards profile selects one User Task carrying one interrupting Timer Boundary Event with an exact `PT1S` duration. The Activity and its deadline are armed atomically, the Activity's own completion withdraws the deadline and follows its normal outgoing flow, and a fired deadline abandons the Activity and follows the boundary output instead. The two victories are distinguishable at the public observation boundary.

The [profile artifact](profile.json) names BPMN 2.0.2 Clause 10.5.5, Clause 10.5.6, Clause 13.3.2, Clause 13.5.3, Table 10.91, Table 10.92, Table 10.101, and Table 10.122 as normative authority — Table 10.91 for the Boundary Event attributes, Table 10.92 for the legal `cancelActivity` values per trigger, Clause 10.5.6 for what interrupting means, Clause 13.5.3 for the handling order, Clause 10.5.5 with Tables 10.101 and 10.122 for `timeDuration`, and Clause 13.3.2 for the Activity lifecycle the deadline observes. Relationships `CIB-AGR-0001` and `CIB-OP-0001` govern only the reused User Task interaction boundary — its lifecycle, and the mapping of semantic task identity with stale-command refusal. No CIB Boundary Event, deadline-versus-completion race, or retained-evidence claim is selected: the boundary mechanism itself is vendor-neutral here, and admitting an omitted `cancelActivity` rests on the XSD and CMOF default of `true` rather than on engine behavior.

One interpretation is recorded in the [capsule](../../docs/capsules/ACTIVITY-BOUNDARY-TIMER-PROPOSAL.md) rather than claimed as normative. BPMN 2.0.2 does not fix when a Boundary Event's waiting begins — Clause 13.5.2 starts waiting when an Intermediate Event is *reached*, and a Boundary Event never is — so arming at Activity activation is this profile's decision, and the refusal of a pre-due firing is the only thing that discriminates it.

Two admitted freedoms are deliberate and recorded as exclusions. Admission pins that every deadline resolves to a unique same-scope User Task host, but not *which* of the two chained tasks hosts it; and it does not pin which None End Event each route reaches, which is semantically inert because the canonical observation exposes no terminal element identity.

The exact account, evidence boundary, and exclusions belong to the [interrupting Activity boundary Timer proposal](../../docs/capsules/ACTIVITY-BOUNDARY-TIMER-PROPOSAL.md). Status remains `draft`; the profile makes no claim about non-interrupting boundaries, other host Activity types, other boundary trigger types, more than one boundary per Activity, other Timer expressions, a winner for coalesced host readiness, repetition, general cancellation, CIB compatibility, A12 adoption, BPMN Process Execution Conformance, or production history compatibility.
