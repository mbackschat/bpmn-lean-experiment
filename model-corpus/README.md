# Executable BPMN model corpus

This directory is the maintained entry point for representative whole BPMN models used to test what the engine and platform can actually run. It keeps executable project-owned scenarios separate from exact external research candidates and counts clone families instead of inflating priorities with copied or versioned files. The retained, business-purpose-shaped suite covers every executable BPMN element or semantic variant registered by the production pipeline, while exact external product-shaped candidates expose realistic admission and mechanism gaps. The generated [corpus map](EXECUTABLE-MODEL-CORPUS-MAP.md) owns the current counts.

After `@bpmn-lean/differential` and its dependencies have been built once (`./scripts/pnpm.sh run build:differential`), run the provenance and kernel admission check with:

```sh
gtimeout 60s node --test --test-concurrency=1 model-corpus/test/executable-model-corpus.test.ts
```

On a clean checkout, verify the registered external research checkouts and run the gate; it builds the TypeScript packages and Lean `kernelRun` first. Each retained model's scenario runs through Lean, the TypeScript kernel and its retained CIB evidence in the [kernel oracle](../packages/differential/test/kernel-behavior-oracle.integration-test.ts), and through the Temporal host in the hosted differential lane:

```sh
./scripts/doctor.sh research
gtimeout 120s ./scripts/pnpm.sh run test:model-corpus
```

The machine-owned model source is [`manifest.json`](manifest.json), while [`mvp-capabilities.ts`](mvp-capabilities.ts) is the canonical executable capability and restriction catalog shared with the Product 2 About page. The guard derives the exercised variant set from every scenario and population scenario the differential discovers, requires the catalog to match it exactly, and requires the retained-model union to cover it. Admission is the kernel's own decision (the kernel reader, then `Kernel.Admission`); a model whose recorded admission differs from it is listed, never reconciled, and a rejected model's recorded digest is the SHA-256 of the kernel's stable refusal code. A new supported variant therefore cannot land without a project-owned whole model, business purpose, capability row, discovered scenario, and regenerated [corpus coverage and blocker map](EXECUTABLE-MODEL-CORPUS-MAP.md) and [retained-model capability list](retained-model-capabilities.json), which the guard keeps exact and the browser showcase catalog reads in place of the kernel; `./scripts/pnpm.sh run render:corpus-map` regenerates both through the guard's own inspection, after `build:differential`, and the evidence-branch workflow runs it in every evidence commit. External model bytes stay in the registered checkouts or official archive from [the source registry](../docs/SOURCES.md); this directory records only exact paths, revisions or archive identity, licenses, and digests. The archive consumer requires `unzip`, verifies both the complete archive and selected entry, and never writes extracted external bytes into the repository.

The variable values and payloads of a claiming scenario are read by the kernel's own value and stimulus codec, supplied to the guard by the test as admission is, and no table keyed by process name says which kinds a scenario may carry: a scenario whose stimulus the codec refuses fails the guard, naming the scenario, the stimulus and the refusal. The wire bounds of a value belong to the [scenario schema](../contracts/schemas/scenario.schema.json) and its domain bounds to the kernel, which answers a value outside the domain with a rejection, so an oversized value is expressible as a witness of that rejection.

What the BPMN source of a claiming scenario claims is the kernel's admission decision, never a declaration: an admitted source claims the catalog variants its admitted kernel program exercises, derived by the one table from IL kinds to variants in [`kernel-capabilities.ts`](../packages/differential/test/kernel-capabilities.ts) and never by reading the BPMN text, and a refused source claims the restriction its refusal code names in [`mvp-capabilities.ts`](mvp-capabilities.ts), taken from the register entry or semantics document it cites. The guard fails naming the code and the witness when a refusal code a claiming witness exhibits has no restriction row, and naming the code when no retained scenario exhibits a row's code, so a refusal witness can widen no capability and no list of witness paths exists.

Retained scenario admission preserves [source-overlay identity](../docs/A12-ADD-ON-BOUNDARY-SPEC.md#identity-and-compilation-contract) and loads the exact bytes of the overlay retained beside the scenario or its BPMN source; an identity no neighbouring file matches fails closed.

A model is not a browser-catalog model merely because the engine admits it. Browser eligibility additionally requires a named production-backed Playwright journey that deploys or selects the exact model, starts it through the public platform, observes every mutation precondition, claims each human-work User Task before completing it, completes its advertised work, and verifies the resulting instance, History, and applicable audit surfaces.

## Admission and product-readiness gate

The curated corpus is an engine and product acceptance input, not a fourth conformance denominator. Its manifest distinguishes exact source admission, semantic execution, durable Temporal execution, selected CIB comparison, and Product 2 usability. Clone-normalized family reach and semantic risk remain separate scheduling inputs under the [breadth-ordering rule](../docs/PROJECT-DESIGN.md#cib-seven-220-breadth-ordering).

A model may succeed in one lane and fail in another without that distinction being collapsed. An engine-runnable User Task model without public assignment metadata is not operator-workspace-ready, and a viewer-renderable model is not necessarily startable.

Corpus admission, pipeline discovery and named journey eligibility are separate facts; none establishes a row's acceptance, which the [coverage target](../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list) owns.

Every catalog-visible model passes a production-backed headless-Chromium user journey through deploy or selection, start, each required Work or Operations action, terminal or explicit resumption status, and applicable public history or audit. Each mutation's false precondition is separately locked, and strict public-contract failures are corpus failures rather than hidden fixture gaps.

The corpus increment closes only when licence and provenance controls keep external copyrighted or reciprocal material out of the MIT retained tree; duplicate and near-duplicate examples cannot inflate rankings; every retained model is schema-valid, parser-admitted, profile-bound, and exercised to a terminal state or public resumption point through the kernel and the Temporal host; every catalog-visible model has a production-backed browser journey through all required work and operations; unsupported candidates remain classified blockers with an exact first unsupported mechanism and are never offered as runnable examples; the generated roadmap reports clone-family reach separately from the owning semantic-risk assessment; and every newly registered executable variant atomically adds or expands a credible retained model, concrete business purpose, capability/restriction row, discovered scenario, derived map, and Product 2 disclosure.

**Review a request with assignment and form metadata** is covered by the [single-review M3 corpus journey](../showcase/m3-human-work/e2e/corpus-user-task-journey.spec.ts), **Review content and risk in parallel** is covered by the [parallel-review M3 corpus journey](../showcase/m3-human-work/e2e/parallel-user-task-metadata-journey.spec.ts), and **Resolve an expense exception with structured human work** is covered by the [structured Human Work M6 journey](../showcase/m3-human-work/e2e/structured-human-work-journey.spec.ts). Nine additional retained models have [guided RC browser journeys](../showcase/mue-preview-alpha/e2e/rc-showcase-journeys.spec.ts), recorded as `guidedJourneyBacked`: their isolated host supplies explicitly simulated participants and integrations through the existing published command driver. They do not claim human-work assignment or forms. The [RC catalog selection](rc-showcases.ts) reuses exact retained sources and neutral runnable configurations; remaining models stay inspectable engine regression cases until their own complete browser journey is green.
