## Order gates

Order gates bind alongside the day budgets, because a budget of days cannot fire on work that takes hours. Nothing builds on a kernel shape until guards 17 to 21 pass on it and every open row maps onto it. A track's fill starts only when its row fixtures, scenarios and CIB evidence exist, so rows turn red to green against an answer fixed before the code. Agreement between Lean and TypeScript is a transcription check, never evidence of meaning.

## Proof wave

The proof wave proves the Lean kernel sound against the laws of the four [open proof lanes](kernel/KERNEL-STATUS-MAP.md#open-proof-lanes) (concurrency, cancellation, Multi-Instance, Compensation and Transaction), the state invariant they rest on and the former lanes of PC-DATA-01, PC-HUM-04, PC-SCOPE-04 and PC-SCOPE-05 ([Lean assurance lane](kernel/ARCHITECTURE-SPEC.md#lean-assurance-lane)). The other laws (`Population`, `Subscriptions`, `Correlation`, `Starts`, `Work`, `Decision` and most of `Data` and `Flow`) stay witness-only. Today no theorem relates `Step` to a law: each law carries only its non-vacuity witnesses, and nothing executable imports it. Scenario agreement stays the evidence for finite behavior and for the TypeScript kernel, which no proof covers.

A lane theorem has explicit premises, fixed at P0 and approved by its review: the state premise is `Laws.State.WellFormed` of the before-state, and each model premise is a declarative IL condition that cites the refusal code or profile option enforcing it. That admission enforces a premise stays scenario evidence (guard 12's refusal tests), disclosed with the lane, because a law's type may not name the admission evaluator.

The proof estate of the deleted library was the second cause of the [slowdown](kernel/ARCHITECTURE-SPEC.md#why-delivery-slowed): proofs shaped per variant and per pair, unfolding evaluator bodies, so that a behavior-neutral change broke dozens of proofs. The wave is shaped so that cannot recur:

| Cause | Rule of the wave |
|---|---|
| 1, 2 proofs per variant and per pair | No case split over a guarded type outside its owner; an executable module's body is seen by exactly one `Laws` module (its own), which holds that module's lemmas; `Kernel.Proofs.*` compose those lemmas and never unfold or `simp` a body (guard 6). Commutation is proved once, over `Laws`-level footprint lemmas showing that each feature's runtime writes stay within [`Kernel/IL/Footprint.lean`](../Kernel/IL/Footprint.lean)'s account, which admission already uses; no `Hooks` footprint field is added. A proof that seems to need a per-variant or per-pair case stops, and the laws stating the hook contracts are restructured instead. The behavior-neutral body-edit probe of P0 is repeated at every lane review. |
| 1 proof-motivated executable code | No IL field, state slot, `Hooks` field or TypeScript code exists for a proof. A `Step` restructure a proof needs is an ordinary, behavior-neutral commit paired in TypeScript, held to guard 18's eight-module cap, with the behavior oracle unchanged; it is not a `kernel-shape` commit. |
| 3 build cost | Nothing executable imports `Laws` or `Proofs`; no `decide`, `native_decide`, `cbv` or `rfl` reduction of `Step`, `Run` or a registry, and no kernel-decided fixture (guard 6); finite examples stay in the runner; no Lean option change. The root module imports the proof estate, so guard 15's existing bounds bind it (3 minutes clean, 30 seconds per module and per edit); a P0 measurement above them stops P0 with options for the owner, never a new bound. |
| 4 ceremony | Lean checks the proofs, so a review reads statements and structure, never proof bodies: this plan's review, the P0 checkpoint review, P1's interpretation review and track review, one review per lane and the wave-end reconciliation. A correction gets at most one audit. |
| 5 documentation | This section is the plan; each theorem's statement and its BPMN clause or register citation live in Lean; the status map changes at a lane's closure. No new document. |
| 6 guards as negotiation | No new guard: the existing [proof-escape guard](../scripts/lean-proof-escapes.test.ts) already fails `sorry`, `admit` and `axiom` throughout `Kernel/**`. ## Verification cadence

Locally: the kernel build of touched modules, the kernel runner, TypeScript type checks and unit tests, and the fast guard suite ([local loop](kernel/ENGINEERING-POLICY.md#local-loop)). Docker, the Temporal server, PostgreSQL, browsers, the CIB oracle suites and other long-running lanes run in hosted CI on the pushed branch, once per milestone or track, which is also the landing gate; a hosted failure is reproduced locally only by its narrowest command. CIB evidence for new scenarios is produced in one batched hosted run per track.

## Delegation

HIGH track agents author kernel feature, admission and laws modules in Lean and their TypeScript pairs on disjoint files, and run only narrow builds of their own modules (`./scripts/lake.sh build Kernel.Feature.<F>`, `Kernel.Laws.<F>` and `Kernel.Run` for their own scenarios) under the shared project lock; an agent that finds the lock held waits and retries. The root alone accepts shape edits, runs full builds, the full runner and every hosted lane, and integrates. Agents never run heavy lanes. Workers on scenarios and models stay MEDIUM. The guards, the architecture checkpoint and the track review replace the old rule that only the root writes Lean.
