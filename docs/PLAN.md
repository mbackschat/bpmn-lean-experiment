Three facts bound any fix. This toolchain's Lake exposes **no job-count option** — `-j` is rejected as an unknown short option and no `--jobs` appears in its help — so parallelism cannot be capped at the command line, and a polling watchdog cannot bound a process that allocates gigabytes between samples. The consequence is that `lake build`, `lake test`, and therefore the complete `./scripts/verify.sh` gate all carry this exposure, including on any CI runner with less memory than the owner's machine. The open question is which lever to take: pin parallelism through a Lake configuration option if one exists, restore `native_decide` more broadly and give back the recorded 48% CPU saving, or accept an 8 GB build and state that requirement for contributors and CI. **Resolved by pinning the thread pool, and the reverts were therefore unnecessary.** `LEAN_NUM_THREADS` is the lever: it appears in the toolchain libraries while `--jobs` does not, and Lake schedules its module builds on the Lean task pool that variable sizes. A clean `LEAN_NUM_THREADS=1 lake build` exits 0 with a **2411 MB** peak and at most two concurrent `lean` processes, against 7978 MB and four-plus unpinned — a 3.3-fold reduction — at 100.2 seconds wall and 97.5 seconds user. [The Lean wrapper](../scripts/lake.sh) now applies the pin to every invocation unless the environment supplies one, and [an executable check](../scripts/verification-entrypoint.test.ts) fails if that pin disappears.

The pin is a target rather than a hard cap, which is why the measured peak still showed two concurrent processes: [Lean's documentation](https://lean-lang.org/doc/reference/latest/IO/Tasks-and-Threads/) states the pool may be exceeded to avoid deadlock. Two upstream facts make this a known class rather than a local quirk. Lean's kernel reduction of `decide` is a recognised memory and performance bottleneck — the reference release notes record `whnf` exhausting stack space on terms such as `2^1024` — and the community's usual answer is `native_decide` precisely to avoid kernel checking, which is the trade this repository makes in the opposite direction for the two `String`-parsing modules. Setting `LEAN_NUM_THREADS=1` is also the documented mitigation in [an upstream memory report](https://github.com/leanprover/lean4/issues/6753), where it caps server growth without eliminating it.

Because the pin resolves the peak, the 38 sites reverted under the memory hypothesis are **restored**: at one thread the kernel form is affordable, and it is better than `native_decide` on both axes there, keeping the CPU saving while leaving no compiler-trusting axiom in those theorems. With all 262 kernel sites present, a clean pinned build and `lake test` both exit 0 at a 4699 MB peak with three concurrent processes at two threads, and 69.5 seconds wall against 128.1 seconds user. `native_decide` is retained only where the kernel cannot reduce at all, which is the 16 `String`-parsing sites.

**The pinned default is `1`, chosen conservatively because this peak grows with the fixture count and the fixture count grows with every capsule.** The published GitHub-hosted runner sizes make that concrete rather than cautious: a standard runner for a **private** repository has 2 vCPU and **7 GB**, the lightweight `ubuntu-slim` tier has 1 vCPU and **5 GB**, and only a public-repository standard runner has 4 vCPU and 16 GB. An unpinned 8-core build already exceeds the first two, so the gate must not inherit the host's core count. `config.leanBuildThreads` in [package.json](../package.json) is the pin's single owner, and [the Lean wrapper](../scripts/lake.sh) derives it through [the pin reader](../scripts/pinned-toolchain.sh).

**The first version of that pin covered the gates instead of the toolchain, and the difference is the whole lesson.** Exporting `LEAN_NUM_THREADS` from `verify.sh` and `pnpm.sh` pinned exactly the two entry points that had been measured, while the documented experiment gates in [TESTING-SPEC.md](TESTING-SPEC.md#focused-gate-matrix), the experiment reproduction blocks, and every `lake build` a contributor or agent types directly all stayed at the host's core count. What stood in that gap was one sentence of prose asking the reader to export the pin themselves — and the agent that wrote that sentence then relied on remembering it, which is the failure mode this repository already records as *fresh prose does not bind you*. The fix routes every Lean invocation through [one wrapper](../scripts/lake.sh) that accepts Lake's arguments unchanged, and [the executable check](../scripts/verification-entrypoint.test.ts) rejects a bare `lake` subcommand in the enumerated verification scripts, manifest, and documentation surfaces rather than in every tracked file. Records of past measurements keep their literal bare commands, because there the absence of the pin is the measured fact rather than a call site to migrate. A machine with spare RAM may raise the value by exporting `LEAN_NUM_THREADS` before the gate, and should measure the resulting peak rather than assume it scales linearly — it did not here, moving from 2411 MB at one thread to 4699 MB at two.
