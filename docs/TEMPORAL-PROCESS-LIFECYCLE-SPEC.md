# Temporal Process lifecycle specification

## Status

**Implemented current pre-release contract** of the generic host [`@bpmn-lean/temporal-host`](../packages/temporal-host/src/workflow-host.ts) and the [engine API](../packages/engine-api/src/index.ts), restated against their code on 2026-11-13. The [deleted temporal-adapter record](#deleted-temporal-adapter-record-2026-11-09) keeps, in the past tense, the contract of the per-capsule adapter that the generic host replaced on 2026-11-09; none of it applies to the current host.

## Scope

This specification defines how the generic host runs one process instance as a Temporal Workflow chain: what is checked before a Workflow starts, when the Workflow closes, what a retried command gets, and how a command that arrives after closure is classified, without inventing BPMN behavior. The kernel owns every semantic verdict; the host carries the kernel state, drives timers and effects from the kernel's host view and publishes the kernel journal ([kernel architecture](kernel/ARCHITECTURE-SPEC.md#temporal-hosting-and-refinement-preflight)).

It does not itself add BPMN semantics, a task inbox, general host cancellation, an external database, or an immutable deployment/history baseline. The [Workflow-chain production contract](#workflow-chain-production-contract) below owns bounded continuation and capacity; the [archived proposal](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/docs/archived/TEMPORAL-WORKFLOW-CHAIN-BOUNDS-PROPOSAL.md) retains its selected-design and review rationale. The [population ingress](kernel/ARCHITECTURE-SPEC.md#population-ingress) owns Message publication, Signal broadcast, Conditional and population starts across instances. Scopes, Error propagation, Terminate, Call Activity, Multi-Instance and Compensation are kernel transitions inside one chain's state: the host emits no Child Workflow, external Signal or external cancellation request for them ([capacity table](#workflow-chain-capacity), "Pending Child Workflows" row), and plans only timers and effect Activities from the open waits ([`host-machine.ts`](../packages/temporal-host/src/host-machine.ts), `planHost`).

## Selected lifecycle

Adopt a **semantic-lifetime Workflow chain that closes when the instance ends**:

- one Workflow chain hosts one kernel state, addressed by `processInstanceWorkflowId(population, instanceId)` ([`population-address.ts`](../packages/temporal-host/src/population-address.ts)); every Run receives the kernel program in its wire form and decodes it afresh ([`host-contract.ts`](../packages/temporal-host/src/host-contract.ts), `RunProcessArgs`);
- the engine API refuses a start before any Workflow exists when the deployment does not serve a capability the program requires (`engineHostRefusal` in [`definition.ts`](../packages/engine-api/src/definition.ts)), when the program or start stimulus exceeds its byte bound, or when the stimulus does not decode (`prepareStart` in [`start-dispatch.ts`](../packages/engine-api/src/start-dispatch.ts)); the Workflow admits the program again with the kernel's `admit` and measures both byte bounds again before its first step ([`workflow-host.ts`](../packages/temporal-host/src/workflow-host.ts));
- the Workflow returns once the host view's status is no longer `running` or the chain halts: it cancels its live timers and Activities, clears its population registration, waits until every accepted Update handler has finished, and returns a `ProcessResult` (`ended` with the kernel status, or `halted` with the halting input, each with its publication revision);
- the host keeps no ledger of caller command results: a repeated Update ID is deduplicated by Temporal within one Run, and any other repeat reaches the kernel again, whose state decides it ([capacity record](#workflow-chain-capacity));
- a command sent after the chain closed is reported by the host client as `rejected` with the host code `workflow-closed` and never reaches the kernel ([`client.ts`](../packages/temporal-host/src/client.ts), `submitUpdate`); the engine API turns that code into a `processClosed` result carrying the final status it reads from the closed chain ([`process-observation.ts`](../packages/engine-api/src/process-observation.ts), `submitCommand`);
- a command sent to an address that holds no chain Temporal can describe, one never started or one Temporal no longer retains, is reported as `rejected` with the host code `workflow-unknown`, and the engine API turns it into `processUnknown`, never `processClosed`;
- a Workflow ID is used once (`workflowIdReusePolicy: "REJECT_DUPLICATE"` in [`client.ts`](../packages/temporal-host/src/client.ts)), and a caller's command Update addresses an existing chain only, so a late command cannot create another instance. The only Update-with-Start is the population ingress's `populationStart`, which starts a chain under the kernel-derived identity of the instance a population command starts ([population ingress](kernel/ARCHITECTURE-SPEC.md#population-ingress)).

Temporal lifecycle results and kernel command outcomes remain different types: `workflow-closed`, `workflow-unknown`, `host-halted` and the `host.capacity.*` codes are host codes, never kernel outcomes.

## Alternatives

| Account | Benefit | Rejection or deferral rationale |
|---|---|---|
| Keep the semantic Workflow alive permanently | Every later command reaches the core | Host status remains running after semantic completion, cleanup has no semantic bound, history grows until Continue-As-New, and another retention policy is still required |
| Add a durable router or parent entity now | Stable address survives closure of the process Workflow | Introduces another durable state machine, result-publication races, cross-Workflow ordering, cleanup, and identity without a current retention or discovery consumer |
| Close with semantic completion | Host lifetime matches semantic lifetime | Selected; availability after Temporal history retention is explicitly bounded and may later justify a tombstone or router |

The executable comparison and pinned platform facts behind this selection are recorded in the [Temporal production-lifecycle experiment](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/docs/experiments/TEMPORAL-PRODUCTION-LIFECYCLE-EXPERIMENT.md), run against the deleted adapter.

## Result contract

The host's types are in [`host-contract.ts`](../packages/temporal-host/src/host-contract.ts):

- `CommandResult` is `{outcome, code, revision}`: the kernel's outcome name and refusal code, and the publication head after the input, `null` for an input the Workflow never accepted.
- `ProcessResult`, the Workflow's own result, is `ended {status, revision}`, `notStarted {outcome, code}` for a start the kernel did not commit, `halted {halt, revision}` for a chain whose host input the kernel would neither commit nor reject as stale, or `refused {code}` for a program the kernel's admission refuses.

`ProcessClient.start` ([`client.ts`](../packages/temporal-host/src/client.ts)) answers `committed` with the revision once the start committed and its open waits are registered with the population, the kernel's outcome and code for a start that did not commit, `unsupported` with the admission code for a refused program, and `rejected workflow-already-started` when the Workflow ID is taken. The engine API's dispatch then reads the start memo the chain retains: the same intent is this start retried after a lost response, another intent is the integrity failure `startAddressTaken` ([`start-dispatch.ts`](../packages/engine-api/src/start-dispatch.ts), `dispatchStart`).

A refused Update is refused by its validator, which runs the kernel on the current state, so it never enters Event History; the client returns it as `rejected` with the validator's code and a `null` revision. Temporal SDK 1.21.0 answers an Update with `WorkflowNotFoundError` both for a closed Workflow and for an address it never held or no longer retains, so the client describes the address before it classifies the error: a Workflow Temporal still describes as closed is `rejected workflow-closed`, and an address it cannot describe is `rejected workflow-unknown` ([`client.ts`](../packages/temporal-host/src/client.ts), `notFoundVerdict`). A never-started address and an execution removed after retention stay indistinguishable without another durable store; both are unknown. A description that finds the Workflow running contradicts the Update's answer, and it and every other failure of the Update or describe call propagate to the caller as an infrastructure failure. The memory host answers the same two codes ([`memory-host.ts`](../packages/temporal-host/src/memory-host.ts)).

The engine API's command result ([`process-observation.ts`](../packages/engine-api/src/process-observation.ts), `EngineCommandResult`) is `semantic {commandId, outcome, code}`, `processClosed {commandId, receipt: {processInstanceId, status}}`, whose `status` is `null` when the closed chain's state could not be read, or `processUnknown {commandId, processInstanceId}` for a `workflow-unknown` address. Product 2 classifies `processUnknown` as `indeterminate`, never as a closed process ([human work](BPM-PLATFORM-HUMAN-WORK-SPEC.md), [incident operations](BPM-PLATFORM-INCIDENT-OPERATIONS-SPEC.md)). Its reads distinguish `closed`, `unknown` and `unavailable`: a chain Temporal does not describe, or one whose start memo names another instance, is `unknown`; a chain it could not reach is `unavailable` (`observeProcess`).

Workflow cancellation, termination, timeout, service or Worker unavailability, client deadline and replay incompatibility are infrastructure failures. They do not become a kernel outcome.

## Identity and retry contract

The semantic process-instance ID, Temporal Workflow ID, Run ID, semantic command ID, and Temporal Update ID remain distinct.

The host encodes the address as the typed tuple `["semanticProcessInstance", population, processInstanceId]`, where `population` is the engine population (named by its Task Queue) that hosts the instance: kernel-derived instance identities are unique only within one population, so two populations sharing a namespace never address one chain. It hashes the canonical JSON with SHA-256 and prefixes the digest with `bpmn-process-sha256:` ([`population-address.ts`](../packages/temporal-host/src/population-address.ts)). The engine API derives the same ID from the semantic identity (`engineProcessWorkflowId` in [`host.ts`](../packages/engine-api/src/host.ts)) and hands Product 2 only an opaque locator over it ([`process-locator.ts`](../packages/engine-api/src/process-locator.ts)). The encoding is host policy and never appears in kernel state.

A start's identity is its intent: the digest of the protocol, Workflow ID and type, Task Queue, definition identity, program digest and start stimulus, which the chain retains in its memo ([`start-dispatch.ts`](../packages/engine-api/src/start-dispatch.ts), `prepareStart` and `startMemo`).

Caller commands (User Task completion, incident Retry and Cancel, addressed Message delivery) travel as `command` or `deliver` Updates without a caller-chosen Update ID: `ProcessClient` passes none to `submitUpdate`, which accepts one ([`client.ts`](../packages/temporal-host/src/client.ts)). The kernel judges every arrival, so a repeat of a committed command is judged against the state the first one left. Population commands carry the content-bound Update ID `population-sha256:<sha256([commandId, digest])>` and the ingress ledger answers a repeat ([`population-address.ts`](../packages/temporal-host/src/population-address.ts), `populationCommandUpdateId`); a receiver delivery carries the digest of its `deliveryId` as Update ID and the chain's carried delivery ledger, keyed by the `deliveryId` itself, answers a repeat across Continue-As-New; no derived Update ID embeds a caller's identifier, which may exceed Temporal's identifier limit ([`workflow-host.ts`](../packages/temporal-host/src/workflow-host.ts), `populationDeliver`).

## Workflow lifetime contract

A `start` Run commits the start stimulus through the kernel before any caller Update is applied; a `populationStart` Run commits the population start the ingress made; a `continue` Run decodes the carried state ([`workflow-host.ts`](../packages/temporal-host/src/workflow-host.ts)). Each input is applied in its own Update handler through the kernel's `step`; host arrivals (a due timer, an Activity's result) are queued as they resolve and applied one at a time from the main loop in recorded order, timers due together by deadline (`nextArrival` in [`host-machine.ts`](../packages/temporal-host/src/host-machine.ts)). An arrival the kernel rejects is stale and is dropped; one it would neither commit nor reject halts the chain.

Under durable scheduling, which every engine start uses ([`host.ts`](../packages/engine-api/src/host.ts), `engineHostConfig`), the host owns logical time: it stamps every input with Workflow time in epoch milliseconds and refuses a caller's stimulus that states its own as `host-owns-logical-time` (`clockStimulus` in [`host-machine.ts`](../packages/temporal-host/src/host-machine.ts)). Under external scheduling the caller submits timer firings and effect results itself and keeps the logical times it states.

The Workflow persists the kernel's complete replacement state, definition-scope occurrences included. Temporal does not project a child scope into a Child Workflow, Activity, Timer, Signal, cancellation command, or separate host lifecycle; entry, completion, Error throw and catch, regional cancellation and continuation remain kernel transitions within the one chain.

When the instance ends, the main loop stops, cancels every live timer and Activity scope, clears its population registration, and waits for `allHandlersFinished()` before it returns. Temporal decides whether a racing Update was accepted before that boundary: an accepted one is applied by the kernel and answered; one not accepted reaches a closed Workflow and resolves as `workflow-closed`.

## Workflow-chain production contract

The generic host ([`@bpmn-lean/temporal-host`](../packages/temporal-host/src/workflow-host.ts)) runs each process instance as one Workflow chain. A Run carries its program, host configuration, population scope, encoded kernel state, publication cursor, population carry and its ordinal in one Continue-As-New argument. It continues as new only from a stable checkpoint: once a rollover trigger fires it starts no further Activity, waits until none is in flight, no arrival is queued and every accepted Update handler has finished. A terminal state completes the Workflow normally.

The generic host does not implement native Worker Deployment Versioning. The deleted adapter's contract (a Build ID from the Workflow bundle digest, `PINNED` Process and correlation-ingress Workflows, fresh-Namespace initialization and retained-Run Query obligations) is recorded in the [Worker deployment specification](TEMPORAL-WORKER-DEPLOYMENT-REPAIR-SPEC.md), and adopting it again is hosting work under the held delivery rows ([architecture](ARCHITECTURE.md#worker-deployment-ownership)).

### Workflow-chain capacity

The owner-approved table of 2026-08-17 ([archived proposal](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/docs/archived/TEMPORAL-WORKFLOW-CHAIN-BOUNDS-PROPOSAL.md)) bounds every chain; [`capacity.ts`](../packages/temporal-host/src/capacity.ts) holds its values and its one measure, the UTF-8 bytes of a value's canonical JSON. A bound is checked on the candidate the kernel's step produced, before the host commits it, publishes its journal or starts its work ([`chain-candidate.ts`](../packages/temporal-host/src/chain-candidate.ts)), so an overflow commits, publishes and starts nothing. Its refusal code is `host.capacity.<bound>`: a host restriction, never a meaning of the construct. A caller's Update over a bound is refused in its validator, so it never enters Event History; a population delivery or start over a bound fails with the code; a host arrival (a Timer, an Activity's result) over a bound halts the chain as an unsupported arrival does. Rollover triggers are no refusals: they make the Run continue as new. Deployment configuration may lower a test trigger (`historyEventBudget`) but no bound is raised without reopening the table.

| Budget | Bound | Behaviour | Code |
|---|---:|---|---|
| Event History Events | the SDK suggestion, or 8,000 Events, or the program's own lower budget | rollover trigger, after the activation that reaches it | — |
| Event History bytes | the SDK suggestion, or 8 MiB | rollover trigger | — |
| Retained publication batches of one Run | 2 MiB canonical bytes | rollover trigger once one more batch could cross it | — |
| Accepted Updates per Run | 1,500 | rollover trigger; a caller's Update beyond it is refused until the next Run | `host.capacity.updates` |
| Caller Updates in flight | 8 | refused in the validator | `host.capacity.updatesInFlight` |
| Pending Activities | 32 (raised 2026-11-13) | candidate refused | `host.capacity.pendingActivities` |
| Pending durable Timers | 64 | candidate refused | `host.capacity.pendingTimers` |
| Pending Child Workflows, external Signals and external cancellation requests | 0 | the host emits none | — |
| Program | 192 KiB | start or deployment refused before any Workflow starts | `host.capacity.program` |
| Start stimulus | 64 KiB | start refused before any Workflow starts | `host.capacity.start` |
| Caller, population or derived stimulus | 64 KiB | refused before it is applied | `host.capacity.stimulus` |
| Committed kernel state, without the last input's journal and outbox | 256 KiB (raised 2026-11-13) | candidate refused | `host.capacity.state` |
| One input's execution and occurrence publication batches together | 64 KiB | candidate refused | `host.capacity.publicationBatch` |
| Query answer | 192 KiB | paged: a publication page is the largest complete batch prefix that fits; the observation, state, host-view, pending-intent and start-outcome answers travel as the largest whole-code-point prefixes of their canonical JSON text; the population ingress's result and deployment Queries are not paged | — |
| Effect Activity request | 64 KiB | candidate refused | `host.capacity.effectRequest` |
| Effect Activity result | 64 KiB | the Activity fails non-retryably before it returns; a result arriving larger halts the chain | `host.capacity.effectResult` |
| Effect Activity failure projection | 16 KiB | a longer failure message halts the chain with the code instead | `host.capacity.effectFailure` |
| Continue-As-New argument, of a process chain or of the population ingress | 448 KiB | a process candidate refused; a successor that would exceed it halts the chain; see the population ingress below | `host.capacity.continuation` |
| Workflow chain | 128 Runs | a chain needing a 129th Run halts | `host.capacity.runs` |

Two values were raised on 2026-11-13 on measured numbers, and the owner ratified both the same day ([owner decisions](kernel/ARCHITECTURE-SPEC.md#owner-decisions-on-the-path)):

- Pending Activities 1 to 32: the 1 preserved the deleted adapter's single-effect invariant, while the generic host runs concurrent effects; it would have refused 68 accepted witnesses of 18 done rows, and the realistic sixteen-body parallel Multi-Instance journey needs 16. 32 is the value the embedded Sub-Process profile already admitted.
- Committed state 64 KiB to 256 KiB, now measured without the per-input journal and outbox, which the publication batch and effect request rows bound: the realistic sixteen-body journey peaks at about 250,000 bytes (measured 2026-11-13), and its continuation still fits the unchanged 448 KiB.

Four rows of the approved table were retired on 2026-11-13 because their object does not exist in the generic host:

- Command-recovery ledger, 512 entries and 96 KiB: the host keeps no ledger of caller command results; Temporal deduplicates a retried Update by its Update ID within its Run, and any other retry reaches the kernel again, whose state decides it. The population delivery ledger, its last 1,024 outcomes, is carried inside the continuation row.
- Terminal Workflow result envelope, 192 KiB: there is no receipt-plus-recovery envelope; the Workflow's result is the fixed-shape `ProcessResult` (a status or a halt, and a revision), whose only variable text, a halt code, is bounded by the failure projection.
- Publication segment directory, 64 KiB: the chain carries only its publication cursor, not a directory of Run descriptors; the 128-Run row stays.
- Accepted semantic-input queue, 64 entries and 256 KiB: an Update applies its input in its own handler, so no input queue exists; the queued host arrivals are bounded by the pending Activity and Timer rows.

The population ingress Workflow carries its registry, chain registrations, Timer start ledger, command ledger, queue and in-flight fan-out in one Continue-As-New argument under the same 448 KiB row, beside its declared counts ([population ingress](kernel/ARCHITECTURE-SPEC.md#population-ingress)). A deployment, chain registration, queued command or Timer start that would leave the state at rest with less room than one settling answer needs is refused with `host.capacity.continuation` (a refused registration halts its chain); an emitted hand-off is measured the same way and deferred instead, since its input has committed. The state at rest counts the item in flight as the queue entry it was admitted as, since the reserve leaves out the identifiers that entry carried. That answer reserve is the Query row plus the ledger entry's fixed overhead: a command's ledger entry is its `populationResult` answer, which the unpaged Query must return, inside `{"kind":"command","commandId":…,"digest":…,"answer":…}` instead of `{"kind":"settled","answer":…}`, and its identifier and digest were already carried in its queue entry, so the reserve is 196,608 + 51 − 28 = 196,631 bytes and an admission may fill 262,121 bytes ([`answerReserve`](../packages/temporal-host/src/population-carry.ts)). A fan-out stops by its answer's bytes as it stops at the receiver cap, with a last entry `failed {receiver, unsupported, host.population.fanOutCapacity}`: it reaches a receiver only with room left for the entry that receiver commits with and for the largest stop entry a later receiver could need, its identifiers bounded by the registered chains', the instances the fan-out started and the registered programs' longest element identifier; a receiver that fails commits nothing, so when its entry leaves no room the fan-out stops at it instead. Each entry is measured once, as it is recorded, and an emitted cascade stops within the same reserve. Every answer of a command therefore fits the Query row; a Signal start that rethrows its own Signal, whose started identities embed their emitter's ([#126](https://github.com/mbackschat/bpmn-lean-experiment/issues/126)), stops after 91 started instances at a 190,656-byte answer (measured 2026-11-13) where the receiver cap would allow 1,000. A settled item grows the ledger, which yields its oldest entries, each settled item fitted on its own; since every admission keeps room for one answer, no state built from admitted inputs settles past the continuation row, and a settlement that still would marks a broken invariant and fails the ingress closed. An emitted hand-off the ingress cannot hold waits outside its carried state in the Run's arrival order, the emitter keeping it in its own continuation row, and is accepted as soon as a settled item or a shrunk registration leaves room; while one waits, later emits wait behind it and later commands are refused. The emitter's every later Signal-throwing commit is judged with its held hand-offs in its carry, so an overflow refuses that commit before it publishes or starts anything, a caller's input in its Update validator and a host arrival by halting the emitter alone ([#138](https://github.com/mbackschat/bpmn-lean-experiment/issues/138)). The ingress wakes the chain once it accepted the hand-off; a Run continuing as new hands its waiting hand-offs back to their chains, which offer them to the next Run, where they wait behind what reached it first. The emitter's Update answers only once its hand-off is accepted, holding its in-flight Update slot meanwhile, and an emitter that ended stays open until then. The in-flight fan-out is measured only when the ingress would continue as new during it, once per item, and holds that rollover until it settles when it does not fit; measuring it at every driver step made one cascade quadratic in its receivers. A queued command or deployment program also meets the stimulus and program rows.

Three kernel witnesses are refused on the host, each declared with its code in [`host-capacity-restrictions.ts`](../packages/differential/test/host-capacity-restrictions.ts), which both host targets check: PC-CF-06's accepted `automatic-loop-long-burst` publishes 2,604,132 bytes in one batch, so its start is `host.capacity.publicationBatch`, beyond Temporal's own payload limit as well; the closure-bound witness `automatic-loop-tail-at-closure-bound` is `host.capacity.publicationBatch` and `automatic-loop-waiting-branch-at-work-bound` is `host.capacity.state`. The kernel-runner witnesses are unchanged.

Detection follows an activation, so a Run overshoots a trigger by the work it drains before it rolls over. The [hosted capacity witnesses](../packages/temporal-host/test/host-capacity.temporal-test.ts) carry exactly 448 KiB across a real Continue-As-New and refuse one byte more before Event History, roll a Run over in the first Workflow Task the server suggests it for history size (Temporal Server 1.31.2 suggests at 4 MiB by default, `limit.historySize.suggestContinueAsNew`, so its default suggestion precedes the table's 8 MiB trigger; the host reads a suggestion alike whatever its reason, so the server's 4,096-Event suggestion is covered by the pure test of the suggestion trigger, which also covers the table's own Event and byte triggers), reach the 128th Run and halt at the 129th, refuse one state byte over 256 KiB in the Update validator, run the realistic sixteen-body journey on durable scheduling across Runs with its sixteen effects as concurrent Activities, and deliver a hand-off the full ingress deferred once a closed wait frees room. The [memory-host witnesses](../packages/temporal-host/test/memory-host-capacity.test.ts) find each exact fit and its one-over refusal with the Workflow's own measure, an emitter's Signal throw refused at its own row by the hand-offs it holds included; the [pure witnesses](../packages/temporal-host/test/capacity.test.ts) cover the triggers, the Update fence, paging and the ingress; and the [hand-off witnesses](../packages/temporal-host/test/handoff-capacity.test.ts) cover an emit's exact fit, its deferral, the arrival order of waiting hand-offs and the analysis's two overflow constructions, which now settle within the bound.

## Command ingress

`ProcessClient` submits each caller input as the Update its kernel input kind travels on: `command`, `deliver`, and, under external scheduling only, `timerFire` and `effectResult` ([`client.ts`](../packages/temporal-host/src/client.ts), `Route` in [`port.ts`](../packages/temporal-host/src/port.ts)). Every call addresses the Workflow ID, never a Run ID, so it reaches whichever Run of the chain is current. The validator refuses, before Event History, an Update over the per-Run or in-flight fence, a chain that halted (`host-halted`), an input the host schedules itself (`host-scheduled-input`), a stimulus over its byte bound, a stimulus stating a time the host owns, a malformed stimulus, an input sent on the wrong Update (`wrong-update`), and every input the kernel rejects or the capacity bounds refuse ([`workflow-host.ts`](../packages/temporal-host/src/workflow-host.ts)). An accepted Update applies its input in its handler and returns only once the waits its commit opened are registered with the population and the Signals it threw are accepted by the ingress, which may first defer them.

The engine API routes User Task completion ([`process-work.ts`](../packages/engine-api/src/process-work.ts), `completeWork`) and incident Retry and Cancel ([`process-operations.ts`](../packages/engine-api/src/process-operations.ts)) through `submitCommand`, whose task or incident occurrence may belong to an instance other than the hosting one; the kernel accepts only the exact live occurrence and rejects any other without routing to another Workflow. Incident operations first read the chain and answer a closed chain with `processClosed`, and throw when it is unknown or unavailable.

## Committed execution publication

Publication is derived from the kernel journal ([`publication.ts`](../packages/temporal-host/src/publication.ts)). Every micro-step of a committed input is one revision, numbered across the whole chain. Each input yields an execution batch, one transition per micro-step with its cause as role, and a flow-node-occurrence batch over the same revisions holding the micro-steps that started or ended occurrences, so both publications page in step. Occurrences keep the kernel's `OccurrenceKey` (`processInstanceId`, `elementId`, `activation`, `role`) as their identity; revisions only position them. A rejected input appends nothing, and revision never enters kernel state or BPMN meaning. Neither batch carries a commit time ([#134](https://github.com/mbackschat/bpmn-lean-experiment/issues/134)).

The unconditional `publication` Query is registered with the host's other Queries before the first step. It returns the largest complete prefix of the first `limit` inputs' execution and occurrence batches after the cursor that fits the Query bound, with the head revision; a cursor before the Run's first retained revision gets `gap`, and at revision zero the page is available with head 0 and no batches, because the contract retired `notReady` ([`publication.ts`](../packages/temporal-host/src/publication.ts)). The engine API adds the committed state at the head when a page reaches it ([`process-publication.ts`](../packages/engine-api/src/process-publication.ts)). Query execution is pure and creates no history event.

A Run retains only the batches it published; the cursor alone crosses Continue-As-New, so a page never spans Runs and a reader asking for a revision an earlier Run published is told it is a gap. The engine API checks the chain's retained definition and instance before it returns a page, answering another one as `integrityFailure`, a chain Temporal does not describe as `unknown`, and a transport failure as `unavailable` ([`process-publication.ts`](../packages/engine-api/src/process-publication.ts)). It exposes the execution and occurrence batches as two reads over the one Query (`observeEngineProcessExecution`, `observeEngineProcessFlowNodeOccurrences`). Availability after Temporal retention remains deliberately unsupported rather than inferred.

## Effects and incidents

Every open wait with an effect is one Activity, keyed by its occurrence identity and the number of incidents it has had (`effectKey` in [`host-machine.ts`](../packages/temporal-host/src/host-machine.ts)); a Script Task's effect evaluates its Script in the Worker instead. The handler receives that key as its idempotency key, which a handler with external writes honours ([`activities.ts`](../packages/temporal-host/src/activities.ts)); the Activity ID is the SDK's own, since the key embeds the instance identity, which a caller's start may make longer than Temporal's identifier limit. Temporal retries an Activity's transport failures without an attempt bound (`transportRetry` in [`workflow-host.ts`](../packages/temporal-host/src/workflow-host.ts)); a CIB-visible failure is a returned result, never an exhausted retry. A handler's business result is `success`, `businessFailure`, `technicalFailure` or `unsupported` ([`port.ts`](../packages/temporal-host/src/port.ts), `EffectResult`), and the kernel turns a technical failure into a retry or an incident as its profile selects.

An incident is kernel state: the wait shows its `incident` generation and whether it may cancel the process, and Query exposes it through the observation. No Temporal attempt, Activity ID, exception or Event History fact becomes incident identity. Retry and Cancel are `retryIncident` and `cancelIncidentProcess` commands naming the occurrence and generation; the kernel rejects a generation that is not open (`incident-generation-stale`) in the same step ([`process-operations.ts`](../packages/engine-api/src/process-operations.ts)). A committed Retry reopens the effect with one more recorded failure, which is new work under a new key; a committed Cancel ends the instance, and the Workflow closes normally without a Temporal cancellation or termination.

Every open effect wait runs as its own Activity, so concurrent effects, Compensation handlers included, run concurrently within the pending-Activity bound. An Activity whose wait leaves the host view is withdrawn by cancelling its scope, and its late outcome is dropped; the Activity options set no heartbeat timeout and no cancellation type, so Temporal's default cancellation applies. While a Run drains towards Continue-As-New it starts no Activity and waits until none is in flight, so no Activity crosses a Run boundary; the next Run starts the open effects afresh from the carried state.

## Message and Signal ingress

An addressed Message delivery is a `deliver` Update to one chain, judged by the kernel in the validator like any other input. Message publication by channel or name, Signal broadcast, Conditional evaluation and population starts are population commands: the engine API submits them to the population ingress as an Update-with-Start under the content-bound Update ID, and reads a command's settled answer from the `populationResult` Query when the Update answered `pending` ([`population-client.ts`](../packages/temporal-host/src/population-client.ts), [`message-publication.ts`](../packages/engine-api/src/message-publication.ts)). The ingress reaches a receiver through its chain's `populationDeliver` or `populationStart` Update, and a chain hands the Signals a committed input threw to the ingress through `emit` ([population ingress](kernel/ARCHITECTURE-SPEC.md#population-ingress)). No Temporal Signal carries a BPMN input.

## Conformance evidence extraction

The scenario runner drives one scenario through the host under external scheduling, so timer firings and effect results stay the scenario's explicit inputs, and returns the kernel runner's canonical result shape for comparison with the kernel's own ([`scenario-runner.ts`](../packages/temporal-host/src/scenario-runner.ts)). Each verdict comes from the host, except where the host has no Workflow to send an input to: before any instance exists the kernel judges it with no state, and after the chain ended the kernel judges it from the chain's final state read through the `state` Query. A late input therefore carries the kernel's code, never the host's `workflow-closed`; a `workflow-unknown` answer for a chain the runner started fails the run as a harness failure, never a verdict. The `state` Query exists for this reader only.

## Verification contract

The [Workflow-chain capacity](#workflow-chain-capacity) section names the capacity witnesses. The [hosted host witnesses](../packages/temporal-host/test/host.temporal-test.ts) cover start, effect and command, Message delivery, the durable timer and the refused client timer firing, chain handoff by Continue-As-New, Timer start Schedules, Script recovery on a replacement Worker, replay of every captured history, and the scenario runner on external scheduling. The complete applicable pipeline must remain green. No legacy lifecycle, finite scenario-stimulus-count lifetime, or compatibility branch is retained during pre-release.

## Optional and excluded functionality

An external tombstone or durable router is optional only after a consumer requires command-result or closed-address lookup beyond Temporal retention. That later proposal must specify its support window, atomic publication, rebuild or reconciliation path, authorization, cleanup, and failure classification.

Excluded from this specification:

- returning a kernel outcome for a command a closed Workflow never accepted;
- keeping a Workflow alive solely to reject future commands;
- starting or reopening a Process through a caller's command Update;
- Workflow-ID reuse and host-derived semantic identity;
- host cancellation, termination, timeout, reset, pause, failure, and operator-repair semantics beyond the kernel's incident commands, which close the Workflow normally and use no Temporal cancellation or termination;
- Search Attributes, forms, and task discovery beyond the observation.

## Re-open conditions

Reconsider the selected account only if:

- a required API consumer needs result lookup beyond Temporal retention;
- a future semantic profile permits commands after Process completion;
- a required publication, Message, Timer, effect, or deployment case cannot preserve the transparent cross-Run contract;
- a platform limitation prevents reliable accepted-handler draining;
- an authorization or audit requirement needs an independently retained command ledger.

Nothing in this section applies to the current host; it records what the adapter did, and the [last adapter-era revision of this specification](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/docs/TEMPORAL-PROCESS-LIFECYCLE-SPEC.md) keeps its full text.

- Results: the adapter returned a typed `BpmnProcessStartResult` (`started` or `rejected`) and a `ProcessCommandResult` of `semantic`, `processClosed` with a validated `CompletedProcessReceipt` (`bpmn-lean.process-terminal-receipt.v1`), or `processUnknown` for an address Temporal no longer retained.
