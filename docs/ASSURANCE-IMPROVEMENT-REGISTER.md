# Assurance improvement register

## Purpose and authority

This living register retains assurance findings, corrections, unresolved acceptance and reopening conditions. Its denominator is registered findings, not complete Lean or TypeScript correctness. It accepts new findings without authorizing implementation. [PLAN](PLAN.md#exact-resume-point) selects work; [project design](PROJECT-DESIGN.md), [review policy](REVIEW-POLICY.md) and [testing selection](TESTING-SPEC.md#select-the-task-owner) continue to own the contracts and gates.

Migration status: the [repair proposal](archived/ASSURANCE-ARCHITECTURE-REPAIR-PROPOSAL.md#bounded-closure-amendment) is retired after independent bounded-closure approval. AA-01–AA-26 retain their identities. Active records preserve unresolved findings and acceptance obligations; the compact resolved index links the complete historical finding and accepted evidence; dated baseline observations and “uncommitted” descriptions in that text are historical evidence, while each disposition states the current boundary.

Update an existing record when the same mechanism gains evidence; add the next unused AA identifier for a distinct mechanism. Never renumber or delete a finding identity. Move a fully accepted repair to the resolved index; keep partial repairs active until every residual closes. New records state the observed or suspected mechanism, exact evidence, correction boundary, deciding oracle, disposition and reopening condition. Distinguish a demonstrated defect from an investigation lead. A correction closes only its stated acceptance; residual work remains explicit. Update the owning specification or implementation map when its contract or claim changes, and link it here rather than establishing another semantic authority. A corrected entry reopens when its retained oracle fails, new evidence contradicts its accepted claim, or a reviewed extension changes its contract; the original finding alone does not reopen completed work.

Deferred entries remain open. Their shared reason is the owner-directed bounded implementation/review cost, not a separately established lack of value for each row. Held entries require reviewed outcome/admission decisions. Neither migration nor proposal retirement lifts those restrictions. AA-18's family extension additionally retains the explicit one-CPU/3-GiB resource boundary. No SDK repair, private rebuild, dependency change or performance investigation is authorized by this register.

## Activation and ownership

The implementing agent owns trigger assessment for the selected task; the root integrator checks it before acceptance. Run `what-binds` for each target before editing, read its routed active findings and record the reviewed result in [PLAN](PLAN.md#ordered-work). The Active findings table owns declared path routes and trigger conditions. Only its Owners links bind paths: exact files and explicitly linked directories, without inference from historical mentions, implementation areas or sibling names. Add a newly discovered consumer to the owning record in the same change. This routing does not detect unregistered consumers or decide semantic relevance.

PLAN retains one immutable pre-task `Assurance base` and the active `Assurance work ID` with a compact trigger-assessment table. Keep that base through commits and closure; replace it and the judgments only when selecting a genuinely new task. The control-plane guard compares that base with current tracked content and pending files, so committing cannot erase a missing assessment. A `not-met` judgment states why the trigger is unmet. A `met` judgment names a bounded action and linked acceptance. Held/deferred triggers use `met-review`: select only the required outcome/admission decision or amendment review, preserving implementation restrictions. No assessment or guard result itself authorizes implementation, lifts holds or proves that the judgment is true.
