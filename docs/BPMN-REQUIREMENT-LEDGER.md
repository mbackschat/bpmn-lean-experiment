# BPMN 2.0.2 requirement-disposition ledger

## Boundary

This ledger owns the disposition of reviewed BPMN 2.0.2 Process Execution requirements. It records what the standard requires and how the project currently classifies that requirement; it does not describe implementation inventory, which belongs only in [IMPLEMENTATION-MAP.md](IMPLEMENTATION-MAP.md).

The ledger is deliberately seeded from the requirements already reviewed for the sequential lifecycle, User Task interaction, import boundary, parallel fork/join, and Intermediate Catch Timer specs. It is not an exhaustive extraction of BPMN 2.0.2 and supplies no denominator for Process Execution Conformance. Counts here measure reviewed scope only.

The initial seed avoids reconstructing closed capsule decisions. The owner has selected BPMN coverage as the primary engine roadmap and CIB Seven `2.2.0` executable breadth as the primary near-term ordering baseline, so the two-pass growth rule below expands the construct/mechanism map and then prioritizes its uncovered executable CIB-backed surface without pretending that the line-by-line conformance corpus is already complete. The present ledger makes reviewed scope countable; it still does not make the distance to full Process Execution Conformance measurable.

This is the BPMN engine-coverage ledger. CIB profile relationships belong in the [CIB–BPMN register](CIB-BPMN-RELATION-REGISTER.md), and downstream A12 model/delegate/API adoption belongs in the [A12 Workflows compatibility ledger](research/A12-WORKFLOWS-COMPATIBILITY-LEDGER.md). A requirement may link to both as evidence or priority, but the three denominators are never combined.

## Dispositions

| Disposition | Meaning |
|---|---|
| `supported` | The current reviewed profile assigns bounded executable meaning to the requirement. Evidence can still be draft or incomplete, as linked in the row. |
| `rejected` | Current execution admission deliberately refuses the stated document or construct shape rather than silently assigning behavior. |
| `unsupported` | The requirement is part of the ultimate conformance target but the current reviewed profile has no complete executable disposition for it. |
| `undecided` | A normative conflict, ambiguity, observation boundary, or profile choice remains unresolved. |

These are requirement dispositions, not implementation statuses. A `supported` row does not imply general conformance, and an `unsupported` row does not remove the requirement from the ultimate target.

The dependency graph deliberately exposes why “another BPMN element” is often not a small unit. Cycles identify semantics that must be reviewed together, such as Process/Event instantiation and Activity/scope interruption; they are not an implementation order. Exclusive Gateway work depends on exact expression and Sequence Flow decisions; Message Events depend on Collaboration/correlation and Process identity; Sub-Processes depend on Activity, Event, scope, and data lifetime; compensation depends on nearly every stateful family below it.

`BPMN-MECH-EXPRESSION-01` does not require one universal project grammar, AST, or evaluator. The vendor-neutral account owns the evaluation point, visible semantic context, typed result or failure, and consuming BPMN transition; each language profile selects its exact grammar and runtime. The first standards profile is the dependency-free [Simple Boolean expression language](SIMPLE-BOOLEAN-EXPRESSION-DECISION.md), implemented independently in Lean and TypeScript under one explicit URI. The [JUEL architecture](JUEL-EVALUATION-ARCHITECTURE-DECISION.md) remains a deferred CIB compatibility direction. This closes only the exact Simple Boolean expression provider and its Exclusive Gateway consumer; general `FormalExpression`, XPath, and Common Executable expression coverage remain unsupported.

## Reviewer proto-MVP dependency map

The [reviewer proto-MVP](PLAN.md#reviewer-proto-mvp-milestone) schedules three bounded propositions. This map records the minimum reusable semantic delta before any proposal is approved; it is not an implementation design or evidence claim.

| Candidate requirement | Existing mechanisms that match exactly | New information or transition obligation | First bounded discriminator | Deliberately deferred dependency |
|---|---|---|---|---|
| `BPMN-INCLUSIVE-GATEWAY-01` | Simple Boolean v1 evaluation, flow-identified token multiplicity, Process-scope bindings, User Task waits, canonical stable observation | Evaluate every candidate from one committed state; create tokens for every true output or the default when none is true; retain an occurrence-owned selected-branch set so a paired join waits for all and only those selected arrivals | One acyclic split/join region with two conditional User Task branches and one default User Task branch; compare one selected branch, both conditional branches, and default-only, including the stable state after only one of two selected tasks completes | General Table 13.3 graph-reachability synchronization, unstructured or nested Inclusive Gateways, repeated activation, missing-default exception, expression languages beyond Simple Boolean v1 |

| `BPMN-CALL-ACTIVITY-01` | Definition-scope ownership, semantic Process-instance identity, embedded-scope quiescence, User Task wait/completion, parent continuation, restart and replay | Resolve one `calledElement` QName to a distinct in-document Process definition; create a separately owned called Process instance linked to the caller occurrence; keep the caller active until normal called-instance completion; resume the parent exactly once | One private calling Process invokes one distinct private executable Process containing None Start → User Task → None End, with no data contract or exceptional path | Imports, Global Tasks, input/output matching and mappings, overrides, version/tenant selection, recursion, repeated or concurrent calls, cancellation, Errors/Escalations, definitional Collaborations, Temporal Child Workflow identity |

No CIB relationship is selected by this planning map. The standard remains the semantic authority for all three candidates. A proposal may add a CIB relationship only after a project-owned phase-zero probe identifies a distinct public observation and the relationship is registered with verifier coverage; lexical fixture prevalence or a pinned engine source test alone is not such evidence.

## Growth rule

Grow the ledger in two passes. First enumerate Process Execution-relevant construct and lifecycle families from Clauses 8, 9, 10, 13, and 15 plus their CMOF/XSD anchors, assign stable requirement IDs, record dependency edges, and keep unreviewed details explicitly open. Then deepen one family into precise propositions when its semantic capsule begins. Link to capsule rule IDs only after the capsule owns them, and link to evidence rather than copying implementation details.

Group work by reusable semantic mechanism rather than XML element count or downstream model: Process lifecycle and graph flow; Activity lifecycle; branching/merging; scopes and interruption; event subscription/consumption; variables/data/mapping; looping/multi-instance; compensation; and import/reference closure. After the runnable MVP, order uncovered mechanisms primarily by whether CIB Seven `2.2.0` executes them, then by prerequisite closure and Temporal feasibility. This priority does not alter the normative disposition, import CIB product APIs into the mechanism, or imply coverage of Collaboration, Human Resources, forms, Tasklist, or identity facilities that the selected executable baseline does not establish.

An exhaustive percentage-complete claim remains prohibited until the applicable corpus extraction has a reviewed completeness argument. Until then, report exact implemented mechanisms and explicitly unmeasured remainder rather than a guessed percentage.
