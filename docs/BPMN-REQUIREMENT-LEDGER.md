# BPMN 2.0.2 requirement-disposition ledger

## Boundary

This ledger owns the disposition of reviewed BPMN 2.0.2 Process Execution requirements. It records what the standard requires and how the project currently classifies that requirement; it does not describe implementation inventory, which the [kernel status map](kernel/KERNEL-STATUS-MAP.md#row-status) owns.

The ledger is deliberately seeded from the requirements already reviewed for the sequential lifecycle, User Task interaction, import boundary, parallel fork/join, and Intermediate Catch Timer specs. It is not an exhaustive extraction of BPMN 2.0.2 and supplies no denominator for Process Execution Conformance. Counts here measure reviewed scope only.

The owner has selected BPMN coverage as the primary engine roadmap and CIB Seven `2.2.0` executable breadth as the primary near-term ordering baseline, so the two-pass growth rule below expands the construct/mechanism map and then prioritizes its uncovered executable CIB-backed surface without pretending that the line-by-line conformance corpus is already complete. The present ledger makes reviewed scope countable; it still does not make the distance to full Process Execution Conformance measurable.

This is the BPMN engine-coverage ledger. CIB profile relationships belong in the [CIB–BPMN register](CIB-BPMN-RELATION-REGISTER.md), and downstream A12 model/delegate/API adoption belongs in the [A12 Workflows compatibility ledger](research/A12-WORKFLOWS-COMPATIBILITY-LEDGER.md). A requirement may link to both as evidence or priority, but the three denominators are never combined.

## Dispositions

| Disposition | Meaning |
|---|---|
| `supported` | A reviewed interpretation, restated in its kernel semantics document, assigns bounded executable meaning to the requirement for its profile. Whether the kernel executes it is the kernel status map's. |
| `rejected` | Current execution admission deliberately refuses the stated document or construct shape rather than silently assigning behavior. |
| `unsupported` | The requirement is part of the ultimate conformance target but the current reviewed profile has no complete executable disposition for it. |
| `undecided` | A normative conflict, ambiguity, observation boundary, or profile choice remains unresolved. |

These are requirement dispositions, not implementation statuses. A `supported` row does not imply general conformance, and an `unsupported` row does not remove the requirement from the ultimate target.

A row is **structural** or **operational**, and that distinction is not a fifth disposition. A structural row disposes what the source compiler admits and retains; an operational row disposes what the engine executes. One construct can carry a `supported` structural row and an `unsupported` operational one at the same time, which is how retained notation becomes countable without reading as executable support. [Why `preserved` is not a disposition](PRESERVE-ONLY-ADMISSION-SPEC.md#why-preserved-is-not-a-disposition) owns that decision. A structural row names the operational requirement that stays open, and every `BPMN-STRUCT-` row below is bounded to one profile's admitted source.

The dependency graph deliberately exposes why “another BPMN element” is often not a small unit. Cycles identify semantics that must be reviewed together, such as Process/Event instantiation and Activity/scope interruption; they are not an implementation order. Exclusive Gateway work depends on exact expression and Sequence Flow decisions; Message Events depend on Collaboration/correlation and Process identity; Sub-Processes depend on Activity, Event, scope, and data lifetime; compensation depends on nearly every stateful family below it.

`BPMN-MECH-EXPRESSION-01` does not require one universal project grammar, AST, or evaluator. The vendor-neutral account owns the evaluation point, visible semantic context, typed result or failure, and consuming BPMN transition; each language profile selects its exact grammar and runtime. The first standards profile is the dependency-free [Simple Boolean expression language](SIMPLE-BOOLEAN-EXPRESSION-DECISION.md), implemented independently in Lean and TypeScript under one explicit URI. From M2 the kernel adds a read-only JUEL subset by levels ([architecture](kernel/ARCHITECTURE-SPEC.md#runtime-state-and-step)), amending the [JUEL decision](JUEL-EVALUATION-ARCHITECTURE-DECISION.md). This closes only the exact Simple Boolean expression provider and its Exclusive Gateway consumer; general `FormalExpression`, XPath, and Common Executable expression coverage remain unsupported.

## Growth rule

Grow the ledger in two passes. First enumerate Process Execution-relevant construct and lifecycle families from Clauses 8, 9, 10, 13, and 15 plus their CMOF/XSD anchors, assign stable requirement IDs, record dependency edges, and keep unreviewed details explicitly open. Then deepen one family into precise propositions when its mechanism track begins. Link to rule IDs only after the family's kernel semantics document owns them, and link to evidence rather than copying implementation details.

Group work by reusable semantic mechanism rather than XML element count or downstream model: Process lifecycle and graph flow; Activity lifecycle; branching/merging; scopes and interruption; event subscription/consumption; variables/data/mapping; looping/multi-instance; compensation; and import/reference closure. Order uncovered mechanisms primarily by whether CIB Seven `2.2.0` executes them, then by prerequisite closure and Temporal feasibility. This priority does not alter the normative disposition, import CIB product APIs into the mechanism, or imply coverage of Collaboration, Human Resources, forms, Tasklist, or identity facilities that the selected executable baseline does not establish.

An exhaustive percentage-complete claim remains prohibited until the applicable corpus extraction has a reviewed completeness argument. Until then, report exact implemented mechanisms and explicitly unmeasured remainder rather than a guessed percentage.
