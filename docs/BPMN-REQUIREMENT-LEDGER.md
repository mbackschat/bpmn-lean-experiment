# BPMN 2.0.2 requirement-disposition ledger

## Boundary

This ledger owns the disposition of reviewed BPMN 2.0.2 Process Execution requirements. It records what the standard requires and how the project currently classifies that requirement; it does not describe implementation inventory, which belongs only in [IMPLEMENTATION-MAP.md](IMPLEMENTATION-MAP.md).

The ledger is deliberately seeded from the requirements already reviewed for the sequential lifecycle, User Task interaction, import boundary, and parallel fork/join spec. It is not an exhaustive extraction of BPMN 2.0.2 and supplies no denominator for Process Execution Conformance. Counts here measure reviewed scope only.

Seeding at this boundary avoids later reconstruction of closed capsule decisions while keeping the expensive corpus-extraction half of a conformance program deferred until it has an approved consumer. The ledger makes reviewed scope countable; it does not make the distance to full Process Execution Conformance measurable.

## Dispositions

| Disposition | Meaning |
|---|---|
| `supported` | The current reviewed profile assigns bounded executable meaning to the requirement. Evidence can still be draft or incomplete, as linked in the row. |
| `rejected` | Current execution admission deliberately refuses the stated document or construct shape rather than silently assigning behavior. |
| `unsupported` | The requirement is part of the ultimate conformance target but the current reviewed profile has no complete executable disposition for it. |
| `undecided` | A normative conflict, ambiguity, observation boundary, or profile choice remains unresolved. |

These are requirement dispositions, not implementation statuses. A `supported` row does not imply general conformance, and an `unsupported` row does not remove the requirement from the ultimate target.

## Growth rule

Add a row when a conformance-relevant clause, machine-readable construct, or known source conflict enters review. Link to capsule rule IDs only after the capsule owns them, and link to evidence rather than copying implementation details. Corpus extraction, exhaustive requirement enumeration, and a percentage-complete claim require a separately approved conformance-program consumer; until then, the unreviewed remainder stays explicitly unmeasured.
