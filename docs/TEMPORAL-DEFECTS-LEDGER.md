## TD-001: Query loss during Run eviction

- **Impact:** Concurrent reads of a completed Run can lose queued requests and reach their RPC deadlines, making an otherwise retained publication unavailable to callers.
- **Established cause:** Core takes the evicted Run's task buffer, reinstates its first task and drops the remainder. A tiny constant-Query Workflow reproduces the loss under supported usage, independently of the BPMN adapter's size or semantics.
- **Correction:** The [private patch](experiments/temporal-query-eviction-core/core.patch), Core commit `7cb28c68`, preserves remaining requests, their supersession groups and the activation produced when a later task can run before an earlier history fetch completes. It is retained locally; installed SDK and production distribution dependencies are unchanged.
- **Evidence:** [Query-loss investigation](research/TEMPORAL-EXECUTION-RESEARCH.md#closed-run-query-eviction-investigation) and [private correction validation](research/TEMPORAL-EXECUTION-RESEARCH.md#private-core-correction-and-usage-check) own the baseline comparison, live one/two/three-Query results, complete Core unit suite, adversarial controls and exact build provenance. Seven [focused product checks](research/TEMPORAL-EXECUTION-RESEARCH.md#product-qualification-and-digest-discrimination) now pass on macOS arm64, covering Transaction cancellation, replacement, publication traversal, recovery capacity and replay.
- **Product attribution:** The [released-Core product logs](research/TEMPORAL-EXECUTION-RESEARCH.md#released-core-product-read-attribution) associate four Transaction read failures before the gRPC update and the single segment-traversal failure after it with Core's exact leftover-buffer warning. This supports TD-001 attribution for those reads; it does not establish the cause of earlier browser or CI failures that lack underlying error evidence.
- **Next action:** The owner reaffirmed on 2026-10-13: record the filed defect and continue project delivery. SDK work remains deferred under the stop above. Retain the failure and upstream report while continuing project implementation; broader product/distribution qualification and dependency adoption remain prerequisites to shipping a correction.
- **Hosted-test reads (2026-10-13):** Each `unavailable` read failing the complete Temporal gate at `2c5f4c3e` follows Core's leftover-buffer warning (`/tmp/pbv-closure-temporal-2c5f4c3e-a`); host load widens the window. The owner decided that hosted refinement tests reread `unavailable` through one logged harness reader, matching the retryable public contract that Product 2 already applies. This aligns the tests with that contract and repairs nothing: each retry stays visible in its receipt, the retained reproducer remains the defect witness, and this entry stays open.
- **Closure:** The adopted dependency contains the demonstrated correction and applicable product/distribution gates pass against that exact artifact. After first declining upstream publication, the owner approved a reviewed report, filed as [Core issue 1621](https://github.com/temporalio/sdk-rust/issues/1621) on 2026-10-01 with the production diff inline; the [reproducer](research/TEMPORAL-EXECUTION-RESEARCH.md#retained-query-eviction-reproducer) is retained locally. ## TD-002: Transaction publication descriptor rejected

- **Impact:** A compensated Transaction's selected publication segment has rejected its descriptor digest, preventing the client from accepting that read as a valid publication.
- **Established cause:** A legacy Query can carry new Activity/Timer/Signal history ending before the next Workflow Task starts. Core treats that incomplete tail as runnable, delivers the input with the preceding task's clock and advances its cache. Live publication therefore hashes the old timestamp; cold replay uses the next task's recorded timestamp. All twelve captured failing Transaction Runs reconstruct exactly this difference, with unchanged semantic state.
- **Correction:** The [private clock patch](experiments/temporal-query-eviction-core/query-clock.patch), commit `14ce5270` on top of TD-001's `7cb28c68`, preserves initialization and recorded-command validation while deferring new inputs until their task starts. It remains experimental; installed SDK and production dependencies are unchanged. Execution termination/timeout tails are outside this correction's guarantee.
- **Evidence:** The [clock-ordering investigation](research/TEMPORAL-EXECUTION-RESEARCH.md#legacy-query-pending-input-clock-investigation) retains exact twelve-Run reconstruction, a second independent minimal Workflow failure on released Core, red/green Timer delivery, missing-command rejection and startup guards, independent correction review, 397 passing Core tests and a 20-round live/cold comparison. Seven unchanged product publication/recovery/replay checks pass on the combined private bridge; this is focused macOS arm64 evidence, not final qualification.
- **Next action:** Deferred under the owner's SDK-work stop above; retain [Core issue 1623](https://github.com/temporalio/sdk-rust/issues/1623) and failed qualification. Dependency adoption and Linux/distribution qualification remain open. The owner approved the report after joint review; it was filed on 2026-10-02 using Temporal's inherited bug-report template with the complete SDK reproducer and deterministic Core witness. Preserve the earlier failed push receipt.
- **Closure:** The adopted dependency contains the demonstrated correction and applicable complete product/distribution gates pass under the unchanged identity and digest checks. Successful reruns alone do not close this entry.

## TD-003: Native V8 garbage-collection crash

- **Impact:** Temporal test children terminate in native code, failing qualification without a TypeScript assertion or semantic result.
- **Established cause:** The installed Node binary saves unused register `x4` into a GC-scanned baseline-prologue frame on a configuration without dispatch-handle linkage. A live debugger capture locates invalid value `0x0f` in that exact saved slot, where root scanning dereferences `0x0e`. This demonstrates the V8 mechanism for the captured crash; it does not assign every historical native failure to it.
- **Correction:** V8 commit `0b94a9fd`, retained as the [upstream patch](experiments/node-runtime-corrections/v8-0b94a9fd.patch), saves the zero register instead of `x4` when JavaScript linkage carries no dispatch handle. The unmodified upstream patch applies to Node `24.18.0`. A private build of it differs from the equivalent private baseline only in the prologue's saved register pair. That private validation changed neither the installed SDK nor the project runtime pins; the later official-runtime migration is recorded below.
- **Evidence:** [Observed crashes](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#environment-and-observed-failures), [ordinary-setting recurrences](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-09-30-documentation-checkpoint-recurrence) and [source, binary and live stack evidence](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-source-binary-and-live-stack-evidence) establish the mechanism. The [corrected-build validation](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-corrected-build-validation) retains the separating regression. With an invalid `x4` injected at the prologue's slow path, the release and private baselines fault at `0xe`, and the candidate passes. The same holds for the captured Temporal workload under ordinary flags. The candidate also passes all 818 `test:temporal` checks. An unforced stress comparison reproduced the fault on neither binary and is not repair evidence. On 2026-10-01 the [installed runtime crashed](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-recurrences-after-the-harness-correction) in 15 of 60 rounds of two direct-VM files, independently of the harness revision, while the candidate crashed in none of 20.
- **Release status:** Official Node `v24.21.0` LTS still faults on the separating witness; official `v26.10.0` contains the correction and passes it. A static disassembly shows the defective prologue in official linux-arm64 and linux-x64 `v24.18.0` and the corrected one in both `v26.10.0` builds. The adopted release's current product qualification is recorded below.
- **Adoption:** On 2026-10-09 the owner approved migration to official Node `26.10.0`. Its verified darwin-arm64 binary passes the retained injected-register witness with the corrected `x3, xzr` save and 65 injections (`/tmp/node26-migration-20261009/v8-witness`). Project selectors and the digest-pinned evaluation image now select that release. The Linux arm64 image binary has the corrected prologue; its SHA-256 is `71b004f18a82f3ea8f26109798564a12e5e4c7989a4c35b93851830b5815dd03`. The built Docker distribution passes the public browser walkthrough (`/tmp/node26-migration-20261009/docker-walkthrough-path`) and removes its task containers and volumes. Linux injected-register and Linux x64 product qualification remain open.
- **Product qualification:** On official darwin-arm64 Node 26.10.0, strict harness types, the full build, 598 component tests and 407 concurrent Temporal tests pass without an observed native crash. The complete gate fails with hosted publication Query failures and the held parallel-scope admission assertion (`/tmp/node26-migration-20261009/temporal`); the separately executed serial recovery/replay group passes all 30 checks (`/tmp/node26-migration-20261009/temporal-hosted-serial`). Complete infrastructure (663 checks), platform (1,263 checks), core/source/differential and distribution-structure gates also pass under the official runtime (`/tmp/node26-migration-20261009/infrastructure-corrected`, `/tmp/node26-migration-20261009/platform`, `/tmp/node26-migration-20261009/engine-compatibility`). Query loss and held admission remain distinct from the demonstrated V8 repair; this is not a successful complete Temporal gate.
- **Next action:** The owner authorized the migration commit on 2026-10-10 with these failures disclosed. Resolve the separate hosted qualification failures before release qualification. ## TD-004: Direct-VM initialization timeout

- **Impact:** A direct-VM test activation fails with `Script execution timed out after 1000ms`, so its semantic assertions cannot establish a passing result. On the affected runtimes the timeout can also trigger TD-005's abort.
- **Established cause:** The [project harness](../packages/temporal-adapter/testkit/test/direct-vm-activation-harness.ts) passed a one-second isolate execution timeout. The pinned SDK's production default is five seconds, and no project Worker overrides it. Node enforces the limit by wall clock. An activation needs about 250 ms of CPU, but its wall time includes main-thread GC pauses, and those stretch under host CPU oversubscription. On a quiet host the slowest activation took 224 ms; under 2× oversubscription it took 847 ms; under 4× it exceeded the limit in each of three rounds. Workflow VM retention was excluded.
- **Correction:** On the owner's 2026-10-01 decision, the harness takes its limit from the execution timeout the installed SDK compiles for a Worker that leaves it unset, as the production Worker does. A [harness test](../packages/temporal-adapter/testkit/test/direct-vm-activation-harness.test.ts) runs a 1.5-second initialization that the one-second limit terminated and the production default admits.
- **Evidence:** The [timeout mechanism investigation](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-direct-vm-timeout-and-async-hooks-abort-mechanisms) retains the GC attribution, contention matrix, retention probe, deadline provenance and the corrected harness's contended rounds. The earlier [2026-09-30 observation](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-09-30-documentation-checkpoint-recurrence) records the original failure.
- **Separate cleanup correction:** The direct-VM harness awaited `createWorkflow` before entering its cleanup block, so a creation failure bypassed `creator.destroy()` and left the SDK's bundle source-map registration retained. The retention probe found no growth in passing runs, and the gap was not the timeout's cause. The harness now destroys the creator whenever it was created; the [harness test](../packages/temporal-adapter/testkit/test/direct-vm-activation-harness.test.ts) fails a bundle's evaluation and requires its registration to be gone.
- **Qualification:** At `2eae85c0` the complete `test:temporal` lane passes 820 of 820 on the V8-corrected candidate (`/tmp/mue-td004-test-temporal-candidate`, asserted). On the installed `v24.18.0` the same lane stops on TD-003 crashes, independently of the harness revision.
- **Next action:** Close this entry when the complete lane passes on the runtime adopted for TD-003.
- **Closure:** The chosen correction passes the original workload and a separating guard under the intended configuration. Changing the deadline requires that owner decision; raising it or reducing concurrency merely to obtain a pass does not close this entry. Keep it distinct from TD-003.

## TD-005: Async-hooks callback abort

- **Impact:** A native callback-scope assertion aborts a Node process. In project test children it removes the remaining tests of that file from the run.
- **Established cause:** Node's `ContextifyScript::EvalMachine` can terminate a `microtaskMode: 'afterEvaluate'` promise job between its async-hook `before` and `after` callbacks. `CancelTerminateExecution` then leaves the async-id stack deeper than at entry, and the next top-level callback scope aborts once async-hook checks are armed. Node's test runner arms them in every test process. A ten-line reproducer aborts on Node `24.18.0`, `24.21.0`, `26.10.0` and the 2026-10-01 `main` nightly. Each contended product abort followed a TD-004 timeout in the same child.
- **Correction:** A private ten-line [`src/node_contextify.cc` patch](experiments/node-runtime-corrections/node-contextify-async-stack.patch) pops the contexts entered during the terminated evaluation and keeps outer contexts. With it, the reproducer, the context-preservation check and three contended product rounds no longer abort. Node's vm, async-hooks and AsyncLocalStorage selection passes 241 of 241, and `test:temporal` passes 818 of 818. Installed Node and distributions are unchanged. The reproducer and patch were reported upstream as [Node issue 66439](https://github.com/nodejs/node/issues/66439) on 2026-10-01. The owner had approved the report only for joint review; filing it without that review was an agent error ([process finding 74](PROCESS-ASSESSMENT-LEDGER.md#finding-74)).
- **Evidence:** [Mechanism and correction validation](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-direct-vm-timeout-and-async-hooks-abort-mechanisms), with the earlier [observed abort](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#environment-and-observed-failures).
- **Next action:** Track the upstream issue and adopt a Node release that contains a correction. Adopting Node 26 for TD-003 does not remove this defect. Both the small SDK control and a [production BPMN Worker-factory witness](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-02-production-worker-hook-control) observe no enabled hooks in their default Workflow thread. These witnesses do not exclude hook-enabled callers or qualify Linux/distribution. Complete that exposure classification; an abort there also requires a terminated activation under the five-second default. [Temporal TypeScript SDK issue 939](https://github.com/temporalio/sdk-typescript/issues/939) reports the same message from a Worker on a Workflow Task timeout, which makes a production path plausible but does not demonstrate this mechanism there. The TD-004 correction removes the known project trigger in test runs.
- **Closure:** The adopted runtime contains this or an equivalent upstream correction and passes the separating reproducer and the applicable gates, or an evidence-backed disposition excludes the affected production paths. Merely avoiding timeouts does not close this entry.
