## TD-002: Transaction publication descriptor rejected

- **Impact:** A compensated Transaction's selected publication segment has rejected its descriptor digest, preventing the client from accepting that read as a valid publication.
- **Established cause:** A legacy Query can carry new Activity/Timer/Signal history ending before the next Workflow Task starts. Core treats that incomplete tail as runnable, delivers the input with the preceding task's clock and advances its cache. Live publication therefore hashes the old timestamp; cold replay uses the next task's recorded timestamp. All twelve captured failing Transaction Runs reconstruct exactly this difference, with unchanged semantic state.
- **Correction:** The [private clock patch](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/docs/experiments/temporal-query-eviction-core/query-clock.patch), commit `14ce5270` on top of TD-001's `7cb28c68`, preserves initialization and recorded-command validation while deferring new inputs until their task starts. It remains experimental; installed SDK and production dependencies are unchanged. Execution termination/timeout tails are outside this correction's guarantee.
- **Evidence:** The [clock-ordering investigation](research/TEMPORAL-EXECUTION-RESEARCH.md#legacy-query-pending-input-clock-investigation) retains exact twelve-Run reconstruction, a second independent minimal Workflow failure on released Core, red/green Timer delivery, missing-command rejection and startup guards, independent correction review, 397 passing Core tests and a 20-round live/cold comparison. Seven unchanged product publication/recovery/replay checks pass on the combined private bridge; this is focused macOS arm64 evidence, not final qualification.
- **Under the hosted reread (2026-10-13):** At `8094bf6d` the Transaction `success` read returned `unavailable` from `QueryNotRegisteredError: Workflow publication descriptor digest substitution` on all 1,029 attempts until the 120-second hang guard failed it (`/tmp/pbv-closure-temporal-8094bf6d-a`). The [TD-001 reread](#td-001-query-loss-during-run-eviction) therefore cannot mask this persistent defect; it delays the failure.
- **Approved test workaround (2026-10-13):** The owner approved marking the compensated `success` and `failure` Transaction publication subtests as `todo` until the defect is fixed. They still run and report each failure, but no longer fail the gate; the uncompensated `empty` case stays binding. Consequence: a different regression in those two subtests would also go unflagged. Remove the marker when an adopted SDK contains the correction and this entry closes.

## TD-003: Native V8 garbage-collection crash

- **Impact:** Temporal test children terminate in native code, failing qualification without a TypeScript assertion or semantic result.
- **Established cause:** The installed Node binary saves unused register `x4` into a GC-scanned baseline-prologue frame on a configuration without dispatch-handle linkage. A live debugger capture locates invalid value `0x0f` in that exact saved slot, where root scanning dereferences `0x0e`. This demonstrates the V8 mechanism for the captured crash; it does not assign every historical native failure to it.
- **Correction:** V8 commit `0b94a9fd`, retained as the [upstream patch](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/docs/experiments/node-runtime-corrections/v8-0b94a9fd.patch), saves the zero register instead of `x4` when JavaScript linkage carries no dispatch handle. The unmodified upstream patch applies to Node `24.18.0`. A private build of it differs from the equivalent private baseline only in the prologue's saved register pair. That private validation changed neither the installed SDK nor the project runtime pins; the later official-runtime migration is recorded below.
- **Evidence:** [Observed crashes](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#environment-and-observed-failures), [ordinary-setting recurrences](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-09-30-documentation-checkpoint-recurrence) and [source, binary and live stack evidence](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-source-binary-and-live-stack-evidence) establish the mechanism. The [corrected-build validation](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-corrected-build-validation) retains the separating regression. With an invalid `x4` injected at the prologue's slow path, the release and private baselines fault at `0xe`, and the candidate passes. The same holds for the captured Temporal workload under ordinary flags. The candidate also passes all 818 `test:temporal` checks. An unforced stress comparison reproduced the fault on neither binary and is not repair evidence. ## TD-004: Direct-VM initialization timeout

- **Impact:** A direct-VM test activation fails with `Script execution timed out after 1000ms`, so its semantic assertions cannot establish a passing result. On the affected runtimes the timeout can also trigger TD-005's abort.
- **Established cause:** The [project harness](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/packages/temporal-adapter/testkit/test/direct-vm-activation-harness.ts) passed a one-second isolate execution timeout. The pinned SDK's production default is five seconds, and no project Worker overrides it. Node enforces the limit by wall clock. An activation needs about 250 ms of CPU, but its wall time includes main-thread GC pauses, and those stretch under host CPU oversubscription. On a quiet host the slowest activation took 224 ms; under 2× oversubscription it took 847 ms; under 4× it exceeded the limit in each of three rounds. Workflow VM retention was excluded.
- **Correction:** On the owner's 2026-10-01 decision, the harness takes its limit from the execution timeout the installed SDK compiles for a Worker that leaves it unset, as the production Worker does. A [harness test](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/packages/temporal-adapter/testkit/test/direct-vm-activation-harness.test.ts) runs a 1.5-second initialization that the one-second limit terminated and the production default admits.
- **Evidence:** The [timeout mechanism investigation](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-direct-vm-timeout-and-async-hooks-abort-mechanisms) retains the GC attribution, contention matrix, retention probe, deadline provenance and the corrected harness's contended rounds. The earlier [2026-09-30 observation](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-09-30-documentation-checkpoint-recurrence) records the original failure.
- **Separate cleanup correction:** The direct-VM harness awaited `createWorkflow` before entering its cleanup block, so a creation failure bypassed `creator.destroy()` and left the SDK's bundle source-map registration retained. The retention probe found no growth in passing runs, and the gap was not the timeout's cause. The harness now destroys the creator whenever it was created; the [harness test](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/packages/temporal-adapter/testkit/test/direct-vm-activation-harness.test.ts) fails a bundle's evaluation and requires its registration to be gone.
- **Qualification:** At `2eae85c0` the complete `test:temporal` lane passes 820 of 820 on the V8-corrected candidate (`/tmp/mue-td004-test-temporal-candidate`, asserted). On the installed `v24.18.0` the same lane stops on TD-003 crashes, independently of the harness revision.
- **Next action:** None; closed.
- **Disposition:** Closed on 2026-11-13. The adapter whose harness carried the one-second limit was deleted with the pre-kernel stack, and the complete Temporal lane of the generic host, which sets no isolate timeout of its own, passes on the runtime adopted for TD-003 (Verify [43464313994](https://github.com/mbackschat/bpmn-lean-experiment/actions/runs/43464313994)).
- **Closure:** The chosen correction passes the original workload and a separating guard under the intended configuration. Changing the deadline requires that owner decision; raising it or reducing concurrency merely to obtain a pass does not close this entry. Keep it distinct from TD-003.

## TD-005: Async-hooks callback abort

- **Impact:** A native callback-scope assertion aborts a Node process. In project test children it removes the remaining tests of that file from the run.
- **Established cause:** Node's `ContextifyScript::EvalMachine` can terminate a `microtaskMode: 'afterEvaluate'` promise job between its async-hook `before` and `after` callbacks. `CancelTerminateExecution` then leaves the async-id stack deeper than at entry, and the next top-level callback scope aborts once async-hook checks are armed. Node's test runner arms them in every test process. A ten-line reproducer aborts on Node `24.18.0`, `24.21.0`, `26.10.0` and the 2026-10-01 `main` nightly. Each contended product abort followed a TD-004 timeout in the same child.
- **Correction:** A private ten-line [`src/node_contextify.cc` patch](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/docs/experiments/node-runtime-corrections/node-contextify-async-stack.patch) pops the contexts entered during the terminated evaluation and keeps outer contexts. With it, the reproducer, the context-preservation check and three contended product rounds no longer abort. Node's vm, async-hooks and AsyncLocalStorage selection passes 241 of 241, and `test:temporal` passes 818 of 818. Installed Node and distributions are unchanged. The reproducer and patch were reported upstream as [Node issue 66439](https://github.com/nodejs/node/issues/66439) on 2026-10-01. The owner had approved the report only for joint review; filing it without that review was an agent error ([process finding 74](https://github.com/mbackschat/bpmn-lean-experiment/blob/404a39d7/docs/PROCESS-ASSESSMENT-LEDGER.md#finding-74)).
- **Evidence:** [Mechanism and correction validation](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-01-direct-vm-timeout-and-async-hooks-abort-mechanisms), with the earlier [observed abort](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#environment-and-observed-failures).
- **Next action:** Track the upstream issue and adopt a Node release that contains a correction. Adopting Node 26 for TD-003 does not remove this defect. Both the small SDK control and a [production BPMN Worker-factory witness](research/NODE-V8-CRASH-INVESTIGATION-RESEARCH.md#2026-10-02-production-worker-hook-control) observe no enabled hooks in their default Workflow thread. These witnesses do not exclude hook-enabled callers or qualify Linux/distribution. Complete that exposure classification; an abort there also requires a terminated activation under the five-second default. [Temporal TypeScript SDK issue 939](https://github.com/temporalio/sdk-typescript/issues/939) reports the same message from a Worker on a Workflow Task timeout, which makes a production path plausible but does not demonstrate this mechanism there. The TD-004 correction removes the known project trigger in test runs.
- **Closure:** The adopted runtime contains this or an equivalent upstream correction and passes the separating reproducer and the applicable gates, or an evidence-backed disposition excludes the affected production paths. Merely avoiding timeouts does not close this entry.

## TD-006: Native-connection calls ignore the abort signal

- **Impact:** A Client call that an Activity makes over the Worker's native connection cannot be cancelled. An Update or Query that waits for a Workflow task on the Activity's own Task Queue therefore never settles once that queue's Worker drains, and holds `Worker.shutdown` open. The m2 showcase hung this way until the release-acceptance job timed out (release-acceptance run 43102322753, 2026-11-11).
- **Established cause:** `@temporalio/worker` 1.21.0 `NativeConnection.sendRequest` does not pass the call context's abort signal on (`// TODO: add support for abortSignal`, `lib/connection.js:91`), although `withAbortSignal` installs one.
- **Project disposition:** The population Activities ignored their own cancellation; that project defect is corrected (`packages/temporal-host/src/population-activities.ts`, `settlingOnCancellation`), and they now settle as cancelled while the abandoned call may still take effect, as after a Worker crash, and is repeated by the Activity's retry. No SDK repair, private build or patch is made (owner direction, 2026-10-10).
- **Closure:** An adopted SDK release passes the abort signal on to native calls, or an evidence-backed disposition shows no project Activity awaits a native call that cancellation must interrupt.
