# Internal commutation proposal

## Status

Lifecycle: implementation-in-progress
Review: approved

## Decision question and boundary

What is the smallest reusable rule that lets bounded internal closure advance every simultaneously enabled, observationally independent operation and represent every residual observable choice without treating program collection order as BPMN scheduling meaning?

The implemented first `INTERNAL-COMMUTATION` Beta risk checkpoint replaced the constructor-specific exception for exactly two distinct `awaitUserTask` operations with one semantic-footprint criterion over an exact two-operation frontier. The checkpoint covers ordinary `awaitUserTask`, `awaitMessage`, `awaitTimer`, and `awaitEffect` arming operations in Lean and the independently written TypeScript core. It added no BPMN source shape, profile capability, Semantic Process operation, RuntimeState field, stimulus, public wire field, Temporal host capability, MUE content ID, or support claim.

The broader final-closure obligation remains open. The selected RC amendment is closure-reviewed and does not graduate this proposal. The general account selects larger enabled sets, every current operation family and explicit choice representation without adding a BPMN construct or newly admitted topology. The independently approved [selected-join readiness amendment](#selected-join-readiness-dependency-amendment) extends only its dependency vocabulary; its [dependency checkpoint](#selected-join-dependency-checkpoint) and [local-control outcome](#local-control-preparation-prerequisite) retain their accepted implementation boundaries. Earlier approved checkpoints retain their recorded boundaries.

## Existing risk

[The Semantic Process contract](SEMANTIC-PROCESS-IL-SPEC.md#internal-scheduling) requires every material internal choice to be explicit or observationally irrelevant under exact hypotheses. Before this proposal's first Beta checkpoint, production closure recognized only one exact pair of distinct ordinary User Task arms. That check named operation constructors and three identifiers without stating the semantic resources each transition reads and writes. Extending that checklist would repeat the mechanism without establishing why the pair commutes. Current batch coverage belongs to [`implementation-status-owner:ENGINE-RUNTIME-PROOF`](ENGINE-RUNTIME-AND-PROOF-IMPLEMENTATION-MAP.md#current-boundary); the checkpoint sections below retain their bounded laws and exclusions.

Canonical operation-ID selection is necessary for reproducibility but is not evidence of commutation. Sorting two conflicting transitions merely makes one conflict deterministic. The deciding rule must establish non-interference before the selector may use canonical order.

## Implemented checkpoint semantic-footprint rule

Each candidate transition receives a dynamic `InternalTransitionFootprint` derived from the admitted program, the exact pre-state, and the operation before its successor is selected. The footprint contains canonical sets of tagged semantic atoms, split into `reads`, `writes`, and `publications`. Shared reads are permitted. A pair is non-interfering only when neither side's writes intersect the other side's reads or writes and the publication keys are distinct.

The checkpoint state-atom vocabulary is closed:

- `controlToken(owner, place)` for one exact token unit whose presence enables the operation and whose multiplicity is decremented;
- `scopeOccurrence(owner)` and `runtimeControl(instance)` for owner liveness and the exact running Process instance;
- `logicalTime` for Timer deadline calculation;
- `activation(kind, elementId)` for the per-family counter value that mints the next occurrence;
- `wait(kind, occurrence)` for absence of, and insertion of, the complete User Task, Message, Timer, or effect occurrence;
- `openWaitAnchor(occurrence)` for absence from, and addition to, the actual derived untagged public wait-anchor domain shared by User Task, Message, Timer, effect, and incident occurrences;
- `activityVariableScope(effectOccurrence)` for absence of, and insertion of, the complete effect-owned local scope, including an empty scope;
- `activityVariable(effectOccurrence, name)` for every literal input binding inserted into that local scope.

The closed publication-atom vocabulary is `committedTransition(operationId, kind, origin, owner, logicalTime, positionDelta)`, `flowNodeLifecycle(waitAnchor(occurrence))`, and `publicationPair(operationId, occurrence)`. The lifecycle atom deliberately omits the wait family because the published `SemanticFlowNodeOccurrenceAnchor.wait` contract is keyed only by `(processInstanceId, elementId, activation)`. A User Task and Timer with the same complete occurrence therefore collide even though their private wait collections and activation counters differ. A publication pair binds one transition record and its one lifecycle delta before either receives a batch index. Its canonical sort key is the exact tuple `(operationId, occurrenceKind, processInstanceId, elementId, activation)`, where `occurrenceKind` is the private wait-family discriminator and never part of the public lifecycle anchor.

Occurrence atoms include the state-derived next activation, not only an element ID. Every User Task, Message, Timer, and effect occurrence in the equations uses `owner.processInstanceId`; only the separate `runtimeControl(state.control.instanceId)` read names the top-level running Process instance. Atom tags keep User Task, Message, Timer, effect, control-place, and Activity-local domains distinct. Every set and sort key uses the repository's canonical Unicode scalar ordering, numeric activation ordering, and explicit tagged equality. Locale collation, object enumeration order, and a successor-state diff are excluded from footprint construction.

The constructor equations are exact:

| Constructor | Required reads | Complete writes | Publication bundle |
|---|---|---|---|
| `awaitUserTask` | `runtimeControl(instance)`, `scopeOccurrence(owner)`, `controlToken(owner,input)`, `activation(userTask,taskId)`, and absence of both `wait(userTask,occurrence)` and `openWaitAnchor(occurrence)` | decrement `controlToken(owner,input)`; replace `activation(userTask,taskId)` by the next value; canonically insert `wait(userTask,occurrence)`, thereby adding the derived `openWaitAnchor(occurrence)` | one `committedTransition` carrying the exact operation metadata, owner, unchanged logical time, and the token-to-User-Task position delta; one started `flowNodeLifecycle(waitAnchor(occurrence))`; one `publicationPair(operationId,occurrence)` |

Current effect input mappings are literals and therefore read no Process or Activity-local runtime variable. Adding a variable-reading expression reopens this table and the atom vocabulary before implementation.

For the first checkpoint, footprint construction returns `none` for every operation outside ordinary `awaitUserTask`, `awaitMessage`, `awaitTimer`, and `awaitEffect`. It also returns `none` unless the selected operation is the unique program operation in its complete wait-family declaring set for the emitted element, that declaration is owned by the selected scope, and the new untagged wait anchor is absent from the exact pre-state. The declarer census includes every ordinary and composite operation that can emit that wait family, including bounded, monitored, Sequential Multi-Instance, Parallel Multi-Instance, event-race, and boundary-host operations even though those operations cannot themselves receive a checkpoint footprint. Program admission now requires that census to resolve every family-tagged declaration uniquely even when no wait is live; the footprint check retains the same rule defensively at its local boundary. The open-anchor census includes existing incident occurrences as well as every live User Task, Message, Timer, and effect wait. An unavailable footprint, more or fewer than two enabled operations, an intersection, an existing or paired untagged wait-anchor collision, a duplicate publication key, or a failed second step retains the existing fail-closed ambiguous-choice result. Separately, an unavailable pre-state or intermediate open-set projection retains the traced boundary's existing no-publication failure rather than counting two equal projection failures as commutation evidence. This is a sufficient rule, not a necessary characterization of every commuting transition.

At the first checkpoint, the Activity data-input operation `awaitDataInputUserTask` and its data-output sibling `awaitDataOutputUserTask` entered the composite wait-and-Activity-arming declarer criterion but received no checkpoint footprint. The legacy footprint facade retains that refusal; complete preparation is owned by the later [standalone Activity-data arming outcome](#standalone-activity-data-arming-outcome). The `LocalDataOwner` discriminator distinguishes `effectOccurrence` and `activityOccurrence` while preserving the checkpoint's effect-arm meaning. The complete data-input footprint includes its Process-variable read, Activity occurrence, local scope, wait, counters, and publication. Shared Process-variable reads are permitted by the existing equation, while a Process-variable write conflicts with that read.

## Checkpoint execution and publication contract

The pair predicate requires an admitted `WellFormedProgram`, a `runtimeStateWellFormed` exact-instance pre-state, successful `projectOpenFlowNodeOccurrences?` projection of that exact program and pre-state, two distinct operations contained in that program, successful independent enabledness witnesses from the same pre-state, complete unique-declarer footprints from the equations above, no write/read or write/write intersection in either direction, and distinct actual publication atoms. Successful open-set projection supplies the current `flowNodeOccurrenceProgramValidity`, association validity, and untagged anchor uniqueness premises that `runtimeStateWellFormed` alone does not establish. Shared reads are permitted.

Given those premises for `left` and `right`, the checkpoint requires all of these facts:

1. firing `left` preserves `right` enabledness and firing `right` preserves `left` enabledness;
2. both two-step executions succeed;
3. both executions produce exactly equal raw RuntimeState values whose affected collections retain canonical order, and both intermediate states remain runtime-well-formed and open-set-projectable;
4. the actual accepted transition and lifecycle facts are defined and identical, not merely two equal candidate values or two equal projection failures;
5. sorting the two unnumbered publication pairs by the complete paired sort key and only then assigning consecutive transition indices produces one identical committed publication without separating a transition from its lifecycle delta.

“Canonical RuntimeState” does not mean equality after a projection or an assertion-time sort. The implementation extends `runtimeStateWellFormed`'s canonical-collection criterion and every production insertion site so User Task, Message, Timer, and effect waits are ordered by complete occurrence identity; their four activation-counter families are ordered by element ID; and Activity-variable scopes are ordered first by `LocalDataOwner` discriminator and then by complete identity within that arm. The invariant applies to every add site for an affected collection, including composite operations outside this checkpoint, rather than only to the four constructors named here.

This is an internal pre-release runtime-representation replacement owned jointly with the [scoped runtime data specification](capsules/SCOPED-DATA-SPEC.md#runtime-replacement). It changes no public wire. Its targeted preservation obligation requires every existing producer, consumer, well-formedness check, fixture, and proof to use the replacement order directly; existing canonical observations and retained Temporal histories must replay unchanged; and no compatibility reader, order-normalizing boundary, or second RuntimeState shape is permitted.

The production evaluator continues to select the canonical lowest operation ID first. The proof makes that selection observationally irrelevant for the admitted pair; the sort does not serve as the proof. No existing committed-transition or lifecycle wire shape changes. Raw evaluator visit order remains private, while the published batch order remains canonical and replay-stable.

An overlapping pair is not forced into either order. It remains `ambiguousInternalChoice` until a later reviewed profile supplies an explicit semantic choice or a stronger checked commutation account.

## Checkpoint Lean assurance lane

The checkpoint's Lean lane is **proved**. Its proof owners are grouped by responsibility:

- Canonical insertion and ordering: [InternalArmingOrder](../BpmnSemantics/SemanticProcess/InternalArmingOrder.lean) owns reusable canonical insertion, ordered distinct-key counter replacement, and Activity-scope order laws.
- Preparation and footprints: [InternalCommutationCore](../BpmnSemantics/SemanticProcess/InternalCommutationCore.lean) owns the private prepared-patch representation, exact pre-state constructor, closed atom projection, and non-interference predicate.
- Program validity: [structural validity](../BpmnSemantics/SemanticProcess/FlowNodeOccurrenceProgramValidityCore.lean), [Effect validity](../BpmnSemantics/SemanticProcess/FlowNodeOccurrenceEffectProgramValidity.lean), [User Task validity](../BpmnSemantics/SemanticProcess/FlowNodeOccurrenceUserTaskProgramValidity.lean), [wait validity](../BpmnSemantics/SemanticProcess/FlowNodeOccurrenceWaitProgramValidity.lean), and [validity frames](../BpmnSemantics/SemanticProcess/FlowNodeOccurrenceProgramValidityFrames.lean) keep family validators private while exposing the structural, wait-family, and insertion-preservation facts needed by the checkpoint.
- Projection structure: [lifecycle order](../BpmnSemantics/SemanticProcess/FlowNodeOccurrenceLifecycleOrder.lean), [Process identity](../BpmnSemantics/SemanticProcess/FlowNodeOccurrenceProcessIdentityProofs.lean), and [projection shape](../BpmnSemantics/SemanticProcess/FlowNodeOccurrenceProjectionShapeProofs.lean) prove canonical lifecycle order, static/runtime owner Process-ID correspondence, and complete projected-anchor shape without duplicating production algorithms.
- Preservation: [commutation projection](../BpmnSemantics/SemanticProcess/InternalCommutationProjection.lean), [state frames](../BpmnSemantics/SemanticProcess/InternalCommutationStateFrames.lean), [runtime preservation](../BpmnSemantics/SemanticProcess/InternalCommutationRuntimePreservation.lean), and [open projection](../BpmnSemantics/SemanticProcess/InternalCommutationOpenProjection.lean) compose those facts into projectability, collection-order, identity, aggregate runtime, and accepted-lifecycle preservation.
- Commutation: the [InternalCommutation facade](../BpmnSemantics/SemanticProcess/InternalCommutation.lean) proves opposite-arm enabledness and exact raw-state commutation.
- Publication: [transition records](../BpmnSemantics/SemanticProcess/InternalCommutationTransitionRecord.lean) and [control-position deltas](../BpmnSemantics/SemanticProcess/ControlPositionDeltaProofs.lean) prove the prepared record and exact public control delta. [InternalCommutationPublication](../BpmnSemantics/SemanticProcess/InternalCommutationPublication.lean) composes them with lifecycle preservation into complete actual-publication equality plus canonical pair numbering.
- Serialization and conformance: [publication JSON](../BpmnSemantics/SemanticProcessJson/Publication.lean) consumes canonical traced order and independently replays it without re-deciding pair order. [InternalCommutationConformance](../BpmnSemantics/InternalCommutationConformance.lean) imports the public proof and publication surfaces as the exact conformance target.

This acyclic responsibility split avoids sixteen constructor-pair proofs and prevents the footprint, validity, state-update, projection, and publication accounts from drifting.

The theorem begins from admitted-program well-formedness, exact-instance runtime-state well-formedness, successful exact pre-state open-set projection, two independently enabled `OperationStep` facts, and the complete prepared-patch footprint predicate. It proves both intermediate states runtime-well-formed and open-set-projectable before proving the opposite operation remains enabled. It then proves both exact patch applications commute and proves equality of the actual accepted transition/lifecycle publication. It must not assume either intermediate invariant, either second `fire?`, equal successors, equal final states, canonical intermediate storage, defined lifecycle projection, or equal publications. Constructor proofs may reuse established transition relations, canonical collection insertion, exact occurrence issuance laws, and the existing flow-node program-validity account. They may not cite finite fixture evaluation as the theorem.

This does not claim arbitrary closure confluence, Church-Rosser, arbitrary-cardinality independence, general BPMN scheduler determinism, or the open run-level checked-source preservation theorem.

## Checkpoint independent TypeScript realization

The TypeScript core defines the same state atom vocabulary, actual untagged lifecycle-anchor collision rule, exhaustive family-declarer census, and non-interference equation without generated Lean code or a copied decision table. Program admission applies that census globally, and footprint construction reuses it for the selected operation. It corrects ordinary Message wait issuance and footprint derivation to use `owner.processInstanceId`, matching the other three families, while preserving top-level `state.control.instanceId` only as the runtime-control read. Production closure classifies the complete two-operation enabled set through that predicate and retains current ambiguity and bound precedence. The traced boundary additionally requires the exact pre-state and both intermediates to remain open-set-projectable before accepting the paired publication.

The independent executable oracle explicitly runs both orders outside the production selector and compares canonical state, transition records, and lifecycle publication. The production code must not implement commutation by running both orders and comparing their results, because that would make the claimed reason a successor-equality test rather than the reviewed footprint rule.

#### Compensation checkpoint dependency assessment

Assessment independently accepted on 2026-09-24 at `2c52c622`. Its domain is the currently admitted checked-source Compensation checkpoint, not arbitrary snapshot-declaring Programs. It changes no admission predicate, transition, theorem, profile registration or Temporal mechanism. The [source owner](../packages/bpmn-source/src/compensation-checked-admission.ts) fixes the named nodes, scopes, ten Sequence Flows, three subjects, direct dependency, dormant handler body and limits. The [Program topology owner](../packages/semantic-core/src/compensation-source-checkpoint-topology.ts) independently enforces the corresponding twelve operation edges after lowering; cardinalities alone do not establish the boundary.

Write A for the ordinary root task preceding the child, B for that child's ordinary task, and C for the independent root task. The only forward topology is Start → Split → {A → child entry → B → child End → child completion, C} → Join → global trigger → root End → root completion. The dormant Compensation Event Sub-Process has no ordinary operations or control places. The three declared handler bodies are single effects owned by the trigger, not additional internally offered operations.

The exclusion argument is by successive command boundaries. Start offers the root start and split singly, then exactly the ordinary A/C arms. Each arm consumes its branch token and leaves a wait; the accepted finite snapshot-arming account covers either order. No other operation can become enabled while either arm remains: A/C continuation tokens require later external completions. Every later command resumes exactly one wait after the preceding command has drained its full closure. A completion therefore offers child entry and B arming in sequence while C is waiting or its token is parked at the join. B completion offers child End and child completion in sequence; C completion only advances its join input. The join requires both branches, so it and the trigger are singleton offers after all three forward tasks and the child have completed. During compensation the trigger withholds the sole continuation token; each handler completion atomically updates the declared frontier. There is no ordinary internal offer until final success releases the root End, followed singly by root completion. Handler failure terminates the Process; rejected/stale inputs and capacity refusal preserve the preceding command state and introduce no new frontier. Values and command identities do not add a control edge.

#### Transaction dependency assessment

The [Transaction cancellation account](capsules/TRANSACTION-CANCELLATION-SPEC.md) fixes a role grammar rather than fixture identities. [Checked admission](../packages/bpmn-source/src/transaction-checked-admission.ts) and independent [TypeScript](../packages/semantic-core/src/transaction-cancellation-admission.ts) and [Lean](../BpmnSemantics/SemanticProcess/TransactionSourceAdmission.lean) Program traversals cover every operation and place exactly once. ### Numbering-free publication template

`InternalPublicationTemplate` is private and contains the exact unnumbered committed-transition record plus lifecycle starts and ends whose anchors are `wait`, `scope`, `callActivity`, `compensationTrigger`, `compensationHandler`, or `transitionTemplate`. ### Arbitrary complete-frontier batches

At each closure step the evaluator derives the complete prepared alternative frontier from one exact state. Zero candidates is stable. Before exposing a choice, it takes every singleton-operation candidate that is independent of every other member of the complete alternative frontier and executes that complete universally independent set as one batch; it then recomputes the frontier. It never selects a favorable independent subset or treats one alternative of a local-choice operation as independently batchable from its siblings. If every candidate belongs to a singleton operation and every pair is independent, the universally independent set is the complete frontier. If no universally independent member remains, the complete canonical alternative frontier is the next observable choice point.

Pairwise independence is sufficient only together with the preparation-frame laws above. Lean proves by adjacent swaps that every permutation of one finite pairwise-independent prepared batch reaches the same raw canonical RuntimeState and the same canonically sorted numbering-free publication. Production executes that complete batch in canonical `InternalAlternative` order, instantiates publication indices only after sorting, and then recomputes the frontier. The TypeScript both-order oracle becomes an arbitrary-permutation oracle outside production selection and must include a three-arm same-family batch and a mixed four-family batch.

The universal-normalization rule removes an operation that commutes with every remaining alternative before a directive is presented. It does not claim a unique schedule for every conflict graph: a connected chain in which `A` conflicts with `B`, `B` conflicts with `C`, and `A` commutes with `C` may still admit different valid directive sequences reaching the same result. The exact presented alternatives and consumed directive sequence remain semantic input, and an executable oracle retains this permitted non-uniqueness rather than silently canonicalizing it.

Closure fuel counts operations, not batches. If the complete batch has more members than remaining fuel, the evaluator reports the existing bound failure before applying any member. No partial batch state or publication is committable. The longest newly admitted batch and one over-limit case are required in both languages.

### Explicit observable choice

The pure semantic layer adds a required closed `InternalSchedulingMode` to the Program with `rejectObservableChoice` and `requireChoiceSchedule`. Every existing profile lowers to `rejectObservableChoice`; this capsule admits no new BPMN topology or profile. The scheduled mode exists so a later reviewed profile can select material nondeterminism without reinterpreting an already admitted Program.

The explicit input is an `InternalChoiceSchedule`, an ordered list of directives carried beside one external `Stimulus` at the pure evaluator boundary. Each directive contains its zero-based choice ordinal, the exact canonical nonempty list of alternatives presented at that point, and one selected member of that list. An alternative is the exact closed `InternalAlternative` union used by preparation and publication: `operation(operationId)` or `mergeInput(operationId, owner, inputControlPlace)`. Exact alternatives are carried rather than a digest, host index, random seed, or collection position.

Choice processing consumes the unified frontier above. An independent batch consumes no directive. A non-independent frontier under `requireChoiceSchedule` exposes its complete canonical `InternalAlternative` list to the next directive and fires only the exact selected prepared member before recomputing every unselected alternative from the successor. This covers a multi-offer `mergeExclusive`, another conflicting operation in the same state, and interactions between them without a second choice mechanism. Under `rejectObservableChoice`, the same frontier retains the existing `ambiguousInternalChoice` result and consumes no directive. Canonical order encodes the choice point and independent publication; it never makes the choice.

The existing `applyStimulus` remains the empty-schedule, result-only entry point. Its `CommandResult` and internal/traced companions carry both `internalStepBoundExceeded` and `ambiguousInternalChoice`. Under the approved [closure atomicity repair](capsules/INTERNAL-CLOSURE-ATOMICITY-REPAIR-SPEC.md#command-contract), either closure flag after committed admission returns `rolledBack` with the exact input RuntimeState before admission, preserves the actual flags, and erases selected steps, batches, transition records, and lifecycle deltas. The harness classifies either flag before observation. Successful stable and admission-rejected results remain exact. The distinct lower-layer `applyStimulusWithSchedule` returns a closed `ScheduledStimulusResult` containing `outcome`, `state`, both closure flags, and either no failure or one exact `InternalChoiceScheduleFailure`. The failure union is `scheduleForbiddenForMode`, `missingDirective`, `ordinalMismatch`, `alternativesMismatch`, `selectedAlternativeMissing`, or `unusedDirective`. A schedule failure returns `rolledBack`, the exact pre-command RuntimeState, `internalStepBoundExceeded=false`, `ambiguousInternalChoice=false`, and empty transition/lifecycle publication. Lean receives the same result and failure unions. The scheduled function and its traced companion remain private to the pure lower layer and are not exported through the engine API until a separately reviewed profile selects scheduled choice.

Precedence is exact. External stimulus admission runs first; `rejected`, `semanticFailure`, or `unsupported` returns its existing result without inspecting or consuming the schedule. After committed admission, `rejectObservableChoice` accepts only an empty schedule: a nonempty schedule rolls back as `scheduleForbiddenForMode`, while an encountered choice with an empty schedule rolls back the whole command with `ambiguousInternalChoice=true`. Under `requireChoiceSchedule`, absence of the next directive is `missingDirective`; a present directive is validated in the fixed order `ordinalMismatch`, then `alternativesMismatch`, then `selectedAlternativeMissing`, and a later predicate is inspected only after every earlier predicate does not match. The first resulting directive defect rolls back the whole command even if admission or earlier internal steps succeeded. Closure-fuel exhaustion is decided before the next batch or choice directive and returns `rolledBack` with the exact input before admission, `internalStepBoundExceeded=true`, the actual ambiguity flag, no schedule failure, and empty selected-step, batch, transition, and lifecycle material; remaining directives are not classified as unused because stable closure was not reached. Only a successful stable closure checks for trailing directives, which roll back as `unusedDirective`. Thus late directive failure cannot leak partial state or publication, an overlapping malformed directive has one cross-language discriminant, and a bound failure is never misreported as a schedule defect. The [exact Merge outcome](#exact-merge-frontier-outcome) implements this precedence in the private lower-layer evaluator; public and Temporal admission remain excluded.

The schedule is semantic input, not RuntimeState, observation, or Temporal metadata; it cannot be inferred from Event History, Workflow task order, SDK readiness, randomness, or program collection order.
