# Temporal Worker deployment repair proposal

Lifecycle: implementation-in-progress
Review: approved

The first implementation checkpoint contains immutable native Worker registration, explicit fresh-Namespace initialization, creation-readiness checks, Process and ingress pin inheritance, retained paired-publication/recovery Query isolation, and the Query-only replay discriminator. The complete Temporal package gate covers those live witnesses and the maintained product-start fixtures; the client gate separately covers every creation entry point. [The evidence map](TEMPORAL-TEST-EVIDENCE-MAP.md) identifies the deciding tests.

Downstream witnesses now preserve one A ingress across A/B Process populations, same-B-target response-loss recovery, and exact A-created Schedule dispatch under B. Evaluation initialization/readiness composition, the final complete verifier, and reflection/cost remain downstream obligations. Existing unversioned environments remain unchanged. ## Problem and bounded outcome

The original [deployment admission helper](../packages/temporal-adapter/worker/src/workflow-deployment-admission.ts) ordered caller-supplied fencing, poller inventory, candidate replay, and Worker replacement. The maintained [external Worker startup](../packages/temporal-adapter/worker/src/external-temporal-runtime.ts) did not invoke that helper and started an unversioned Worker. Its bundle-derived poller identity labelled bytes without making the Temporal Service route a retained history to those bytes. The [lifecycle contract](TEMPORAL-PROCESS-LIFECYCLE-SPEC.md#workflow-chain-production-contract) consequently overstated the enforced production deployment boundary.

Candidate replay also cannot establish observation preservation: a candidate that changes only a Query's publication projection can emit the same Temporal Commands and pass replay while answering an old Run differently. The retained [callback deployment witness](../packages/temporal-adapter/testkit/test/workflow-deployment-admission.temporal-test.ts) separates patch-marker nondeterminism; the checkpoint's [native routing witness](../packages/temporal-adapter/testkit/test/worker-deployment-pinning.temporal-serial-test.ts) supplies the distinct Query counterexample.

Use native Worker Deployment Versioning with immutable bundle-derived Build IDs and `PINNED` Process and correlation-ingress Workflows. Each enrolled chain, including retained Run Queries, stays with its enrolled executable bytes. Explicit native Current selection controls new enrollment. This repairs hosting and public-observation preservation without changing BPMN meaning, source admission, profiles, Lean, or the semantic core.

## Required deployment contract

`DEPLOY-BUNDLE-01`: the maintained Worker startup loads one immutable Workflow bundle, computes SHA-256 over its exact UTF-8 executable `code`, and supplies that digest as the native deployment Build ID. A configured expected digest must match before polling; callers cannot substitute a label for computed bytes. One stable deployment name groups versions on the existing Task Queue. Worker identity remains diagnostic. The exact bundle and its runtime image/configuration must remain available throughout their support obligation.

`DEPLOY-PIN-01`: startup uses native `workerDeploymentOptions` with `useWorkerVersioning: true` and `defaultVersioningBehavior: "PINNED"`. Both production Workflow types inherit that behavior; no type override may select auto-upgrade. Existing and candidate versions may poll concurrently. A candidate starts inactive and never promotes itself, creates a ramp, redirects an enrolled execution, or changes another version's routing. Promotion uses the native deployment management API or CLI and verifies the selected Current version and required Workflow/Activity Task Queue registration before new enrollment is enabled.

`DEPLOY-ENROLL-01`: ordinary Process starts, exact-definition starts, Message starts, and first creation of a correlation ingress use the explicitly selected Current version when Temporal dispatches their initial Task. There is no ramping version in this bounded contract. Worker registration, process liveness, and successful start submission are distinct from operational enrollment readiness. A deployment without an established versioned Current is not ready to accept new starts or create Schedules; it must not fall through to native unversioned routing. Native administration owns that initialization boundary, not a replacement application-wide admission lock.

`DEPLOY-CHAIN-01`: Process and correlation-ingress Continue-As-New retain their Workflow type and Task Queue and inherit the pinned version. No `initialVersioningBehavior` upgrade/ramping override, deprecated versioning intent, redirect, or operator pin override is selected. Existing carried state, semantic identities, publication descriptors, recovery precedence, stable rollover checkpoints, and capacity ceilings remain governed by the [lifecycle specification](TEMPORAL-PROCESS-LIFECYCLE-SPEC.md) and [correlation specification](capsules/MESSAGE-KEY-CORRELATION-SPEC.md). A deployment change creates no semantic transition and is not a migration checkpoint.

`DEPLOY-QUERY-01`: retain the original Workers for every supported running chain and every retained completed, failed, or continued Run whose Query may be needed. Temporal's Drained status alone does not permit retirement. While such histories remain retained, an absent original Worker is an infrastructure availability failure; neither a candidate Worker nor another Run may manufacture the answer. After the existing retention boundary, the existing public unavailable/unknown classifications apply. Retiring the version requires the end of all its retained-Run support obligations, including old publication segments of a still-running chain.

## Correlation, Activities, and Schedules

The [complete correlation address](capsules/MESSAGE-KEY-CORRELATION-SPEC.md#temporal-hosting-and-refinement-preflight) continues to identify one ingress Workflow independently of deployment version. Its Workflow ID gains no Build ID suffix. An ingress created under A stays pinned to A when new Process instances enroll under B; those Processes still register and publish through that same ingress. Splitting the address by build would split the candidate population and change Message meaning.

`DEPLOY-PROTOCOL-01`: every concurrently supported version preserves the existing private registration, identity/configuration Query, candidate scan, publication/status, target delivery, and recovery contracts in both directions. An A ingress must inspect and deliver to a B Process, and a B Worker must communicate with an A ingress. Exact identities, barrier membership, reservation, ordinal, selected-target retention, no-rematch recovery, and quarantine remain unchanged. This repair freezes those protocols across its deployment versions; changing them later requires a separately reviewed compatibility account. Worker Versioning does not prove cross-Workflow protocol compatibility.

Activities remain on the same Task Queue registered in the enclosing Workflow's deployment version, preserving native version routing for effect and correlation Activities. Their implementation/configuration is retained with that version's runtime artifact. A Workflow bundle digest does not certify Activity implementation equivalence, external-effect idempotency, or a remote service's behavior; the existing effect and correlation refinement contracts still decide those facts. Independent Activity queues are excluded from this repair.

`DEPLOY-SCHEDULE-01`: a one-shot Schedule retains its exact admitted BPMN Program and resolved Timer Start input. Its future action enrolls under Current at initial Task dispatch, not at Schedule creation. A Schedule created while A is Current may therefore start a B-pinned Process after B becomes Current. This changes no selected definition or BPMN Timer meaning. The pinned SDK's Schedule action offers no deployment-version override; this proposal introduces no raw-protocol workaround or pre-dispatch Build ID promise. Once the action enrolls, ordinary pin and continuation rules apply.

## Existing unversioned environments

Native enrollment is selected only for a fresh Temporal Namespace with no pre-existing Process/ingress history or pending Schedule, or an environment already enrolled under this contract. No in-place conversion of existing unversioned histories is admitted. Temporal's [migration guide](https://docs.temporal.io/production-deployment/worker-deployments/unversioned-to-versioned-migration) states that setting Current routes an unversioned in-flight Workflow to the versioned Worker on its next Task; doing so with changed bytes would reproduce the defect. A supported initialization operation must refuse an existing unversioned environment, not treat candidate replay as conversion approval.

Existing unversioned chains, their pending Schedules, retained histories, addresses, and required Workers must remain intact under their existing environment. This proposal authorizes neither deletion nor forced closure, and does not certify their historical compatibility. Moving such an environment requires a separately reviewed migration/support account or an explicit owner disposition after its existing obligations end. That migration is an open restriction, not a hidden prerequisite that may be satisfied by silently discarding live state. The new deployment boundary cannot be claimed for an unconverted environment.

## Native basis and feasibility boundary

The source pins remain owned by [SOURCES.md](SOURCES.md#temporal-typescript-sdk). The inspected SDK declares [deployment name and Build ID](https://github.com/temporalio/sdk-typescript/blob/2595d1b62cf5c3ff1748df0df2f9b303902bb31c/packages/common/src/worker-deployments.ts), requires [default behavior when Worker Versioning is enabled](https://github.com/temporalio/sdk-typescript/blob/2595d1b62cf5c3ff1748df0df2f9b303902bb31c/packages/worker/src/worker-options.ts#L697-L730), exposes only upgrade/ramping choices for the optional initial continuation override, and [omits deployment overrides from Schedule actions](https://github.com/temporalio/sdk-typescript/blob/2595d1b62cf5c3ff1748df0df2f9b303902bb31c/packages/client/src/schedule-types.ts#L779-L804).

Temporal's current official [Worker Versioning contract](https://docs.temporal.io/worker-versioning), checked on 2026-09-05, specifies pinned inheritance across Continue-As-New when the successor queue belongs to that deployment, Current-based routing for new work, same-version Activity routing with a separate-queue exception, and Query work on Drained versions during history retention. These native facts support the selected design; they are not executable evidence for this adapter. The pinned full server must demonstrate each claimed routing boundary. An unsupported API, different retained-Query route, or failed pin inheritance is a blocking feasibility finding, not permission to substitute caller callbacks or weaken observation preservation.

## Invariant and evidence matrix

| Boundary | Required positive evidence | Separating negative |
|---|---|---|
| Maintained startup | Actual external/evaluation Worker options bind the loaded bytes, deployment name, and PINNED behavior; startup leaves Current unchanged | Wrong expected digest, omitted versioning options, auto-promotion, or changed bytes under A's Build ID refuses or fails the guard |
| A/B isolation | A and B poll together; promotion directs new enrollment to B while running A state, commands, and Queries stay on A | B changes only a valid publication Query projection; ordinary replay of A history still succeeds but the A/B observation oracle detects routing to B |
| Retained Run Queries | A publication pages and recovery Queries survive completion, failure, Continue-As-New, and an A Worker restart while B is Current | With only B polling, an exact retained A Query cannot return B's changed answer; restoring exact A bytes restores availability |
| Continuation | Forced Process and ingress rollovers preserve A enrollment after B promotion, with exact state, publication, identity, and recovery | Changing the successor queue or adding an upgrade override fails the binding guard or live version assertion |
| Shared correlation | One address and one candidate population span A and B Processes; A ingress handles B candidate scan/delivery; B communicates with A ingress; response loss retries the retained target | A per-build ingress ID, protocol drift, duplicate result, population omission, or rematch fails public result/state assertions |
| Native Schedule | A-created due action first dispatched under B retains its exact Program/trigger and becomes B-pinned | Treating Schedule creation as bundle enrollment, using the stored base as execution identity, or retargeting the definition fails |
| Legacy restriction | Existing unversioned control histories remain unversioned and unchanged when versioned Workers register | Promotion or Worker startup converts, deletes, or answers legacy histories with candidate bytes |

The smallest live discriminator uses two immutable bundles differing only in one Query projection over the same registered model. It first proves the defect class by replaying A's history with B successfully, then proves A's publication remains byte-identical with both native versions polling and B Current. A new B execution exposes the changed projection, preventing a vacuous mutation. Command outcomes and terminal receipts are checked independently from those Query results. Source/option guards supplement, but cannot replace, the pinned real-server routing witness.

The state relation is unchanged exact committed semantic state, command recovery, and paired E1/E2 publication under one fixed executable per chain. Durable starts, Updates, Signals, Timer wakeups, effects, cancellation acknowledgement, handler draining, and retention keep their existing owners. Deployment ordering, Worker absence, sticky-cache loss, and retries may change availability, never select another semantic result. Replay remains required for each bundle's own histories; candidate replay is not an equivalence claim.

## Scope, review, and closure

Required functionality is exactly the deployment rules and evidence above. Optional functionality: none. Excluded: new BPMN semantics or capability, a CIB relationship, a Lean proof lane, malicious-operator resistance, generic Activity equivalence, auto-upgrade, ramps, forced pin migration, legacy conversion, new queues for workload isolation, post-retention reconstruction, and retirement based only on Drained status. The retained runtime/configuration obligation is operational; a human with unrestricted Temporal or artifact administration remains outside the guarantee.

Cold proposal approval precedes production code. The first green implementation checkpoint must include maintained startup, both Workflow pinning paths, native enrollment and continuation, retained Query isolation, and the Query-only mutation before downstream composition proceeds. Closure requires shared-correlation and Schedule witnesses, affected package gates, the complete applicable verifier, exact implemented/absent documentation, reflection/cost, and independent closure review. A combined checkpoint/closure is permitted only under the existing [single-lane rule](TESTING-SPEC.md#independent-cold-review-gate).

The affected existing owners are [Worker startup](../packages/temporal-adapter/worker/src/external-temporal-runtime.ts), [bundle loading](../packages/temporal-adapter/worker/src/workflow-bundle.ts), [deployment admission](../packages/temporal-adapter/worker/src/workflow-deployment-admission.ts), [evaluation Worker composition](../packages/temporal-adapter/runner/src/evaluation-worker-main.ts), [Schedule creation](../packages/temporal-adapter/client/src/definition-schedule-client.ts), and their testkit witnesses. The obsolete stop-the-world production claim must be replaced atomically in [the lifecycle specification](TEMPORAL-PROCESS-LIFECYCLE-SPEC.md), [Temporal research](research/TEMPORAL-EXECUTION-RESEARCH.md), [architecture](ARCHITECTURE.md), [testing specification](TESTING-SPEC.md), and [`implementation-status-owner:TEMPORAL-HOSTING`](TEMPORAL-HOSTING-IMPLEMENTATION-MAP.md). Existing wrapper, package-boundary, production-start, and deployment witness contracts must be updated with their producers, not disabled to admit the new policy.

Document integration is governed by [documentation control](../scripts/document-control-plane.test.ts), [reviewability](../scripts/document-reviewability.test.ts), [links](../scripts/markdown-links.test.ts), [review receipts](../scripts/independent-review-policy.test.ts), and [target-bound review packets](../scripts/semantic-review-packet.test.ts). Re-run the path bindings before implementation growth. The exact current work order and legacy-environment blockers belong in [PLAN.md](PLAN.md).
