# Process transfer from `a12-kernel-lean`

## Purpose and conclusion

This bounded study asks how the sibling `a12-kernel-lean` experiment turns runtime probes into durable evidence, captures semantic knowledge in Lean, and keeps formal code synchronized with language-neutral specification documents. It transfers process disciplines, not A12 domain semantics.

The main result is a **semantic capsule closure discipline** for this project. Each approved BPMN feature slice should connect a normative or profile clause, a separating example, executable Lean semantics, a useful law, the nearest checked non-law, an independent TypeScript implementation, retained CIB observations at an explicit fidelity, and Temporal refinement/replay evidence. Those lanes remain distinct: a Lean proof establishes a universal property of the chosen Lean account, while a finite CIB trace establishes only correspondence for its declared cases and observation boundary.

The study does not justify importing A12 types, rules, evidence schemas, governance, or repository structure. BPMN execution introduces graph topology, concurrency, externally visible waits and effects, logical time, and host refinement obligations that the validation-kernel experiment does not have.

## How the sibling turns probes into durable evidence

The sibling uses the real kernel as the behavioral authority and Lean as the semantics-of-record for its chosen account. The bridge between them is finite, explicit, and deliberately non-magical:

```text
focused external kernel probe
        │
        ▼
compact immutable observation bundle
  ├─ producer and revision
  ├─ raw-capture digest
  ├─ family and projection identity
  └─ cases: input + observed output
        │
        ▼
strict generic bounded reader
        │
        ▼
family-owned typed decoder/projection
        │
        ├────────────► retained external observation
        │
        ▼
live evaluation of Lean semantic definitions
        │
        ▼
typed mismatch report + mutation-sensitive tests
```

Important safeguards make the evidence meaningful:

- input and observed output are separate, so the evaluator cannot obtain the answer from its input;
- generic loading owns only transport invariants such as bounds, identity, path safety, duplicate rejection, and strict JSON shape;
- each semantic family owns its typed projection and observation fidelity;
- retained bytes are immutable and are never refreshed merely to make a mismatch green;
- mutation tests change a meaningful observed distinction and require replay to disagree;
- rich internal Lean state is not attributed to an external observation that exposed only a narrower projection;
- raw one-off capture machinery is removed from the live replay path once compact artifacts and recovery identities exist.

This is closely aligned with the pipeline already established here. The BPMN scenario keeps CIB calibration outside the TypeScript semantic core, the core has a poisoned-calibration guard, the differential pipeline requires a seeded semantic mutation to be classified, and Temporal retained history is not regenerated by ordinary replay. The immediate transfer is therefore to state and preserve these invariants, not to introduce a generic evidence framework before a second semantic family needs it.

## How Lean captures knowledge

The sibling treats executable code as only one part of a semantic claim. A representative feature is distributed across owners with different meanings:

```text
language-neutral clause
        │
        ▼
Semantics: executable definition
        ├────────────► Conformance: small positive and negative examples
        └────────────► Proofs: universal law with explicit hypotheses
                              + nearest plausible false generalization
        │
        ▼
Evidence: finite correspondence to retained external observations
```

This separation prevents several common overclaims:

- an executable example does not become a universal theorem;
- a theorem about the Lean definition does not prove correspondence with the external implementation;
- a successful outcome theorem does not silently cover failures, divergence, or excluded syntax;
- an empirical match does not transfer Lean’s proofs to CIB Seven, TypeScript, or Temporal;
- attractive stronger statements remain visible as checked counterexamples instead of disappearing into prose.

For this BPMN project, the corresponding semantic units are:

| Claim lane | BPMN project owner |
|---|---|
| Normative syntax and conformance clause | BPMN 2.0.2 pointer and project-authored digest |
| Compatibility interpretation | Versioned CIB Seven semantic profile |
| Executable chosen account | Lean semantic definition |
| Small separating witnesses | Lean conformance examples and focused TypeScript tests |
| Universal internal consequences | Lean laws with exact hypotheses |
| Nearest false generalization | Checked Lean non-law or bounded counterexample |
| Empirical compatibility | Retained CIB observation at a declared projection |
| Independent implementation | Pure TypeScript semantic core |
| Durable-host correctness | Temporal refinement, replay, and fault evidence |
| Current coverage and absences | [IMPLEMENTATION-MAP.md](../IMPLEMENTATION-MAP.md) |

Physical folders are secondary to these ownership boundaries. The current Lean capsule need not be moved merely to imitate the sibling. The next semantic capsule should prove that the split helps a second BPMN feature before a broader module reorganization is adopted.

## How specification synchronization works

The sibling’s `spec/` directory is a language-neutral semantic body, not a work log, implementation map, or evidence inventory. Its `SEMANTICS-MAP.md` supplies stable taxonomy and drill paths. Implementation, proof, and evidence status live elsewhere.

Changes that originate locally and must be reconciled with another project enter a dedicated synchronization ledger in the same change. A ledger entry links to the canonical clause and records transport facts, evidence basis, compatibility consequence, target surfaces, and lifecycle status. It does not duplicate the clause. Inbound findings already owned by the other repository are recorded as provenance rather than echoed back as a new outbound task.

The useful transfer is the ownership rule, not the exact ledger:

- project-authored BPMN semantic clauses should eventually live in a stable, language-neutral body with normative pointers;
- implementation status, open work, and evidence inventories must not leak into that body;
- a reconciliation ledger is justified only when this repository actually has a second maintained semantic consumer or producer that needs cross-repository handoff;
- the copyrighted OMG specification must not be copied into a tracked `spec/` tree; tracked clauses must be original digests and interpretations with precise normative references.

Creating a new tracked `spec/` tree now would be premature. The production source model, parser preservation contract, executable IR, and first post-M0 interpretation are not approved yet. The first general ingestion capsule should establish the minimum durable clause format from a concrete consumer need.

## Adopted semantic capsule closure

For each approved post-M0 semantic capsule, the working record must answer:

1. Which BPMN 2.0.2 clause, machine-readable artifact, or explicit CIB-profile interpretation is in scope?
2. Which realistic wrong account does the smallest separating witness reject?
3. What source information and provenance must import preserve?
4. What executable IR and static admission rule does the Lean account require?
5. What useful law follows, under exactly which hypotheses?
6. What is the nearest plausible stronger false claim, and where is its checked witness?
7. Which CIB observation is retained, at what projection fidelity and pinned environment?
8. Does the independent TypeScript semantic core derive the same public behavior without reading the calibration answer?
9. Which hidden Temporal steps are allowed, and what refinement, replay, cleanup, and fault evidence checks them?
10. Which dimensions are complete, pending, or explicitly excluded in [IMPLEMENTATION-MAP.md](../IMPLEMENTATION-MAP.md)?

The dimensions are independent. A capsule may be executable while proof, CIB calibration, Temporal refinement, or broader conformance evidence remains pending. Documentation must name that state instead of collapsing it into a single “supported” label.

## Practices adopted now

The following practices improve the existing project without expanding semantic scope:

- Treat semantic definitions, executable examples, universal laws, checked non-laws, CIB evidence, independent implementation, and Temporal refinement as separate claim lanes.
- Require a concrete adapter consumer/refinement risk before finalizing a representation or generalized semantic mechanism.
- Keep retained CIB observations and Temporal histories immutable; investigate disagreements at the semantic or projection boundary instead of refreshing expected bytes to green.
- Require at least one meaningful seeded mutation for each new evidence projection so that the comparison can be shown to detect a semantic distinction.
- Record exact observation fidelity. Silence, acceptance, completion, history shape, and an internal runtime fact are different evidence.
- Batch external CIB probing by coherent semantic family after the internal separating examples and observation needs are understood.
- Use one documentation owner per volatile fact and avoid new ledgers, indexes, generators, or shared evidence infrastructure until a second real consumer demonstrates the recurring mechanism.

## Deferred or rejected transfers

| Candidate | Decision | Reason |
|---|---|---|
| Generic observation-bundle loader | Defer | One production semantic family does not justify infrastructure; the current scenario and pipeline already enforce answer separation and mutation sensitivity |
| Immediate Lean folder reorganization into `Semantics/Conformance/Proofs` | Defer | The claim lanes are adopted, but moving one small capsule would be imitation-driven churn |
| Tracked language-neutral `spec/` tree | Defer to first general ingestion capsule | It needs an approved clause format, parser preservation contract, and concrete second consumer; OMG text cannot be redistributed |
| Open-only semantic-gaps document | Defer | [PLAN.md](../PLAN.md) and [IMPLEMENTATION-MAP.md](../IMPLEMENTATION-MAP.md) currently own the small live queue without duplication |
| Cross-project specification-sync ledger | Reject for current topology | There is no maintained second semantic repository requiring outbound reconciliation |
| Full Lean trust-zone and axiom audit machinery | Defer | The current dependency-free theory is small; revisit when evidence I/O, generated code, opaque axioms, or public proof shipment materially enlarge the trust boundary |
| A12 evidence schema, proof statements, or domain types | Reject | They encode a validation kernel rather than BPMN execution and would violate clean domain transfer |

## Consequence for the next phase

The next work remains the BPMN XML ingestion decision. This study sharpens its acceptance contract: the parser is only a source-admission mechanism; it must preserve enough source identity and unresolved detail for profile decisions, while executable normalization stays explicit and versioned. Parser success must not imply semantic admission, CIB compatibility, or BPMN execution conformance.

The dependency decision should therefore compare exact parser versions on namespace handling, reference resolution, extension and diagram-interchange preservation, diagnostics, round-trip behavior, license graph, runtime footprint, and removal cost. The first ingestion experiment should use the existing sequential fixture plus selected BPMN MIWG models and should stop at a source-preserving model; it must not prematurely design the complete executable IR.
