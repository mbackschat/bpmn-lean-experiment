# Executable BPMN model corpus research

## Status

Implemented living MVP suite, independent external-source expansion, three catalog journeys, and reviewer-facing capability disclosure. The corpus method, exact source records, local admission results, 24-model execution gate, 25-variant coverage contract, six-family external blocker ranking, and three production-backed browser-eligible models are maintained.

## Question

Which representative whole BPMN models can this project execute now, which exact external model families fail, and which reusable mechanisms block the most independent families after physical clones and versions are deduplicated?

This is one prioritization input, not a semantic authority or the whole priority rule. BPMN requirements and their dependencies remain primary. Model-family reach and high semantic risk are co-equal scheduling inputs after those dependencies, CIB Seven remains a classified compatibility oracle, and platform demand only breaks ties after standards value, reach, and risk are considered.

The [generated corpus map](../../model-corpus/EXECUTABLE-MODEL-CORPUS-MAP.md) is the current result. The fast guard verifies source identity, license class, business purpose, profile and scenario binding, construct inventory, admission result, pipeline route, clone-family consistency, and generated ranking. It separately derives the exact supported variant set from every registered pipeline BPMN source, requires the [canonical capability catalog](../../model-corpus/mvp-capabilities.ts) to match it, and requires the retained-model coverage union to contain every variant. That equality is the co-evolution contract. A tag-level count is insufficient because several supported variants share the same BPMN XML element name.

## External whole-model candidates

The exact CIB Seven candidates are intentionally product-shaped rather than one-element tests:

- Order goods uses a collaboration and two sequential User Tasks.
- Review invoice uses two User Tasks with assignment, forms, and a due date.
- Invoice receipt versions 1 and 2 share one clone family and combine lanes, User Tasks, decisions, Service Tasks, a Business Rule Task, a Call Activity, and data associations.
- Vacation request combines multiple User Tasks, an Exclusive Gateway, task metadata, and a generic Task.

All five currently reject under the calibrated User Task profile. The admission guard reruns the real compiler and compares a normalized diagnostic digest, so accepting a model or changing its blocker set requires an explicit manifest and index update rather than silently changing the ranking.

Two independent candidates widen the sample beyond CIB Seven:

- The official OMG Incident Management executable example is a product-shaped collaboration with a Message Start Event, Script Tasks, User Tasks, decisions, a Service Task, a Send Task, process data, resources, lanes, and DI. Its exact ISO-8859-1 bytes currently fail the compiler's UTF-8-only encoding admission before element support is considered.
- Betsy Workflow Pattern 16 combines a Parallel Gateway, timer wait, signal throws and catches, an Event-Based Gateway race, conditional routing, and Script Tasks. Its exact UTF-8 bytes currently reach the compiler and fail as an unsupported model.

The archive path is not a copied fixture. The guard first verifies the complete official ZIP SHA-256, extracts the named entry in memory with a one-megabyte bound, verifies the entry SHA-256, and then sends the exact bytes to the production compiler. Archive and entry digest mutations are permanent negative oracles.

## Findings

The first result confirms the 80/20 intuition only as a hypothesis worth measuring, not as a percentage claim. A small set of mechanisms recurs across several independent candidate families, but the current top blockers are mostly ingestion, preservation, and product metadata rather than missing token semantics. Frequency therefore cannot be the only semantic priority signal: rare elements can carry the highest risk to concurrency, cancellation, scope, liveness, identity, data, or Temporal refinement.

Diagram interchange and vendor runtime metadata each affect four clone families. Collaboration presentation and User Task metadata each affect three. Data association, lane presentation, and Script Task execution each affect two. Business Decision affects one family represented by two files; generic Task, resource assignment, Send Task delivery, and signal events each affect one family. Event race, Message Start, parallel split, and timer waits no longer rank as absent reusable mechanisms because the expanded retained suite now exercises their current bounded forms. That does not imply the broader external variants are admitted.

That ordering must not be read as “implement vendor attributes first.” Some attributes are preservation-only, some belong to Product 2, some select a CIB compatibility overlay, and some imply a new BPMN semantic family. The next semantic proposal must first classify each candidate against the BPMN requirement ledger, normative dependencies, the current execute/preserve/reject split, and Temporal feasibility.

Two CIB invoice versions count as one family. The index retains both files because version drift is useful evidence, but ranking by two would inflate one product example into two independent demands. The corpus guard also rejects byte-identical files assigned to different clone families.

## Browser eligibility

Admission and engine execution are insufficient for a browser catalog. A catalog claim requires a named production-backed Playwright journey over the exact model. The journey must select or deploy it through the public platform, start it, claim before completing every User Task, exercise the advertised route or effect, verify the finished Process instance and published history, and cover the relevant Operations or Audit surface without fixture-only answers.

Three retained models are catalog-ready. **Review a request with assignment and form metadata** uses the [single-review Chromium journey](../../showcase/m3-human-work/e2e/corpus-user-task-journey.spec.ts). **Review content and risk in parallel** uses the [parallel-review Chromium journey](../../showcase/m3-human-work/e2e/parallel-user-task-metadata-journey.spec.ts), which deploys the exact retained BPMN, starts exact version 1, claims and inspects both tasks, preserves the live sibling after the first completion, completes the Process, verifies contiguous semantic History, and verifies exact claim/reserved/committed Work-audit events for both occurrences. **Resolve an expense exception with structured Human Work** uses the [structured Human Work Chromium journey](../../showcase/m3-human-work/e2e/structured-human-work-journey.spec.ts), which covers priority ordering, six field kinds, all three resolution actions, conditional reason input, client/server refusal, canonical retry, conflict, History, and Work audit at both desktop widths. The other 21 retained models remain explicitly ineligible until equivalent model-specific journeys exist.

This boundary prevents the previous failure class where a model appeared selectable but start media types, task ownership, or incident/audit contracts failed only during manual use. Engine admission and pipeline success do not satisfy it.

## Second-model outcome

The second honest catalog model required a profile composition rather than another renamed XML file:

- Product 2 deliberately hides every open User Task whose publication lacks a candidate group. The parallel, Boolean-routing, called-Process, Message Start, Timer Start, and other metadata-free profiles therefore cannot support a Work claim-and-complete journey.
- The ordinary M1 and M3 production hosts configure no effect handler. An effect-bearing model without a declared exact protocol/operation handler fails closed rather than receiving fabricated success.
- The M4 incident showcase supplies a specialized test effect implementation for retry and cancellation evidence. Treating that harness configuration as a general catalog integration would confuse one bounded incident demonstration with a reusable product integration.
- Authoring several renamed `Start -> User Task -> End` files under the one metadata profile would create cosmetic clone families and inflate the appearance of breadth without adding a reusable mechanism.

The implemented [parallel User Task metadata composition](../capsules/PARALLEL-USER-TASK-METADATA-COMPOSITION-SPEC.md) takes the first route without widening the metadata-free parallel profile. It exercises two simultaneous claims, both completion orders, sibling preservation, join progress, terminal History, and per-occurrence audit without introducing external I/O.

## Recommendation

Use the current 24 retained models as the minimum MVP engine regression suite and retain the sequential metadata, parallel metadata-composition, and structured expense-exception models as the three catalog models. Require the suite to co-evolve through the derived 25-variant equality guard rather than relying on prose or manual inventories. Keep the existing metadata-free parallel model as an engine regression control, and do not reinterpret or silently widen it.

For the next semantic-family decision, classify Script Task execution because it is now the only unsupported execution mechanism shared by two independent external families, then compare it with the standing high-risk semantic families in [PLAN.md](../PLAN.md#executable-model-corpus-decision-gate). Its prevalence and its language selection, deterministic sandbox, data boundary, security, and Temporal-hosting risk are evidence, not automatic approval to execute arbitrary scripts. A less frequent family may go first when it is more likely to invalidate the current representation or expose an unclosed concurrency, cancellation, scope, liveness, identity, or refinement obligation. Preserve-only DI and product metadata remain separate work classes and must not inflate the semantic priority.

## Non-claims

The corpus does not establish BPMN conformance, CIB Seven compatibility outside selected evidence, representativeness of all enterprise processes, or a combined support percentage. Model counts, clone-family counts, BPMN requirement coverage, CIB profile coverage, and platform milestone coverage remain separate denominators.
