# Compensation semantics

## Status

Adopted kernel owner document (W0 extraction, 2026-11-09). The kernel modules it cites are the executable authority; where they differ, the difference is a defect of one of them.

`Kernel.Feature.Compensation` ([Lean](../../../Kernel/Feature/Compensation.lean)) owns `FeatureSlots.compensation`: the records of completed compensable work (`Compensable`) and the compensation runs in progress (`CompensationRun`), together with Transaction cancellation's compensation step. It dispatches on no guarded type of its own; [propagation](PROPAGATION-SEMANTICS-SPEC.md) hands it a Compensation throw or a caught Cancel through `Signal.compensate`, and the pipeline reports completions through `Hooks.completed` and `Hooks.handlerCompleted`. Admission is in `Kernel.Admission.Work`, `Kernel.Admission.Propagation`, `Kernel.Admission.Scopes` and `Kernel.Admission.Profile`.

## Interpretation

### Eligibility and retention

- Only successfully completed work with a compensation handler is compensable: an Activity with a boundary Compensation Event and its associated handler, or a Sub-Process containing a Compensation Event Sub-Process (BPMN 2.0.2 Tables 10.88 and 10.89, §13.5.5). An omitted `activityRef` selects every visible eligible record; it never makes handler-free work eligible ([CBR account][cbr-normative], [experiment result][cre-result]). The IL lists a subject's handlers (`Envelope.compensationHandlers`), of which admission admits one (`compensation.handlerCount`), and marks a handler `Envelope.forCompensation`, which no Scope's implicit start begins.
- Eligibility is decided by the handler, lifetime by the scope: a completion of a subject with a handler is retained in the scope occurrence it completed in, and the record lives as long as that scope occurrence ([experiment result][cre-result], [`Compensation.completed`](../../../Kernel/Feature/Compensation.lean)). Retention is hidden semantic state, never reconstructed from publication ([experiment result][cre-result], [experiment scope][cre-scope]).
- A record carries the subject, its handler, the completed occurrence's identity and a completion ordinal; ordinals and identities are monotonic and never reused ([CBR contract][cbr-contract]). Active, interrupted or failed work completes nothing and retains nothing; an interrupting boundary path retains nothing ([CBR scope][cbr-scope], `TXC-RETAIN-01` in [TXC rules][txc-rules]).
- A boundary handler restores no context. A Compensation Event Sub-Process restores its parent's own variables as they were when the parent completed, never Task I/O, other Activities' local scopes or an entry-time copy, and reads every other name live through its context's chain (§13.5.4, §13.5.5, §10.3.5, §10.4.1; D9 of [Interpretation M9](#interpretation-m9), which supersedes the [CESP account][cesp-normative]'s copy of every visible variable). Records and snapshots are keyed by the complete runtime occurrence, so a later per-instance account for loops and Multi-Instance parents needs no new identity ([CESP account][cesp-normative]).
- When a Sub-Process completes, the records retained inside it stay compensable: a Sub-Process with a handler keeps them as children its handler's own throw compensates, and one without a handler passes them to its parent's scope occurrence (§13.5.5; `Compensable.children`). The old accounts excluded implicit and recursive compensation and left OMG BPMN21-403 unresolved ([CBR account][cbr-normative], [CTH scope][cth-scope]), so admission refuses every program that would hand records on: `compensation.implicit` when a handler-less Scope's records would reach a parent occurrence a Compensation throw shares, `compensation.recursive` when the retaining Scope's handler body throws Compensation (PC-COMPENSATION-03 lifts them after its interpretation review).
- Leaving a scope occurrence without completing it drops every record retained in it ("presumed abort"; `State.leaveScope`), and ending the instance drops every record. The snapshot account retained a promoted root snapshot in the terminal state for a later parent host ([CESP scope][cesp-scope]); that retention is track work of PC-COMPENSATION-05, listed under the row below.

### Trigger and order

- A Compensation throw compensates the records retained in its own scope occurrence (BPMN 2.0.2 §10.7.2, §13.5.5): the run takes them out of retention atomically, so no other trigger can compensate them again, and the thrower continues only after every handler has completed; an empty set continues at once ([CTH basis][cth-normative], [CTH contract][cth-contract], [`Compensation.compensate`](../../../Kernel/Feature/Compensation.lean)). Only the global synchronous form is admitted.
- Order is the reverse of dependency: a direct Sequence Flow from subject A to subject B makes B's handler complete before A's starts; handlers without such a dependency run concurrently. Every pending handler none of whose successors is pending or running starts at once, in program order (§13.5.5; [CTH basis][cth-normative], [CSL account][csl-normative]). Completion chronology is not that order, and CIB's reverse creation-time order cannot implement it in general (`ProfileOptions.compensationOrder = dependency`). Gateway-mediated dependencies are not inferred ([CTH scope][cth-scope]).
- Each handler begins in a context scope occurrence of its own inside the run's scope, holding the restored context; its subject's child records move into that context, where a throw inside the handler compensates them ([`Compensation.beginHandler`](../../../Kernel/Feature/Compensation.lean)). The handler begins there as a token would: its input mappings read that context, it may do any work the kernel admits, and a Service Task handler's effect stays asynchronous, where CIB runs it inside the triggering command (CIB-LIM-0042); an unavailable Data Input has no flow to be held on and is the dynamic-only `compensation.handlerInputUnavailable`.
- A second trigger while a run is in progress in the same scope occurrence has no selected relation to the first and is refused (`compensation-concurrent-trigger`); so is a subject retained twice in one scope, which §13.5.5 compensates in reverse completion order (`compensation-repeated-subject`) ([CTH contract][cth-contract]).
- Compensation Start `isInterrupting`, Compensation Boundary `cancelActivity`, catch-side `waitForCompletion` and Association direction neither classify nor lower (Tables 10.87, 10.91, 10.92, 8.20; [CSL account][csl-normative]).

### Handler failure

- An Error a handler's effect reports, or an Error End Event inside a handler Sub-Process throws, and nothing inside the handler catches fails the process instance: the handler and its run fail, every token, item, occurrence and handler is removed, nothing continues, and the failed state publishes the run's trigger, the handler, the raising effect or End Event, the code and the message (`COMPH-FAIL-01`; [CTH contract][cth-contract], [`Compensation.failCompensation`](../../../Kernel/Feature/Compensation.lean)). BPMN 2.0.2 §13.3.2 names the handler states but not this disposition; it is a project interpretation, not BPMN or CIB transcription ([CTH basis][cth-normative]), selected by `ProfileOptions.compensationHandlerFailure = failsInstance`. A failed instance accepts no further input and is not a host failure; transport retries are never typed BPMN errors ([TXC rules][txc-rules]).
- Under `failsInstance` propagation never searches past a handler's context, so an event a handler leaves uncaught reaches the handler failure rule; under `propagatesFromTrigger` (CIB-INT-0038, the cibseven profiles) the search goes on from the handler context's parent, the scope occurrence the trigger ran in (I11; see [propagation](PROPAGATION-SEMANTICS-SPEC.md)).

### Transaction cancellation

- A Transaction is a Sub-Process whose cancellation interrupts its running work and compensates its completed eligible work; its Cancel Boundary Event takes control after rollback and compensation finish (BPMN 2.0.2 §10.3.5). Ordinary interruption is no implicit compensation trigger, and quiescence alone does not implement protocol success ([TXC basis][txc-normative]).
- A Cancel End Event raises Cancel from the scope occurrence it ran in. A caught Cancel clears the Transaction's interior, compensates the records retained in it, and only once the last handler has completed cancels the Transaction occurrence and takes the Cancel boundary's flows in the parent; the Transaction's normal outflow never fires (`TXC-CANCEL-01`, `TXC-EMPTY-01`, `TXC-JOIN-01`; [`Propagation`](../../../Kernel/Feature/Propagation.lean)). With no eligible record the boundary is taken in the same step; unfinished work disappears uncompensated. Records of nested scopes the cancellation interrupts are dropped with them.
- A handler failure during cancellation fails the instance as above, and neither the boundary nor the normal flow continues (`TXC-FAIL-01`, a project extension of `COMPH-FAIL-01`, not a hazard boundary). Regional cancellation preserves everything outside the Transaction's region except its continuation (`TXC-FRAME-01`).
- `method` is omitted or exactly `##Compensate`, the XSD default; other spellings are neither case-folded nor aliased (OMG BPMN2-60; [TXC basis][txc-normative]). Under `transactionMethods = compatibilityAsCompensate` (CIB-INT-0039, the cibseven profiles) `##Store` and `##Image` run as `##Compensate`; a protocol URI is refused under every profile (I14).
- Publication: the Transaction stays open while it compensates, interrupted work closes as cancelled, the handler's lifecycle is published, and the Transaction then closes as cancelled before the boundary occurrence; retention and trigger ownership are no public fields, and there is no public cancel command ([TXC public][txc-public]).
- The old account rejected a Cancel boundary on an ordinary Sub-Process, a non-interrupting Cancel boundary and a Cancel End outside a Transaction before lowering (§10.5.5; [TXC contract][txc-contract]). The kernel refuses the same set (§10.5.5): `boundary.cancel.host` for a Cancel boundary on anything but a Transaction, `boundary.cancel.nonInterrupting` for a non-interrupting one, and `throw.cancel.outsideTransaction` for a Cancel throw whose direct parent is not a Transaction (`Admission.Subscriptions.boundary`, `Admission.Propagation.throwRecord`) (PC-TX-02). It also refuses a Cancel End whose Transaction has no Cancel boundary (`throw.cancel.uncaught`: the boundary directs the flow after the cancellation, §10.3.5) and a second Cancel boundary on one Transaction (`boundary.cancel.duplicate`) (I13, [CIB-LIM-0043](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0043--cib-deploys-cancel-forms-bpmn-does-not-define-and-fails-or-strands-them)); a Cancel therefore always finds its Transaction's boundary, and `Propagation.exhausted` treats one that does not as the invariant failure `cancel-uncaught`.

#### I1 — Invocation order and completion chronology (PC-COMPENSATION-01)

- BPMN: §13.5.5 Operational Semantics: default compensation runs Compensation Activities "in reverse order of the execution of the original Activities, allowing for concurrency when there was no dependency", and it MUST consider these dependencies: a Sequence Flow between A and B "results in compensation of B to be performed before compensation of A"; "a data dependency between Activities A and B, e.g., through an IORules specification in B referring to data produced by A", likewise; two Activities of an Ad-Hoc Sub-Process, B before A if A completed before B started; instances of a loop or sequential Multi-Instance "in reverse order of their forward completion", parallel instances "can be compensated in parallel"; "If a Sub-Process A has a boundary Event connected to Activity B, then compensation of B MUST be performed before compensation of A if that particular Event occurred. This also applies to multi-instances and loops."
- CIB: `bpmn/helper/CompensationUtil.java:55-88` creates one concurrent compensating execution per retained subscription and signals every one at once, in reverse `created` order (`:78-87`); a waiting handler (a Human Task) is therefore open together with every other handler of the trigger, and only the start order of handlers that run synchronously follows creation time. The subscriptions reach that sort through a `HashSet` (`:191-205`), whose iteration follows `EventSubscriptionEntity.hashCode` over the identifier (`persistence/entity/EventSubscriptionEntity.java:331-336`), and `Collections.sort` is stable, so under a frozen clock equal `created` times keep the hash iteration order (the runner pins identifiers, `CibSevenEngineBundleFactory.ScenarioIds`).
- Witnesses: retained `compensation-order-chronology/*` (5): after the throw CIB opens `UserTask_UndoA`, `UserTask_UndoB` and `UserTask_UndoC` together, where the kernel holds `UserTask_UndoA` until `UserTask_UndoB` completes (B follows A by Sequence Flow); `compensation-multi-instance-bodies/*-sequential-in-turn` and `compensation-order-and-multiplicity/call-sequential-three-reviewers`: CIB opens the handlers of all instances together. `later-handler-first`, `with-message-before-a-completes` and `without-message` agree. Once the refusals of I3, I9 and I10 lift, `compensation-targeting/chain-handlers-forward`, `chain-handlers-reversed`, `end-untargeted` and `compensation-eligibility/*` keep disagreeing by this order.
- Relation: the kernel keeps `compensationOrder = dependency` under every profile (D1). B's handler completes before A's starts when (a) a Sequence Flow leads directly from A to B; (b) a Sequence Flow leads directly from a boundary Event attached to A to B: B's record exists only if B completed, so when every incoming flow of B leaves a boundary of A, the Event occurred, and admission refuses a B with another incoming flow (`compensation.dependency.boundary`), since its record cannot show which arrival it stems from; (c) a data dependency, which the kernel sees as a sound over-approximation: B completed after A (`Compensable.completion`) and an expression of B's element (its envelope, its work and, for a Scope, its interior) reads a name A's element can write, a name its output mappings target or, when A writes names chosen at run time (a User Task under `submission = installsVariables`), every name; an IORule pairs an Activity's own InputSet and OutputSet and names no other Activity, so it adds nothing beyond the reads; (d) repeated records of one subject run in reverse completion order, and the instances of a parallel Multi-Instance Sub-Process concurrently (I9). Ad-Hoc Sub-Processes are outside the IL. Gateway-mediated flows stay uninferred, as adopted above. CIB's order is a candidate deviation. Draft register entry:
  > **CIB-DEV-0011 — CIB starts every compensation handler of one trigger at once.** **Status:** Deviation candidate from the pinned source and retained evidence; selected by no profile. BPMN 2.0.2 §13.5.5 requires default compensation to consider a Sequence Flow between two compensated Activities, compensating the later one before the earlier, and sequential Multi-Instance instances in reverse completion order. CIB Seven `2.2.0` creates a concurrent execution for every retained subscription and signals them all in reverse creation order (`CompensationUtil.java:55-88`), so every waiting handler is open at once. **Evidence:** retained `compensation-order-chronology/*`, `compensation-multi-instance-bodies/tasks-sequential-in-turn`, `regions-sequential-in-turn`, `compensation-order-and-multiplicity/call-sequential-three-reviewers`, `compensation-targeting/chain-handlers-forward`, `chain-handlers-reversed`, `end-untargeted`, `compensation-eligibility/*`. **Boundary:** triggers retaining two subjects that a §13.5.5 dependency orders, or repeated records of one subject; this entry owns those witnesses in the ledger.
- Shape: `CompensationOrder.reverseCreation` names an order CIB does not have for waiting handlers; it becomes `allAtOnce` (CIB's), refused as `profile.compensationOrder.allAtOnce`. New admission code `compensation.dependency.boundary`. The data and same-subject rules read `Compensable.completion` and the program; no State change.

#### I2 — Which records an untargeted throw sees (PC-COMPENSATION-02, PC-COMPENSATION-05)

- BPMN: §10.7.2 and §13.5.5 Compensation Triggering: "If the Activity is clear from the context, it doesn't have to be specified and defaults to the current Activity. A typical scenario for that is an inline error handler of a SubProcess that cannot recover the error, and as a result would trigger compensation for that Sub-Process"; in a "global" context every completed Activity of the Process. Tables 10.88 and 10.89 compensate, with no Activity identified, "all successfully completed Activities visible from" the throw, where "Visible means" the throw "is contained in normal flow and at the same level of Sub-Process as the Activities" or "in a Compensation Event Sub-Process which is contained in the Sub-Process containing the Activities".
- CIB: `CompensationUtil.collectCompensateEventSubscriptionsForScope` (`CompensationUtil.java:184-206`) walks the flow scopes outward from the throw with `walkUntil` (`tree/ReferenceWalker.java:88-101`), whose post-visitor collects the subscriptions of every scope it moves to, up to and including the first scope that consumes compensation; `bpmn/parser/BpmnParse.java:3885` marks every Event Sub-Process as not consuming. A throw inside an Event Sub-Process therefore takes the union of the Event Sub-Process's own records and those of the Sub-Process holding it (source and retained); a throw inside a Compensation Event Sub-Process reaches the event-scope execution that holds the parent's inner subscriptions (I7).
- Witnesses: retained `compensation-event-subprocess-throws/error-esp-throws-untargeted`: the untargeted throw in an Error Event Sub-Process opens `UserTask_UndoTask` of its parent's completed Task; the kernel compensates nothing (its run scope is the Event Sub-Process occurrence) and continues to *Continue after the recovery*.
- Relation: the kernel follows CIB's union (D15), which is BPMN-consistent: the Activities at the same level as an Event Sub-Process's throw and those of the Sub-Process its inline handler compensates. An untargeted throw takes the records retained in every scope occurrence from the throw's own outward through Event Sub-Process occurrences, up to and including the first scope occurrence of another kind. A compensation-handler context (`ScopeRole.compensationHandler`) ends the walk and stands for the Compensation Event Sub-Process's parent, since `Compensation.beginHandler` moved that parent's records into it; without the stop, a throw inside a Compensation Event Sub-Process would reach the outer run's scope and fail as `compensation-concurrent-trigger`. The run's scope is the throw's own scope occurrence, where its handlers begin; `compensation-concurrent-trigger` refuses a trigger while a run is in progress in any scope occurrence the walk covers. No register entry: the retained answer becomes agreeing evidence.
- Shape: none; the walk reads `ScopeKind.eventSubProcess` and `Ctx.scopeRole` on the throw's scope chain.

#### I5 — Records of a completed Sub-Process without a handler, and Transaction success (PC-COMPENSATION-03, PC-TX-01)

- BPMN: §10.5.1: "The compensation handler is either user defined or implicit. The implicit compensation handler of a Sub Process calls all compensation handlers of its enclosed Activities in the reverse order of Sequence Flow dependencies." Tables 10.88 and 10.89: "To be compensated, an Activity MUST have a boundary Compensation Event, or contain a Compensation Event Sub-Process." §10.7.1 and §13.5.5 tie default compensation of a Sub-Process to an attribute `compensable` that neither the CMOF nor the XSD defines (OMG BPMN21-403). The standard is inconsistent: §10.5.1 makes every Sub-Process compensable through its implicit handler, the tables only those with a handler. Transaction (Table 10.21 and its outcomes): successful completion leaves by normal Sequence Flow; ordinary interruption causes no compensation.
- CIB: `bpmn/behavior/SubProcessActivityBehavior.java:61-66` calls `CompensationUtil.createEventScopeExecution` (`CompensationUtil.java:100-152`) on every completed Sub-Process and Transaction (`BpmnParse.java:3902-3911` gives a Transaction the Sub-Process behavior), and `MultiInstanceActivityBehavior.java:172-175` on every completed Multi-Instance body; when the scope holds compensate subscriptions or a Compensation Event Sub-Process (`CompensationUtil.java:108`), it keeps the inner subscriptions under an event-scope execution, copies the Sub-Process's local variables into it by value (`:118-124`) and subscribes the Sub-Process itself, without a handler, to its parent (`:143-151`, `:167-178`); compensating that subscription descends into the event scope and compensates the inner records as one group (`CompensationEventHandler.java:61-64`). Every Sub-Process with compensable content is thus implicitly compensable.
- Witnesses: retained, committed in CIB, refused by the kernel as `compensation.implicit`: `compensation-regions/*` (4), `transaction-paths/success-then-outer-throw`, `cancel-end`, `error-end`, `compensation-multi-instance-bodies/regions-*` (2), `compensation-context-live-outer/default-handler-reads-and-writes-outer`, `compensation-event-subprocess-throws/error-esp-completes-then-outer-throw`, `transaction-and-error-exits/error-end-in-subprocess`; `compensation-context/*` has no CIB answer (CIB-LIM-0048). Agreeing: `transaction-and-error-exits/transaction-completes-while-boundary-path-runs`.
- Relation: CIB's implicit compensation of every Sub-Process with compensable content is its interpretation of the inconsistency between §10.5.1 and Tables 10.88 and 10.89, which BPMN21-403 leaves open (D3). Draft:
  > **CIB-INT-0036 — CIB compensates every completed Sub-Process without a handler as the group of its inner records.** **Status:** Recorded interpretation from the pinned source and retained evidence; selected by `ProfileOptions.implicitCompensation = everySubProcess` through the cibseven profiles. BPMN 2.0.2 §10.5.1 gives every Sub-Process an implicit compensation handler, while Tables 10.88 and 10.89 compensate only an Activity with a boundary Compensation Event or a Compensation Event Sub-Process, and §13.5.5's `compensable` attribute is not in the metamodel (OMG BPMN21-403). - Kernel meaning: today `Compensation.completed` moves a handler-less Scope's records to its parent occurrence, flattening the group; under `everySubProcess` the completed Scope with at least one inner record is retained as one record without a handler whose `children` are its inner records, so a throw naming the Sub-Process selects the group (I3), the group is one subject for I1's order relative to its siblings, and compensating it runs its children as a nested run in a context occurrence holding the Sub-Process's snapshot (I12). The nested run's end needs its own `Resume` (shape S1): `Compensation.advance` today ends a run with `resume = none` without telling the outer run, which then waits forever.
- Shape: `Compensable.handler : Option ElementId` (`none` = a group); `Resume.group` (S1); `ProfileOptions.implicitCompensation : ImplicitCompensation` with `refused` (default, standards, refusal `compensation.implicit`) and `everySubProcess` (cibseven).

#### I6 — An Error leaving a Sub-Process with completed compensable work (PC-COMPENSATION-03, PC-TX-01)

- BPMN: inconsistent. §10.7.3 and §13.5.5 Relationship between Error Handling and Compensation: "If no error Event Sub-Process is specified for a particular Sub-Process and a particular error, the default behavior is to automatically call compensation for all contained Activities of that Sub-Process". Against it, §10.3.5 Transaction outcome 2: "other mechanisms for interrupting a Transaction Sub-Process will not cause compensation (e.g., Error, Timer, and anything for a non-Transaction Activity)", and the presumed-abort principle of the same clauses: "Compensation of a failed Activity results in a null operation", and the error handler is responsible "to ensure that no further compensation will be necessary". Transaction outcome 3: a Hazard "is interrupted (without compensation)".
- CIB: an Error leaving a Sub-Process interrupts it without `doLeave`, so no event-scope execution is created and its subscriptions are deleted with it (`SubProcessActivityBehavior.java:61-66` runs only on completion): nothing is compensated (source and retained).
