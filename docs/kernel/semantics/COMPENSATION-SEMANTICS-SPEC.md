# Compensation semantics

## Status

Adopted kernel owner document (W0 extraction, 2026-11-09). The kernel modules it cites are the executable authority; where they differ, the difference is a defect of one of them.

`Kernel.Feature.Compensation` ([Lean](../../../Kernel/Feature/Compensation.lean)) owns `FeatureSlots.compensation`: the records of completed compensable work (`Compensable`) and the compensation runs in progress (`CompensationRun`), together with Transaction cancellation's compensation step. It dispatches on no guarded type of its own; [propagation](PROPAGATION-SEMANTICS-SPEC.md) hands it a Compensation throw or a caught Cancel through `Signal.compensate`, and the pipeline reports completions through `Hooks.completed` and `Hooks.handlerCompleted`. Admission is in `Kernel.Admission.Work`, `Kernel.Admission.Propagation`, `Kernel.Admission.Scopes` and `Kernel.Admission.Profile`.

## Interpretation

### Eligibility and retention

- Only successfully completed work with a compensation handler is compensable: an Activity with a boundary Compensation Event and its associated handler, or a Sub-Process containing a Compensation Event Sub-Process (BPMN 2.0.2 Tables 10.88 and 10.89, §13.5.5). An omitted `activityRef` selects every visible eligible record; it never makes handler-free work eligible ([CBR account][cbr-normative], [experiment result][cre-result]). The IL names one handler per subject (`Envelope.compensationHandler`).
- Eligibility is decided by the handler, lifetime by the scope: a completion of a subject with a handler is retained in the scope occurrence it completed in, and the record lives as long as that scope occurrence ([experiment result][cre-result], [`Compensation.completed`](../../../Kernel/Feature/Compensation.lean)). Retention is hidden semantic state, never reconstructed from publication ([experiment result][cre-result], [experiment scope][cre-scope]).
- A record carries the subject, its handler, the completed occurrence's identity and a completion ordinal; ordinals and identities are monotonic and never reused ([CBR contract][cbr-contract]). Active, interrupted or failed work completes nothing and retains nothing; an interrupting boundary path retains nothing ([CBR scope][cbr-scope], `TXC-RETAIN-01` in [TXC rules][txc-rules]).
- A boundary handler restores no context. A Compensation Event Sub-Process restores its parent's frozen completion-time context: the Process and Sub-Process variables visible inside the parent when it completed, never Task I/O, other Activities' local scopes, a live alias or an entry-time copy (§13.5.4, §13.5.5, §10.3.5, §10.4.1; [CESP account][cesp-normative], [CESP contract][cesp-contract]). Records and snapshots are keyed by the complete runtime occurrence, so a later per-instance account for loops and Multi-Instance parents needs no new identity ([CESP account][cesp-normative]).
- When a Sub-Process completes, the records retained inside it stay compensable: a Sub-Process with a handler keeps them as children its handler's own throw compensates, and one without a handler passes them to its parent's scope occurrence (§13.5.5; `Compensable.children`). The old accounts excluded implicit and recursive compensation and left OMG BPMN21-403 unresolved ([CBR account][cbr-normative], [CTH scope][cth-scope]), so admission refuses every program that would hand records on: `compensation.implicit` when a handler-less Scope's records would reach a parent occurrence a Compensation throw shares, `compensation.recursive` when the retaining Scope's handler body throws Compensation (PC-COMPENSATION-03 lifts them after its interpretation review).
- Leaving a scope occurrence without completing it drops every record retained in it ("presumed abort"; `State.leaveScope`), and ending the instance drops every record. The snapshot account retained a promoted root snapshot in the terminal state for a later parent host ([CESP scope][cesp-scope]); that retention is track work of PC-COMPENSATION-05, listed under the row below.

### Trigger and order

- A Compensation throw compensates the records retained in its own scope occurrence (BPMN 2.0.2 §10.7.2, §13.5.5): the run takes them out of retention atomically, so no other trigger can compensate them again, and the thrower continues only after every handler has completed; an empty set continues at once ([CTH basis][cth-normative], [CTH contract][cth-contract], [`Compensation.compensate`](../../../Kernel/Feature/Compensation.lean)). Only the global synchronous form is admitted.
- Order is the reverse of dependency: a direct Sequence Flow from subject A to subject B makes B's handler complete before A's starts; handlers without such a dependency run concurrently. Every pending handler none of whose successors is pending or running starts at once, in program order (§13.5.5; [CTH basis][cth-normative], [CSL account][csl-normative]). Completion chronology is not that order, and CIB's reverse creation-time order cannot implement it in general (`ProfileOptions.compensationOrder = dependency`). Gateway-mediated dependencies are not inferred ([CTH scope][cth-scope]).
- Each handler begins in a context scope occurrence of its own inside the run's scope, holding the restored context; its subject's child records move into that context, where a throw inside the handler compensates them ([`Compensation.beginHandler`](../../../Kernel/Feature/Compensation.lean)).
- A second trigger while a run is in progress in the same scope occurrence has no selected relation to the first and is refused (`compensation-concurrent-trigger`); so is a subject retained twice in one scope, which §13.5.5 compensates in reverse completion order (`compensation-repeated-subject`) ([CTH contract][cth-contract]).
- Compensation Start `isInterrupting`, Compensation Boundary `cancelActivity`, catch-side `waitForCompletion` and Association direction neither classify nor lower (Tables 10.87, 10.91, 10.92, 8.20; [CSL account][csl-normative]).

### Handler failure

- An Error a handler's effect reports and nothing inside the handler catches fails the process instance: the handler and its run fail, every token, item, occurrence and handler is removed, nothing continues, and the failed state publishes the run's trigger, the handler, the raising effect, the code and the message (`COMPH-FAIL-01`; [CTH contract][cth-contract], [`Compensation.failCompensation`](../../../Kernel/Feature/Compensation.lean)). BPMN 2.0.2 §13.3.2 names the handler states but not this disposition; it is a project interpretation, not BPMN or CIB transcription ([CTH basis][cth-normative]), selected by `ProfileOptions.compensationHandlerFailure = failsInstance`. A failed instance accepts no further input and is not a host failure; transport retries are never typed BPMN errors ([TXC rules][txc-rules]).
- Propagation never searches past a handler's context, so an event a handler leaves uncaught reaches the handler failure rule (see [propagation](PROPAGATION-SEMANTICS-SPEC.md)).

### Transaction cancellation

- A Transaction is a Sub-Process whose cancellation interrupts its running work and compensates its completed eligible work; its Cancel Boundary Event takes control after rollback and compensation finish (BPMN 2.0.2 §10.3.5). Ordinary interruption is no implicit compensation trigger, and quiescence alone does not implement protocol success ([TXC basis][txc-normative]).
- A Cancel End Event raises Cancel from the scope occurrence it ran in. A caught Cancel clears the Transaction's interior, compensates the records retained in it, and only once the last handler has completed cancels the Transaction occurrence and takes the Cancel boundary's flows in the parent; the Transaction's normal outflow never fires (`TXC-CANCEL-01`, `TXC-EMPTY-01`, `TXC-JOIN-01`; [`Propagation`](../../../Kernel/Feature/Propagation.lean)). With no eligible record the boundary is taken in the same step; unfinished work disappears uncompensated. Records of nested scopes the cancellation interrupts are dropped with them.
- A handler failure during cancellation fails the instance as above, and neither the boundary nor the normal flow continues (`TXC-FAIL-01`, a project extension of `COMPH-FAIL-01`, not a hazard boundary). Regional cancellation preserves everything outside the Transaction's region except its continuation (`TXC-FRAME-01`).
- `method` is omitted or exactly `##Compensate`, the XSD default; other spellings are neither case-folded nor aliased (OMG BPMN2-60; [TXC basis][txc-normative]).
- Publication: the Transaction stays open while it compensates, interrupted work closes as cancelled, the handler's lifecycle is published, and the Transaction then closes as cancelled before the boundary occurrence; retention and trigger ownership are no public fields, and there is no public cancel command ([TXC public][txc-public]).
- The old account rejected a Cancel boundary on an ordinary Sub-Process, a non-interrupting Cancel boundary and a Cancel End outside a Transaction before lowering (§10.5.5; [TXC contract][txc-contract]). The kernel refuses the same set (§10.5.5): `boundary.cancel.host` for a Cancel boundary on anything but a Transaction, `boundary.cancel.nonInterrupting` for a non-interrupting one, and `throw.cancel.outsideTransaction` for a Cancel throw whose direct parent is not a Transaction (`Admission.Subscriptions.boundary`, `Admission.Propagation.throwRecord`) (PC-TX-02).

#### I1 — Invocation order and completion chronology (PC-COMPENSATION-01)

- BPMN: §13.5.5 Operational Semantics: default compensation runs Compensation Activities "in reverse order of the execution of the original Activities, allowing for concurrency when there was no dependency"; a Sequence Flow from A to B "results in compensation of B to be performed before compensation of A"; instances of a loop or sequential Multi-Instance are compensated in reverse forward completion order, parallel instances may run in parallel.
- CIB: `bpmn/helper/CompensationUtil.java:55-88` creates one concurrent compensating execution per retained subscription and signals every one at once, in reverse `created` order (`:78-87`); a waiting handler (a Human Task) is therefore open together with every other handler of the trigger, and only the start order of handlers that run synchronously follows creation time. Under a frozen clock the tie is the subscription identifier order of a `HashSet` (`:184-206`; the runner pins identifiers, `CibSevenEngineBundleFactory.ScenarioIds`).
- Witnesses: retained `compensation-order-chronology/*` (5): after the throw CIB opens `UserTask_UndoA`, `UserTask_UndoB` and `UserTask_UndoC` together, where the kernel holds `UserTask_UndoA` until `UserTask_UndoB` completes (B follows A by Sequence Flow); `compensation-multi-instance-bodies/*-sequential-in-turn` and `compensation-order-and-multiplicity/call-sequential-three-reviewers`: CIB opens the handlers of all instances together. `later-handler-first`, `with-message-before-a-completes` and `without-message` agree.
- Relation: the kernel keeps `compensationOrder = dependency` under every profile, and CIB's order is a candidate deviation (D1). Draft register entry:
  > **CIB-DEV-0011 — CIB starts every compensation handler of one trigger at once.** **Status:** Deviation candidate from the pinned source and retained evidence; selected by no profile. BPMN 2.0.2 §13.5.5 requires default compensation to consider a Sequence Flow between two compensated Activities, compensating the later one before the earlier, and sequential Multi-Instance instances in reverse completion order. CIB Seven `2.2.0` creates a concurrent execution for every retained subscription and signals them all in reverse creation order (`CompensationUtil.java:55-88`), so every waiting handler is open at once. **Evidence:** retained `compensation-order-chronology/*`, `compensation-multi-instance-bodies/tasks-sequential-in-turn`, `regions-sequential-in-turn`, `compensation-order-and-multiplicity/call-sequential-three-reviewers`. **Boundary:** triggers retaining two subjects joined by a Sequence Flow, or the instances of a sequential Multi-Instance subject; this entry owns those witnesses in the ledger.
- Shape: `CompensationOrder.reverseCreation` names an order CIB does not have for waiting handlers; replace it by `allAtOnce` (CIB's), kept refused as `profile.compensationOrder.allAtOnce` (D1). Sequential Multi-Instance instance order needs each record's completion ordinal, which `Compensable.completion` holds.

#### I2 — Which records an untargeted throw sees (PC-COMPENSATION-02, PC-COMPENSATION-05)

- BPMN: §10.7.2 and §13.5.5 Compensation Triggering: "If the Activity is clear from the context, it doesn't have to be specified and defaults to the current Activity. A typical scenario for that is an inline error handler of a SubProcess that cannot recover the error, and as a result would trigger compensation for that Sub-Process"; in a "global" context every completed Activity of the Process; Table 10.94 broadcasts an untargeted throw "to all completed Activities in the current Sub-Process (if present), or the entire Process instance".
- CIB: `CompensationUtil.java:184-206` walks the flow scopes outward from the throw and collects every compensation subscription until a scope that consumes compensation; `bpmn/parser/BpmnParse.java:3885` marks every Event Sub-Process as not consuming, so a throw inside an Event Sub-Process compensates the records of the Sub-Process holding it (source and retained).
- Witnesses: retained `compensation-event-subprocess-throws/error-esp-throws-untargeted`: the untargeted throw in an Error Event Sub-Process opens `UserTask_UndoTask` of its parent's completed Task; the kernel compensates nothing (its run scope is the Event Sub-Process occurrence) and continues to *Continue after the recovery*.
- Relation: agreement with the BPMN reading; the kernel's run scope changes: an untargeted throw compensates the records of the nearest enclosing scope occurrence that is no Event Sub-Process occurrence. No register entry: the retained answer becomes agreeing evidence once the kernel follows §10.7.2. Whether an Event Sub-Process is itself the "current Sub-Process" of Table 10.94 is the close call D15.
- Shape: none; the run scope is derived from `ScopeKind.eventSubProcess` on the throw's scope chain.

#### I5 — Records of a completed Sub-Process without a handler, and Transaction success (PC-COMPENSATION-03, PC-TX-01)

- BPMN: §10.7.1 and §13.5.5: a Sub-Process "can be compensated without having to define the compensation handler" through the attribute `compensable`, whose default compensation "recursively compensates all successfully completed Activities within that Sub-Process"; the attribute exists in neither the CMOF nor the XSD (OMG BPMN21-403). Transaction (Table 10.21 and its outcomes): successful completion leaves by normal Sequence Flow; ordinary interruption causes no compensation.
- CIB: `bpmn/behavior/SubProcessActivityBehavior.java:61-66` calls `CompensationUtil.createEventScopeExecution` (`CompensationUtil.java:100-152`) on every completed Sub-Process and Transaction (`BpmnParse.java:3902-3911` gives a Transaction the Sub-Process behavior): it keeps the inner subscriptions under an event-scope execution, copies the Sub-Process's local variables into it by value (`:118-124`) and subscribes the Sub-Process itself, without a handler, to its parent (`:143-151`, `:167-178`); compensating that subscription descends into the event scope and compensates the inner records as one group (`CompensationEventHandler.java:61-64`). Every Sub-Process is thus implicitly compensable.
- Witnesses: retained, committed in CIB, refused by the kernel as `compensation.implicit`: `compensation-regions/*` (4), `transaction-paths/success-then-outer-throw`, `cancel-end`, `error-end`, `compensation-multi-instance-bodies/regions-*` (2), `compensation-context-live-outer/default-handler-reads-and-writes-outer`, `compensation-event-subprocess-throws/error-esp-completes-then-outer-throw`, `transaction-and-error-exits/error-end-in-subprocess`; `compensation-context/*` (standing harness failures). Agreeing: `transaction-and-error-exits/transaction-completes-while-boundary-path-runs`.
- Relation: CIB's implicit compensation of every Sub-Process is its interpretation of BPMN21-403 (D3). Draft:
  > **CIB-INT-0036 — CIB compensates every completed Sub-Process without a handler as the group of its inner records.** **Status:** Recorded interpretation from the pinned source and retained evidence; selected by `ProfileOptions.implicitCompensation = everySubProcess` through the cibseven profiles. BPMN 2.0.2 §13.5.5 gives a Sub-Process default compensation through an attribute `compensable` the metamodel does not define (OMG BPMN21-403). CIB Seven `2.2.0` retains the inner records of every completed Sub-Process and Transaction under the Sub-Process and compensates them as one group when the Sub-Process is compensated, by an untargeted throw of its parent or a throw naming it (`SubProcessActivityBehavior.java:61-66`, `CompensationUtil.java:100-152`, `CompensationEventHandler.java:61-64`). **Evidence:** the retained witnesses listed above. **Boundary:** completed Sub-Processes and Transactions without a compensation handler; under `bpmn-2.0.2` admission keeps `compensation.implicit`.
- Kernel meaning: today `Compensation.completed` moves a handler-less Scope's records to its parent occurrence, flattening the group; under `everySubProcess` the completed Scope is retained as one record without a handler whose `children` are its inner records, so a throw naming the Sub-Process selects the group (I3), the group is one subject for the order of I1 relative to its siblings, and compensating it runs its children as a nested run in a context occurrence holding the Sub-Process's snapshot (I12).
- Shape: `Compensable.handler : Option ElementId` (`none` = implicit group); `ProfileOptions.implicitCompensation : ImplicitCompensation` with `refused` (standards, refusal `compensation.implicit`) and `everySubProcess` (cibseven).

#### I7 — Recursive compensation, Compensation Event Sub-Processes, consumption and rethrow (PC-COMPENSATION-05)

- BPMN: §10.7.1 and §13.5.5: a Compensation Event Sub-Process "can recursively trigger compensation for Activities contained in its parent" and restores the parent's snapshot; consuming the trigger excludes implicit deeper handlers unless rethrown (PC-COMPENSATION-05's own acceptance).

- Relation: the kernel lifts `compensation.recursive` for a Compensation Event Sub-Process whose throws target its parent's records: `beginHandler` already moves the record's `children` into the handler context, where I2 resolves the throw; children no throw selects are dropped when the handler context ends (consumption). No register entry; P1 classifies CIB's rollback.
- Shape: none beyond I5.

#### I8 — A boundary handler on a Sub-Process (PC-COMPENSATION-05)

#### I9 — Multi-Instance, Call and effect subjects (PC-COMPENSATION-03)

- BPMN: §13.5.5 Operational Semantics: for a Multi-Instance or loop Activity "the Compensation Activity is triggered only once, too, and thus has to compensate the effects of all instances"; §10.7.2: a boundary handler of a Multi-Instance Sub-Process "is invoked once for each instance"; the two disagree for a Multi-Instance Sub-Process (D6).
- CIB: every completed instance leaves its own subscription at the Multi-Instance body (`AbstractBpmnActivityBehavior.java:69-74`), for Tasks, Call Activities and Sub-Processes alike; instances a completion condition cancelled leave none; zero instances leave none (retained).
- Witnesses: retained, refused by the kernel as `activity.compensationHandler` or `activity.multiInstanceBody`: `compensation-order-and-multiplicity/user-handler-two-items` (two handlers), `user-handler-zero-items` (none), `user-parallel-quorum-ends-after-one` (one, for the completed instance), `call-parallel-three-reviewers`, `call-sequential-three-reviewers` (three), `compensation-multi-instance-bodies/tasks-*` (three), `compensation-effect-and-call-records/call-completed-then-throw` (a Call subject). Agreeing: `success-then-throw`, `business-failure-ineligible`, `compensation-eligibility/completed-then-throw`, `interrupted-then-throw`.
- Relation: per-instance retention under the cibseven profiles is CIB's reading of the inconsistency (D6):
  > **CIB-INT-0037 — CIB retains one compensation record per completed Multi-Instance instance.** **Status:** Recorded interpretation from the pinned source and retained evidence; selected by `ProfileOptions.multiInstanceCompensation = perInstance` through the cibseven profiles. BPMN 2.0.2 §13.5.5 triggers a Multi-Instance Activity's Compensation Activity once and §10.7.2 once per instance of a Multi-Instance Sub-Process. CIB Seven `2.2.0` subscribes every completed instance at the Multi-Instance body (`AbstractBpmnActivityBehavior.java:69-74`), for any Activity. **Evidence:** the retained witnesses above. **Boundary:** Multi-Instance Activities with a compensation handler.

#### I10 — Handler bodies, inputs, effects and asynchronous marks (PC-COMPENSATION-04)

- BPMN: §10.7.1: a Compensation Activity "can be either a Task or a Sub-Process", outside normal flow; nothing restricts its work kind or data.
- CIB: a boundary handler starts with `PvmAtomicOperation.ACTIVITY_START` on a compensating execution that `throwCompensationEvent` placed under the throwing execution (`CompensationEventHandler.java:73-78`, `CompensationUtil.java:62-75`), so its input mappings read the throw's live scope chain, and its `camunda:asyncBefore` is never honored: `ACTIVITY_START` is no asynchronous operation (the asynchronous ones are listed in CIB-INT-0035's evidence). A Service Task handler's effect therefore runs inside the triggering command.
- Witnesses: retained, refused by the kernel as `activity.compensationHandler.input`: `compensation-eligibility/late-third-second-throw`, `two-records-live-data`, `unfinished-third-ineligible`, `transaction-cancel-mixed/*` (5 retained); as `compensation.handlerWork`: `compensation-handler-bodies/*`, `compensation-handler-bodies-without-receive/*` (Receive, effect, Call and Sub-Process handler bodies); synchronous handler effects: `compensation-handler-failures/*` (7; CIB's handler effect runs in the command that completes `UserTask_Book2`, a business failure rolls that command back, P2), `transaction-cancel-waiting-handlers/handlers-user-first`, `stale-interior-result-while-handlers-wait` (CIB never waits for the Service Task handler).
- Relation: the kernel admits input mappings on a handler, read in the handler's context occurrence (live data from the run scope's chain, I12), and handler bodies of every work kind the kernel otherwise admits; a Service Task handler stays an asynchronous effect. CIB's synchronous handler is a limitation (D7):
  > **CIB-LIM-0042 — CIB ignores the asynchronous continuation of a boundary compensation handler.** **Status:** Known CIB limitation within reviewed scope; selected by no profile, since the kernel waits for every handler effect under every profile. CIB Seven `2.2.0` starts a boundary compensation handler with `ACTIVITY_START` (`CompensationEventHandler.java:73-78`), which never defers to a job, so `camunda:asyncBefore` on the handler has no effect and its delegate runs inside the triggering command. **Evidence:** retained `compensation-handler-failures/*`, `transaction-cancel-waiting-handlers/handlers-user-first`, `stale-interior-result-while-handlers-wait`, `transaction-cancel-mixed/refund-business-failure`, `refund-incident-retried`. **Boundary:** Service Task compensation handlers attached by a boundary Event; this entry owns their witnesses.
- Shape: none for inputs and bodies (`Envelope.inputs` and `Work` exist); admission drops `activity.compensationHandler.input` and widens `compensation.handlerWork` to the admitted work kinds. `compensation.handlerMultiInstance` stays (CIB skips a handler's Multi-Instance asynchronous marks, `BpmnParse.java:2412-2425`).

#### I11 — An Error, Escalation or Terminate leaving a handler (PC-COMPENSATION-01, PC-COMPENSATION-04)

- BPMN: §13.3.2 names the handler states but no disposition for a failing handler; §13.5.6 Terminate ends its own scope.
- CIB: a handler's compensating execution is a child of the throwing execution (`CompensationUtil.java:62-75`), so an Error or Escalation the handler raises propagates from there to catchers enclosing the throw; an Error with no catcher ends the throwing path (CIB-INT-0013, `unhandledError = endsThrowingPath`), so the handler completes and the trigger continues (retained).
- Witnesses: retained `compensation-handler-failure-at-wait/error-caught-handler-fails-after-wait` and `escalation-caught-*` (the Error boundary on `SubProcess_Outer` catches it; `UserTask_Caught` runs), `error-uncaught-*` and `escalation-uncaught-*` (the run continues to `UserTask_After`); the kernel answers `compensation-handler-error-without-effect` or `compensation-handler-escalation`. `compensation-handler-terminate/*`: CIB rolls back the command that starts the handler Sub-Process (P3); the kernel ends only the handler Sub-Process and the run waits for it.
- Relation: under the cibseven profiles a handler's raise propagates from the trigger's occurrence, and an uncaught one follows the profile's `unhandledError` and `abnormalScopeEnd`; under the standards profile `failsInstance` stays (COMPH-FAIL-01) and is extended to Error End Events and Escalations, which also fail the instance (D8). Draft:
  > **CIB-INT-0038 — CIB propagates a compensation handler's Error or Escalation from the compensation trigger.** **Status:** Recorded interpretation from the pinned source and retained evidence; selected by `ProfileOptions.compensationHandlerFailure = propagatesFromTrigger` through the cibseven profiles. BPMN 2.0.2 §13.3.2 states no disposition for a failing handler. CIB Seven `2.2.0` runs every handler in an execution under the throwing one (`CompensationUtil.java:62-75`), so the raise reaches the catchers that enclose the throw, and an uncaught Error ends only the throwing path (CIB-INT-0013). **Evidence:** retained `compensation-handler-failure-at-wait/*`. **Boundary:** Errors and Escalations leaving a compensation handler after it waited; a synchronous handler's raise is CIB-LIM-0042's.
- Shape: `CompensationHandlerFailure.propagatesFromTrigger` (new variant); the propagation search finds the trigger through `CompensationRun.trigger` and `running`, so State needs no field. Refusal codes `compensation-handler-error-without-effect` and `compensation-handler-escalation` end under `propagatesFromTrigger`; `compensation-handler-cancel` stays.

#### I12 — Context a handler reads (PC-COMPENSATION-01, PC-COMPENSATION-05)

- BPMN: §13.5.5 Operational Semantics: a Compensation Event Sub-Process restores "a snapshot of the data associated with the parent Activity"; a boundary Compensation Activity restores nothing.
- CIB: the event scope copies only the completed Sub-Process's own local variables (`CompensationUtil.java:118-124`); variables of enclosing scopes stay live, and a write to them reaches the live scope.
- Witnesses: retained `compensation-context-live-outer/default-handler-reads-and-writes-outer` (refused today by `compensation.implicit`); `esp-handler-reads-and-writes-outer` has no retained answer (harness failure this retake); `compensation-context/*` (standing harness failures).
- Relation: the kernel snapshot today holds every variable visible inside the parent when it completed (CESP account); CIB's and the narrower BPMN reading ("data associated with the parent Activity") hold only the parent's own data (D9). Recommendation: snapshot the parent's own scope occurrence variables, read every other name live through the handler context's chain.
- Shape: none (`Compensable.snapshot` keeps its type; its content narrows).

#### I13 — Cancel over mixed work, an uncaught Cancel and the Cancel boundary forms (PC-TX-02)

- BPMN: Transaction outcome 2: a Cancel End within the Transaction cancels it, compensation runs, and the Cancel boundary "will direct the flow after the Transaction has been rolled back and all compensation has been completed"; the Cancel Intermediate Event "can only be used when attached to the boundary of a Transaction Sub-Process"; the kernel's existing §10.5.5 reading admits only an interrupting Cancel boundary (Table 10.91 exempts Error and Compensation boundaries from `cancelActivity` and leaves Cancel unnamed).
- CIB: `bpmn/behavior/CancelEndEventActivityBehavior.java:39-53` interrupts the Transaction's flow scope (`BpmnParse.java:3165-3167`), compensates its retained records, joins the handlers (`:64-72`) and executes the Cancel boundary (`:56-62`); without a Cancel boundary `ensureNotNull` (`:41-42`) fails and the command rolls back; two Cancel boundaries are refused at deployment (`BpmnParse.java:1776-1779`); a non-interrupting Cancel boundary deploys and leaves the instance running with no wait after its path ends (retained).
- Witnesses: retained `transaction-cancel-mixed/*` (refused by I10's input code today), `transaction-cancel-waiting-handlers/*` (I10), `transaction-cancel-refusals/cancel-end-without-boundary` (CIB rolls back; kernel `raise-cancel`), `non-interrupting-cancel-boundary` (CIB strands the instance; kernel refuses), `two-cancel-boundaries` (CIB refuses; kernel admits), `cancel-boundary-on-subprocess`, `cancel-end-at-process-level`, `cancel-end-in-subprocess` (both refuse); `transaction-nested/*` agree.
- Relation: the kernel refuses at admission a Cancel End whose Transaction has no Cancel boundary (`throw.cancel.uncaught`, replacing dynamic `raise-cancel`) and two Cancel boundaries on one Transaction (`boundary.cancel.duplicate`, the row's "one host permits only one Cancel boundary"); `boundary.cancel.nonInterrupting` stays. Draft (D10):
  > **CIB-LIM-0043 — CIB deploys Cancel forms BPMN does not define and fails or strands them.** **Status:** Known CIB limitation within reviewed scope; selected by no profile, since the kernel refuses both forms under every profile. CIB Seven `2.2.0` deploys a Cancel End Event whose Transaction has no Cancel boundary and rolls back the command that reaches it (`CancelEndEventActivityBehavior.java:41-42`), and deploys a non-interrupting Cancel boundary, after whose path the instance stays running with no wait. **Evidence:** retained `transaction-cancel-refusals/cancel-end-without-boundary`, `non-interrupting-cancel-boundary`. **Boundary:** those two forms.
- Shape: none (codes only).

#### I14 — Transaction method (PC-TX-01)

- BPMN: Table 10.21: `method` names the transaction protocol, a technology URI or, "for compatibility with BPMN 1.1", `##compensate`, `##store` or `##image`, whose 2.0.2 meaning is not stated.
- CIB: `BpmnParse.java:3902-3915` never reads `method`; every Transaction behaves as a compensating Sub-Process.
- Witnesses: retained `transaction-methods/image-method`, `store-method` (CIB commits as `##Compensate`; the kernel refuses `scope.transaction.method`), `compensate-method` (agrees).
- Relation: CIB's reading of an unstated method is an interpretation (D11):
  > **CIB-INT-0039 — CIB runs every Transaction method as `##Compensate`.** **Status:** Recorded interpretation from the pinned source and retained evidence; selected by `ProfileOptions.transactionMethods = anyAsCompensate` through the cibseven profiles. BPMN 2.0.2 Table 10.21 lets `method` name a protocol and keeps `##store` and `##image` for BPMN 1.1 compatibility without stating their meaning. CIB Seven `2.2.0` ignores the attribute (`BpmnParse.java:3902-3915`). **Evidence:** retained `transaction-methods/image-method`, `store-method`. **Boundary:** Transactions whose method is not `##Compensate`; under `bpmn-2.0.2` admission keeps `scope.transaction.method`.
- Shape: `ProfileOptions.transactionMethods : TransactionMethods` with `compensateOnly` and `anyAsCompensate`; `TransactionScope.method` exists.

#### I15 — Multi-Instance and concurrently cancelled Transactions (PC-TX-03)

- BPMN: §10.3.5 Transaction with Multi-Instance characteristics is not excluded; the Cancel boundary belongs to the Activity.
- CIB: `BpmnParse.java:1765-1770` resolves a Cancel boundary on a Multi-Instance Transaction to the inner Transaction, and `CancelEndEventActivityBehavior.java:56-62` executes it from the boundary's event scope, the Multi-Instance body: one body's Cancel compensates that body's records only and then cancels the whole Multi-Instance Activity, dropping the records of bodies that already completed (retained: `parallel-cancel-after-others-checked` runs only body 2's handler; the handlers of bodies 1 and 3 are rejected).
- Witnesses: retained `transaction-multi-instance/*` (4) and `transaction-multi-instance-concurrent-cancel/*` (4), all refused by the kernel as `scope.multiInstance`; in the concurrent cases the first run to complete takes the boundary and the other body's run is cancelled with its handlers.
- Relation: agreement with BPMN's interruption rule (records of a cancelled Activity's completed bodies are dropped with it; ordinary interruption is no implicit compensation); the kernel admits a Multi-Instance Transaction: a body's Cancel runs a run in that body's Transaction occurrence, and when the run ends the Cancel boundary of the Multi-Instance Activity interrupts every other body, cancelling their runs and handlers (D12 for the concurrent case's order). No register entry unless P4 shows otherwise.
- Shape: none (`Resume.occur` already begins the boundary in the Activity's scope; a run whose scope occurrence is left ends with it).

#### I16 — Handler placement and the forms CIB refuses (PC-COMPENSATION-04, PC-COMPENSATION-05)

- BPMN: §10.7.1: a Compensation Activity is "outside the normal flow" and carries `isForCompensation = true` (Table 10.3); a Compensation Event Sub-Process is "contained within a Process or a Sub-Process" (§13.5.5); BPMN states no limit of one handler per Activity.
- CIB: refuses at deployment an Association to an Activity without `isForCompensation` (`BpmnParse.java:905-910`), a Compensation Boundary Event beside a Compensation Event Sub-Process of the same Activity (`:913-920`, `:1199-1201`), two Compensation Event Sub-Processes of one scope (`:1199`), a Compensation Event Sub-Process at Process level (`:1187-1190`, since Call-hierarchy compensation is unsupported), two Compensation Boundary Events on one Activity (`:1754`) and a Sequence Flow into or out of a compensation handler (`:4327-4337`).
- Witnesses: retained `compensation-handler-form-refusals/*` (6): CIB refuses each, the kernel admits each and its instance runs.
- Relation: the kernel refuses all six at admission. The handler Sequence Flow and the non-compensation target are BPMN-invalid; the other four are CIB limitations of forms BPMN admits (D13):
  > **CIB-LIM-0044 — CIB refuses a second compensation handler of one Activity and a Process-level Compensation Event Sub-Process.** **Status:** Known CIB limitation within reviewed scope; selected by no profile, since the kernel refuses the same forms under every profile. CIB Seven `2.2.0` keeps at most one compensation handler per Activity or scope (`BpmnParse.java:913-920`, `:1199-1201`, `:1754`) and refuses a Compensation Event Sub-Process at Process level (`:1187-1190`). **Evidence:** retained `compensation-handler-form-refusals/esp-and-boundary-same-scope`, `two-esps-same-scope`, `two-compensation-boundaries`, `esp-at-process-level`. **Boundary:** those forms.
- Shape: `Envelope.compensationHandler : Option ElementId` cannot carry a second handler, so a refused field would be erased before admission. Replace it by `compensationHandlers : List ElementId` (admission: more than one is `compensation.handlerCount`) and add `ActivityPayload.forCompensation : Bool` (`isForCompensation`; an associated target without it is `compensation.handlerNotForCompensation`; a handler with flows `compensation.handlerFlow`); a Process-level Compensation Event Sub-Process is `compensation.processEventSubProcess`.
