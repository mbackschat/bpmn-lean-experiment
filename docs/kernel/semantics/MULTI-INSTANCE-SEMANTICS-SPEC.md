# Multi-Instance semantics

## Status

Adopted kernel owner document (W0 extraction, 2026-11-09). The kernel modules it cites are the executable authority; where they differ, the difference is a defect of one of them.

`Kernel.Feature.MultiInstance` ([Lean](../../../Kernel/Feature/MultiInstance.lean)) owns the guarded type `MultiInstanceMode` and the Multi-Instance body: a token reaching an Activity with Multi-Instance loop characteristics begins the body occurrence, which reads the input collection once, holds one slot per item in `FeatureSlots.multiInstances`, and begins each instance as an ordinary occurrence of the Activity in a scope occurrence of its own. `Kernel.Admission.MultiInstance` ([Lean](../../../Kernel/Admission/MultiInstance.lean)) admits the loop characteristics; `Kernel.Admission.Work` admits the instance's work. `Kernel.Publish.multiInstances` ([Lean](../../../Kernel/Publish.lean)) publishes the open bodies.

## Interpretation

### Entry and generation

- BPMN 2.0.2 §10.3.8, §13.3.7 and Tables 10.29 and 10.30 own the wrapper: the number of instances is evaluated once on entry; a parallel Activity generates every instance together, a sequential one the next only after the previous completes ([SMI account][smi-normative], [PMI account][pmi-normative]).
- The project resolutions of what the standard leaves open: the input collection is read once on entry, in declared order, into an immutable snapshot; the instance counter is zero-based and names the item and the output slot; extraction and update are exact index operations with no coercion or reordering; duplicate items keep multiplicity and distinct identity ([SMI account][smi-normative], [PMI account][pmi-normative], `PMI-ENTER-01` and `SMI-ENTER-01`, `SMI-DATA-01` in [PMI rules][pmi-rules] and [SMI rules][smi-rules]). Each instance holds its item as its input data item.
- An empty collection completes the Activity at once, normally, with an empty output collection and no instance, wait or controller ([SMI account][smi-normative], [PMI account][pmi-normative]).
- The body and its instances number apart: the body's activation is counted under its own role, so the first instance is activation 1 whatever the body entries before it ([row traceability F10](../ROW-TRACEABILITY-MAP.md#lifecycle-fit)).
- An instance's activation is its generation order: instances begin in item order, a sequential Activity's each after the previous completes, so within one body entry the instance for item `loopCounter` is activation `offset + loopCounter + 1`, `offset` counting the instances of earlier entries. That offset under re-entry through a Sequence Flow cycle belongs to PC-MI-11.
- When a parallel Activity's instances begin is the closure's branch schedule (`ProfileOptions.branchSchedule`), never the construct's meaning: BPMN generates parallel instances with no order among them (§13.3.7), and concurrent paths interleave in any order (§13.3.1, Table 13.1). Under `orderInvariant` every instance begins at entry, as a `begin` signal before any token moves. Under `declarationDepthFirst`, CIB's schedule ([CIB-OP-0016](../../CIB-BPMN-RELATION-REGISTER.md#cib-op-0016--a-splits-branches-run-in-declaration-order-each-to-its-next-wait-join-or-end)), the body enters every instance's scope occurrence at entry and defers their begins onto the closure's work stack, instance 0 on top (`MultiInstance.queueInstances`, `State.deferBegins`), as CIB starts the instance executions from the last index down onto its LIFO operation queue (`ParallelMultiInstanceActivityBehavior.java:50-61`). Each instance runs to its next wait, join or end, its own completion included, before the next begins, and all of them run before the work queued beneath the body, so an instance's entry reads see what earlier instances wrote before their next wait.
- Under `declarationDepthFirst` an instance whose scope occurrence, or an enclosing one, is removed within the closure before its turn never begins: a completion condition that holds, an interrupting boundary or an Error raised out of an earlier instance removes it with the body. It has had a scope occurrence and a slot, but has no flow-node occurrence and no journal fact. CIB deletes the still-active execution (`ParallelMultiInstanceActivityBehavior.java:99-104`, `PvmExecutionImpl.java:624`) and skips its queued start (`AtomicOperationInvocation.java:77-82`), so no activity instance is recorded for it (`PvmExecutionImpl.java:855`, `PvmAtomicOperationActivityInstanceEnd.java:73-75`, `AbstractEventAtomicOperation.java:50`). BPMN permits the interleaving in which the remaining instances took no step before the condition held, and fixes no history for such an instance.
- Which variables bind the collection and the item is a profile decision (`ProfileOptions.multiInstanceBinding`). The standards reading takes them from the Data Input Associations the reader folds into the loop (`count`, `inputDataItem`); [CIB-INT-0014](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0014--a-multi-instance-loop-binds-its-collection-and-item-by-the-loops-own-references-not-by-data-associations) reads the collection from the variable the loop's `loopDataInputRef` names and binds each instance's item to the `inputDataItem`'s `name`, or, for a loop without an `inputDataItem`, to `camunda:elementVariable`, as CIB sets the element variable from that attribute and lets an `inputDataItem`'s `name` replace it (`BpmnParse.java:1863-1873`; `MultiInstance.collectionOf`, `MultiInstance.itemName`). Under the standards reading `camunda:elementVariable` is a foreign extension.
- An embedded Sub-Process may loop (PC-MI-04, PC-MI-05): each instance is an occurrence of the Scope in a scope occurrence of its own below the body's, holding its item (BPMN 2.0.2 §10.3.8, §13.3.7; CIB makes the Sub-Process a scope under the body, `BpmnParse.java:3887`). A Transaction loops the same way, a body's Cancel compensating its own instance (PC-TX-03, [I15](COMPENSATION-SEMANTICS-SPEC.md#i15--multi-instance-and-concurrently-cancelled-transactions-pc-tx-03)); a looping Event Sub-Process is refused (`scope.multiInstance`). The instance submits no output data item, so a Sub-Process loop naming one is `multiInstance.instanceResult` (PC-MI-10).

### Completion and output

- An instance's completion submits exactly its output data item, which fills that instance's slot whatever the completion order; a Service Task instance, whose loop names no output data item, submits the empty OutputSet, so its effect result carries no value, or under `ResultValues.activityLocals` only values that end with the instance ([CIB-EXT-0015](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0015--serial-business-task-enclosing-inputs-and-local-results)); the Activity's output collection, in item order, is written only when every slot is filled (`SMI-ITERATE-01`, `SMI-COMPLETE-01`, `PMI-COMPLETE-01`, `PMI-FINISH-01`). The output collection keeps the form of the input: a String List stays a String List.
- The completion condition is evaluated after each instance completes; a true result before every slot is filled completes the Activity, ends the remaining instances, follows normal control and writes no output collection; a true result on the completion that fills the final slot writes the complete collection (`PMI-EARLY-01`, [PMI account][pmi-normative]). The no-partial-output rule reconciles early completion with the standard's caution that the output collection should not be accessible until all items are written; it is a profile resolution, not a claim about every BPMN implementation. The sequential account left the partial-output question open and excluded the completion condition ([SMI account][smi-normative]); the kernel applies the parallel resolution to both modes, and its selection for the sequential mode is track work of PC-MI-01, listed under the row below.
- Under BPMN the condition is evaluated on every completion, the final one included (`MultiInstanceFinalBody.conditionEveryCompletion`).
- The condition is evaluated in the completing instance's scope occurrence before it is left, so it reads the instance's item and, under `ResultValues.activityLocals`, the instance's result values (BPMN 2.0.2 §13.3.7: it "can refer to … inputDataItem"). A non-Boolean result or a failing evaluation fails the operation that reached it, following the stimulus table of the [Multi-Instance level](EXPRESSION-SEMANTICS-SPEC.md#multi-instance-level).
- Cardinality-driven generation runs one item-less instance per count; under `Evaluator.juel` the count, collection and completion expressions, their counters and their failures are the [Multi-Instance level's](EXPRESSION-SEMANTICS-SPEC.md#multi-instance-level).
- All-complete outcomes are invariant under the order of distinct completion inputs; which instances an early completion ends follows the explicit input order (`PMI-ORDER-01`).
- Wrong, stale, substituted or inactive identities and an output outside the declared item commit nothing (`SMI-REFUSE-01`, `PMI-REFUSE-01`).

### Interruption

- The boundaries of a Multi-Instance Activity belong to its body (BPMN 2.0.2 §13.5.3; CIB `BpmnParse:3291-3295`): an instance arms none, and an interrupting boundary on the body cancels every instance, generates no pending item, writes no output collection and follows only the boundary flow (`SMI-CANCEL-01`, `PMI-TIMER-01`). One deadline covers the whole Activity, not one per instance ([SMI scope][smi-scope]). A raised event's search skips an instance's scope occurrence for boundaries (see [propagation](PROPAGATION-SEMANTICS-SPEC.md)).
- A task completion and the body's Timer aimed at the same committed state are ordered inputs: the first committed wins and the other is stale; a nonfinal completion leaves the Timer's identity and deadline unchanged ([SMI rules][smi-rules]).

### Service Task bodies (PC-MI-02)

- Each instance of a Service Task body opens its own effect, identified by the instance's occurrence; an effect result addresses exactly one instance, and a result for an instance not open (not yet begun, ended, or never generated) is rejected with the state unchanged. A sequential body opens the next effect only after the current instance completed; a technical failure turns only the addressed instance's effect into an incident, which a retry turns back.
- Argument ownership is claimed at identity level only: which instance's effect a result reaches. Under the standards binding a Multi-Instance Activity admits no input mapping, and under `loopReferences` its own input mappings may not read the instance ([counters and the item](#counters-and-the-item-at-every-instance-site)), so an instance's effect carries no per-instance argument, and CIB publishes none for an asynchronous effect; that the item reaches the instance is shown by its local, not by an argument. Per-instance argument values belong to PC-MI-10.
- The marks on the loop characteristics put a transaction boundary before each instance begins or after it completes; the Activity's own marks bound the body ([CIB-EXT-0027](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0027--an-asynchronous-continuation-commits-the-input-at-its-boundary), `marks` in `Kernel.State.Journal`).

### Publication

- `openMultiInstances` is published in every state, as an empty list before entry and after either end, exactly when the program declares a Multi-Instance Activity; other programs omit it ([SMI contract][smi-contract], [PMI contract][pmi-contract]). Each entry carries the body occurrence's identity (process instance, element, activation), its mode, `plannedInstanceCount` (the once-evaluated cardinality), `pendingItemCount`, the Table 10.30 counters `numberOfInstances`, `numberOfActiveInstances` and `numberOfCompletedInstances`, and one entry per active instance with its counter, task identity, input data item and output binding name. `numberOfInstances` counts the instances generated so far, so `plannedInstanceCount = pendingItemCount + numberOfInstances`; the two planned counts are project extensions, not BPMN runtime attributes ([SMI account][smi-normative]). The snapshot and partial slots are never published. The sequential contract also published `numberOfTerminatedInstances` ([SMI contract][smi-contract]); the kernel publishes none, for the reason [terminated instances](#terminated-instances-pc-mi-12) gives.
- Ended instances are transition facts, never a retained open state: the journal closes each live instance as cancelled, and every begun instance is counted once as a flow-node occurrence (`SMI-OCCURRENCE-01`, [PMI contract][pmi-contract]); under `declarationDepthFirst` an instance removed before its turn never begins and has none ([entry and generation](#entry-and-generation)).

### Counters and the item at every instance site

Interpretation I1 (2026-11-10; cold interpretation review approved with required changes, folded in here). The [Multi-Instance level](EXPRESSION-SEMANTICS-SPEC.md#multi-instance-level) owns the counter values; this section owns where the counters and the item are visible.

- **What BPMN gives.** Each instance has its item: the `inputDataItem` represents "for every Activity instance the single item of the collection" and can be the source of the Activity's Data Input Associations (Table 10.29, [BPMN 2.0.2](../../reference/bpmn-2.0.2/README.md) reading copy line 5726). Table 10.30 gives each inner instance a `loopCounter` and the outer instance `numberOfInstances`, `numberOfActiveInstances`, `numberOfCompletedInstances` and `numberOfTerminatedInstances`, and §13.3.7 lets the completion condition refer to them. BPMN names no expression variable for these attributes and says nothing about their visibility at any other site; it never makes the counters visible at every site.
- **What CIB selects** ([CIB-INT-0018](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0018--multi-instance-counters-are-cibs-execution-locals-at-every-site-inside-an-instance)). The names `loopCounter`, `nrOfInstances`, `nrOfActiveInstances` and `nrOfCompletedInstances`; their values; no terminated count; and their visibility. CIB sets them with `setVariableLocal` (`MultiInstanceActivityBehavior.java:196-198`), `loopCounter` and the item on each instance's execution (`:76-88`) and the three body counters on the body's (`Parallel…:64-68`, `Sequential…:38-45`), updating them as instances complete (`Parallel…:84-87`, `Sequential…:47-61`, `:67-70`). So every expression evaluated in an execution below an instance resolves them: the completion condition, and every site nested in a Sub-Process instance, its mappings, conditions and Call inputs.
- **The kernel under `MultiInstanceCounters.cibLocals`.** The body's scope occurrence holds the three body counters and each instance's scope occurrence holds its `loopCounter` beside its item, as locals (`MultiInstance.counterLocals`); a continuing completion rewrites the body's counts in its own scope occurrence. A site inside an instance reads them through its scope chain, so the innermost loop's counters hide an enclosing loop's while an enclosing loop's item stays visible. Admission admits a counter name at a site inside an instance (`Admission.MultiInstance.countersAt`) and keeps `expression.juel.multiInstanceCounter` everywhere else. A sequential `nrOfInstances` read inside an instance is the count from entry ([CIB-INT-0002](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0002-sequential-multi-instance-nrofinstances-is-desired-cardinality-from-outer-entry)). Publication keeps Table 10.30's accounting in `openMultiInstances`; the counters are evaluation-context values, shown only in the kernel-only `scopes` publication. Under `none` no counter is held and no counter name resolves; the item is visible inside the instance under both.
- **A loop's own count.** The loop's cardinality and collection are evaluated before any of its own counters exists, so this loop's counters are absent there; for a loop nested in another loop's instance, an enclosing loop's counters are visible. The kernel refuses a counter name in a loop's own count expressions as `expression.juel.multiInstanceCounter` under every profile, a restriction that does not tell the two apart.
- **The looping Activity's own input mappings** ([CIB-LIM-0019](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0019-a-looping-activitys-own-input-mapping-that-reads-its-counters-or-item-is-refused)). CIB evaluates them in the parent of the execution entering the Activity (`core/variable/mapping/IoParameter.java:50-51`, called from `pvm/runtime/PvmExecutionImpl.java:1309-1314`, whose own comment marks the choice `<LEGACY>` at `:1310-1314`). Which execution that is depends on whether the inner Activity is a scope, and a read of a counter or the item that it does not hold rolls the start back, where BPMN gives each instance its item. The kernel does not reproduce that rollback: under `loopReferences` it admits own input mappings but refuses a read of a counter name or the item name in them as `multiInstance.ownInputReadsInstance`, for every inner kind and both modes. Under the standards binding own mappings stay refused (`multiInstance.mappings`), as do own output mappings under both, a CIB deployment error (`BpmnParse.java:4855-4857`).
- **Writes to a counter** ([CIB-LIM-0020](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0020-a-target-named-like-a-multi-instance-counter-inside-an-instance-is-refused)). Under `cibLocals` admission refuses a target named like a counter that a model writes inside an instance: an own input mapping's target, and an output mapping, Call output or subscription output written in a scope inside an instance, as `multiInstance.counterTarget`. A write admission cannot see, an effect result or a submission that reaches a counter local, is `unsupported` when it occurs (`multiInstance.resultShadowsInstance`, dynamic-only): CIB reads a counter back typed (`MultiInstanceActivityBehavior.java:200-204`), and the kernel decides no value other than its own count there.
- **User Task bodies.** A looping User Task has no admitted read site inside its instance other than its own input mappings, which read before any Process write inside the instance, and the completion condition. So a read of a counter through a write made inside the instance is witnessed only with Sub-Process bodies.
- **Separating witnesses** against "counters are visible only in the completion condition": [multi-instance-instance-sites](../../../scenarios/open-rows/multi-instance-instance-sites/README.md) reads the counters and the item at a User Task nested in a Sub-Process instance in both modes; its sequential schedule reads `nrOfInstances` there, separating the count from entry from the count generated so far (CIB-INT-0002); its nested model has an inner loop's `loopCounter` hide the outer one's; and its counter-target model is CIB-LIM-0020's refusal witness. The own-input start-rollback witnesses already retained in `multi-instance-user-task`, `multi-instance-nesting`, `multi-instance-expressions`, `multi-instance-activity-mapping-scope`, `input-mapping-contexts` and `expression-cardinality-and-collections` (59 retained answers measured 2026-11-10: 54 roll back, and the 5 zero-instance schedules commit, since no instance starts) are CIB-LIM-0019's refusal witnesses, not row acceptance.

### Terminated instances (PC-MI-12)

Interpretation I2 (2026-11-10; cold interpretation review approved with required changes, folded in here). "Body" in PC-MI-12 means one instance.

- **On the admitted surfaces every termination ends the body in the same step.** An interrupting boundary on the body, an interruption of an enclosing scope, a Terminate End Event outside the instance and an early completion each end every open instance and the body together, so no state that keeps a body holds a terminated instance and `numberOfTerminatedInstances` is always 0 where it could be published. The kernel therefore publishes no terminated count. This is a property of today's admitted surfaces, not the general meaning: BPMN 2.0.2 §13.5.6 (reading copy line 12734) terminates only the affected instance when a Terminate End Event ends a Multi-Instance Sub-Process instance, and a terminated instance whose body is kept is BPMN meaning.
- **The current instance's abnormal end.** An interrupting Event Sub-Process or a Terminate End Event inside a Sub-Process instance ends that instance abnormally. Under the CIB profiles it completes normally ([CIB-INT-0007](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0007--a-sub-process-left-abnormally-completes-normally)), so it counts as completed and the body continues; CIB keeps no terminated count. Under the standards reading the shape is refused (`profile.abnormalScopeEnd.withoutOutflow`).
- **An uncaught Error inside an instance.** Under the CIB profiles it is `unsupported` (`unhandled-error-leaves-multi-instance-instance`, [CIB-INT-0013](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0013--an-error-that-no-catcher-takes-ends-only-its-throwing-path)); under the standards profile `UnhandledError.failsInstance` ends the whole Process instance, the body with it.
- **Reopen triggers.** The terminated count needs a decision again when any of these admits a terminated instance beside a kept body: PC-ERROR-03 (M7), PC-MI-03 (Call bodies), and PC-MI-04 and PC-MI-05 as they lift `scope.multiInstance`.
- **Terminate End in an instance (PC-TERMINATE-02).** Decided by [CIB-INT-0007](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0007--a-sub-process-left-abnormally-completes-normally): under the CIB profiles the instance counts as completed and triggers the completion condition, with no terminated count; the standards profile refuses the shape. Witnesses: [terminate-multi-instance-bodies](../../../scenarios/open-rows/terminate-multi-instance-bodies/README.md) `parallel-first-body-terminates` and `parallel-second-body-terminates` (`numberOfCompletedInstances` incremented while a sibling instance is still active) and `parallel-first-body-completes-loop` and `sequential-first-body-completes-loop` (the completion condition ends the loop).

CIB's schedule (`declarationDepthFirst`, CIB-OP-0016) admits it ([#72](https://github.com/mbackschat/bpmn-lean-experiment/issues/72)) |
| `multiInstance.resultShadowsInstance` (`unsupported`, dynamic-only) | an instance result named like a counter or the item, or a write that reached a counter local | [counters and the item](#counters-and-the-item-at-every-instance-site) |
| `activity.multiInstanceBody` | an instance doing anything but a User Task, a Service Task or an embedded Sub-Process | PC-MI-03 |
| `scope.multiInstance` | a looping Event Sub-Process | BPMN 2.0.2 §10.3.5 starts an Event Sub-Process by its event |
| `instance-output-kind`, `undeclared-output`, `output-unavailable` (`rejected`) | an instance completion that is not exactly its output data item, or a non-String into a String List | the slot rule above |
| `multi-instance-collection` (`semanticFailure`) | under `MultiInstanceInputFailure.hold`, a collection value that is no list; under `rollback` it is `multiInstance.notACollection` and fails the operation | the run's data |

Superseded first-profile restrictions: the sequential and parallel User Task profiles fixed one Activity, explicit `isSequential` and `behavior="All"`, an exact data-association graph, at most sixteen items of at most 512 bytes in an 8,192-byte collection, one exact completion predicate and exactly one interrupting `PT5S` Timer ([SMI boundary][smi-boundary], [SMI limits][smi-limits], [SMI scope][smi-scope], [PMI scope][pmi-scope], [PMI source][pmi-source]); the Sub-Process accounts bounded operations, simultaneous waits and pending effects per closure and fixed a structured body grammar ([PMIS purpose][pmis-purpose], [PMIS capacities][pmis-capacity], [SMIS scope][smis-scope], [SMIS admission][smis-admission]). The kernel imposes none of these counts or byte bounds; its admission codes above are the restrictions.
