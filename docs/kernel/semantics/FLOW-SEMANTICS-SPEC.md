# Flow semantics

## Status

Adopted kernel owner document (W0 extraction, 2026-11-09). The kernel modules it cites are the executable authority; where they differ, the difference is a defect of one of them.

The flow feature owns how tokens move: starts leaving, gateways, Link Events, and every occurrence's outflow. Its rules live in [Kernel/Feature/Flow.lean](../../../Kernel/Feature/Flow.lean), its admission in [Kernel/Admission/Flow.lean](../../../Kernel/Admission/Flow.lean); it dispatches on the guarded type `GatewayKind` and on `Leave`, and it is the only module that adds flow tokens (`Hooks.outflow`); the closure's work stack, `State.tokens`, also holds deferred begins, `begin` signals moved onto it, which only [multi-instance](MULTI-INSTANCE-SEMANTICS-SPEC.md) stacks, for a parallel body's instances (CIB-OP-0016). Per-token arrival is [Kernel/Step.lean](../../../Kernel/Step.lean)'s `arrive`; throw Events, including None Ends, are [propagation](PROPAGATION-SEMANTICS-SPEC.md); pass-through Tasks are [work](WORK-SEMANTICS-SPEC.md); scope completion is [scopes](SCOPES-SEMANTICS-SPEC.md).

## Interpretation

### Arrival and leaving

- **One occurrence per arriving token.** A token arriving on any incoming flow of any element begins one fresh occurrence of that element, independently of tokens on its other incoming flows; only Parallel and Inclusive joins collect arrivals (BPMN 2.0.2 §13.3.1 uncontrolled flow, the Activity note of §10.3, the Event notes of §10.5 and §10.5.4, the End Event rules of §10.5.3). The merge itself has no occurrence, no micro-step and no publication of its own: each arrival publishes exactly what one arrival at a single-incoming element of the same kind publishes ([IFI basis][ifi-basis], [IFI rules][ifi-rules], [IFI contract][ifi-contract], [NEF basis][nef-basis], [NEF rules][nef-rules], [NEF contract][nef-contract], [AISM basis][aism-basis], [AISM rules][aism-rules], [ACTH basis][acth-basis], [ACTH rules][acth-rules], [PTSM basis][ptsm-basis], [PTSM rules][ptsm-rules]). A second arrival never reuses the first arrival's occurrence.
- **Leaving takes every outgoing flow.** An element that leaves through its own outgoing selection puts one token on every outgoing flow in the micro-step it already is, with no step, position or occurrence for the split: an Activity's completion (§13.3.1 parallel split), a Start Event's start (§10.5.1, §13.2), an embedded Sub-Process's completion, and a pass-through node's activation ([ACSP basis][acsp-basis], [ACSP rules][acsp-rules], [ACSP contract][acsp-contract], [AISM contract][aism-contract], [ACTH contract][acth-contract], [PTSM contract][ptsm-contract]). An element without outgoing flows consumes its token.
- **A split's branch schedule is profile data.** The branches of a split are concurrent and BPMN permits any interleaving of them (§13.3.1, Table 13.1, [BPMN21-429](https://issues.omg.org/issues/BPMN21-429)), so no order among them is the construct's meaning, and a branch that writes a name another branch reads or writes before either waits races with it. `ProfileOptions.branchSchedule` names the schedule a closure gives them (`Step.settle`, `Feature.Flow.queued`), as candidate order is definition data for an Exclusive Gateway:
  - `orderInvariant`, the standards reading: the closure takes queued tokens first in, first out, and admission refuses a split one of whose branches writes a name another branch reads or writes before its next wait, join or end (`flow.concurrentWrite`), or acts on work another branch begins or completes in that closure: it may remove a region holding it (an Error, Escalation or Cancel an interrupting boundary or Event Sub-Process around it catches, a Terminate End, an interrupting Event Sub-Process), resume a Signal subscription it opens, or compensate an Activity it completes (`flow.concurrentInterference`, [#81](https://github.com/mbackschat/bpmn-lean-experiment/issues/81)); both checks also compare the continuations of Signal subscriptions two branches leave open, which one later broadcast resumes in the order this closure opened them ([`Admission.Flow.Concurrency`](../../../Kernel/Admission/Flow/Concurrency.lean)). So the schedule, the order of idle scope completions included, is immaterial for every admitted model; the instances of one parallel Multi-Instance body are refused the same way, by their own footprint and completion (`multiInstance.concurrentInstances`, [multi-instance](MULTI-INSTANCE-SEMANTICS-SPEC.md#restrictions)). A branch's footprint is what the work it runs through in the closure, a Sub-Process's from its entry (its start Events, or without one the children it begins implicitly), reads (input and output mapping sources, a Call's input sources, outgoing conditions, a Multi-Instance definition) and writes (output targets, a Call's outputs, a work's result, a catch's outputs and variables, what a Signal throw's receivers install, a loop's output collection); the closure also runs the catchers a raise or a thrown Error, Escalation or Cancel reaches, the handlers a Compensation throw begins and their continuation, every Signal catch a Signal throw resumes, every Conditional once anything is written, a loop that may run no instance through to its completion, and an interrupted host's outputs. A loop's counters and each instance's items sit in scope occurrences of its own and race nothing. An element it stops at counts only what it reads when it begins. The [closure law](../../../packages/differential/test/closure-reach.integration-test.ts) holds the walk to every committed closure of every admitted scenario: it reaches every occurrence the closure begins and counts every name the closure writes after the input's own installation ([#99](https://github.com/mbackschat/bpmn-lean-experiment/issues/99)). This is a forward-compatible restriction, not a reading of the race: a later profile may take the interleaving as an explicit choice input instead. It is conservative, since it counts a Call's output mappings as written in the closure even when the called instance waits, and a JUEL text as reading every name; it does not count what a waiting element evaluates besides its input mappings and Multi-Instance definition, such as a User Task's assignment expressions; under the standards profile a plain Task has no output parameters (they need [CIB-EXT-0031](../../CIB-BPMN-RELATION-REGISTER.md)), and the refusal reaches none of the 1,568 discovered scenarios under their own profiles (measured 2026-11-12, with CIB-OP-0016 added to both CIB profiles); `flow.concurrentInterference` and the widened `multiInstance.concurrentInstances` change the outcome of none of the 1,732 discovered scenarios (measured 2026-11-13).
  - `declarationDepthFirst`, CIB's schedule, which both CIB profiles select through CIB-OP-0016: the first-declared branch runs first, each to its next wait, join or end, before the next branch starts, so the last-declared branch's write is the one left. CIB reverses a split's outgoing executions (`PvmAtomicOperationTransitionDestroyScope:128-134`) for the LIFO invocation queue of `CommandInvocationContext` (`:95,139`); the kernel queues a split's flows reversed and takes the newest token first. A parallel Multi-Instance body's instances are scheduled the same way: the body defers their begins onto the stack, instance 0 on top, above every token queued before it ([multi-instance](MULTI-INSTANCE-SEMANTICS-SPEC.md)). An idle scope occurrence completes before the next token moves, since CIB ends a Sub-Process in the operation that ends its last execution, before its LIFO queue reaches a sibling branch (`PvmAtomicOperationActivityEnd:105`); `Step.nextToken` withholds the token while one is idle.
  - The reader keeps the program's flows, every `outgoing` list and an Inclusive Gateway's candidates in document order, never identifier order, so a renaming cannot change CIB's answer (PC-BASIC-03). The [split-branch-order](../../../scenarios/open-rows/split-branch-order/README.md) witnesses separate the schedules: `uneven-fork` when the first-declared branch is the longer one, `nested-fork` when a branch splits again, `subprocess-fork` when the first branch is an automatic Sub-Process; the kernel agrees with their retained CIB evidence.
- **An Activity's own selection.** Several outgoing flows of an Activity or Scope form a parallel split, conditioned ones an inclusive split, and a mix of both (§13.3.1, Figure 13.1): its completion takes every outgoing flow whose condition holds or that has none, its default flow only when it takes no other (§10.3.1 `default`), and, when it has outgoing flows but takes none, rolls the command back as an Inclusive split without a match does (Table 13.3, [CIB-INT-0012](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0012--a-diverging-inclusive-gateway-that-selects-no-flow-rolls-its-command-back); CIB `BpmnActivityBehavior#performOutgoingBehavior` throws and rolls back too). An absent condition is always true, the reading [CIB-INT-0005](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0005--an-inclusive-gateway-output-without-a-condition-is-always-taken) gives an Inclusive output. The kernel's `ownFlows` applies this to every element that leaves through its own selection; admission puts a condition only on an Activity's or Scope's non-default flows and on a gateway's candidates (`flow.conditionalOutflow`), so every other element takes all its flows. The standards reading writes an Activity's outputs before its outgoing conditions are evaluated (§13.3.2, `ConditionOrder.afterOutputs`), so a following decision reads the value the completion wrote ([SPC basis][spc-basis], [SPC rules][spc-rules], [SPC contract][spc-contract]); [CIB-INT-0011](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0011--an-activitys-outgoing-conditions-evaluate-before-its-output-writes) selects the reverse order (`ConditionOrder.beforeOutputs`, read by `Hooks.select`). CIB installs a User Task's submitted variables before it leaves and runs its output parameters after, which neither order reproduces alone; the open-rows table lists it under PC-CF-07.
- **Ends and quiescence.** A None End consumes only its own token. A scope occurrence, the process root included, stays live while it holds a token, a blocking open item, a begun occurrence or a child; it completes exactly when the last of those is gone, and the root's completion completes the instance (§10.5.3, §13.5.6). Several None Ends, terminal unjoined forks, and terminal branches that reach their End without a wait are ordinary ([TFK basis][tfk-basis], [TFK rules][tfk-rules], [TFK contract][tfk-contract]).
- **No Sub-Process is required.** The process root is itself a scope; every flow rule holds identically in the root and in a Sub-Process body (§10.2, §10.4.1, §13.2–§13.5) ([SSM basis][ssm-basis], [SSM rules][ssm-rules], [SSM contract][ssm-contract]).
- **Start combinations.** A process has at most one initial start, a None or a Timer Start, and a Sub-Process at most one start, as pinned CIB parses them (`BpmnParse#selectInitial`, `BpmnParse#parseScopeStartEvent`); §10.5.2 admits several Start Events, which lie outside the target (`start.rootCombination`, `start.subProcessCombination`, PC-BASIC-01). Message, Signal and Conditional Starts beside them keep their own accounts.

### Exclusive Gateway

- **Ordered first-true routing.** One arrival consumes its token and puts exactly one token on the first candidate, in the process-level XML `sequenceFlow` declaration order, whose condition is true; no later condition is evaluated and no later branch receives a token; the default is taken exactly when every candidate is false (§13.4.2, Table 13.2, §10.6.2). The number of candidates is unbounded; gateway `<outgoing>` reference order does not matter ([XGW basis][xgw-basis], [XGW rules][xgw-rules], [XCA basis][xca-basis], [XCA rules][xca-rules], [XCA contract][xca-contract]). Candidate order is definition data, never runtime collection order or a host scheduling choice.
- **No match without a default rolls the command back.** When no candidate holds and there is no default, the input whose closure reached the gateway has outcome `rolledBack` with the exact pre-input state: a start creates no instance, a User Task completion leaves the task open with its values, and nothing is published ([XND basis][xnd-basis], [XND rules][xnd-rules], [XND contract][xnd-contract]). An effect result whose closure reaches it rolls back too, or, under `ContinuationFailure.incident`, becomes the effect's technical failure ([Step/Jobs.lean](../../../Kernel/Step/Jobs.lean) `effectContinuation`).
- **Conditions** are evaluated in the kernel by the profile's evaluator against the variables visible from the gateway's scope occurrence at the input's logical time ([Simple Boolean decision](../../SIMPLE-BOOLEAN-EXPRESSION-DECISION.md)); a non-Boolean value is a semantic failure. The first accounts read only Process-scope bindings and refused body gateways for that reason ([IGR scope][igr-scope]); the kernel reads the visible scope chain, the data visibility of §10.4. Source text in another language is never routed to the evaluator by fallback: the old accounts required `Definitions.expressionLanguage` to name the Simple Boolean URI explicitly ([XGW admission][xgw-admission]). The source reader reads a condition with no `language` on it or on its Definitions as JUEL, CIB's default (CIB-EXT-0030): a Simple Boolean profile refuses it as `flow.condition.foreign`, and a JUEL profile evaluates it at the [core level](EXPRESSION-SEMANTICS-SPEC.md).
- **Exclusive merge.** A converging Exclusive Gateway passes each arriving token on at once, without synchronization and without input-order priority (Table 13.2 Simple Merge and Multi-Merge, §10.6.2) ([CYC basis][cyc-basis], [CYC account][cyc-account], [CYC rules][cyc-rules], [CYC decisions][cyc-decisions]). It is lowered as an Exclusive Gateway whose one unconditioned outgoing flow is its sole candidate.
- **Unconditioned flows of a diverging Exclusive Gateway.** A sole unconditioned non-default flow is a candidate whose condition always holds, tried in declaration order like the others, so declared first it is always taken and declared last it acts as a default; CIB's `ExclusiveGatewayActivityBehavior#doLeave` does the same. CIB refuses to parse a second unconditioned non-default flow and an unconditioned flow beside a default (`BpmnParse#validateExclusiveGateway`), and so does the kernel (`gateway.exclusive.unconditionedFlow`); a sole conditioned flow without a default, which CIB also refuses, is `gateway.exclusive.singleConditionWithoutDefault` (PC-CF-02).

### Parallel Gateway

- **Fork** puts one token on every outgoing flow in the micro-step that reaches it (§10.6.4, §13.4.1) ([RPF basis][rpf-basis], [RPF rules][rpf-rules], [PAR rules][par-rules]).
- **Join by incoming-flow provenance.** A join is ready only when every incoming flow holds a token in the same scope occurrence; a count of arrivals without their flow is insufficient. One activation consumes exactly one token per incoming flow, keeps every excess token, and leaves once on its outgoing flows ([PAR rules][par-rules], [PAR CIB][par-cib]). Each joined arrival is its own occurrence: the one that fires leaves with the outgoing flows, the others end with none, as CIB ends one activity instance per joined execution.
- **Order independence.** Completing branch work in either order reaches an equivalent final state and observation; the intermediate observation exposes the remaining wait but never a hidden join offer or token ([PAR rules][par-rules]). When root branches write one Process name, a reader after the join sees the value committed last ([RPF rules][rpf-rules], [RPF contract][rpf-contract]).

### Inclusive Gateway

- **Split.** One arrival evaluates every candidate against the same state and puts one token on every candidate whose condition is true or absent; the default alone when none holds (§10.6.3, Table 13.3). An absent condition is a condition that is always true, for selection, for the default rule and for the exception rule ([CIB-INT-0005](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0005--an-inclusive-gateway-output-without-a-condition-is-always-taken)) ([IGR basis][igr-basis], [IGR rules][igr-rules], [IGR contract][igr-contract], [IGW rules][igw-rules]). Evaluation order is irrelevant (Table 13.3: pure expressions over one state). A gateway that lists no candidates and no default is a pure join and takes all its outgoing flows. A split with neither a true candidate nor a default rolls the command back like the Exclusive case (kernel `inclusiveChoice`; Table 13.3 names only an exception; [CIB-INT-0012](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0012--a-diverging-inclusive-gateway-that-selects-no-flow-rolls-its-command-back)), as CIB's `stuckExecutionException` does.
- **Join.** The join fires once at least one incoming flow holds a token and no token, open item, child scope or other parked arrival still upstream in the same scope occurrence can reach an incoming flow that holds none without passing the gateway; it consumes one token from each filled flow and keeps every excess token. It is admitted wherever an Inclusive Gateway converges (PC-CF-04). The rule is evaluated on every arrival and again whenever a position of its scope occurrence moves, and which positions reach the join is profile data; [Inclusive join activation and reach](#inclusive-join-activation-and-reach) states both. The reviewed accounts selected an occurrence-owned record of the selected branches for structured acyclic regions, where the two rules agree ([IGR basis][igr-basis], [IGW rules][igw-rules], [IGW scope][igw-scope], [CIB-AGR-0017](../../CIB-BPMN-RELATION-REGISTER.md#cib-agr-0017--a-structured-inclusive-join-fires-when-every-selected-branch-has-arrived)). The rule differs from Table 13.3's text in one case, a token that can reach both an empty and a filled incoming flow: Table 13.3 lets the join fire, the kernel keeps it waiting, as CIB does ([BPMN21-450](https://issues.omg.org/issues/BPMN21-450) is open on that clause). It differs from CIB's `InclusiveGatewayActivityBehavior#activatesGateway` in one class, two tokens that can arrive on the same incoming flow: CIB fires once the arrivals reach the incoming count, or waits for any token that can reach the gateway at all, and then joins every arrival; the kernel joins by incoming-flow provenance as its Parallel join does ([CIB-DEV-0001](../../CIB-BPMN-RELATION-REGISTER.md#cib-dev-0001--parallel-join-activates-from-duplicate-arrivals-through-one-incoming-flow)). Unpaired and looping merges, joins fed by a Parallel block and joins whose unselected path is still reachable agree with the retained CIB evidence of [inclusive-join-compositions](../../../scenarios/open-rows/inclusive-join-compositions/README.md) under a JUEL reading of their conditions.

### Inclusive join activation and reach

**Status:** implemented (2026-11-10) after the cold review of the round-6 interpretation; the trigger follows the standards reading under every profile, as decided by the root under the owner's standing direction of 2026-11-10 to decide autonomously, and the reach is the profile option `ProfileOptions.inclusiveJoinReach`.

#### Activation trigger

- **Standards reading.** Table 13.3 (§13.4.3) states when the Inclusive Gateway "is activated": a predicate over the state of its scope occurrence, not an event of arrival. Table 13.2, the Exclusive Gateway's, is the one that speaks of arrival ("Each token arriving … activates"). The predicate can become true without any arrival, when the last position that could reach an empty input ends, is consumed elsewhere or is withdrawn by an interrupting Event; the table claims the General Synchronizing Merge (WCP-38), which needs exactly that. §13.3.5's fixpoint ("no Gateway […] is activated anymore") is the Ad-Hoc Sub-Process's semantics and lists only Parallel and Complex Gateways, so it is at most an analogy. The reading:
  - a parked join is evaluated on each arrival and again whenever the closure is otherwise quiescent: no signal, no token and no idle scope occurrence is left (`Step.reoffer?`, journalled with the `idle` cause of the join's scope occurrence). At that point every position of the scope occurrence is one `Feature.Flow.positions` sees; a completion still queued as a signal is none, so evaluating a join while one is pending would let a downstream join fire before the upstream join's token is on its flow, and fire again when it arrives;
  - every closure passes that point before it ends, whatever removed the last position: an occurrence's completion, a withdrawal by a Boundary Event, or an uncaught business Error that ends its path without an outflow (CIB-INT-0013). So a join whose condition holds fires within the closure in which it first holds, which is stronger than the weak fairness the reading needs (a join whose condition holds from some point on fires eventually);
  - ready joins are independent: when they are offered, the arrivals parked at one join are positions every other join sees, so a join that is ready cannot be reached by another's parked tokens, and firing one cannot keep another waiting. The order in which they are offered (parking order) is therefore immaterial, an obligation of the commutation laws.
- **Why this is not a reach gap.** Literal Table 13.3 counts only tokens on Sequence Flows. In `unselected-path-parked-then-unselected` *Review B* is an active Activity, so the literal join is activated when *Review A* arrives; under the reading that counts Activity-held tokens (the kernel's and CIB's) it is activated when *Review B* ends at *B closed*. CIB fires under neither, so the witness separates CIB from every reach reading, and the disagreement is a deviation, not an interpretation. [BPMN21-450](https://issues.omg.org/issues/BPMN21-450) concerns the "also a directed path" clause, not the trigger, and leaves this reading unchanged.
- **CIB reading.** `InclusiveGatewayActivityBehavior#execute` is the only caller of `activatesGateway`, and only when an execution arrives at the gateway (`:46-52`); an Activity's end only prunes (`PvmAtomicOperationActivityEnd:77-81`, `PvmExecutionImpl:577-603`). Nothing re-examines the executions waiting at the join when another execution ends, so they stay inactive and the instance stays running with no stimulus that resumes it.
- **Classification: candidate deviation [CIB-DEV-0002](../../CIB-BPMN-RELATION-REGISTER.md#cib-dev-0002--a-parked-inclusive-join-is-re-examined-only-when-another-execution-arrives-at-it).** Table 13.3 is a clear requirement that an activated gateway executes, and PC-CF-04 rejects "waiting forever for an unselected path". The [register's classification order](../../CIB-BPMN-RELATION-REGISTER.md#classification-order) excludes the earlier classes:
  - not agreement, and not an operational detail, since it decides whether downstream work ever becomes active;
  - not a gap resolution: the text defines activation by the state and leaves no trigger open, and the witness separates CIB from every reach reading;
  - not an extension or a configuration: no setting changes it;
  - a limitation would hold only if "is activated" were a precondition checked at arrival, which leaves WCP-38 unsupported.
- **Evidence and its limits.** The retained evidence of [`unselected-path-parked-then-unselected`](../../../scenarios/open-rows/inclusive-join-compositions/README.md) shows CIB `running` with no open wait after *Review B* ends. The producer observes tasks, timer jobs and history only, so "no task, job or subscription" holds because the model has no asynchronous step and no message element. The [evidence threshold](../../CIB-BPMN-RELATION-REGISTER.md#evidence-threshold-for-a-confirmed-deviation) is not met (no pristine probe, no owner review), so the entry stays a candidate.
- **Profile option: none.** Following [CIB-DEV-0001](../../CIB-BPMN-RELATION-REGISTER.md#cib-dev-0001--parallel-join-activates-from-duplicate-arrivals-through-one-incoming-flow)'s profile decision, every profile, both CIB profiles included, uses the standards trigger; the cumulative CIB profile claims no compatibility for a join that becomes ready without an arrival, and CIB-DEV-0002 owns the disagreeing evidence, which agreed with the kernel before this change. Reproducing CIB's stall would need a further option selected only by an explicitly separate compatibility profile, which no profile proposes.

#### Reach from a host with Boundary Events

- **Standards reading.** Table 13.3 follows "directed path[s] formed by sequence flow" from a Sequence Flow that holds a token. It leaves open where a token held by an active Activity, a waiting Event or a child scope continues ([CIB-INT-0016](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0016--a-converging-inclusive-gateway-fires-when-no-further-token-of-its-scope-occurrence-can-reach-it)). The standards profile reads such a position as continuing on the element's outgoing flows and on the outgoing flows of its Boundary Events, since an attached Event can still fire and send a token along its exception flow (§10.5.4). An Event-Based Gateway continues on its arms, a throwing Link at its catch, and a child scope after its host.
- **CIB reading.** `isReachable` (`:141-199`) follows outgoing transitions, an Event-Based Gateway's event activities, and the flow scope of an activity without outgoing transitions. It never follows a Boundary Event, which is no outgoing transition of its host.
- **Classification: interpretation of a BPMN gap** (classification order 3). The text defines no continuation for a token an Activity holds, and both readings are operational.
- **Profile option.** `ProfileOptions.inclusiveJoinReach` with the values `withBoundaries` (the standards profile) and `outgoingOnly`, which both CIB profiles select through [CIB-INT-0020](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0020--a-converging-inclusive-gateways-reach-does-not-follow-a-hosts-boundary-events) (`Feature.Flow.leaving`). CIB-INT-0016 stays the shared reading of Activity-held tokens; the standards profile lists it too, so it cannot also select CIB's reach. Under `outgoingOnly` a join can fire while a Boundary Event that reaches it is still armed; when that Event fires later, its token arrives alone at a join that has already fired and fires it again. Until the `boundary-path` evidence is retained, CIB's reach is a prediction from the pinned source, and `boundary-path-parked-then-escalated` is the witness that decides it.

### Event-Based Gateway

- **Deferred choice.** A token reaching the gateway keeps its occurrence open and arms one subscription per configured catch Event, attached to the gateway's occurrence, with no branch token while armed and no half-armed state (§10.6.6, §13.4.4, Table 13.4 Deferred Choice) ([EBG basis][ebg-basis], [EBG rules][ebg-rules]).
- **First admitted trigger wins.** The first matching delivery or Timer firing in the explicit input order completes its arm, completes the gateway with no flows, and so disarms every other arm before the next observation; the losing branch never receives a token. Declaration order, configuration order and evaluator search order never select a winner, and no physical-simultaneity tie-break exists: of two Conditional arms true at one evaluation the input's ranking `conditionChoices` names the winner, and without one the input is dynamic-only `unsupported` (`gateway-arms-simultaneous`, see [subscriptions](SUBSCRIPTIONS-SEMANTICS-SPEC.md#conditions)). A wrong or late stimulus, the loser's included, is rejected with the state unchanged ([EBG rules][ebg-rules]). Arms are reservations: each has a published identity from arming, and its occurrence begins only when it fires.

### Link Events

- A throwing Link continues at the one catching Link of the same name in the same process level or Sub-Process, as if a Sequence Flow connected the throw's predecessor to the catch's successor; the pair adds no wait (§10.5.5, Table 10.89) ([LNK basis][lnk-basis], [LNK rules][lnk-rules], [LNK contract][lnk-contract]). No Link Event publishes an occurrence: the observation contract's [Link exception](PUBLICATION-AND-OBSERVATION-SEMANTICS-SPEC.md#flow-node-occurrences) states the rule, and the kernel's pass-through occurrences of a throw and of a flow-reached catch stay internal. Several throws of one name may target one catch (§10.5.5 "multiple source Link Events"). A catching Link that a Sequence Flow also reaches passes that token on like any intermediate Event; §10.5.5 describes a target without incoming flows but forbids none, and CIB runs it so.

### Cycles

- A Sequence Flow cycle (Table 7.2) re-enters elements with fresh occurrences: each traversal of an element begins an occurrence whose activation is one greater than the previous one of that element in the instance; a command addressed to an earlier activation is rejected with the state unchanged; termination is never asserted, and a schedule that keeps choosing the back-edge keeps the instance running ([CYC rules][cyc-rules], [CYC decisions][cyc-decisions], [CYC selection][cyc-selection]).
- **Closure bound.** The reviewed accounts admitted a cycle only when every cycle crosses an external-stimulus wait, and bounded each resumption's internal closure at admission ([CYC graph admission][cyc-graph], [MTC representation][mtc-representation], [SPC admission][spc-admission]). The kernel has no such admission check. PC-CF-06's declared limit on an automatic burst is `Step.closureBound` micro-steps in one closure: a closure that does not settle within it is `unsupported "closure-bound"`, a stable outcome class, and commits nothing, so no prefix of the burst is observed. CIB runs a burst to its end in one transaction, however long ([CIB-LIM-0016](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0016-pinned-cib-runs-an-automatic-burst-beyond-the-kernels-closure-limit), PC-CF-06). The limit is dynamic: no static check refuses an internal-only cycle before start, since whether a cycle ends depends on its data.

**Status:** interpretation approved with required changes by its cold review (2026-11-10), revised here, and implemented: the reader's QName rule, `reader.eventDefinitionRef` and `source.schema` invariant, and the admission refusals of the facts the IL carries for them. ### References and QName closure

- Pinned CIB qualifies a reference with the Definitions' `targetNamespace` only for `messageRef` (`BpmnParse:1264`) and `signalRef` (`:3542`), through `BpmnParse#resolveName`. It reads prefix bindings only from the root `definitions` (`:388-397`).
- An `errorRef` or `escalationRef` is looked up by its raw text (`:520`, `:533`, `:1217`, `:3146`, `:3375`, `:3632`, `:3673`, `:3689`). As a result:
  - a prefixed or dangling `errorRef` deploys, and CIB uses the literal text as the error code (`:1218`, `:3157`, `:3376`, `:3633`);
  - a prefixed `escalationRef` is refused.
- `bpmn-moddle` resolves a reference by identifier only and reports `unresolved reference <value>`. The reader handles every such warning by one reviewed rule, shared by every profile.
  - **Bound:** the reference is a `messageRef` or `signalRef` written `p:local`; `p` is declared on the root Definitions, bound there to the `targetNamespace` and not declared again below; and `local` is the identifier of an element of the expected type. The reader binds such a reference as CIB does.
  - **Refused:** every other unresolved reference is refused as `source.reference`. This one code covers a dangling identifier, a prefix not declared on the Definitions, a prefix declared again below them, a prefix that names another namespace (an import, outside the target), a prefixed `errorRef` or `escalationRef`, and a reference that resolves to the wrong type.
- CIB's reading of a dangling or prefixed `errorRef` as a literal error code is not imitated. It is a ledger item until a witness retains it.
- Renaming identifiers consistently cannot repair a malformed reference, because its text names no identifier before or after the renaming.
- Witnesses: [event-reference-forms](../../../scenarios/open-rows/event-reference-forms/README.md).
  - `message-ref-qname` is read and agrees with CIB.
  - `message-ref-foreign-prefix`, `typo-message-ref`, its renamed twin and `dangling-signal-ref` are refused as `source.reference`, as CIB refuses them at deployment.

### Preserved inert notation

Inert content is kept only in the exact source bytes, never in the IL, and never changes execution. It covers:
- BPMN DI, `documentation`, Text Annotations, Associations, Groups and Categories, Lanes and Lane Sets;
- names, `gatewayDirection` and the Definitions' `exporter` attributes;
- a User Task's opaque `rendering` content inside its `extensionElements`;
- a root-level EventDefinition, which acts only through an `eventDefinitionRef` the reader refuses.

A construct that has execution meaning in BPMN 2.0.2 or in pinned CIB is never inert: it is either read into the IL or refused with a stable code. An unknown element, attribute or extension stays refused (`reader.unknownElement`, `reader.unknownAttribute`, `reader.unknownExtension`).

### Parser warnings

Every `bpmn-moddle` warning blocks admission as `parser.warning`, with two exceptions:
- a warning raised inside a User Task's opaque `rendering`;
- an unresolved reference, which the QName rule above either binds or refuses as `source.reference`.

Only reviewed reader rules, shared by every profile, make a warning safe.

### XSD validity

**Invariant:** a model the reader admits is valid against the pinned OMG `BPMN20.xsd`. Pinned CIB validates every deployment against its own copy of that schema (`BpmnParse:324`, `DeploymentEntity:46`, `BpmnDeployer:102`). That copy differs from OMG only at `Semantic.xsd` line 149, where it types `calledElement` as `xsd:string`.

**How it is checked.** [`schema.ts`](../../../packages/bpmn-source/src/kernel-reader/schema.ts) walks the exact source bytes, since the parsed tree loses child order and the attribute-or-element form. It walks them against a table that [`scripts/bpmn-schema-table.ts`](../../../scripts/bpmn-schema-table.ts) generates from `BPMN20.xsd` and `Semantic.xsd`. A violation is refused as `source.schema`, after the parse, the references and the containment check, and before the reader reads any element.

**Facets the table covers,** in the BPMN model namespace:
- the root element;
- each element's place in its parent's content model: order, cardinality, required children, substitution groups and wildcards;
- undeclared and required attributes;
- model-namespace attributes, and foreign-namespace attributes outside the attribute wildcard;
- text in element-only content;
- abstract types and `xsi:type`;
- the lexical forms of `xsd:ID`, `xsd:IDREF`, `xsd:QName` (with its prefix bound in scope), `xsd:boolean`, `xsd:integer`, `xsd:int` and the enumerations.

**Facets that earlier codes refuse first or cover:**
- well-formedness: `parser.failure`;
- unknown unqualified attributes or elements, illegal or duplicate identifiers, body text and an unknown `xsi:type`: `parser.warning`;
- an `xsd:IDREF` or reference that names no identifier: `source.reference`;
- a `1` boolean lexeme: `source.ambiguousBoolean`.

**Not covered:** the BPMN DI content, which stays in the exact bytes, and the value range of `xsd:int`.

**Guards.** The [oracle guard](../../../packages/bpmn-source/test/kernel-reader-basic-schema.test.ts) runs [`validate-bpmn-xml.sh`](../../../scripts/validate-bpmn-xml.sh) over:
- one valid case and one invalid case per facet, written only to a temporary directory and so outside the set `verify.sh` validates;
- every package fixture.

It asserts that the reader refuses every rejected document and refuses no valid one as `source.schema`. A second guard locks the committed table to its generator.

**Consequence: a `calledElement` expression is refused.** A `calledElement` written as an expression (`${calleeKey}`) is valid in CIB's schema copy and invalid in OMG's, so it is refused as `source.schema`. This touches PC-SCOPE-03's [binding-dynamic](../../../scenarios/open-rows/call-binding-time/README.md) model; it is listed under the open questions of the track hand-back.

### Diagnostics

Each refusal names:
- its stable code;
- the element identifier, when one exists;
- the offending text as evidence, with the source line for `source.schema`.

The reader runs in passes, in this order:
1. the source bytes;
2. the parse and its warnings;
3. the references;
4. the containment cardinality;
5. the schema;
6. the readable forms, in identifier order;
7. the elements, in document order, compensation handlers and their bodies after the rest;
8. the carried facts.

A model with a single defect therefore refuses with one stable code, and a consistently renamed model refuses with the same code at the renamed element. A model with several defects refuses with the code of its earliest pass, which is not necessarily its first defect in document order.
