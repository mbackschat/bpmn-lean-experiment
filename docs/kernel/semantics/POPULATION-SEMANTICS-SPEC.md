# Population semantics

## Status

Adopted kernel owner document (W0 extraction, 2026-11-09). The kernel modules it cites are the executable authority; where they differ, the difference is a defect of one of them.

`Kernel.Population` ([Lean](../../../Kernel/Population.lean)) owns the mechanisms that span process instances: which instance, definition or start an input reaches. It never changes an instance itself; every input reaches an instance through `Kernel.Step.step`, and a scenario is one ordered list of stimuli mixing instance inputs and population stimuli. It dispatches on no guarded type of its own; it asks `Hooks.correlates` and `Hooks.startsFired` (owned by `Kernel.Feature.Subscriptions`, see [subscriptions](SUBSCRIPTIONS-SEMANTICS-SPEC.md)) for the facts that need one.

## Interpretation

Interpretation M8 (2026-11-11; cold interpretation review approved with required changes R1–R11, folded in here; R1, the population's unit of atomicity, decided by the root as per-receiver commitment). It covers every section below.

### Message key correlation

- Correlation is BPMN 2.0.2 §8.4.2 key- and context-based correlation: a Process `CorrelationSubscription` binds the single `CorrelationProperty` of one `CorrelationKey` to an expression over the Process context, and the current Process values decide the match ([MKC][mkc-normative]). The kernel evaluates the bound criterion when a publication is matched, never when the subscription opens, so a later write to the bound variable changes what matches ([`Subscriptions.correlationMatches`](../../../Kernel/Feature/Subscriptions.lean)).
- The key domain is one non-empty String compared by exact equality; composite, null, empty, Boolean, numeric, structured and collection keys, wildcard and uninitialized matching are outside it ([MKC scope][mkc-scope]). A candidate whose key does not evaluate to a non-empty String is no match.
- Routing is exact-cardinality and fail-closed: exactly one current candidate is delivered to; zero (`noMatch`) or several (`ambiguous`) reject the publication and change no instance. Candidate order never picks a winner and no canonical sort becomes a tie-breaker ([MKC contract][mkc-contract]). The standard expects one active receive per key but does not license the engine to arbitrate when admitted facts contradict that ([MKC][mkc-normative]).
- A publication names a Message channel, or under `MessageNames.addresses` a Message name (CIB-LIM-0022), and carries criteria, an optional payload, variables, an optional business key and a mode (`any`, `executionsOnly`, `startOnly`); it names no process instance or subscription. An optional definition selector resolves to one deployment, `{processKey}` to the key's current deployment and `{deploymentId}` to that deployment, else the publication is `rejected definition-not-deployed`. With a selector the publication inspects only that deployment's instances and starts, so two definitions whose local identifiers agree but whose source digest, overlay or profile differ stay distinct addresses ([MKC contract][mkc-contract]; [CIB-INT-0032](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0032--a-publications-definition-selector-restricts-its-waiting-receivers-too)); without one it reaches every instance and the current deployment of each key ([CIB-INT-0031](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0031--a-triggered-start-reaches-the-current-deployment-of-its-key-unless-the-command-names-one-deployment)).
- Unless start-only, a publication first seeks its receivers: the open Message subscriptions on its channel, or for a name those that resolved that name when they opened, that accept its criteria (`Hooks.correlates`) and, given a business key, belong to an instance with that key, a called instance's own. The sole receiver takes the delivery with the payload and variables at the command's logical time, so the step it causes evaluates `now` and arms Timers from that time; the resolution is `committed {target}`, with a `cascade` when the Signals that step threw reached a receiver. With none, unless executions-only, it seeks its start candidates: the root Message starts on its channel, or whose literal name it is under the deployment's `MessageNames.addresses`. The sole candidate starts an instance with the payload, variables and business key at the command's logical time, under the identity `start:<len>:<commandId>:<len>:<deploymentId>:<len>:<startEvent>`; the resolution is `fanOut` with its one `started` entry, or its `failed` entry when the start step refuses it. Several receivers or several candidates are `ambiguous`, neither `noMatch`. Criteria the reading of any registered deployment refuses refuse the publication before any receiver or start is sought ([`criteriaRefusal`](../../../Kernel/State.lean), [`Population.publish`](../../../Kernel/Population/Messages.lean)): two naming one target are `rejected criteria-duplicate`; under `apiCriteria` a start-only publication carrying a variable criterion is `rejected criteria-start-only`, as CIB fails it, and otherwise a variable criterion whose value CIB's variable query cannot compare is `unsupported correlation-criterion-not-primitive`, where CIB rolls the correlation back before it seeks a start ([CIB-EXT-0025](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0025--message-correlation-by-api-criteria-and-delivered-variables)); under `modeledKey` a target other than a Process variable is `unsupported profile-message-correlation-api-criteria`. The refusal is the command's, never read per receiver as no match. Where a publication falls through to its sole start candidate, a business-key or process-instance criterion under that deployment's `apiCriteria` is `unsupported start-criterion-not-variable` ([`startCriteriaRefusal`](../../../Kernel/State/Criteria.lean)): CIB starts under the criterion's key or ignores the instance, which the kernel does not reproduce; a variable criterion reaches the start, which ignores it as CIB does.
- The selected target rechecks the delivery itself (definition, channel, criteria and payload) before it withdraws the subscription and continues; it never trusts the population's selection ([MKC contract][mkc-contract]; `Subscriptions.admitFiring`). Population commands are numbered in scenario order from 1 and every step result carries its ordinal and logical time. An instance input is no command and takes no ordinal: one that does not commit is an `inputFailures` entry, and one that commits and whose thrown Signals reach a receiver is an `inputCascades` entry `{commandId, entries}` with that cascade. `cascade` and `inputCascades` are present only when non-empty, so a step or an input whose throws reached nobody reports none. The run's ledger keeps each command's result under the digest of its content, its canonical wire form without its logical time `at`, since a retry arrives later than the command it repeats: a command whose identifier the ledger holds with an equal digest answers the recorded resolution again under its own ordinal and time and changes nothing (no rematch, no second start), and one with another digest is `rejected command-content-mismatch`. Only the TypeScript harness computes the digests ([`population-digest.ts`](../../../packages/differential/test/population-digest.ts)) and both kernels take them as given, so the binding of a digest to its content is outside the Lean authority.
- Harness refusals are distinct from results: a malformed scenario is a stable harness code (`population-unknown-definition` for a step naming an undeclared definition, `population-time-backward` for a step time before the previous one, `population-time-mismatch` for an instance step and its stimulus giving different times). A publication to a deployment that does not exist is the `rejected` resolution `definition-not-deployed`; an instance input reaching no deployment, an instance input that does not commit and a delivery its sole candidate refuses are results ([`Population.publish`](../../../Kernel/Population/Messages.lean)).
- The publication contract's capacity and infrastructure arms (queue and ledger capacity before acceptance, `infrastructureIndeterminate` with phase and target, no rematch after a target contradiction) are host contracts of the ingress, not kernel semantics; content-bound command identity is kernel semantics, the ledger above. The kernel reports a sole candidate's refusal as the `failed` resolution with its target and never rematches ([MKC contract][mkc-contract]). Reported as a difference in the hand-back.
- The durable host realizes this routing in its population ingress ([population ingress](../ARCHITECTURE-SPEC.md#population-ingress)): each running instance registers its open Message waits with the ingress, which asks every registered instance for `Population.messageReceivers` at delivery time and delivers to exactly one. The engine API's correlated Message is the publication `executionsOnly` to its definition version's registered deployment, and answers zero receivers as `message.notCorrelated` and several as `message.correlationAmbiguous`, changing no instance. Registrations only narrow whom the ingress asks; the instance's own answer and the target's recheck decide.

### Deployments

- A deploy event deploys one scenario definition at the step's logical time and takes the next deploy ordinal, from 1, as its `deploymentId`; one definition may be deployed several times, each a new deployment. A deployment the reader, the assembly or admission refuses takes its ordinal too and is the result `deploymentRefused` with the refusal's code, never a harness error; it registers nothing ([`Population.deploy`](../../../Kernel/Population/Deploy.lean)).
- Each process key a deployment contains, its root and its own document's processes, takes version 1 + the number of registered deployments that contain that key, so a refused deployment numbers no version. The current deployment of a key is its last registered deployment in step order. A definition no population deployment stamped, as every process of a single-instance program is, is version 1: that program is its one deployment's first.
- A program carries, beside its own processes, copies of other deployments' processes that `bpmn-source`'s assembly stamped with their deployment, key, namespace and source digest. A copy of a later deployment or of a refused one is removed with every element under it and every flow touching them, so a Call binds only callees registered at or before its caller (PC-SCOPE-03). Every other copy must name a registered deployment that contains its key in its namespace from its source, else the deployment is refused as `population.callee.stamp`; it takes that deployment's version of the key. The deployment's own processes and its root take its `deploymentId`; then admission runs.
- Under `MessageNames.addresses` a root Message start name another key's current deployment already subscribes refuses the deployment (`deployment.messageStartName`, [CIB-LIM-0028](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0028--cib-keeps-a-root-message-start-name-unique-across-the-current-deployments-of-all-keys)).

### Start selection

- A root start input selects the start Event it names if its trigger fires it, else the one start its trigger fires, a none trigger firing every none start; several unnamed are `start-ambiguous`, none `no-start-event` ([`Starts.startsFired`](../../../Kernel/Feature/Starts.lean)). Admission refuses a second root None or Timer start (`start.rootCombination`, [CIB-LIM-0007](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0007-pinned-cib-parses-one-initial-start-per-process-and-one-start-per-sub-process)), so no admitted program has several none starts. How a start trigger is admitted and fires is stated in [subscriptions](SUBSCRIPTIONS-SEMANTICS-SPEC.md#starts).

### Timer starts

- A `timerStart` names a Timer-start occurrence by its deployment, start Event and due instant and fires it at the command's logical time. The due instants count from the deployment's logical deploy time: a duration `origin + d`, a date its own instant, the `k`-th period after the origin of a cycle, a Cron match strictly after the origin ([`Timer.occurs`](../../../Kernel/IL/Timer.lean)). It is rejected as `definition-not-deployed` for a deployment that is not registered, `no-start-event` for a start that is not a root Timer start of it, `timer-occurrence-unknown` for an instant the schedule does not name, `timer-not-due` for a firing before it, `timer-start-superseded` when another deployment of the key is current and `timer-start-occurrence-consumed` for an occurrence that already started an instance ([`Population.timerStart`](../../../Kernel/Population/Timers.lean), [CIB-INT-0029](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0029--a-timer-start-counts-from-its-deployment-and-fires-each-occurrence-once-while-the-deployment-is-current)).
- A committed occurrence starts one instance, which takes the firing time and the identity `timer:<len>:<deploymentId>:<len>:<startEvent>:<dueMs>`, as the `fanOut` resolution's one `started` entry, and consumes the occurrence; a start the start step refuses is the `failed` entry and consumes nothing. A single-instance scenario fires a Timer start through the same check, deployed at 0 and on time: the trigger's logical time must be one of the start's due instants.
- Which due instants a host fires after waking late is its catch-up policy, not kernel state (`TSTART-SCHEDULE-01`): the kernel commits any due, unconsumed occurrence of a current deployment. A host reproducing CIB fires the overdue occurrence and then only the first due instant after that firing's time ([CIB-DEV-0008](../../CIB-BPMN-RELATION-REGISTER.md#cib-dev-0008--a-late-cycle-firing-skips-missed-occurrences-and-spends-their-count)).

### Conditional start evaluations

- An `evaluateConditions` evaluates every root Conditional start of the selected deployment, or of each key's current deployment, over the submitted variables alone, as a start input does ([CIB-EXT-0044](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0044--cib-evaluates-a-root-conditional-start-over-the-variables-a-request-submits)). The starts are reached in deploy order, then document order, unless the command's `order` names each of them exactly once ([`Population.evaluateConditions`](../../../Kernel/Population/Conditions.lean)).
- Each start whose predicate holds starts one instance with the business key and every submitted variable at the command's logical time, under `start:<len>:<commandId>:<len>:<deploymentId>:<len>:<startEvent>`, as its `started` entry; a start whose predicate or start step fails is its `failed` entry with its outcome class and code; a false start adds nothing. Each start is its own unit of commitment, so a failing start leaves the others' instances in place ([CIB-INT-0033](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0033--cib-commits-every-receiver-of-one-stimulus-in-one-transaction)). The resolution is the `fanOut` of these entries, `fanOut []` when none held.
- It is rejected as `definition-not-deployed` for a selector naming no registered deployment, `no-conditional-start` for a scope without a root Conditional start and `discovery-order-mismatch` for an `order` that is not a permutation of the starts in scope.

### Signal broadcasts

- A `broadcast` names a Signal address (its `signalRef` under `SignalNames.identifier`, its name under `addresses`) and carries variables, but no business key and no target: it reaches every receiver of its address in one population, and so does each `BroadcastIntent` a committed step leaves in `State.outbox` ([`Population.broadcast`](../../../Kernel/Population/Signals.lean)). Its receivers are the open Signal items of every running instance, of any deployment, whose address matches (`SignalAddress.matches`), and the root Signal starts of each key's current deployment ([CIB-INT-0031](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0031--a-triggered-start-reaches-the-current-deployment-of-its-key-unless-the-command-names-one-deployment)); an intent never reaches its emitter's own State, whose receivers fired inside the throwing step ([propagation](PROPAGATION-SEMANTICS-SPEC.md)).
- Each delivery takes its snapshot of the receivers when it begins, so a receiver armed during it is not reached, and reaches them in the command's `order` when it gives one, else in the defined linearization: waiting catches first, instances by instance identifier and items within an instance in arming order, then starts, deployments in deploy order and starts in document order ([CIB-INT-0030](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0030--a-signal-reaches-a-snapshot-of-its-receivers-waiting-catches-by-instance-before-starts)). Within one State the linearization decides which of two same-Signal catches or Event-Based arms fires when the first one's continuation withdraws the second. An `order` that is not a permutation of the snapshot is `rejected discovery-order-mismatch`.
- A waiting catch takes a delivery through `Step.step` at the command's logical time, its trigger's reach `broadcast` ([subscriptions](SUBSCRIPTIONS-SEMANTICS-SPEC.md#signals)): only the fan-out builds that reach, and every wire form and external ingress decodes a Signal `deliver` as `targeted`, so no caller can pass a targeted delivery off as a broadcast. A start starts its instance with the variables by the start rule, under `start:<len>:<commandId>:<len>:<deploymentId>:<len>:<startEvent>` for a broadcast. A catch withdrawn since the snapshot, read off its instance's open items before its turn and never off a Step failure, is the `skipped` entry; the others are `delivered`, `started` or `failed {target, outcome, code}` entries of the command's `fanOut`, `fanOut []` when nothing receives.
- Under `signalPayload = none` a Signal carries no data, so a broadcast with variables whose snapshot reaches a program under that option is `rejected broadcast-variables-not-admitted` before any receiver, while an intent's receiver there refuses them itself as its `failed` entry; under `variables` each receiver installs them by the catch or start rule.
- Each receiver is its own unit of commitment, and the outcome of the command or step that broadcast or threw never depends on a receiver ([CIB-INT-0033](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0033--cib-commits-every-receiver-of-one-stimulus-in-one-transaction)). After a receiver commits, the intents its step left are delivered next, depth-first, each with its own snapshot, before the next receiver of the enclosing delivery; the cascade of a start a `publish`, `timerStart` or `evaluateConditions` makes likewise follows its `started` entry. A `publish` delivery's and an instance input's intents are delivered the same way after that step commits, never inside it, into `committed`'s `cascade` and the input's `inputCascades` entry, at the command's logical time or, for an instance input, its instance's time after the step; the started instances take the cascade identity with the input's `commandId`. The kernel finishes a thrower's step before another instance receives its Signal ([CIB-INT-0035](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0035--cib-runs-a-throwers-earlier-queued-sibling-branches-after-its-signals-receivers)).
- A start an intent reaches takes `start:<len>:<commandId>:<len>:<deploymentId>:<len>:<startEvent>:<len>:<emitter>`, `commandId` the command or instance input that began the cascade and `<emitter>` the throw's own occurrence `<len>:<processInstanceId>:<len>:<elementId>:<activation>`, its element by public identifier; every length counts UTF-8 bytes ([`Population.cascadeInstanceId`](../../../Kernel/Population/Contract.lean)). A Conditional start is reached only through its own `evaluateConditions`, so it never takes this form.
- One command or instance input reaches at most `cascadeBound` (`Step.closureBound`) receivers, its cascades included; the next one ends the `fanOut` as `failed {target, unsupported, population-cascade-bound}`, and the receivers before it stay committed. The bound is the kernel's own resource bound, not BPMN meaning, and counts what the fan-out reaches: a start's `started` entry counts, so the cascade of a single start may reach `cascadeBound - 1` receivers, while a `publish` delivery's target is not counted and its `committed` cascade may reach `cascadeBound` ([`Population.cascadeCommitted`](../../../Kernel/Population/Signals.lean)); a Conditional start whose predicate is false records no entry and still takes one receiver of the bound ([`Population.fanOutPass`](../../../Kernel/Population/Signals.lean), [`Population.evaluateConditions`](../../../Kernel/Population/Conditions.lean)).
- Engine contract: a Signal broadcast, a thrown Signal and a Conditional start evaluation reach their receivers one at a time. (1) The unit of atomicity is one receiver: each delivery to a waiting catch and each instance start commits or fails on its own; no receiver's failure undoes another receiver or the emitter. (2) The outcome of the command that broadcast, threw or evaluated depends only on its own step; it never waits for or reflects a receiver's outcome. (3) A failing receiver is observable at that receiver: as its `failed` entry with target, outcome class and code in the population result, and on the hosted engine as that receiver's own failure or incident record and in the command's fan-out report, since the emitter's caller already has its answer. (4) Other commands may interleave between two receivers of one broadcast; the order in which receivers were reached is the recorded discovery order. A command's own receivers take it as the explicit input `order`, which replays reproduce; a cascade's receivers take no order input and always follow the linearization above, so a replay reproduces their order by that fixed rule. (5) A retried command is deduplicated by its command identity (the command ledger returns the recorded result whatever the retry's logical time) and by the derived identity of every instance it starts, so a retry never delivers twice or starts a second instance. CIB Seven delivers all receivers in one transaction instead ([CIB-INT-0033](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0033--cib-commits-every-receiver-of-one-stimulus-in-one-transaction)).

## Restrictions

| Refusal code | Refused | Reason or owning row |
|---|---|---|
| `message.correlation.keys` | more than one modeled correlation key on a catch | a compound modeled key; CIB executes no modeled key, so the standards reading `messageCorrelation = modeledKey` stays at one key ([CIB-LIM-0002](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0002-modeled-bpmn-key-and-context-correlation-is-not-executed)) |
| `message.correlation.value` | a criterion bound to anything but a variable read | the key domain above |
| `message.correlation.channel` | a correlated catch without Message, Interface and Operation | the publication addresses an Operation channel |
| `message.correlation.output` | a correlated catch that writes its payload | the payload is the key; it is never written ([MKC scope][mkc-scope]) |
| `message.correlation`, `work.receive.correlation` | a modeled correlation key on a boundary, start or Receive Task | CIB executes no modeled key, so the standards reading `messageCorrelation = modeledKey` stays at catches ([CIB-LIM-0002](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0002-modeled-bpmn-key-and-context-correlation-is-not-executed)); API criteria reach these waits under `apiCriteria` |
| `correlation-key-empty`, `correlation-key-type` (dynamic-only `unsupported`) | a bound key that evaluates to an empty or non-String value | the run's data; no admission can see it |
| `broadcast-variables-not-admitted`, `discovery-order-mismatch` (`rejected`) | a broadcast with variables reaching a program under `signalPayload = none`; an `order` that is no permutation of the snapshot | the broadcast rules above |
| `population-cascade-bound` (dynamic-only `unsupported`) | a receiver past `cascadeBound` in one command | a cascade that does not settle; the bound above |
| `population.callee.stamp`, `deployment.messageStartName` (`deploymentRefused`) | a copy whose stamp no registered deployment matches; a root Message start name another key's current deployment subscribes | the deployment rules above |
| `population-unknown-definition`, `population-time-backward`, `population-time-mismatch`, `instance-id-duplicate` | harness refusals of a population scenario | not semantic outcomes |

Superseded first-profile restrictions: the correlation profile admitted one Collaboration with two sequential catches, one Conversation and key, no Process-context change while the correlated wait is active, and no Message Start, Receive Task, boundary, throw or End correlation ([MKC scope][mkc-scope]). The kernel admits a correlated catch wherever a catch Event is admitted under the codes above and evaluates the criterion against the current state; the remaining exclusions are the codes above or open rows below.
