# Data semantics

## Status

Adopted kernel owner document (W0 extraction, 2026-11-09). The kernel modules it cites are the executable authority; where they differ, the difference is a defect of one of them.

How values are carried, read, copied into Activities and Scopes and written back. [`Kernel.Feature.Data`](../../../Kernel/Feature/Data.lean) owns expression evaluation and is the only writer of variables; it matches on the guarded type `Expression` (`literal`, `simpleBoolean`, `variable`, `juel`, `foreign`) and sends `juel` to [`Kernel.Feature.Data.Juel`](../../../Kernel/Feature/Data/Juel.lean), whose meaning the [expression semantics](EXPRESSION-SEMANTICS-SPEC.md) own. [`Ctx.evaluateMappings`](../../../Kernel/Hooks.lean) evaluates a mapping list by its `MappingDialect` (`dataAssociation`, `ioParameter`, `callVariable`) for every feature. [`Kernel.Admission.Data`](../../../Kernel/Admission/Data.lean) admits expressions and mappings. Activity mediation runs in [`Kernel.Feature.Work`](../../../Kernel/Feature/Work.lean) (see [work semantics](WORK-SEMANTICS-SPEC.md)), Scope mappings in the [scope semantics](SCOPES-SEMANTICS-SPEC.md).

## Interpretation

### Values

- One closed, tagged, recursive value type: String, Null, Boolean, Integer, Decimal, List and Map; each node carries its own type, so heterogeneous collections are values; absence of a variable or Map entry is never Null; it is not arbitrary JSON, a field-schema language or host-object serialization ([decision][pbv-decision], [contract][pbv-contract]). Boolean is distinct from the strings `"true"` and `"false"`, from null and from absence in every decoder, comparator and identity ([BVAL-WIRE-01][bval-rules]); it was chosen as the first non-string value because it widens the union without reinterpreting any accepted value ([selection basis][bval-basis]). The kernel's [`Value`](../../../Kernel/IL/Types.lean) carries these arms and the legacy `stringList`, which stays outside the portable domain at every depth ([contract][pbv-contract]).
- Domains: String is unnormalized Unicode of at most 1,024 UTF-8 bytes; Integer is `0..9007199254740991`; Decimal is `coefficient × 10^-scale` with a signed 64-bit coefficient in canonical spelling and scale `0..6`; Map keys are unique and in strictly increasing Unicode-scalar order. A root value has at most four container levels, 32 members per container, 256 nodes and 16,384 canonical JSON bytes; one over a limit is refused, never truncated ([contract][pbv-contract]). The scenario schema checks only the per-container member count, String length and Decimal spelling, so the kernel checks the whole domain at ingress. Every value an input carries passes the shared predicate `admitValues` ([`Kernel.Hooks`](../../../Kernel/Hooks.lean)) where its owner first reads it, before anything is written. `Step` checks the Start's bindings and a variable update's values. `Work` checks a User Task completion's values, an effect result's outputs and a payload delivered to a Receive Task. `Subscriptions` checks a payload delivered to a catching subscription and a Start trigger's payload or variables. One value outside the domain, at any depth, rejects the whole input with the state unchanged (`value-outside-domain`): a rejected Start creates no instance, and a rejected completion leaves the task open for a later valid one ([PBV-BOUND-01][pbv-ingress]). The legacy `stringList` is admitted only as a whole variable value, within its wire bounds of 32 Strings of at most 1,024 bytes.
- Canonical value JSON has no whitespace, fields in code-point order, unchanged List order and specified Map order; command identity extends the typed tuple recursively ([contract][pbv-contract]). [`Submission.valueBytes`](../../../Kernel/Feature/Work/Submission.lean) measures exactly this encoding.
- Wire integer tokens match `0|[1-9][0-9]*` and their field bound before conversion; malformed encoding, unknown fields, duplicates and noncanonical Decimals or Maps are wire-boundary errors with no typed stimulus ([raw-wire checkpoint][pbv-rawwire], [ingress][pbv-ingress]). The kernel's codec reads a noncanonical Decimal or Map order as a value, which the ingress check then rejects.
- Eligibility is per surface: Start, human completion, payload Message, effect result and Call interface may each take the whole domain; expression evaluation is not widened by it. A well-formed value outside a profile's surface domain is unsupported in a scenario and rejected as a command; absence fails a required input while Null succeeds only where the port permits it; nothing is coerced or defaulted ([ingress][pbv-ingress]). A profile admitting Boolean only at User Task completion is such a surface selection ([BVAL-PROFILE-01][bval-rules]). The kernel keeps no per-surface value domain in `ProfileOptions`: a scenario's values are admitted by the scenario schema, strict decoding and the ingress check.
- CIB evaluates `${name}` mappings to the stored Java object by reference; the project copies by value, and in-place aliasing is outside the domain. Under the default Java serialization a CIB Map, List, Integer or BigDecimal result projects to the portable value of the same mathematical value; other types are outside the domain ([CIB relationship][pbv-cib], [authority][bval-cib]).

### Process data and Start

- A valid Start installs exactly its initial bindings in the fresh root scope before internal closure, and no Activity-local scope; a refused Start installs nothing ([PSTART-INSTALL-01, PSTART-REFUSE-01][pstart-rules], [`State.initial`](../../../Kernel/State.lean)). Binding names are nonempty, unique and canonically ordered at the wire boundary ([data contract][pstart-contract]). Start data changes no node, operation or wait ([consequence][pstart-consequence]).
- Published `variables` are the root scope's bindings only; they survive local cleanup until the instance ends ([SDATA-PROCESS-01, SDATA-OBSERVE-01][sdata-rules]). An Activity-local binding is projected only as an open effect's arguments or an open User Task's inputs ([SDATA-OBSERVE-02][sdata-rules], [required scope][sdata-required]).
- A read resolves from the reading scope occurrence outward; the first scope declaring the name decides, a present null included, otherwise the root ([NSD-READ-01][nsd-rules]). An unknown variable is no value (`unknown-variable`), which each mapping dialect reads below.
- A write resolves outward to the nearest scope occurrence that declares the name, otherwise the instance root when its process declares the name (§10.4.1); it never creates a local or touches another frame ([NSD-WRITE-01][nsd-rules], [`Data.write`](../../../Kernel/Feature/Data.lean)). Any other name is the profile's `UndeclaredWrite`: `refused` (`undeclared-write`) or `atInstanceRoot`, the CIB write.
- The old profiles derived required Start bindings statically: every read not declared by an enclosing input or definitely produced earlier on every path became a required Start binding, and Start without one was `rejected`, so no unavailable read was reachable after an accepted Start ([SBT-AVAILABLE-01][sbt-rules], [NSD-AVAILABLE-01][nsd-profile], [CSD-AVAILABLE-01][csd-admission], [CVM-START-01, CVM-AVAILABLE-01][cvm-profile], [UTL-AVAILABLE-01][utl-admission]) The kernel derives no required binding: `State.initial` accepts any binding list, and an absent source surfaces at run time by its dialect. PC-DATA-09 adopts no static rule: the CIB profiles have none, and the retained `entry-missing` and `call-in-absent` answers are the run-time readings.

### Activity data

- When an Activity is ready its inputs are evaluated once, all against the same enclosing context, before the occurrence's local scope exists, so no input reads a sibling input, whatever the declaration order (§10.4.2, §13.3.2) ([normative account][adin-norm], [SBT-INPUT-01][sbt-rules], [UTL-INIT-01][utl-rules], [`Work.arriveActivity`](../../../Kernel/Feature/Work.lean)).
- A missing binding is unavailable; a present null and an empty string are available and copied unchanged ([normative account][adin-norm]).
- Every mapping list, inputs and outputs alike, is evaluated in document order, left to right, as CIB runs a parameter list one at a time (`BpmnParseUtil.java:89-110`, `IoMapping.java:38-48`); the reader keeps that order in the IL ([`Ctx.evaluateMappingsWith`](../../../Kernel/Hooks.lean)). The first rollback or `unsupported` ends the evaluation, so a later mapping is never reached; an unavailable Data Association source does not end it. A target named twice keeps the value written last ([mapping-order](../../../scenarios/open-rows/mapping-order/README.md)).
- A Data Association whose source is unavailable makes the InputSet unavailable: an occurrence a token began holds that token and waits, with no reevaluation ingress and no progress claim ([runtime contract][adin-runtime], [runtime contract][adio-runtime]). The old account published no started occurrence while waiting ([runtime contract][adin-runtime]); the kernel begins the occurrence before its inputs are evaluated and holds it in `FeatureSlots.held`, the Activity lifecycle's Ready state while its InputSet is unavailable (§13.3.2). An occurrence no token began cannot wait (`started-activity-input-unavailable`).
- An unresolved `camunda:inputParameter`, `outputParameter` or `camunda:in`/`out` `sourceExpression` expression rolls the command back with its evaluation's code (`unknown-variable` for an absent name), never a wait ([CIB-EXT-0024](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0024--an-unresolved-input-or-output-parameter-expression-fails-its-evaluation)).
- Non-empty inputs fill one local scope owned by the complete occurrence identity, never by element, activation, host identity or name; it is disposed with the occurrence, and each activation gets a fresh one ([SDATA-ACTIVITY-01, SDATA-REFUSE-01][sdata-rules], [owner decision][sdata-owner], [UTL-FRESH-01][utl-rules], [`Work.enterLocal`](../../../Kernel/Feature/Work.lean)).
- An effect's arguments are the inputs committed when it opens; a later write, also by a sibling branch, changes no open snapshot ([SBT-SNAPSHOT-01][sbt-rules], [CSSD-SNAPSHOT-01][cssd-rules]). CIB evaluates an `asyncBefore` Service Task's inputs when its job runs, so arguments agree only on schedules where the job runs before the next command commits ([effect argument timing][cssd-norm]).
- Activation does not depend on outputs: an OutputSet constrains completion, not entry ([runtime contract][adout-runtime]). An empty OutputSet means the Activity produces no data and its completion submits nothing ([normative account][adin-norm]).
- A completion or effect result submits exactly the OutputSet: under the standards reading (`OutputContext.submission`) every output mapping evaluates against the submitted values alone, never a captured input or a parent namesake; a missing source is `output-unavailable`, a repeated name `duplicate-output`, a superfluous name `undeclared-output`, each rejected with the state unchanged ([unavailable output][adout-norm], [runtime contract][adio-runtime], [SBT-RESULT-01][sbt-rules], [public contract][sbt-contract], [`Work.completionOutputs`](../../../Kernel/Feature/Work.lean)). One source feeding two targets is one submitted entry; no output mapping means the empty patch ([public contract][sbt-contract]). Under `ResultValues.activityLocals` ([CIB-EXT-0015](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0015--serial-business-task-enclosing-inputs-and-local-results)) a superfluous value in the effect result of a Multi-Instance instance is instead a local discarded with the instance (`Work.unconsumed`); every other effect result and a User Task submission keep the rule above. Under `OutputContext.activityScope` ([CIB-EXT-0031](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0031--an-output-parameter-reads-the-activitys-own-scope)) the mappings read the submitted values first and then the variables visible from the Activity's own scope occurrence, its captured inputs first, as CIB evaluates an output parameter in the Activity's execution (`OutputParameter.java:47`); a source the submission omits but a captured input or an ancestor holds is then available ([`Work.outputScope`](../../../Kernel/Feature/Work.lean)). CIB writes each output into the outer scope before it evaluates the next (`OutputParameter.java:44-52`), so under the same option a later output reads an earlier one's target, unless a submitted value or a local of the Activity's own scope of that name shadows it ([`Ctx.outputReads`](../../../Kernel/Hooks.lean)); under the standards reading every output reads the context before any is written. A value the completion installed through the Activity's frame before its outputs run (a User Task submission under `SubmissionRule.installsVariables`, a decision task's result, the caught Error variables on the mapped Error path) is read where CIB's `setVariable` left it (`AbstractVariableScope.java:331-345`): one whose name the frame holds as a local is that local and shadows; any other reached its nearest owner or the root, so a later output reads an earlier output's write of its name first and the installed value only behind the outputs written so far ([mapping-order](../../../scenarios/open-rows/mapping-order/README.md) `installed-`, `decision-` and `caught-chained-outputs`).
- Outputs are copied to the containing context (§10.4.2), reading §13.3.2's "context of the Activity" as loose wording for it ([normative account][adout-norm], [normative account][adio-norm]). The selected representation is "materialize then copy": the output belongs to the occurrence before it is associated outward, which while-executing outputs and Multi-Instance need; while no construct reads it in between, fill and association are one step ([competing accounts][adout-accounts]).
- A business Error result writes outputs only under `ErrorPathOutputs.mapped`; otherwise its patch must be empty (`error-path-outputs-not-accepted`) ([work](WORK-SEMANTICS-SPEC.md#service-tasks-and-effects)).
- Standard Data Associations select no CIB relation; the reused User Task lifecycle is all CIB contributes ([CIB boundary][adin-cib], [CIB boundary][adio-cib], [CIB boundary][adout-cib]).
- The A12 `CreateDocument` profile (CIB Seven `2.0.0`, distinct from every `2.2.0` profile) binds one delegate expression to a neutral operation: a literal input fills one local binding and the effect's arguments, a successful result carries exactly the one local patch, the output mapping writes one Process variable and the locals stay unobserved; a wrong patch is rejected unchanged. Success alone refines CIB's one-command transaction; no equivalence is claimed for failure, rollback or cancellation ([CDATA rules][cdata-rules], [approved decisions][cdata-approved], [source admission][cdata-source], [required scope][cdata-required]). The A12 source stays outside the repository under EUPL-1.2; repository gates use a project-authored equivalent ([license boundary][cdata-license]).

### User Task completion data

- `SubmissionRule.outputSet` (§10.4.1) applies the OutputSet rule above. Under `SubmissionRule.installsVariables` a User Task without output mappings writes its submitted values outward as Process data, the CIB public completion ([`Work.completeUserTask`](../../../Kernel/Feature/Work.lean)). Submitted data cannot change which step is enabled before completion commits ([runtime consequence][utc-runtime]).
- Under the scope-chain rule (`scopeChainSubmissionBytes`) a submission may name only variables a scope occurrence on the task's chain declares below the instance root, or in a called instance the Call's input targets and output sources, each once; its canonical JSON takes at most the selected bytes (16,384 in the old profile). Anything else is rejected (`submission-duplicate-name`, `submission-undeclared-name`, `submission-value-domain`, `submission-too-large`). The name restriction is profile admission, not CIB behaviour, which would create a root binding ([NSD-TASK-01][nsd-profile], [CVM-TASK-01][cvm-rules], [`Submission.check`](../../../Kernel/Feature/Work/Submission.lean)).
- A mapped User Task's completion may also name its own locals, the task's frame first, and its outputs read the task's own locals, retiring the frame in the same step ([UTL-TASK-01, UTL-OUTPUT-01][utl-rules], [public contract][utl-contract]). Under `SubmissionRule.installsVariables` the values are written from the task's frame (`Work.completeUserTask`), and the scope-chain rule checks the names from that frame outward, so a name only the task declares is admitted and ends with the task, as CIB writes it through the task's scope execution ([scope-chain-task-locals](../../../scenarios/open-rows/scope-data-visibility/README.md)). Under `OutputContext.activityScope` the outputs read the task's own locals, a submitted value of a local's name in that local's place, and a submitted value the frame does not hold behind the outputs already written (CIB-EXT-0031). A completion naming an earlier activation is rejected ([UTL-STALE-01][utl-rules]).
- The kernel publishes an open task's evaluated inputs; name lookup for hosted task detail is a host query, resolving through the task's frame chain and, for a called task, the called root only ([UTL-DETAIL-01][utl-rules], [CVM-OBSERVE-01][cvm-rules]).
- Forms, validation, assignment, task-local transient variables, deletion and A12 task-list behaviour are not completion data ([exclusions][utc-excl], [exclusions][pstart-excl]).

### Scope data

- Each embedded Sub-Process occurrence is a contextual scope whose data lives and is visible within that occurrence and its descendants; two occurrences of one definition own separate data (§10.3.5, §10.4.1). BPMN references data by element identity; name-based declaration, shadowing and nearest-owner writes are the CIB extension [CIB-EXT-0020](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0020--nested-embedded-scope-locals-and-nearest-owner-writes) ([normative basis][nsd-norm], [normative basis][csd-norm]).
- Entry evaluates the Scope's inputs against the parent occurrence's chain before its frame exists; an empty input list installs no frame. Normal completion, and an interruption by a caught Error under `ErrorPathOutputs.mapped`, evaluates the outputs against the occurrence's chain, under `OutputContext.activityScope` each after the earlier ones are written as for an Activity, writes them through the nearest-owner rule from the parent and disposes exactly the completing frame; ancestors keep their bindings ([NSD-INIT-01, NSD-OUTPUT-01, NSD-RETIRE-01][nsd-rules], [CSD-INIT-01, CSD-RETIRE-01][csd-rules]).
- The chain is the live occurrence chain, never the definition chain: a read, write, input or output never consults a frame off the performer's chain, and two live occurrences never share a frame ([CSD-CHAIN-01, CSD-ISOLATE-01][csd-rules], [CSSD-REUSE-01][cssd-rules]).
- Structured values keep multiplicity, order, Map keys, Decimal scale and present nulls through every frame, snapshot, result, called root and restoration; every copy across a boundary is by value ([CSSD-VALUE-01][cssd-rules], [NSD-VALUE-01][nsd-rules], [normative basis][cssd-norm]).
- CIB also runs outputs when a scope is destroyed abnormally; outputs at normal completion only is a restriction, and the abnormal-exit output policy belongs to the interruption and Error rows ([normative basis][nsd-norm]).
- An End and a sibling path's declared Scope entry are unordered by BPMN (§10.5.3, §13.5.6); both orders give one state, data or not ([normative basis][dtb-norm], [DTB-ADMIT-01, DTB-COMMUTE-01][dtb-rules]).
- Every refusal leaves state, frames, waits and snapshots unchanged ([NSD-REFUSE-01][nsd-rules], [CSD-REFUSE-01][csd-rules], [CSSD-REFUSE-01][cssd-rules]).

### Source mapping grammar

- A Service Task binds through its delegate token `${identifier}` to the operation of the same name. An input source is a nonempty literal without `${` or `#{`, or exactly `${identifier}`, read in the containing context before the Activity's own inputs exist; an output source is exactly `${identifier}`. Identifiers exclude the JUEL keywords, the engine-context names (`execution`, `caseExecution`, `task`, `externalTask`, `authenticatedUserId`) and every delegate identifier, which would shadow the handler ([public contract][sbt-contract]). Any other expression is refused (`mapping.expression`) until the M2 JUEL level.
- The serial, mixed-task and business-Error compositions select BPMN authority with classified extensions: [CIB-EXT-0015](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0015--serial-business-task-enclosing-inputs-and-local-results) for enclosing inputs and local results, [CIB-EXT-0016](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0016--cib7-220-caught-business-error-output-mapping) for the caught path ([registration boundary][sbt-registration]).

### Call variable mappings

- BPMN moves data across a Call only through matching Data Inputs and Outputs and gives the called Process its own instance; name-based `camunda:in` and `camunda:out` are the CIB extension [CIB-EXT-0021](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0021--call-variable-mappings-by-name-across-the-instance-boundary), composed with the nearest-owner write ([normative basis][cvm-norm]).
- Invocation evaluates every input against the Call's enclosing chain before the called instance exists; a present value or null is copied, an absent source gives a present null; the called root holds exactly the input targets ([CVM-IN-01][cvm-rules], [`Call.invoke`](../../../Kernel/Feature/Work/Call.lean)).
- While the call is live, called reads and writes end at the called root and never change a caller frame ([CVM-ISOLATE-01][cvm-rules]).
- At normal return every output reads its source from the called root, an absent source giving a present null, and writes by the nearest-owner rule from the Call's enclosing occurrence; all reads precede all writes and the whole return is atomic ([CVM-OUT-01][cvm-rules], [`Call.returnFromCall`](../../../Kernel/Feature/Work/Call.lean)). No called variable stays readable from the caller ([CVM-RETIRE-01][cvm-rules]). Every copy is by value ([value domain][cvm-profile]).
- `calledElement` is bound once, at program assembly, to a carried Process and recorded; recovery and later commands never re-resolve it ([CVM-RESOLVE-01][cvm-profile]).
- No invocation or return can fail after an accepted command; a wrong Start, patch or addressed completion is rejected unchanged ([CVM-REFUSE-01][cvm-rules]).

### Superseded first-profile restrictions

The deleted implementation admitted data only in exact shapes: one Property, one input or output, one InputSet and OutputSet, one Activity type, String or null values, Boolean at completion only, serial chains, definition depth three, eight mappings per Scope, one or two Calls, no forks beside data, mapped User Tasks off forked and called Processes, and `variables="all"`, `sourceExpression`, `local`, business keys and reserved Multi-Instance output targets refused ([input scope][adin-scope], [input/output scope][adio-scope], [output scope][adout-scope], [Boolean scope][bval-scope], [Call mapping scope][cvm-scope], [nested scope][nsd-scope], [concurrent scope][csd-scope], [concurrent scope contract][csd-contract], [concurrent structured scope][cssd-scope], [concurrent structured contract][cssd-contract], [concurrent structured admission][cssd-admission], [terminal branches scope][dtb-scope], [terminal branches admission][dtb-admission], [User Task local scope][utl-scope], [User Task local data][utl-norm], [CreateDocument exclusions][cdata-excluded], [scoped data exclusions][sdata-excluded], [serial scope][sbt-scope], [CVM-ADMIT-01][cvm-rules]). The kernel admits every shape its codes below do not refuse: any number of mappings and values of every arm, mappings only on User and Service Tasks and Scopes, `variables="all"` and business keys refused by [work](WORK-SEMANTICS-SPEC.md#restrictions) codes. A Call output targeting `nrOfInstances`, `nrOfActiveInstances` or `nrOfCompletedInstances`, which CIB drops, is refused as `work.call.multiInstanceCounterOutput` (PC-SCOPE-04).
