# Scopes semantics

## Status

Adopted kernel owner document (W0 extraction, 2026-11-09). The kernel modules it cites are the executable authority; where they differ, the difference is a defect of one of them.

`Kernel.Feature.Scopes` ([Lean](../../../Kernel/Feature/Scopes.lean)) owns the guarded type `ScopeKind` (`embedded`, `transaction`, `eventSubProcess`): entering a Scope, beginning its start Event or implicit children, arming its boundaries and Event Sub-Process starts, and completing it when its scope occurrence is idle. `Kernel.Admission.Scopes` ([Lean](../../../Kernel/Admission/Scopes.lean)) admits it. Idleness, the completion pipeline and generic subtree removal belong to `Kernel.Step` and `Kernel.State`; a Terminate End is dispatched by `Kernel.Feature.Propagation`, which owns `Throw`; Transaction cancellation is stated in [compensation](COMPENSATION-SEMANTICS-SPEC.md); the variables a Scope declares and writes are stated in [data](DATA-SEMANTICS-SPEC.md).

## Interpretation

### Entry and quiescent completion

- An embedded Sub-Process (BPMN 2.0.2 §10.3.5, §13.3.4) is instantiated when a token reaches it: each arrival creates exactly one fresh scope occurrence owned by the arriving occurrence and one entry token in it ([SUBPROC][subproc-normative], [SUBPROC rules][subproc-rules], `NSC-ENTER-01` in [NSC rules][nsc-rules]).
- A Scope without a start Event: under `ScopeStart.implicit` (the standards reading) its entry begins every child Activity and Scope without incoming flow (§13.3.4), and a Gateway or Event among them is refused (`scope.implicitStart`); under `ScopeStart.required` (the cibseven profiles, [CIB-LIM-0024](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0024--cib-needs-a-start-event-in-a-sub-process-and-a-transaction)) an embedded Sub-Process or Transaction without one is refused at admission (`scope.withoutStart`).
- A None End inside the Scope consumes only its own token and completes nothing while the occurrence owns other work (`SUBPROC-END-01`, `NSC-END-01`).
- A scope occurrence completes exactly when it owns no token, no open wait, no begun occurrence and no child scope occurrence, independently of declaration order and of other live occurrences of the same definition; completion removes the occurrence and continues the parent exactly once (`SUBPROC-QUIESCE-01`, `NSC-QUIESCE-01`, `CEA-QUIESCE-01` in [CEA rules][cea-rules]). The kernel's `Step.idle` is that test; a passive item (an Event Sub-Process start subscription) keeps nothing alive and is removed with its scope.
- A join inside a Scope fires only from tokens of its own scope occurrence; a completion in a nested scope never satisfies an outer join early, and work in one branch leaves every sibling unchanged (`NSC-JOIN-01`, `NSC-OUTSIDE-01`). Join semantics are stated in [flow](FLOW-SEMANTICS-SPEC.md).
- Every outgoing flow of a None Start and of a completing Sub-Process receives a token in that one step, with no separate split step or position (BPMN 2.0.2 §10.5.1, §13.3.1, §13.3.4; `SCPH-START-01`, `SCPH-EXIT-01` in [SCPH rules][scph-rules]; [SCPH basis][scph-normative]). The kernel completes a Sub-Process with `Leave.outgoing`, which `Feature.Flow.outflow` turns into one token per outgoing flow.
- A command addressed to a completed or absent occurrence is rejected and changes nothing, before and after its Scope completes (`SUBPROC-REFUSE-01`, `NSC-REFUSE-01`, `CEA-REFUSE-01`).
- Declaration order of children and flows is not semantics ([SUBPROC admission][subproc-admission]).

### Concurrent activations and re-entry

- Each token reaching a Scope creates a fresh occurrence even while another occurrence of the same definition is live, and progress in one occurrence leaves every other occurrence, its tasks and tokens, and outside work unchanged (`CEA-OCCUR-01`, `CEA-ISOLATE-01`; [CEA basis][cea-normative]). Two arrivals through a converging Exclusive Gateway give two passes and two occurrences ([CEA basis][cea-normative]). Occurrences of one element are told apart by their activation number, counted per process instance and element ([CEA contract][cea-profile]).
- A Sequence Flow loop that re-enters a Scope or Call creates a new instance on every traversal (BPMN 2.0.2 Table 7.2, §13.3.4, §10.3.6; [SRE basis][sre-normative]): each traversal's occurrence has an activation one greater than the previous one and no identity is reused (`SRE-FRESH-01` in [SRE rules][sre-rules]); a re-entered Scope holds exactly its inputs evaluated at that entry and no local of an earlier occurrence is readable (`SRE-INIT-01`); values an earlier iteration wrote outward stay until replaced (`SRE-RETAIN-01`); each completion writes its outputs once from its own occurrence (`SRE-OUTPUT-01`); a command or result addressed to an earlier iteration's occurrence is rejected (`SRE-STALE-01`). Re-entry is visible only through activation numbers; the scope occurrence itself is never published ([SRE contract][sre-profile]).

### Terminate End

- A Terminate End (BPMN 2.0.2 §10.5.6, §13.2, §13.5.6, Table 12.22) consumes its token and atomically removes every other live owner in its scope occurrence's subtree, keeping that occurrence, which is then quiescent and completes through the ordinary scope completion; the Terminate End's own occurrence completes normally ([TEND basis][tend-normative], `TEND-REGION-01` in [TEND rules][tend-rules]). The kernel's `Propagation.arriveThrow` clears the scope with `State.clearInside` keeping its own occurrence.
- At the root process level the instance completes without a parent token (`TEND-ROOT-01`); at the process level of a called process the called instance ends and returns to its Call as a Sub-Process does (§13.5.6, §13.3.4). Inside a Sub-Process the reviewed account terminates only that Sub-Process instance (§13.5.6) and continues the parent exactly once through the Sub-Process's ordinary completion (`TEND-NESTED-01`; [TEND account][tend-account]); the kernel reads §13.3.4 and §13.5.6 as leaving the parent's continuation, or the Call's, open (`AbnormalScopeEnd.withoutOutflow`), refuses a program with a Terminate End in a Sub-Process or at a called process's level under that reading, and implements only the normal continuation selected by [CIB-INT-0007](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0007--a-sub-process-left-abnormally-completes-normally), which names both placements. A Terminate End in a Multi-Instance body instance or a non-interrupting Event Sub-Process instance follows [PC-TERMINATE-02](#pc-terminate-02-terminate-inside-called-children-multi-instance-bodies-and-event-sub-process-instances), under the same option.
- Rejected accounts: terminating the root regardless of placement; lowering the Terminate End to the parent's outgoing flow; removing the scope occurrence together with its contents; exposing a half-terminated state ([TEND account][tend-account]). A stale command for cancelled work is rejected (`TEND-REFUSE-01`); termination adds no public field (`TEND-OBSERVE-01`). The pinned CIB cancels the concurrent executions of the flow scope first, in agreement, and no CIB relation is needed ([TEND CIB][tend-cib]).

### Event Sub-Processes

- An Event Sub-Process is dormant outside normal flow, has one triggered start and no incoming or outgoing parent flow (§10.3.5, §10.5.2, §13.5.4); its start subscription is armed when its parent scope occurrence is entered, as a passive item that keeps nothing alive and is removed when the parent completes, and dormant registration creates no scope or flow-node occurrence ([IMESP basis][imesp-source], [IMESP contract][imesp-contract]). The kernel holds the start Event's identity as an unbegun reservation (`Occurrence.begun = false`) and begins it only when the trigger arrives.
- An interrupting start interrupts all non-final ordinary work of the parent, active User Tasks included, while the parent's context is preserved for the handler; this reuses the reviewed Sub-Process interruption reading of §13.3.2 ([IMESP basis][imesp-source]; see [subscriptions](SUBSCRIPTIONS-SEMANTICS-SPEC.md#boundaries)). On delivery the subscription is consumed, ordinary work is cancelled and the handler scope is created in one atomic input; completed history stays completed and no cancelled path can resume ([IMESP contract][imesp-contract]). The kernel clears the parent occurrence, its other Event Sub-Process starts included, keeping the handler occurrence; the parent's own boundaries stay armed until the parent completes.
- When the handler completes it produces no parent token; at the process level the instance then completes ([IMESP contract][imesp-contract]). Ordinary completion before the trigger withdraws the dormant subscription and invents no handler lifecycle. Task completion and delivery are ordered inputs with no BPMN priority: whichever commits first makes the other stale.
- A non-interrupting start leaves the parent's work running; a Message start stays open with its identity and a cycle Timer re-arms ([REPEATABLE scope][rep-scope]); see [subscriptions](SUBSCRIPTIONS-SEMANTICS-SPEC.md#repetition).

### PC-SCOPE-06: exceptional Call return and propagated cancellation

This section owns the contract "Call outputs when a raised event reaches the called root"; [propagation](PROPAGATION-SEMANTICS-SPEC.md) consumes it for PC-ERROR-03 and PC-ESCALATION-03.

**Contract.**

1. Search. An Error or Escalation raised inside a called instance is searched nearest first: the scopes of the called instance outward to its root, the root's own Event Sub-Processes, then the boundaries of the Call Activity in the caller, then onward in the caller, crossing further Calls the same way (BPMN 2.0.2 Table 10.88 Error End "nearest enclosing parent Activity (hierarchically)", §13.3.4 "the Call Activity has the same instantiation and termination semantics as a Sub-Process", §13.5.3). Exact code beats catch-all only within one level, as `Kernel.Feature.Propagation` already does. CIB walks the same order (`tree/ActivityExecutionHierarchyWalker.java:44-73`).
2. Outputs when the search reaches a called root. BPMN 2.0.2 executes a Call's Data Output Associations only when it completes (§10.3.6, §10.4.2, §13.3.4), so under the standards reading (`RaisedCallOutputs.none`) nothing is written into the caller. Under `RaisedCallOutputs.atCalledRoot` (CIB-EXT-0034), each time the search reaches the root scope occurrence of a called instance, the Call's output mappings run against that instance and are written outward from the Call's scope occurrence, as its normal return writes them, whether that level catches, an outer level catches or, once PC-ESCALATION-01 lands, nothing catches (CIB `EscalationEventTest.java:285`, `testPropagateOutputVariablesWithoutCatchEscalation`). CIB: both searches register `tree/OutputVariablesPropagator.java:34-43` as an execution pre-visitor (`bpmn/helper/BpmnExceptionHandler.java:107`, `bpmn/helper/EscalationHandler.java:60`), and the scope finder and the propagator visit the same walked element before the stop condition is tested (`tree/ReferenceWalker.java:89-100`), so the pass happens at the root whether or not the root's own Event Sub-Process catches. Several Call levels pass innermost first, so an outer Call's outputs read what the inner pass wrote (`no-carrier-skips-nested-boundary`: `routeSlot` is the nested `Book` slot). A rethrow from a root Event Sub-Process reaches the root again and passes twice. Under a non-interrupting catch the Call runs on and passes again at each later throw and once more at its normal end (`pvm/runtime/operation/PvmAtomicOperationProcessEnd.java:61`; traceability F3, `Signal.write`). An event caught below the root never reaches it and passes nothing.
3. Order within one crossing. The pass precedes the catcher's code and message variables (`BpmnExceptionHandler.java:111`, the walk, before `:148-154`, which sets them and executes the handler); the Call's own output parameters of an interrupted Call (CIB-EXT-0016) follow when it is destroyed. A raising Service Task inside the called instance runs its output parameters after the pass and the catch variables (`CIB-EXT-0016`), so the pass reads the instance before them. A Call whose catch variable and `camunda:out` target share a name therefore ends with the catch variable where the catch writes it and the output where the output parameters write it, in that order.
4. Busy called root. When the thrower runs directly at a called root that holds another path, the root's own Event Sub-Process catches and the Call has output mappings, CIB's first walked element is, for a thrower that is no CIB scope (an Error or Escalation End Event), the thrower's concurrent execution, not the process-instance execution (`tree/ActivityExecutionHierarchyWalker.java:52-54`), so the walk stops before the propagator sees the root and nothing passes; whether it passes thus rests on CIB's execution tree. A catcher further out, the Call's own boundary included, lets the walk reach the process-instance execution, where the outputs pass (retained `caught-at-busy-called-root`). The kernel refuses that step as dynamic-only `unsupported` with `raise-caught-at-busy-called-root`. A raising Service Task that CIB makes a scope starts the walk at its own execution, which reaches the root's process-instance execution (`:55-58`), so CIB passes there; the refusal is conservative for that class.
5. Caller interruption. An interrupting boundary on the Call, or any removal of its caller region, removes the whole called subtree with its waits, effects and data and passes no output (`pvm/runtime/operation/PvmAtomicOperationDeleteCascade.java:57-64` for a boundary's cancel, `pvm/runtime/PvmExecutionImpl.java:345-359` `clearScope` for a removed region: each deletes the sub-process instance through `deleteCascade`, which runs no `passOutputVariables`). Late commands, deliveries and results addressed into the removed subtree are rejected unchanged; a sibling Call of the same definition and the caller's committed variables survive. This is today's `State.clearInside` (witnesses `timer-interrupts-while-book-called`, `timer-interrupts-after-book-returned` agree).
6. Called Event Sub-Processes. A called process may declare Event Sub-Processes: they are armed when the called root is entered, searched at the root (item 1) and cleared with it. The children of a called root are the called process's process-level elements, not the Call Activity's, in `Kernel.Feature.Subscriptions.armScope` (`Kernel/Registry.lean:37`, `Kernel/Feature/Subscriptions.lean:87-96`) and in `Kernel.Feature.Propagation.eventSubProcesses` (`Kernel/Feature/Propagation.lean:50-52`), both through one `State.childrenOf`. `Work.Call.invoke` arms the root as `Scopes.enter` arms a Sub-Process.

**Register drafts.** New `CIB-EXT-0034 — Call outputs pass when a raised Error or Escalation reaches the called root`: selected bounded extension, items 2–4; boundary: `camunda:out` name mappings of CIB-EXT-0021 only, no `variables="all"`, no delegate mapping; the uncaught-Escalation pass joins with PC-ESCALATION-01; the busy-root case refused. ### PC-TERMINATE-02: Terminate inside called children, Multi-Instance bodies and Event Sub-Process instances

**Contract.** A Terminate End ends the innermost region that holds it and nothing outside it. The region is one scope occurrence: the root of a called instance (BPMN 2.0.2 §13.5.6, process level: "the Process is abnormally terminated—no other ongoing Process instances are affected"; §13.3.4 gives the Call the Sub-Process's termination semantics), the body Sub-Process occurrence of one Multi-Instance instance (§13.5.6, Sub-Process level: "only the affected instance is terminated—no other ongoing Sub-Process instances or higher-level Sub-Process or Process instances are affected"), or one instance of a non-interrupting Event Sub-Process. Its other work is removed atomically, the Terminate's own occurrence completes normally, and a command, delivery or result addressed to removed work is rejected unchanged, before and after a host replacement, since the removed occurrence is gone from the state the continuation carries (`TEND-REFUSE-01`).

What follows is the abnormal-end question CIB-INT-0007 governs for a Sub-Process, at three more placements:

| Placement | Standards reading | CIB 2.2.0 (`abnormalScopeEnd = completesNormally`) |
|---|---|---|
| called instance | the called Process is abnormally terminated (§13.5.6) and the Call with it (§13.3.4); its continuation is open | the process instance ends normally (`bpmn/parser/BpmnParse.java:3170-3173` gives Terminate `INTERRUPT_FLOW_SCOPE`, `pvm/runtime/operation/PvmAtomicOperationInterruptScope.java:29-47` interrupts the flow scope, `bpmn/behavior/TerminateEndEventActivityBehavior.java:35-38` ends it), passes the Call's outputs (`PvmAtomicOperationProcessEnd.java:61`), and the Call leaves on its outgoing flows |
| Multi-Instance body instance | only that instance ends, abnormally; Table 10.30 counts it in `numberOfTerminatedInstances`, apart from `numberOfCompletedInstances`, and §13.3.7 evaluates the completion condition "every time an instance completes", so a terminated instance triggers no evaluation; the Multi-Instance Activity completes when no instance remains active | the instance's Sub-Process completes (`bpmn/behavior/SubProcessActivityBehavior.java:57-58`); the body counts it in `nrOfCompletedInstances` and evaluates the completion condition (`bpmn/behavior/ParallelMultiInstanceActivityBehavior.java:82-96`, `bpmn/behavior/SequentialMultiInstanceActivityBehavior.java:50-53`); CIB keeps no terminated count |
| non-interrupting Event Sub-Process instance | that handler instance ends abnormally; a handler produces no parent token either way (§13.5.4) | the handler instance ends; the host's ordinary work and the other handler instances run on |

The standards reading's open continuation is refused at admission (`profile.abnormalScopeEnd.withoutOutflow`) for all three placements. The kernel needs no new mechanism for the CIB column: `Propagation.arriveThrow` clears the Terminate's scope occurrence keeping its own occurrence, and the ordinary pipeline completes the region (`Hooks.completeCall`, `Hooks.instanceCompleted`, Event Sub-Process completion). "Inner Terminate cannot act like an outer Multi-Instance Cancel boundary" holds because the cleared occurrence is the instance's Sub-Process occurrence, never the Multi-Instance body occurrence.

**Defect and hunk.** Under the standards reading the kernel admits a Terminate End in a called process and returns from the Call normally, silently applying CIB-INT-0007: `AdmissionRegistry.abnormalScope` counts a Terminate only when its `header.parent` is set, and a called process's top-level elements have none. Red: the `terminate-called-child` program under `abnormalScopeEnd = withoutOutflow` is admitted (probe 2026-11-10), while `terminate-event-subprocess-instances` is refused. Green after the hunk, which changes no other scenario's result:

with `programInCalledProcess` added to the registry's `./il/types.js` import, "a Terminate in a Sub-Process or a called process" in the doc comments of `Kernel/Admission/Profile.lean:7-8` and `packages/kernel/src/admission/profile.ts:6`, and the guard row in `packages/kernel/test/admission-refusals-profile.test.ts`: code `profile.abnormalScopeEnd.withoutOutflow`, "reached by a Terminate in a called process", mutating a program whose called process's top-level End terminates under `withoutOutflow`, with the `completesNormally` control.

**Register.** [CIB-INT-0007](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0007--a-sub-process-left-abnormally-completes-normally) covers a Sub-Process, a called process instance, a Multi-Instance body instance and a non-interrupting Event Sub-Process instance left by a Terminate End: each completes normally, and a terminated Multi-Instance instance counts as completed and triggers the completion condition, with no terminated count. PC-MI-12's `numberOfTerminatedInstances` reading (track M5) must agree.

**IL shape.** None. **Refusal codes.** `profile.abnormalScopeEnd.withoutOutflow` also covers a Terminate in a called process. No new code.
