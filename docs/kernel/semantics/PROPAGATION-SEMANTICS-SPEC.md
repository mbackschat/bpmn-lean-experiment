# Propagation semantics

## Status

Adopted kernel owner document (W0 extraction, 2026-11-09). The kernel modules it cites are the executable authority; where they differ, the difference is a defect of one of them.

The propagation feature owns throw Events and the search for a catcher of a raised Error, Escalation or Cancel. Its rules live in [Kernel/Feature/Propagation.lean](../../../Kernel/Feature/Propagation.lean), its admission in [Kernel/Admission/Propagation.lean](../../../Kernel/Admission/Propagation.lean); it dispatches on the guarded types `Throw` and `Raised`. Whether a catch trigger catches a raised event, and with what precedence, is asked of the subscriptions feature through `Ctx.catches` ([subscriptions](SUBSCRIPTIONS-SEMANTICS-SPEC.md)); a Compensation throw and a caught Cancel hand over to [compensation](COMPENSATION-SEMANTICS-SPEC.md); a Terminate End's scope meaning is [scopes](SCOPES-SEMANTICS-SPEC.md); a business error reported by an effect enters here from [work](WORK-SEMANTICS-SPEC.md).

## Interpretation

### Throws without propagation

- **None End** consumes its token ([flow](FLOW-SEMANTICS-SPEC.md)).
- **None Intermediate Throw** has no trigger, so its token moves on at once: its occurrence begins and ends in the micro-step its token arrives, owned by the scope occurrence carrying its path, and one token reaches each outgoing flow (§10.5.4, Table 10.89, §13.5.2) ([NIT basis][nit-basis], [NIT rules][nit-rules], [NIT contract][nit-contract]). Its source kind stays its own (`Header.sourceType`), never a Task or a merge.

### Raising an Error

- **Error End.** An Error End Event consumes its token and raises its Error from the scope occurrence it ran in; it produces no normal outgoing token (§10.5.1: an Error is critical and suspends execution at the throw location). An Error End in an executable Process carries a code; `bpmn-source` refuses one without ([SUBERR basis][suberr-basis], [SUBERR rules][suberr-rules]).
- **Business error from an effect.** A Service Task fault is an interrupting Error and the Activity fails (§13.3.3). An effect result that reports a business error raises the Error with that Activity as its host, so its own boundaries are searched first, unless the Activity is itself an instance of its Multi-Instance loop, whose boundaries belong to the body; an Activity inside an instance of an enclosing Multi-Instance Sub-Process, or inside a called instance of a Multi-Instance Call, is no such instance (`Ctx.runsAsInstance`, [#116](https://github.com/mbackschat/bpmn-lean-experiment/issues/116)). When none catches, the search goes on outward with the Activity still standing. The Activity leaves `raised` once the search has decided (`Propagation.hostLeaves`, `Work.mappedErrorOutputs`): no normal outflow, no compensation retention, journalled as cancelled, and nothing of it is left for a boundary to interrupt ([BERROR basis][berror-basis], [BERROR transition][berror-transition], [BERROR rules][berror-rules], [MTBE contract][mtbe-contract]). Under the standards reading the error path writes no outputs, and a result carrying an output patch is rejected; [CIB-EXT-0004](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0004--caught-error-output-mapping-before-activity-cleanup), [CIB-EXT-0009](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0009---bounded-caught-error-output-mapping-before-activity-cleanup) and [CIB-EXT-0016](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0016--cib7-220-caught-business-error-output-mapping) select `ErrorPathOutputs.mapped`, which evaluates the Activity's output mappings against the reported patch before the Activity is left, so a reported null creates a present null variable ([BERROR owner decisions][berror-decisions]). When the Activity's own boundary catches, the outputs run after its catch variables are set, as CIB sets them on the task's execution before `deleteCascade` destroys it and runs its output parameters (`BpmnExceptionHandler.java:146-154`, `PvmAtomicOperationCancelActivity.java:60`, `ExecutionEntity.java:521-525`): an output reads a catch variable and an output of its name is written after it ([task-caught-outputs](../../../scenarios/open-rows/mapping-order/README.md)). When the search goes on outward, CIB's walk starts at the task's own execution, a scope since the task has output parameters (`BpmnParse.java:4803-4814`), and destroys it only once the catcher starts or the path ends (`BpmnExceptionHandler.java:97-155`), so under the CIB profiles the writes run in this order: each Call output pass at a called root the search visits, innermost first (CIB-EXT-0034); the catcher's code and message variables; the Activity's outputs; the interrupted host's outputs (CIB-EXT-0016); then the catcher begins. Uncaught, the passes precede the Activity's outputs and then the unhandled outcome applies; at a compensation handler the Activity leaves before the handler fails. The Activity's outputs read the caught values where `setVariable` on the event scope's execution left them: behind the Activity's own locals and the locals of every scope between it and the event scope, and never when the event scope lies in another instance (a boundary on a Call, a catcher in a caller). CIB runs the outputs as `deleteCascade` destroys the task (boundary, `PvmAtomicOperationCancelActivity.java:60`, `PvmAtomicOperationDeleteCascade.java:37-66`), as `clearScope` removes its event scope's children (interrupting Event Sub-Process, `PvmAtomicOperationInterruptScope.java:30-48`, `PvmExecutionImpl.java:345-359`) or as `end(true)` ends the path (uncaught, `BpmnExceptionHandler.java:129-137`), each because `skipOutputMappingOnCanceledActivities` keeps its default `false` (`ProcessEngineConfiguration.java:418`, `PvmAtomicOperationDeleteCascadeFireActivityEnd.java:83-89`). A Multi-Instance Activity's own output parameters are refused (`multiInstance.mappings`), as CIB refuses them at deployment (`BpmnParse.java:4855-4857`), so the only outputs a Multi-Instance instance writes on the Error path are a Call's, which pass at the called root ([leaving a called instance](#leaving-a-called-instance-pc-escalation-03-pc-error-03)) and which the Multi-Instance Call witnesses `sequential-child-error` and `parallel-child-error` exercise ([multi-instance-call-activity](../../../scenarios/open-rows/multi-instance-call-activity/README.md)). A technical failure never becomes a business Error ([work](WORK-SEMANTICS-SPEC.md)).
- **Error message.** The optional message travels with the raised Error and is never a matching key. Under the standards reading it is published only in a failure record and never becomes a variable ([BERROR rules][berror-rules]); under the CIB profiles a catcher may write it and the code to named variables (catch variables, below). The open effect publishes neither the error routes it could take nor a future code ([BERROR rules][berror-rules]).

### Finding the catcher

- **Search order** (§10.5.1, §13.5.3, §13.5.4): the boundaries of the Activity that raised the event, when an effect raised it; then, for each scope occurrence from the raising one outward, the Event Sub-Processes declared in that occurrence's element, then the boundaries on that element. The first level that has a catcher wins, so a nearer catch-all precedes a farther exact code; within one level the lowest precedence wins, an exact code before a catch-all, document order breaking ties ([CIB-INT-0010](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0010--at-one-catching-scope-an-event-sub-process-precedes-a-boundary-and-an-exact-code-precedes-a-catch-all)) ([SUBERR rules][suberr-rules], [BERROR basis][berror-basis]). Evaluator list order and source declaration order never pick between levels.
- **Where the search stops.** Under `compensationHandlerFailure = failsInstance` it never passes the scope occurrence of a compensation handler: an Error reaching it uncaught fails the handler ([compensation](COMPENSATION-SEMANTICS-SPEC.md)). Under `propagatesFromTrigger` ([CIB-INT-0038](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0038--cib-propagates-a-compensation-handlers-error-or-escalation-from-the-compensation-trigger), the cibseven profiles) it goes on from the handler context's parent, the scope occurrence the compensation trigger ran in, and an event no catcher takes is handled as one raised there. A Multi-Instance instance's scope occurrence offers no boundaries: they belong to the body, whose scope occurrence is the next one out (`BpmnParse:3291-3295`, §13.5.3). A called instance's root lies inside its Call's scope occurrence, so the search continues to the Call's boundaries and outward.
- **Matching** is by the attached route, never by a Process-wide code lookup: different boundaries may reference one Error, and independent Error declarations may share a code ([MTBE contract][mtbe-contract]).
- **Interruption.** A caught Error cancels the occurrence the boundary hangs on together with everything inside its scope occurrence, sibling waits included, keeps every activation counter monotonic, and puts exactly one token on the boundary's flows in the parent scope (§10.5, §13.5.3; an Error boundary always interrupts, Tables 10.91 and 10.92) ([SUBERR rules][suberr-rules], [BERROR rules][berror-rules]). A command addressed to a cancelled occurrence is rejected with the state unchanged. Under `ErrorPathOutputs.mapped` a Sub-Process that its own Error boundary interrupts first writes its output mappings from its scope occurrence outward, after the catch variables, which those mappings read, as CIB sets the catch variables on the Sub-Process and then runs the mappings when it destroys it (`BpmnExceptionHandler#propagateError:146-154`) ([CIB-EXT-0016](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0016--cib7-220-caught-business-error-output-mapping)).
- **One code, one catcher.** Two interrupting Error boundaries of one host, or two Error Event Sub-Processes of one scope, with the same code are refused under every profile (`boundary.error.duplicateCode`, `scope.eventSubProcess.errorDuplicateCode`), a restriction of the kernel, not the meaning of the construct: §10.5.6 allows one interrupting handler per Event Declaration ("only one Event Sub-Process for the same Event Declaration MUST be modeled", applied to boundary Events alike) and states no precedence between two declarations of one code, and CIB's first in document order (its stable sort by precedence, `BpmnParse.java:3645-3650`) is not adopted. Two catch-alls on one host, or in one scope, catch in document order ([CIB-INT-0010](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0010--at-one-catching-scope-an-event-sub-process-precedes-a-boundary-and-an-exact-code-precedes-a-catch-all)).
- **Catch variables.** BPMN 2.0.2 defines none, and the standards profile refuses `camunda:errorCodeVariable` and `camunda:errorMessageVariable`. The CIB profiles select them (`ErrorCatchVariables.eventScope`, [CIB-EXT-0028](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0028--an-error-catcher-writes-the-caught-code-and-message-to-named-variables)): the code as a String and the message as a String or a present null are written before the catcher begins, from its event scope outward, to the nearest scope occurrence that binds the name and otherwise to the instance root, so they outlive the handler. The event scope is the boundary's host, or the scope occurrence an Event Sub-Process is declared in. A Service Task host is still running when its boundary catches: a variable of a name the task holds, an input local or a reported result value, updates that local and ends with the task, and any other is written from the task outward (`Work.mappedErrorOutputs`).
- **Unhandled Error.** §10.5.1 leaves an Error without a catcher unresolved, and Table 10.88 calls the outcome unspecified, "a common one being termination of the Process instance". The standards profile selects that termination (`UnhandledError.failsInstance`): the input commits, the instance ends `failed` with every token, item and occurrence removed, and its failure record names the Error's code and message and the thrower's occurrence, as a compensation handler's uncaught Error does ([compensation](COMPENSATION-SEMANTICS-SPEC.md)); the standards error path writes nothing. The CIB profiles select CIB's ending of only the throwing path (`UnhandledError.endsThrowingPath`, [CIB-INT-0013](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0013--an-error-that-no-catcher-takes-ends-only-its-throwing-path) under [CIB-CFG-0010](../../CIB-BPMN-RELATION-REGISTER.md#cib-cfg-0010--default-unmatched-bpmn-error-under-cib-seven-220)): the thrower's leave ends its path, writing a Service Task's error-path outputs after every Call output pass, so other paths go on, an enclosing scope completes normally once nothing remains in it, and the instance completes when nothing remains. Where that path is the last one of its instance's root and the thrower has output mappings, CIB rolls the command back; the kernel refuses that run as `unsupported` (`unhandled-error-ends-instance-with-outputs`, [CIB-LIM-0006](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0006-ending-an-instances-last-path-through-an-uncaught-error-rolls-back-when-the-thrower-has-output-parameters)). Inside a called instance the path ends the same way; with nothing left the called instance ends and its Call returns normally, and the root of a called instance counts as an instance root for the rollback refusal (`finance-unlisted-code`). An uncaught Error whose thrower runs anywhere inside a Multi-Instance instance of its own instance is refused as `unsupported` (`unhandled-error-leaves-multi-instance-instance`) until PC-ERROR-03 settles what ending the path does to that instance, even when other paths remain in it; a called instance bounds that search, so a thrower in a called instance under a Multi-Instance Call, or under a Call inside a Multi-Instance Sub-Process, ends its path there and the called instance returns.
- **Unhandled Escalation and Cancel.** An Escalation no catcher takes lets its thrower leave and changes nothing else ([PC-ESCALATION-01](#pc-escalation-01-an-escalation-no-catcher-takes-lets-its-thrower-continue)). For a Cancel no meaning is selected: the input is `unsupported` and commits nothing, since whether a catcher exists depends on where the thrower runs. The reviewed accounts refused an unmatched result as `rejected` and refused a model without a matching handler at admission ([BERROR unhandled][berror-unhandled], [SUBERR rules][suberr-rules]).

### Escalation and Cancel

- An Escalation End or intermediate throw raises its code by the same search; the intermediate throw also continues on its outgoing flows. A caught Escalation interrupts or not as its catcher says; a non-interrupting catch begins its handler and leaves the host running.
- A Cancel End raises Cancel, which only a Cancel boundary catches; on a Transaction it first runs the retained compensation ([compensation](COMPENSATION-SEMANTICS-SPEC.md)).

### Interpretation M9 (draft)

Track M9's [compensation interpretation](COMPENSATION-SEMANTICS-SPEC.md#interpretation-m9) changes where the search stops at a compensation handler: under `compensationHandlerFailure = propagatesFromTrigger` (the cibseven profiles) an Error or Escalation leaving a handler continues the search from the compensation trigger's occurrence, and one no catcher takes follows `unhandledError`; under `failsInstance` (standards) an Error End and an Escalation fail the instance as an effect's Error does (I11, D8). An uncaught Cancel becomes the static refusal `throw.cancel.uncaught` (I13, D10).

### PC-ESCALATION-01: an Escalation no catcher takes lets its thrower continue

**BPMN.** §10.5.1 (trigger propagation): "Escalations are non critical and execution continues at the location of throwing. If no catching Event is found for an error or escalation trigger, this trigger is unresolved." Table 10.88 (Escalation End): "Other active threads are not affected … The behavior of the Process is unspecified if no Activity in the hierarchy has such an Escalation Intermediate Event." Table 8.42 makes `escalationCode` mandatory on an executable throw and optional on a catch, where its absence catches every Escalation.

**CIB 2.2.0.** `ThrowEscalationEventActivityBehavior.java:41-58` runs the search (`EscalationHandler#executeEscalation`, `EscalationHandler.java:50-75`), which starts the catcher's handler synchronously, and then leaves the throw unless the catcher interrupts: an Intermediate throw takes its outgoing flows and an End Event ends its path, catcher or not. Only `EscalationHandler#propagateEscalation:38-44`, which no BPMN throw calls, fails without a catcher. A catcher's `camunda:escalationCodeVariable` (`BpmnParse.java:3681-3699`) receives the code as a String through `setVariable` on the execution of the handler's event scope when it interrupts, and of its flow scope when it does not (`EscalationHandler.java:80-97`): for an Event Sub-Process both are its enclosing scope, for a non-interrupting boundary it is the host's parent scope, not the host.

**Contract (both profiles).**
- A raised Escalation that the search does not catch changes nothing: the input commits, and the thrower's own leave (Intermediate: outgoing flows; End: its token consumed) is the only effect. It never fails the instance, never becomes an Error and never stops another path (CIB-INT-0021). Table 10.88 leaves an uncaught Escalation End unspecified, so the standards profile selects an interpretation, the same one: §10.5.1's "execution continues at the location of throwing" keeps an Escalation non-critical, which failing the instance would not.
- Order: CIB starts the catcher's handler, running it up to its first wait, before the thrower leaves, and the thrower leaves only when the catcher does not interrupt (`ThrowEscalationEventActivityBehavior.java:44-48`); under an interrupting catch, whose interrupted scope always contains the thrower, the thrower ends cancelled with its scope and never completes. The kernel raises first and the thrower leaves afterwards only if its occurrence still stands. The canonical comparison observes the order only through what it changes in state after the input (activation numbers, open waits, variables), not through the occurrence journal, so the retained witnesses pin the observable consequences and the journal's `cancelled` for an interrupted thrower is the kernel's own contract.
- An Escalation that reaches a compensation handler's scope uncaught stays refused (`compensation-handler-escalation`).
- Code variable. The standards profile refuses `event.escalation.codeVariable` (BPMN 2.0.2 defines no catch variables). The CIB profiles admit it under the value that admits the Error catch variables, `ErrorCatchVariables.eventScope` (recommended: widen CIB-EXT-0028 to Escalation, no new option). The code is written as a String before the catcher begins, outward under the set-variable rule (nearest scope occurrence that binds the name, else the instance root): from the host's scope occurrence for an interrupting boundary, from the host's parent for a non-interrupting boundary, from the enclosing scope occurrence for an Event Sub-Process.
- An Escalation whose search walks out of a called instance writes the Call's outputs at each called root it visits, caught or not ([leaving a called instance](#leaving-a-called-instance-pc-escalation-03-pc-error-03)).

**IL.** No shape change: `EscalationTrigger.codeVariable` and `EscalationThrow.code` exist.

**Refusals.** Removed: runtime `unhandled-escalation`. Kept: `compensation-handler-escalation`. `event.escalation.codeVariable` becomes profile-gated.

**Witnesses.** [escalation-uncaught](../../../scenarios/open-rows/escalation-uncaught/README.md) (2), [escalation-code-variable](../../../scenarios/open-rows/escalation-code-variable/README.md) (2); [escalation-throw-propagation](../../../scenarios/open-rows/escalation-throw-propagation/README.md) already agrees. Owed, each needing retained CIB evidence from the root's batched run: code variables of a non-interrupting and of an interrupting boundary whose Sub-Process host holds a local of that name (separating the host from its parent as write origin) and of an Event Sub-Process; an uncaught Escalation inside a called instance whose Call maps an output.

### Leaving a called instance (PC-ESCALATION-03, PC-ERROR-03)

The [scopes semantics](SCOPES-SEMANTICS-SPEC.md#pc-scope-06-exceptional-call-return-and-propagated-cancellation) (PC-SCOPE-06) own this contract and its CIB basis (`OutputVariablesPropagator`, CIB-EXT-0034). What the search consumes:

- Under `RaisedCallOutputs.atCalledRoot` (CIB profiles; `none` under the standards profile, which writes nothing) each time the search for an Error or Escalation reaches the root scope occurrence of a called instance, before any catcher at that or an outer level begins, the search calls `PropagationHooks.callOutputs`, which Kernel.Registry fills from `Work.Call.raisedOutputs` (M4), and the Call's outputs are written. An uncaught Escalation, which goes on to its thrower's leave, passes them the same way.
- A rethrow from a called root's Event Sub-Process reaches that root again and passes again. The PC-ESCALATION-03 clause "Rethrow cannot … map child output twice" binds the standards profile; under the CIB profiles the double pass is CIB-EXT-0034's selected behavior (root decision 2026-11-10; [row amended](../../PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list) 2026-11-11).
- Refused as `unsupported`, dynamic-only: the thrower runs directly at a called root that holds another path, the root's own Event Sub-Process catches, and the Call has output mappings (`raise-caught-at-busy-called-root`). For a thrower that is no CIB scope, an Error or Escalation End Event, the first walked element is the thrower's concurrent execution (`tree/ActivityExecutionHierarchyWalker.java:76-95`, `createTuple` and `getCurrentFlowScope`), so CIB's outcome then rests on its execution tree. A catcher further out, the Call's own boundary included, lets the walk reach the process-instance execution, where the outputs pass (retained `caught-at-busy-called-root`). A raising Service Task that CIB makes a scope (output parameters or a boundary, `BpmnParse.java:3297`, `:4803-4814`) starts the walk at its own execution, which reaches the root's process-instance execution (`:55-58`), so CIB passes the outputs; the refusal is conservative for that class.
- Witnesses: [escalation-call-propagation](../../../scenarios/open-rows/escalation-call-propagation/README.md) (3), [escalation-call-relay](../../../scenarios/open-rows/escalation-call-relay/README.md) (2), [error-called-child](../../../scenarios/open-rows/error-called-child/README.md), [error-called-child-error-data](../../../scenarios/open-rows/error-called-child-error-data/README.md), [error-thrower-leave](../../../scenarios/open-rows/error-thrower-leave/README.md) and, for Multi-Instance hosts, [error-multi-instance](../../../scenarios/open-rows/error-multi-instance/README.md).

### PC-ESCALATION-03: Escalation Event Sub-Processes, rethrow and exceptional output mapping

**BPMN.** §10.5.6 (handling events attached to an Activity): one interrupting handler per Event Declaration, any number of non-interrupting ones, invoked "in a non-deterministic order"; when a Sub-Process has both an inline handler and a boundary for one EventDefinition, a rethrow from the inline handler triggers the boundary, otherwise the handler absorbs the event. §13.5.4: an interrupting Event Sub-Process cancels its enclosing Sub-Process (for a Multi-Instance Activity only the affected instance) and an Escalation puts the parent in Terminating until the handler ends; a non-interrupting one runs beside it.

**CIB 2.2.0.** Escalation definitions are listed on the catching scope: an Event Sub-Process's during its enclosing scope's own parse (`BpmnParse.java:1139-1143`), a boundary's during its host's parent's boundary parse (`BpmnParse.java:3335-3339`, `3652-3656`), so an Event Sub-Process precedes a boundary of the same host, and the finder takes the first matching definition with no exact-before-catch-all rank (`bpmn/helper/EscalationEventDefinitionFinder.java:44-56`). `addEscalationEventDefinition` (`BpmnParse.java:3702-3735`) refuses, among Event Sub-Processes of one scope and among boundaries of one host, two catch-alls, a catch-all beside a coded one and two of one code, so the missing rank never decides. A handler is skipped when its Event Sub-Process is the thrower's direct flow scope (`EscalationEventDefinitionFinder.java:58-61`). An interrupting boundary cancels its host through `deleteCascade` (`pvm/runtime/operation/PvmAtomicOperationCancelActivity.java:60`), whose `destroy` runs the host's output parameters (`persistence/entity/ExecutionEntity.java:521-525`).

**Contract.**
- Both modes, precedence against a boundary, nesting and repeated non-interrupting handlers keep today's search, which the retained [modes](../../../scenarios/open-rows/escalation-event-subprocess-modes/README.md) and [nesting](../../../scenarios/open-rows/escalation-event-subprocess-nesting/README.md) witnesses already agree with. §10.5.6 invokes every non-interrupting handler of one declaration; CIB refuses two of one code at deployment (and among those it admits runs only the first match), a limitation registered as CIB-LIM-0021. The kernel's PC-ESCALATION-02 refusals (`boundary.escalation.duplicate`, `scope.eventSubProcess.escalationDuplicate`) are a restriction under every profile, not an equivalence with BPMN: they keep the one-catcher search from deciding where §10.5.6 would run several. Within what they admit, the exact-before-catch-all rank of `Ctx.catches` never separates two Escalation candidates; CIB-INT-0010's evidence gains the Escalation basis above.
- Rethrow follows the shared rule under [PC-ERROR-02](#pc-error-02-rethrow-from-an-event-sub-process).
- Exceptional output mapping: (1) a Call left by the search writes its outputs at each called root reached ([leaving a called instance](#leaving-a-called-instance-pc-escalation-03-pc-error-03)); (2) under `ErrorPathOutputs.mapped` a Sub-Process or Call that its own interrupting Escalation boundary interrupts writes its `camunda:inputOutput` output parameters after the catch's code variable, exactly as `interruptedOutputs` does for an Error (widen CIB-EXT-0016's boundary to interrupting Escalation catches); CIB's `destroy` runs only those parameters (`ExecutionEntity.java:523-525`), never a Call's `camunda:out`. Output parameters of scopes nested inside an interrupted scope belong to PC-SCOPE-07's interruption cleanup.
- Multi-Instance: a Multi-Instance instance offers no boundaries (they belong to the body); an interrupting Event Sub-Process inside a Multi-Instance Sub-Process interrupts only its instance (§13.5.4). Admission of the Multi-Instance hosts is M5's.

**Refusals.** None new beyond the shared rethrow codes.

**Witnesses.** Modes (5) and nesting (2, the `Wrapper` ⊃ `Core` rethrow among them) agree; call propagation and relay as above, the double pass through a called root's handler ([escalation-call-relay](../../../scenarios/open-rows/escalation-call-relay/README.md)) included; the code variable read by an interrupted host's output parameter, the CIB-EXT-0016 widening ([escalation-catch-write-origin](../../../scenarios/open-rows/escalation-catch-write-origin/README.md)); [escalation-multi-instance](../../../scenarios/open-rows/escalation-multi-instance/README.md) (6), the two Multi-Instance Call hosts included.

### PC-ERROR-02: rethrow from an Event Sub-Process

**BPMN.** §13.5.4: "An Event Sub-Process can optionally re-trigger the Event through which it was triggered, to cause its continuation outside the boundary of the associated Sub-Process. In that case … control passes to the boundary Event"; §10.5.6: a rethrow after completion triggers the boundary, otherwise the handler absorbs the event.

**CIB 2.2.0.** The Error finder skips a handler whose Event Sub-Process is an ancestor flow scope of the thrower at any depth (`bpmn/helper/ErrorDeclarationForProcessInstanceFinder.java:41-58`, `pvm/process/ScopeImpl.java:170-182`); the Escalation finder only when it is the thrower's direct flow scope (above). Neither skips another Event Sub-Process of the same scope, which BPMN's "control passes to the boundary Event" would.

**Contract (both profiles).**
- When the search visits a scope occurrence, an Event Sub-Process declared in its element is no candidate if the raise originates inside an occurrence of that Event Sub-Process held there (the origin's scope chain up to the visited occurrence passes through it). A rethrow therefore goes past the handler that is running, or that an interrupting handler's completion is disposing of, to the next candidate: the host's boundaries at that level, then outward (CIB-INT-0022). Today's search re-catches it: [same-code-rethrow](../../../scenarios/open-rows/error-event-subprocess-rethrow/README.md) reopens `Translate_Raw` where CIB takes `Boundary_Wrapper_Raw`.
- Refused as `unsupported` under every profile, dynamic-only because they depend on the run: an Escalation raised deeper than directly inside an Event Sub-Process that matches it (`escalation-rethrow-reenters-handler`), and a raise from an interrupting handler that a sibling Event Sub-Process of the same scope would catch (`rethrow-caught-by-sibling-handler`). Both are restrictions, never the meaning of the run, and a refused run is refused whole, so admitting either later reinterprets no accepted run:
  - Under `bpmn-2.0.2` both runs have a meaning (§13.5.4). The raise passes the running handler at any depth ("control passes to the boundary Event"), as an Error's already does, and goes on to the host's boundaries and outward. While an interrupting handler runs, its parent is Failing or Terminating and "new Event Handlers MUST NOT be started", so the sibling is not started and the raise goes on past it as well. The two codes are that profile's restrictions of this meaning.
  - Under the CIB profiles: CIB's Escalation finder skips the handler only from its direct flow scope (`EscalationEventDefinitionFinder.java:58-61`), so it catches the deeper raise with that same handler again, re-entering it without bound; and it starts the sibling (`ErrorDeclarationForProcessInstanceFinder.java:41-58` skips only the containing handler), a candidate deviation registered as CIB-DEV-0003. The kernel refuses both runs instead of imitating either.
  - Either way the clause "Rethrow cannot be caught by the same disposed handler" (PC-ESCALATION-03) holds: a refused run is caught by no handler.
- Witnesses owed (retained CIB evidence): an Error End inside an embedded Sub-Process nested in the handler, which CIB skips at any depth (`pvm/process/ScopeImpl.java:170-182`) where it skips an Escalation's handler only from its direct flow scope (`EscalationEventDefinitionFinder.java:58-61`). Kernel tests cover both dynamic refusal codes.
- A non-interrupting Error Event Sub-Process stays refused (`start.error.nonInterrupting`, agreeing with CIB's parse error `BpmnParse.java:1114-1116`).
- A non-interrupting Error boundary stays refused under both profiles (`boundary.error.nonInterrupting`; §13.5.3 and Table 10.90 rule it out). CIB 2.2.0 deploys it and, on a business error, starts the boundary concurrently in the flow scope (`BpmnParse.java:3305-3313`: `CONCURRENT_IN_FLOW_SCOPE`) while the failed Activity's execution stays where it was with nothing left to complete it. That is classified as CIB-LIM-0018 instead of imitated, which moves the ledger owner of [boundary-failure](../../../scenarios/open-rows/error-non-interrupting-declarations/README.md) from PC-ERROR-02 to CIB-LIM-0018. Owed: the same schedule completing `FindSubstitute`, which separates CIB's still-running instance from an interrupting reading (needs regenerated evidence).

**IL.** No change: `ScopeOccurrence.element` and its parent chain identify the Event Sub-Process occurrences on the origin's chain.

### PC-MESSAGE-09: a Message throw performs its send through an effect

**BPMN.** Table 10.88 (Message End) and Table 10.89 (Message Intermediate throw) send a Message to a Participant that a Message Flow may identify (Table 10.1); §13.5.6: "the associated Message is sent for a Message End Event". `tMessageEventDefinition` carries only `messageRef` and `operationRef` (Semantic.xsd:999-1008): beyond an Operation's `implementation`, which the reader does not carry for a throw, BPMN names no sending technology for a throw Event, and a Message Flow names a Participant, not a transport.

**CIB 2.2.0.** A Message throw whose definition declares `camunda:class`, `delegateExpression`, `expression` or `type` is parsed as a Service Task, "same behavior as service task" (CAM-436; `BpmnParse.java:1643-1653`, `3174-3184`); without one it gets `IntermediateThrowNoneEventActivityBehavior` and leaves at once (`BpmnParse.java:1654-1659`, `3185-3189`). Neither reads `messageRef`, `operationRef` or a Message Flow.

**Contract.**
- Bound (`MessageThrow.binding = some b`, only under the CIB profiles, [CIB-EXT-0039](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0039--a-message-throw-performed-by-a-configured-handler), the binding read from `camunda:delegateExpression` and an overlay as for CIB-EXT-0023): the throw's occurrence opens one effect item `{ protocol := b.protocol, operation := b.operation, arguments := [], send := none }`, as a Send Task performed by a configured handler does (CIB-EXT-0023), and waits for its result through `Hooks.effectResult` (Work). Success, which must carry an empty patch since a throw Event has no output mappings, leaves the throw: an Intermediate throw takes its outgoing flows, an End consumes its token. A business failure raises its Error with the throw's occurrence as host, which has no boundaries and writes no outputs, so the search goes on from the throw's scope occurrence as for a Service Task's failure. A technical failure opens an incident under `TechnicalFailure.incident` (CIB-EXT-0013), whose retry reopens the same item: one modeled send occurrence and one activation per arrival. CIB runs the delegate synchronously, so without an asynchronous continuation, which this row does not admit, a technical failure rolls CIB's command back; the kernel keeps its effect lifecycle, an operational mapping classified under CIB-OP-0002.
- The standards profile refuses a bound throw (`throw.message.bound`): a handler binding is a CIB extension attribute. Under the CIB profiles a bound throw whose delegate no binding matches, which the reader carries as an empty operation, is refused (`throw.message.unboundImplementation`): CIB deploys it and fails the throw when it resolves the token ([CIB-LIM-0051](../../CIB-BPMN-RELATION-REGISTER.md#cib-lim-0051--cib-deploys-a-service-task-whose-implementation-no-binding-matches)).
- Unbound (`binding = none`): the standards profile refuses it (`throw.message.unbound`), since passing on would drop the send BPMN requires and nothing names its transport. The CIB profiles pass the token on as a None throw does ([CIB-INT-0027](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0027--an-unbound-message-throw-passes-its-token-on)); one option, `MessageThrowForms` (`refused` | `cibForms`), admits the bound and the unbound CIB forms together. A Message Flow or bare `messageRef` never creates a send in either.
- The throw's Data Input Associations (`MessageThrow.payload`) are refused (`throw.message.payload`): CIB does not execute them, and no row selects a Message payload for a throw.
- Refused on a Message throw under every profile, each with a stable code, since the IL has no field for them and CIB would run them: `camunda:inputOutput` (`throw.message.ioMapping`), `camunda:asyncBefore` and `asyncAfter` (`throw.message.asynchronous`), `camunda:class`, `expression` and `type` (`throw.message.implementation`: only a bound `delegateExpression` is admitted), `camunda:resultVariable` (`throw.message.resultVariable`) and execution listeners (`throw.message.listener`). The reader refuses them with these codes as read refusals. A bound throw's delegate token is `MessageThrow.handlerKey`, which admission compares with the declared names as a Service Task's (`work.handlerKeyName`, CIB-LIM-0017).
- The published source type stays the BPMN tag (`Header.sourceType`), as for the None throw; CIB's activity types (`intermediateMessageThrowEvent`, `messageEndEvent`) lie outside the canonical observation.

**Reader.** `tMessageEventDefinition` has no `implementation` attribute, so `binding.ts#boundBy` matches an event definition's binding on its `delegateExpression` alone, the built-in probe binding included.

**Witnesses.** [message-throw-bound](../../../scenarios/open-rows/message-throw-bound/README.md) (3), [message-throw-unbound](../../../scenarios/open-rows/message-throw-unbound/README.md) (1); [message-throw-retry](../../../scenarios/open-rows/message-throw-retry/README.md) is CIB-EXT-0049's: CIB rolls the starting command back, the kernel opens an incident on the single occurrence.

### PC-SIGNAL-01: a Signal throw and its broadcast intent

**BPMN.** §10.5.1 (publication): a published trigger "MAY be received by any catching Events in any scope of the system where the trigger is published"; Signals serve "broadcast communication within and across Processes". Table 10.88 (Signal End) broadcasts the Signal "to any Process that can receive" it; §13.5.6 sends it at the End. A throw references its Signal by `signalRef` (Table 10.100); the Signal's `name` is descriptive.

**CIB 2.2.0.** `ThrowSignalEventActivityBehavior#execute` (`bpmn/behavior/ThrowSignalEventActivityBehavior.java:46-62`) evaluates, in order, the business key, the payload and the name (lines 48, 49, 51), then calls `eventReceived` on every active subscription of that name in the tenant, start subscriptions and those of other instances included (lines 53-60), and only then leaves (line 61); a receiver whose execution an earlier receiver ended or cancelled is skipped (lines 86-89), and the candidates come from a `HashSet` without order (`persistence/entity/EventSubscriptionManager.java:111-126`). The name is the evaluated `name` attribute of the referenced Signal, an expression where it contains one; duplicate names in one document fail deployment (`BpmnParse.java:474-498`). The payload is the definition's `camunda:in` elements (`BpmnParse.java:4071-4094`): `variables="all"` copies every visible variable, `source` copies one (absent copies a present null: `core/model/CallableElementParameter.java`, `getVariableTyped`), `sourceExpression` evaluates, `local="true"` reads only the throw execution's locals, `businessKey` gives the key. `camunda:async` delivers each receiver in its own job.

**Contract.**
- Evaluation: business key, then payload, then name; the first failure decides. The payload applies the `camunda:in` elements in document order, `variables="all"` at its own position copying every visible variable, a later target replacing an earlier (`VariableMap.put`); the IL carries that position (`SignalThrow.propagateAll : Option Nat`, the index among the mappings; hunk below). An unresolvable name, payload expression or business key rolls the command back (`rolledBack`, as CIB's exception does; [unbound-name](../../../scenarios/open-rows/signal-throw-expression/README.md)), and so does a non-String name or business key (CIB's cast fails, `CallableElement.java:57-61`). A null business key is an absent one. A null name stays `unsupported`, dynamic-only (`signal-name-null`): CIB then matches nothing or fails on an earlier subscription of the same command (`EventSubscriptionManager.java:120-121`). Under the standards profile the name is the literal Signal reference and no expression is admitted.
- Receivers inside the emitter's own kernel State ([CIB-OP-0019](../../CIB-BPMN-RELATION-REGISTER.md#cib-op-0019--a-signal-throws-own-state-receivers-fire-inside-the-throwing-step-the-others-through-its-broadcast-intent), with PC-SIGNAL-02's catch side). Own State is the root instance tree: the emitter's instance, its called instances and, when the emitter runs in a called instance, its callers. CIB takes its receiver list before it delivers to any (`ThrowSignalEventActivityBehavior.java:53-56`), so a receiver armed during the delivery, a re-armed catch of the same name included, is not delivered. Every listed open item whose `kind.view.signal` matches the evaluated address (`SignalAddress.matches`) is fired through `Signal.fire` before the thrower's completion, with the payload as its variables, an item gone by its turn being skipped (lines 86-89), and the thrower leaves only if its occurrence still stands, so a receiver's continuation that removes the thrower leaves no continuation of it. The receivers are taken by process instance, then in arming order, a kernel choice for an order CIB leaves undefined (a `HashSet`); the order across States is PC-SIGNAL-04's.
- Intent: each throw appends exactly one `BroadcastIntent { address, variables, businessKey, origin }` to `State.outbox`, in throw order. It is published only with a committed input, and a rolled-back or rejected input publishes none.
- Population boundary (M8, PC-SIGNAL-02 and PC-SIGNAL-04): the population layer delivers each committed intent to the receivers of every other kernel State and to Signal starts; the emitter's own State is never delivered again. Discovery order across instances, the tenant boundary and atomicity are PC-SIGNAL-04's. The own-State split is an operational mapping (CIB-OP-0019); across instances CIB delivers inside the throwing transaction before the thrower leaves, where the kernel commits each receiver on its own ([CIB-INT-0033](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0033--cib-commits-every-receiver-of-one-stimulus-in-one-transaction)) after the thrower's step ([CIB-INT-0035](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0035--cib-runs-a-throwers-earlier-queued-sibling-branches-after-its-signals-receivers)).
- Refused: `throw.signal.asynchronous` (`camunda:async`: delivery in separate jobs, not this row), `throw.signal.localVariables` (`local="true"` on any `camunda:in`: which locals the throw's execution holds depends on CIB's execution tree; the reader sets `localOnly` for a single `local` copy too, which it now only reports as not carried), and `throw.signal.dataInput` under every profile (the throw's Data Input Associations, `SignalThrow.payload` read from them, which CIB never executes and no row selects); under `signalPayload = none`, where a Signal carries no data, the `camunda:in` copies (`throw.signal.payload`) and the business key (`throw.signal.businessKey`), which [CIB-EXT-0040](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0040--a-signal-throw-carries-camundain-variables-and-a-business-key) admits under `variables`, as it admits a business key expression read at the Events level. The address is admitted as a catch's is (`signal.unspecified`, `signal.unnamed`, `signal.nameExpression`; [CIB-INT-0028](../../CIB-BPMN-RELATION-REGISTER.md#cib-int-0028--a-signal-is-addressed-by-its-name), [CIB-EXT-0041](../../CIB-BPMN-RELATION-REGISTER.md#cib-ext-0041--a-signal-name-is-evaluated-as-an-expression)).

**Shape hunks** (shape commit, shared files): `SignalThrow.propagateAll : Option Nat` replacing the Boolean, with its codec and the reader; `Step.step` empties `State.outbox` when an input begins, as it empties the journal; `Kernel.Publish`'s host view and the canonical `state` observation gain `broadcasts`, a kernel-only member the comparator drops as it drops `scopes` (CIB cannot observe an intent beyond its receivers); `Fired.signal` carries the payload as variables, since `DeliveryInput.payload : Option Value` holds one value.

**Dependencies.** Every retained witness ([literal](../../../scenarios/open-rows/signal-throw-literal/README.md), [expression](../../../scenarios/open-rows/signal-throw-expression/README.md), [payload](../../../scenarios/open-rows/signal-throw-payload/README.md)) observes the throw only through same-instance intermediate catches, so the row closes jointly with PC-SIGNAL-02's intermediate catch ([subscriptions](SUBSCRIPTIONS-SEMANTICS-SPEC.md#signals)). The reader carries a Signal's `signalRef` as a QName and its `name` as a value source (`events.ts#signalAddress`) for throws and catches alike.
