# Call variable mapping specification

## Status

Lifecycle: implemented
Review: closure-approved

## Question and delivery boundary

Can a business process hand named values to a reusable called Process through CIB Seven's `camunda:in` and `camunda:out` mappings, keep the caller's and callee's data isolated while the call is live, and receive the declared outputs exactly at normal return, with an absent source and a present null kept apart where CIB keeps them apart?

This specification closes `PC-SCOPE-04` from the [coverage checklist](../PRACTICAL-CIB7-COVERAGE-TARGET.md#embedded-sub-processes-and-calls). It serves the normal-return clause of that row, restricted to one serial call, and these called-owner clauses: `PC-DATA-04` caller/callee visibility and exact called lifetime; `PC-DATA-05` reference input mappings at Call entry that all read the same pre-entry context; `PC-DATA-06` distinct sources and shared-source fanout to differently named targets with atomic commit. For Call outputs it selects one CIB exception to `PC-DATA-06`: a missing source writes a present null instead of changing nothing, as recorded under `CVM-OUT-01`. Exceptional return and propagated output stay with `PC-SCOPE-06`, `PC-ERROR-03` and `PC-ESCALATION-03`; repeated, nested and concurrent calls with `PC-SCOPE-05`; the general called-definition resolution and version policy with `PC-SCOPE-03`; expression mappings with `PC-DATA-05` and `PC-DATA-07`. This increment proceeds ahead of `PC-SCOPE-03` with in-document key equality only (`CVM-RESOLVE-01`), the degenerate case that policy must preserve for the CIB overlay; the checklist records that obligation on `PC-SCOPE-03`.

The existing [Call data account](CALL-ACTIVITY-DATA-BOUNDARIES-PROPOSAL.md) is the vendor-neutral BPMN account of scalar Call ports and selects no CIB data relationship. This specification neither changes nor supersedes it: the two accounts answer different questions, for different profiles, and share only the Call control mechanism of the [Call specification](CALL-ACTIVITY-SPEC.md). BPMN Call data ports are no part of this CIB account: CIB `2.2.0`'s `parseCallActivity` reads no `ioSpecification` or data association (`BpmnParse.java:3927-4011`), so they stay with that vendor-neutral account.

## Normative basis and CIB classification

BPMN 2.0.2 Clause 10.3.6 transfers data into and out of a called Process only through matching Call Activity and CallableElement inputs and outputs, and Clause 13.3.4 gives the called Process its own instance, so BPMN has no name-based transfer and no inheritance of caller data. Name-based mapping is therefore a CIB extension layered on the BPMN Call lifecycle, not a reinterpretation of it.

CIB Seven `2.2.0` (tag `v2.2.0`, commit `834a987`; every file cited here is unchanged at the pinned `5a45b47`) implements the extension as follows. Paths abbreviate `engine/src/main/java/org/cibseven/bpm/engine/impl` as `E`.

- Parsing: `E/bpmn/parser/BpmnParse.java:4071-4182` reads `camunda:in` and `camunda:out`; `source` wins silently over `sourceExpression`, and under the default strict validation a missing or empty `source`/`sourceExpression` or `target` is a parse error (`BpmnParse.java:4143-4176`).
- Input: `E/bpmn/behavior/CallableElementActivityBehavior.java:115-130` evaluates every input in document order against the Call Activity's execution before the called instance starts, and `CallActivityBehavior.java:55-64` starts it with exactly that variable map. `E/core/model/CallableElementParameter.java:42-66` reads a constant `source` with `getVariableTyped`, which returns null for a missing name, so the target is created with a present null (`CallActivityTest.java:521-559`).
- Isolation: the called instance's parent variable scope is null (`E/pvm/runtime/PvmExecutionImpl.java:1697-1699`), so nothing outside the mapped variables is visible to it and a called namesake is a distinct binding; a change to a called variable leaves the mapped caller variable unchanged until return (`CallActivityTest.java:313-337`, with distinct names).
- Output: `CallableElementActivityBehavior.java:133-150` reads every output from the called process-instance scope at normal end (`E/pvm/runtime/operation/PvmAtomicOperationProcessEnd.java:57-62`) and writes them with `setVariables` on the Call Activity's execution, which updates the nearest existing binding in the caller hierarchy and otherwise creates it at the caller Process (`E/core/variable/scope/AbstractVariableScope.java:327-346`). A source the callee never set therefore overwrites the caller target with a present null (`CallActivityTest.java:642-663`). Before writing, `CallableElementActivityBehavior.java:48,136,160-166` silently drops outputs whose target is `nrOfInstances`, `nrOfActiveInstances` or `nrOfCompletedInstances`.
- Resolution: `BpmnParse.java:3934` reads `calledElement` as a raw deployment key, although BPMN types the attribute as `xsd:QName`, under which an unprefixed value would resolve through the default namespace rather than name an in-document Process.
- Typed values and transient flags survive both directions; a typed null keeps its type (`CallActivityTest.java:376-451`, `1840-1897`).

`CIB-EXT-0021` records this account and is registered with the profile metadata and its verifier coverage. It covers both the mappings and the key reading of `calledElement`: the profile admits only a key equal to the other in-document Process's `id` and claims no BPMN QName resolution for it. It composes with the nearest-owner write of `CIB-EXT-0020` in the [relation register](../CIB-BPMN-RELATION-REGISTER.md) without changing that entry. CIB also runs outputs when an Error or Escalation leaves the called instance (`E/tree/OutputVariablesPropagator.java:36-43`, `CallActivityTest.java:1315-1425`); this profile admits no exceptional exit, so outputs at normal return are an admission restriction and `PC-SCOPE-06` decides the exceptional output policy.

## Required, optional and excluded scope

Required: one `Definitions` document with exactly two private executable Processes, a caller and a called Process. The caller is any model the nested scope-data profile admits without a Call, extended by exactly one Call Activity placed on the serial path of the caller's root. The called Process is one serial path from a None Start through one to three User Tasks to a None End. The Call Activity carries `calledElement` equal to the called Process's `id`, at least one `camunda:in` and at most eight, and at most eight `camunda:out`, each with exactly a nonempty `source` and a nonempty `target`. No output target is `nrOfInstances`, `nrOfActiveInstances` or `nrOfCompletedInstances`, since CIB drops those outputs.

Optional: a caller Process binding or frame local with the same name as a called variable; one source mapped to several targets; Call input targets that the called Process never reads.

Excluded: `sourceExpression`, `variables="all"`, `local="true"`, `businessKey`, `camunda:inputOutput` on the Call Activity, `camunda:variableMappingClass` and `camunda:variableMappingDelegateExpression`, the `calledElementBinding`, `calledElementVersion`, `calledElementVersionTag` and `calledElementTenantId` attributes, a prefixed or foreign `calledElement`, duplicate input targets or duplicate output targets on one Call, any data, boundary Event, loop or Multi-Instance on the Call Activity, called Processes with Sub-Processes, Service Tasks, Gateways or a second Call, more than one Call per caller, a Call inside an embedded Sub-Process, exceptional return, cancellation and the non-strict CIB validation configuration. These bound admission only; the representation below admits repeated, nested and concurrent calls later without reinterpreting accepted models.

## Profile and value domain

Profile family: the mapping is data flow across a scope boundary, and the nested scope-data profile already owns the CIB name-resolution account, the value domain and the Start and completion-patch policies it needs, while the embedded completion profile carries no data. The `DATA` family's cumulative profile `cibseven-2.2.0-nested-embedded-scope-data-draft` therefore grows in place under the [cumulative profile rule](../../contracts/README.md): every model it admits without a Call keeps its exact admission, commands and observations, and only models with one Call become additionally admissible. The `SCOPE` family's embedded completion profile is unchanged.

Values stay `SingletonBusinessItem` from the [portable values capsule](PORTABLE-BUSINESS-VALUES-PROPOSAL.md#public-value-contract) with the 1,024-byte root-String bound, at every surface the [nested scope-data profile](NESTED-EMBEDDED-SCOPE-DATA-SPEC.md#profile-and-value-domain) defines and at both mapping directions. Every copy across the instance boundary is by value.

`CVM-START-01`: Start keeps the required bindings of `NSD-AVAILABLE-01` and additionally admits, optionally and at most once each, a binding for every Call input source and every Call output target that resolves to the Process binding, that is, one no enclosing frame of the Call declares and no earlier step definitely produces. Because an absent input source yields a present null by `CVM-IN-01`, no Call input makes a Start binding required. Any other name is `rejected`. CIB accepts any Start variable; the name restriction is a profile admission restriction.

`CVM-AVAILABLE-01` amends `NSD-AVAILABLE-01`: every Call output target is a definite write at its statically resolved owner, the nearest enclosing scope of the Call that declares the target or otherwise the Process, because `CVM-OUT-01` always writes, with a present null for a missing source.

`CVM-RESOLVE-01`: admission binds `calledElement` to the other executable Process of the same document by exact identifier equality and records that binding in the Program's definition forest. CIB resolves the key to the latest deployed version, which is this co-deployed definition when both Processes are deployed together; recovery and every later command use the recorded binding and never resolve again. `PC-SCOPE-03` owns every other selector.

## Representation and runtime ownership

The checked Call node and the paired `invokeProcess` and `returnProcess` operations already carry the closed `data` variant introduced by the [Call data account](CALL-ACTIVITY-DATA-BOUNDARIES-PROPOSAL.md#checked-representation-and-runtime-ownership), with arms `empty` and `scalar`. A third arm, `variableMappings`, carries `inputs: VariableMapping[]` and `outputs: VariableMapping[]` in document order, since CIB evaluates them in that order, reusing the existing `VariableMapping = { target, expression }` of the [value contract](../../packages/semantic-core/src/semantic-value-contract.ts). An input's expression is `enclosingVariable(source)`, read from the Call's enclosing chain; an output's is `localVariable(source)`, read from the called-root frame. A later `sourceExpression` adds an expression arm under `PC-DATA-05`/`PC-DATA-07` without reinterpreting either. Lowering copies both lists exactly; pairing compares the complete arm; the empty and scalar arms keep their meaning and every existing Program stays byte-identical.

The called Process instance's variables live in one frame of the existing occurrence-keyed `variables.scopes`, owned by the called root occurrence. That frame is the called instance's Process store and differs from an embedded frame in two respects. First, resolution from any called-owned occurrence ends at it: the called root is parentless and the [Call record](CALL-ACTIVITY-SPEC.md#runtime-only-call-record-and-semantic-identity), not a parent pointer, links it to the caller, so no read or write from inside the call reaches a caller frame or the caller's Process binding. Second, a write that no inner frame declares updates or creates its binding there, as CIB's `setVariable` does on a process instance. The caller's Process binding stays the hosting instance's store. The hidden Call record gains no data field.

Invocation evaluates every input against the Call's enclosing chain by `NSD-READ-01`, turns an absent source into a present null, keeps a refused resolution (more than one live frame for a definition) a refusal that disables the step rather than a fabricated null, and installs the called-root frame in the same transition that creates the Call record and called root. Return reads every output source from that frame, turning an absent source into a present null, writes the values by `NSD-WRITE-01` starting at the Call's enclosing occurrence, disposes the frame, the called root and the Call record, and emits the caller token atomically.

## Runtime-only and synthetic constructs

The called-root frame is runtime-only: created by invocation, owned by the called root, read and written only by called-owned work, never part of `StateObservation`, exposed only through hosted called-task detail, and removed exactly with its root by return or by the existing ownership-based removal. Its lifecycle invariant: exactly one such frame exists per live called root and none otherwise, and its names satisfy input targets ⊆ frame names ⊆ input targets ∪ output sources. The core's nested-frame validity predicate, `nestedScopeFramesValid`, requires embedded frames to match declaring occurrences one-to-one and to hold exactly their declared locals, and its called-root arm states this invariant. Lean has no frame-validity predicate, so there the invariant rests on the installation and disposal laws of the [Lean assurance lane](#lean-assurance-lane). No other synthetic construct is added.

## Stable rules

Layers: `CVM-ISOLATE-01` and `CVM-RETIRE-01` restate the BPMN instance separation of Clause 13.3.4; every other rule belongs to the CIB overlay of `CIB-EXT-0021`, and the reused `NSD-*` rules to `CIB-EXT-0020`. The retained models are reusable semantic witnesses, not one-time feasibility fixtures.

`CVM-ADMIT-01`: admission accepts exactly the required and optional scope above, rejects every exclusion and every parser warning, and rejects a mapping with a missing or empty `source` or `target` and an output targeting a reserved Multi-Instance name.

`CVM-START-01`, `CVM-AVAILABLE-01` and `CVM-RESOLVE-01`: as stated under the profile above.

`CVM-IN-01`: invocation evaluates every input against the Call's enclosing chain before the called instance exists. A present value, including a present null, is copied; an absent source yields a present null target. The called-root frame holds exactly the input targets.

`CVM-ISOLATE-01`: while the call is live, every called-owned read and write resolves within the called instance and ends at its root frame, and no called-owned transition changes a caller frame or the caller's Process binding.

`CVM-TASK-01`: a called User Task completion patch may carry only names among the Call's input targets and output sources, each at most once and in the value domain, measured and bounded at 16,384 bytes exactly as `NSD-TASK-01` measures a patch, and writes them into the called-root frame. Caller User Tasks keep `NSD-TASK-01`. A wrong or oversized patch is `rejected`.

`CVM-OUT-01`: at normal return, every output reads its source from the called-root frame, with an absent source yielding a present null, and writes its target by `NSD-WRITE-01` from the Call's enclosing occurrence. Reading all sources precedes every write, and validation, writes, disposal and the caller token commit atomically. No output reaches the caller before return.

`CVM-RETIRE-01`: return disposes exactly the called-root frame together with the called root and the Call record; no called variable remains readable.

`CVM-OBSERVE-01`: hosted User Task detail, which exists only in the Temporal adapter, resolves a called task's requested input names in the called-root frame only; the detail of a caller User Task is unchanged. A caller binding is never visible through a called task by name. `StateObservation` gains no field.

`CVM-REFUSE-01`: every refusal leaves the predecessor state unchanged. Start with an undeclared name, a wrong patch and a stale or caller-addressed called completion are `rejected`; no invocation or return step can fail after an accepted command, because absent sources become present nulls and every value is already in the domain.

## Lean assurance lane

Lane shape: proved

Evidence: isolation is a property of every reachable state while a call is live, which no finite test covers, so the lane extends the frame laws in [NestedScopeDataLaws](../../BpmnSemantics/SemanticProcess/NestedScopeDataLaws.lean), whose read law is [`resolveOwner?_frame_nearest`](../../BpmnSemantics/SemanticProcess/NestedScopeDataLaws.lean#resolveOwner?_frame_nearest), and reuses the Call control evaluators of [CallDataTransfer](../../BpmnSemantics/SemanticProcess/CallDataTransfer.lean) as starting owners.

The lane covers what no finite test can: input installation yields exactly the mapped snapshot with absent sources as present nulls (`CVM-IN-01`); resolution from a called-owned occurrence never selects a caller frame or the caller Process binding, and called-owned transitions preserve both (`CVM-ISOLATE-01`); return writes each output exactly at its nearest caller owner (`CVM-OUT-01`) and disposes exactly the called frame, root and record, keeping every other frame (`CVM-RETIRE-01`); the input and output evaluators distinguish an absent source, which becomes a present null, from a refused resolution, which disables the step. The nearest checked non-law is that resolving a called read through the caller hierarchy is not the isolated read when the caller holds a namesake. Admission and the remaining rules are checked by a conformance fixture. The declarative invocation and return arms take the evaluator result as premise, so their soundness bridge is a dispatcher check and the laws above carry the semantic evidence.

In [CallVariableMappingLaws](../../BpmnSemantics/SemanticProcess/CallVariableMappingLaws.lean): `invokeState?_installs_snapshot` proves that a successful invocation leaves exactly one frame for the derived called root, holding the copies read along the caller's chain in the predecessor state, and `copyValues?_absent_is_null` and `copyValues?_refused` separate an absent source from a refused resolution (`CVM-IN-01`). `readOutcome?_called_ignores_process`, `write?_called_keeps_process` and `resolveOwner?_frame_same_instance` prove that a read or write from a chain ending at a called root neither reads nor changes the hosting Process binding and selects only frames of its own instance (`CVM-ISOLATE-01`). `returnState?_writes_outputs_from_caller` proves that return copies each output source out of the called frame and writes the values from the caller's position after disposal (`CVM-OUT-01`), and `returnState?_retires_called_frames` that no frame of the called instance survives return (`CVM-RETIRE-01`); `writeAll?_frame_owners` proves that writes keep the frame owners. Two parts stay unproved and are checked only by the [conformance fixture](../../BpmnSemantics/CallVariableMappingConformance.lean) and the core: preservation of the caller frames and Process binding by every called-owned transition, as opposed to every called read and write, and that return keeps every other frame. The non-law is the decided fixture `called_reads_do_not_reach_the_caller_namesake`.

## Temporal hosting and refinement preflight

No new hosting mechanism is added. Durable ingress stays the existing Start and User Task completion Updates; called tasks are addressed by their called semantic instance identity as the [Call specification](CALL-ACTIVITY-SPEC.md#data-and-public-boundary-constraints) already requires, with the caller instance selecting the hosting Workflow. Waits are one User Task or one effect at a time, effects under the existing effect contract as in the nested profile; there are no timers, Message waits or BPMN cancellation, and host termination fabricates no return or output. Invocation and return are internal closure steps inside the command that reaches them, so a mapping is evaluated exactly once, deterministically, from committed state, and replay re-derives it. The called-root frame is ordinary runtime state carried through Continue-As-New and restored by ownership; the continuation decoder rejects a frame without its called root, a called root without its frame and a frame owned by the caller, as the [decoder controls](../../packages/temporal-adapter/workflow/test/call-variable-mapping-recovery.test.ts) witness.

The preserved relation is the existing one between hosted committed state and the semantic core's state; the profile only adds frames to it. The hosting risk is size: the profile's [Start capacity envelope](../../packages/temporal-adapter/protocol/src/start-capacity-envelope.ts) counts the called tasks among its journey steps and the called-root frame, bounded by sixteen names at the portable value bound, and keeps refusing a Start whose journey exceeds a budget. The 1,024-journey cap counts called tasks like caller tasks, so some admitted Programs with three called tasks are refused at Start as host-unsupported, as for the nested profile. [Called-task detail](../../packages/temporal-adapter/protocol/src/user-task-detail.ts) changes its source for called tasks only.

One hosted risk is inherited: the [Call data closure review](CALL-ACTIVITY-DATA-BOUNDARIES-PROPOSAL.md#independent-cold-review-receipt) observed a public String journey whose publication read returned `unavailable` after a correct terminal receipt, without proven attribution. This profile's journeys run the same Call hosting path, and the failure did not reproduce in its hosted lanes; a reproduction is recorded, not worked around.

Admission widening adds stable-state shapes around the call, a caller effect wait before it, one called User Task wait and one caller User Task wait after return, each the only open wait. Both resume through the existing User Task completion Update, and host admission accepts this profile's Call Programs with one serial wait and still refuses every concurrent wait set.

The smallest executable refinement witness is one live call with two called tasks, Worker replacement between them, Continue-As-New across the live call, completion, return with outputs into the caller's Process binding, then the review Sub-Process frame initialized from them, and every-Run replay; the [hosted recovery witness](../../packages/temporal-adapter/testkit/test/call-variable-mapping-recovery.temporal-test.ts) executes it.

## Evidence and acceptance

One retained whole model with a business purpose carries most witnesses: a loan application caller acknowledges the application, then passes applicant data into a reusable identity-verification Process whose two tasks collect a document and record a verdict; the Call returns the verdict to the Process, and a review Sub-Process lets a reviewer confirm or override it before publishing the decision back. Two further Starts of the same model hold the present-null, absent-source and never-set-output cases, so no second model is needed. All three run as answer-free scenarios with registered pipeline cases, seeded mutations, value-domain rows, a corpus row and the About disclosure.

The CIB lane is a standalone probe in the CIB runner, modelled on the existing [body-data probe](../../runners/cibseven/src/test/java/org/bpmnlean/cibseven/CibSevenSequentialMultiInstanceDataProbeTest.java). It drives the model's three journeys in CIB `2.2.0` and asserts the caller's Process variables at the same points the scenarios observe, plus the child instance's variables through CIB's own query API for `CVM-IN-01`. It maps no CIB child-instance or task id to the derived called identity, and the bounded [scenario projector](../../runners/cibseven/src/main/java/org/bpmnlean/cibseven/CibSevenScenarioStateProjector.java) keeps refusing child instances. It is the first CIB Call evidence lane, since the [Call specification](CALL-ACTIVITY-SPEC.md#normative-and-compatibility-basis) selected none.

Acceptance: Lean, core and pipeline agree on every scenario's `StateObservation`, the Lean laws hold, the probe agrees with the expected caller observations at its declared fidelity, the hosted called-task detail witnesses pass, and the hosted pipeline passes once at family acceptance.

Nearest unsupported claims: agreement on called-frame contents beyond what reaches the caller's Process variables, which rests on the Lean laws, core state validity and hosted detail; repeated, nested or concurrent calls; a Call output written into a declaring caller frame (`PC-SCOPE-05`); exceptional return; and caller-task detail of frame-shadowed names. Common-mode risk: Lean and the core transcribe one reading of the CIB extraction, and only the CIB probe checks that reading independently.
