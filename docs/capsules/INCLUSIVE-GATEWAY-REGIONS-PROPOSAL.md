# Inclusive Gateway regions proposal

## Status

Lifecycle: implementation-in-progress
Review: approved

## Question and delivery boundary

Can the nested scope-data profile admit structured Inclusive Gateway regions in the Process root, each one diverging Inclusive Gateway paired with one converging Inclusive Gateway, whose outputs carry Simple Boolean v1 conditions or none, with an optional default, and whose branches hold User and Service Tasks, embedded Sub-Processes and nested Parallel regions, so that the split activates exactly the outputs whose condition holds or that carry none (or its default when none holds), the join waits for all and only the branches that split selected, and every other profile, every admitted model and every command and observation keep their meaning?

This is the next family of batch 4 in [PLAN](../PLAN.md#scheduled-delivery-batches) (remaining gateway compositions). Its mechanism is selected-set synchronization in a cumulative profile: the existing `selectMany` and `synchronizeSelected` operations of the [Inclusive Gateway specification](INCLUSIVE-GATEWAY-SPEC.md), widened from exactly two conditional candidates with a default around three User Tasks to structured regions of any admitted arity, with unconditioned outputs and an optional default. It serves these clauses of the [coverage checklist](../PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list):

- `PC-CF-04`, primary: Inclusive selection and synchronization with selected one, two and three branches, an unselected branch and the default, and joins after scopes, where a selected branch is an embedded Sub-Process. The row stays open on unpaired and looping merges, joins after Calls and Multi-Instance, a still-reachable upstream branch outside a structured region, a default-less split whose every output is conditional, and comparison predicates (`PC-DATA-07/08`).
- `PC-CF-08`: the matrix cell *Parallel within Inclusive* for root regions, and the Sub-Process part of *Inclusive after Sub-Process/Call/MI*. The row stays open on its other cells and on Calls and Multi-Instance.

Screened out, each with its reason:

- Implicit Activity split and merge (`PC-CF-07`): every Activity operation has one output place, and the [implicit fan-in proposal](IMPLICIT-FAN-IN-PROPOSAL.md#independent-cold-review-receipt) was rejected because an entry merge needs a control place with no Sequence Flow behind it; both directions need a kernel extension.
- Link Events (`PC-BASIC-02`): the same kernel extension, for 4 models.
- Script and Business Rule Tasks (`PC-AUTO-05` to `PC-AUTO-08`): both open with a dependency and runtime design decision.
- A default-less split whose every output is conditional: when every condition is false it needs the no-match outcome of the [Exclusive Choice without a default](EXCLUSIVE-CHOICE-WITHOUT-DEFAULT-SPEC.md#representation-and-runtime-ownership), whose closure-result, host-start and proof changes are a family of their own; the next reach step of this mechanism.

Selection, 2026-11-04, re-decided after the first proposal review: chosen on semantic risk, standards value and cost; reach, measured on deduplicated whole models for Inclusive only, admits no pinned or MIWG model as it stands. Measured as deduplicated whole models (pinned checkout `5a45b47` and the MIWG reference checkout, 2026-11-04; every `*.bpmn`, `*.bpmn2` and `*.bpmn20.xml` file outside `target/` and `node_modules/` that parses as XML), no pinned or MIWG model holding an Inclusive Gateway falls inside this class as it stands, and none would be admitted anyway, because the profile requires a source overlay and refuses CIB attributes and JUEL. The pinned models fall out on the paired join (`ProcessInstanceAssert-isWaitingForJoinAt3`, `testDefaultSequenceFlow` and the three asynchronous splits to separate Ends), the strict cut (`BPMNParseListenerTest.testAlterActivityBehaviors`), the Call exclusion (`testJoinAfterCall`), the cycle exclusion (`testLoopingInclusiveGateways`) and the conditioned default-less split (13 of the 23 pinned splits); the MIWG hits are four distinct reference models, 48 of 52 splits being copies of B.2.0, none a paired structured region. The split-shape measure that guided the redesign remains: 10 of 23 pinned and 17 of 52 MIWG splits have a shape this class admits, against 1 and 2 for a required default with every other output conditioned. Close call: the Inclusive join is the highest-risk open gateway mechanism, a non-local synchronization whose liveness Table 13.3 defines by reachability, and this family reuses an existing operation pair, two Lean contract field types and one runtime record bound, where implicit flow needs new operation outputs on every Activity.

## Normative basis and CIB classification

BPMN 2.0.2 Clause 10.6.3 evaluates every condition of a diverging Inclusive Gateway and traverses every Sequence Flow whose condition is true; the default is taken only when none is, and Table 13.3 makes that case without a default an exception. The Sequence Flow attribute table (Clause 8.4.13) makes `conditionExpression` an optional gating condition. The text is ambiguous on an output without one: Table 10.124 gives the default a token "when none of the conditionExpressions on other Sequence Flows evaluate to true", and Table 13.3 throws "in case all conditions evaluate to false and a default flow has not been specified", so read literally a split whose conditions are all false would take its default beside an ungated output, or throw without one. This family selects the reading `CIB-INT-0005`: an absent condition is a condition that is always true, for selection, for the default rule and for the exception rule. Clause 13.4.3 with Table 13.3 activates the converging Gateway when at least one incoming flow has a token and, for every directed path that starts at a flow holding a token, ends at an incoming flow without one and does not visit the Gateway, there is also a path from that flow to an incoming flow with a token that does not visit it. Table 13.3 names the Structured Synchronizing Merge (WCP-7). The [Inclusive Gateway specification](INCLUSIVE-GATEWAY-SPEC.md#required-proposition) reviewed the bounded reading this family reuses: in an acyclic structured region the inputs that can still receive a token are exactly the selected branches still live, and an occurrence-owned selected set carries the liveness that an active Activity hides from a control-place-only transcription. [BPMN21-450](https://issues.omg.org/issues/BPMN21-450) remains open; no general algorithm is selected. Consult the [external reading copy](../reference/bpmn-2.0.2/README.md#reading-workflow).

CIB Seven `2.2.0` at the pinned checkout (`InclusiveGatewayActivityBehavior.java:46-129`) takes every non-default outgoing transition whose condition is absent or true, the default when none is, and throws when neither exists. Its join activates once the arrived executions reach the incoming count, or once no other leaf execution of the scope can reach the gateway (`activatesGateway`, `canReachActivity`). In an acyclic structured root region, the only executions that can reach the join are the region's own selected branches still live, including executions inside a Sub-Process on a branch through its flow scope, so the two accounts agree on every admitted model. Classification: two new register entries, added with their verifier coverage. `CIB-INT-0005` (interpretation) records the absent-condition reading above, citing Tables 10.124 and 13.3 and `InclusiveGatewayActivityBehavior.java:61-86`, which treats an absent condition as true and takes the default only when nothing was selected. `CIB-AGR-0017` (normative agreement) records that on admitted structured root regions the reachability join activates exactly when every selected branch has arrived, bound to the new CIB probe and to the existing JUEL condition environment `CIB-CFG-0005`; the profile artifact names all three. CIB's reachability join on unstructured, looping or asynchronous graphs stays outside the class.

## Required, optional and excluded scope

Required, for the nested scope-data profile only:

- **Root Inclusive regions.** In the Process root body, a diverging Inclusive Gateway with one input and two or more outputs, paired with one converging Inclusive Gateway whose inputs are exactly one per split output and which has one output. Each non-default output carries one Simple Boolean v1 condition or none; the default, when named by the `default` reference, carries none. A split without a default has at least one unconditioned non-default output, so its selection is never empty; a split with a default has no unconditioned output, so its default is reachable. Outputs and their expected join inputs are pairwise distinct.
- **Branch content.** Each branch holds the root body content the profile admits between a fork and its join: User Tasks, mapped and unmapped Service Tasks, embedded Sub-Processes of the admitted depth and data, and nested Parallel regions. Every path from a split output reaches a User Task, Service Task or Sub-Process before any join or End (the strict cut, without pass-through branches).
- **Composition.** Regions compose with root Parallel regions, terminal forks and Sub-Processes in both directions of nesting, within the unchanged depth, task and closure bounds.

Optional: none.

Excluded, each refused at admission:

- an Inclusive Gateway in a Sub-Process body or a called Process body: a condition reads Process-scope bindings only, as the root Exclusive Choice does, and a body's nearest declaring frame would be invisible to it;
- a default-less split whose every output is conditional, a split with both a default and an unconditioned output, whose default no state can reach under `CIB-INT-0005`, a condition outside Simple Boolean v1, a mixed or unpaired Gateway, an unstructured or cross-branch flow, and an Inclusive split paired with a Parallel join or the reverse;
- a split whose branches end at separate Ends rather than its join;
- an Inclusive region on a branch of another, directly or through a Parallel block: it creates two live selection records under one owner, which no witness of this family exercises (closure review of `60786474`);
- a branch that reaches its join without arming work: pass-through Tasks or None Throws alone, or directly;
- an Inclusive region in a model that also holds an Exclusive Choice or a cycle, which the profile already routes to its serial re-entry analysis and keeps apart from forks;
- a Call Activity anywhere in a definition that holds an Inclusive Gateway;
- every form above under any other profile. The [Inclusive Gateway specification](INCLUSIVE-GATEWAY-SPEC.md#exact-source-profile)'s profile keeps its exact topology through an explicit predicate (`IGR-PROFILE-01`).

These bound admission only, so later families broaden them without reinterpreting a model. No model this profile admits today changes meaning: it admits no Inclusive Gateway.

## Representation and runtime ownership

No new operation, runtime collection or transition family; the record widens only in arity. A split lowers to `selectMany` and its join to `synchronizeSelected`, as the [Inclusive Gateway specification](INCLUSIVE-GATEWAY-SPEC.md#checked-graph-and-semantic-process-contract) defines them, with `selectionKey` the split's BPMN ID, candidates in canonical flow-ID order and join inputs in canonical place order. The hidden `SelectedBranchSet` record keeps its definition: created by the split, owned by the root scope occurrence, removed only by its join or owner interruption, and blocking the root's quiescent completion while live.

**Optional default.** Lean changes the field type of `selectMany`'s default to `Option InclusiveDefaultBranch`, and of the checked diverging node's default to `Option SequenceFlowId`, keeping both constructors' arity, as the Exclusive Choice without a default did for `choose`. The dispatch on the default sits beside `evaluateInclusiveBranches` in [`InclusiveGateway`](../../BpmnSemantics/SemanticProcess/InclusiveGateway.lean) and in `prepareInternalInclusive?`, the modules that already hold these edges, not in a new leaf, because the precedent's separate dispatch leaf was refused by the `lean-fanout` guard: `some d` calls the existing evaluation with `d`; `none` selects the true candidates and is disabled when they are empty, a case admission makes unreachable. The declarative relation `SelectManyStep` changes with it, and `selectManyState_sound` is re-established for both arms; the existing laws keep their statements for `some`, and a `none` law states that the selection is exactly the true subset.

**Expected join inputs and pairing.** Each candidate's and the default's `expectedJoinInput` is the join input its own branch reaches. One new leaf per language owns a walk from a split output: a serial vertex passes to its sole output, a nested Parallel or Inclusive split passes to its paired join's output, and the walk stops at the input flow into the paired join. The [Lean lowering](../../BpmnSemantics/SemanticProcess/Lowering.lean) and the [TypeScript lowering](../../packages/bpmn-source/src/semantic-process-lowering.ts) call it for `expectedJoinInput`, and the [source projection](../../packages/bpmn-source/src/inclusive-gateway-source.ts) calls the same walk for the converging node's `pairedGatewayId`, replacing today's one-task lookup in `derivePairedGatewayId`. The same walk over Program control places is an admission check at the Program level in both languages (`IGR-BIND-01`).

**Admission projection and routing.** The nested analyses project a split as a fork vertex and its join as a join vertex, at the checked and Program levels alike, so the reviewed contraction, pairing and burst composition apply unchanged; `selectMany` charges one closure step, as `duplicate` does, and a selected subset never exceeds the bound computed for all branches. The projection, the operation and node alphabets and the routers are gated by this profile, so the embedded completion profile, which shares the analyses, does not widen. The Program router (`concurrentProgram` in Lean, `concurrentStructuredScopeDataProgram` in TypeScript) and the checked router (`checkedConcurrent`, `forks`) count an Inclusive split as a fork, so the existing routing of Choices and cycles away from forks applies to it. A new admission leaf per language adds what the shared analysis cannot see: the kind of each paired vertex, root-only placement, the strict cut, the outputs and default rule, the Call exclusion and `IGR-BIND-01`.

**Co-enabled members.** `selectMany` and `synchronizeSelected` are local control in the [commutation census](../../BpmnSemantics/SemanticProcess/InternalCommutationCensus.lean); their selection-record footprints and the pair laws `prepared_local_control_pair_commutes`, `prepared_end_local_control_pair_commutes`, `prepared_declared_entry_local_control_pair` and `prepared_merge_local_control_pair_commutes` already exist, and the TypeScript batch preparation accepts the same pairs. A split's footprint reads one `processVariable` atom per condition name (`InternalLocalControlPreparation`, `internal-transition-local-control-preparation.ts`). The one writer of Process variables inside a closure is the completion of a scope that declares data and copies outputs to the Process. Such a scope is never a regional candidate (`InternalRegionalSelection.lean`, `NSD-OUTPUT-01`; the same rule in `internal-transition-regional-preparation.ts`), so its completion executes unprepared, and a frontier that held it beside a split would be ambiguous and roll back: this pair fails closed. Undeclared completions write no Process data. What this family must re-establish is availability, the singleton premise of the [concurrent scope data specification](CONCURRENT-SCOPE-DATA-SPEC.md#representation-and-runtime-ownership), which names gateway conditions among its reopening triggers: admitted models never reach that ambiguous rollback. A command ends one wait, so a closure starts from one token; a split, like a fork, creates several tokens only on branches that each arm work before any join or End (the strict cut); a region's join fires only when its last selected branch arrives; wait-free joined branches, which the [pass-through branch specification](PASS-THROUGH-PARALLEL-BRANCHES-SPEC.md#representation-and-runtime-ownership) admits in data-bearing definitions, reach only their paired join and never an End; and wait-free terminal branches exist only in data-free definitions (`TFK-DATA-01`). So a scope still becomes quiescent only through the single token of the command that ended its last wait, its completion stays the only offer of its frontier, and a split reads only bindings committed before its step, including outputs that a preceding Sub-Process copied to the Process in the same closure. The premise is argued, not proved; the pipeline journeys lock its consequence, since every witness command commits with no ambiguous refusal. Besides the pair laws above, the fork closure of the event booking batches the split beside a sibling arming (`prepared_local_control_arming_pair`) and the account opening's scope entry beside armings (the scope-creation pair laws).

Rejected alternatives:

- a new `inclusiveRegion` vertex kind in the shared structured analysis: it is also the Multi-Instance owners', and the profile-gated projection plus a leaf check leaves those consumers untouched;
- an `Option` condition on `InclusiveCandidate` for unconditioned outputs: a second hub field type for a value the existing literal already expresses;
- admitting Inclusive regions in Sub-Process bodies with frame-aware condition evaluation: it needs a reading of conditions that `choose` does not have, for no selected model;
- admitting every default-less split with the no-match outcome: see the screened-out list above.

## Admission

Admission stays [profile-parameterized](../PROFILE-PARAMETERIZED-ADMISSION-SPEC.md). Under this profile only, and at the Program and checked levels alike, a definition with Inclusive Gateways admits when:

1. it is admitted by the nested analyses with every split projected as a fork and every join as a join;
2. every Inclusive split lies in the Process root body, on no branch of another Inclusive split, and its analysis-paired join is an Inclusive join naming it, and every Inclusive join is paired with an Inclusive split; a Parallel vertex is paired only with a Parallel vertex;
3. every split has two or more pairwise-distinct outputs, each non-default output with one Simple Boolean v1 condition or none, at most one conditionless default, without a default at least one unconditioned output, and with a default none; its join has exactly one input per split output;
4. every path from a split output reaches a User Task, Service Task or Sub-Process before any join or End;
5. the definition holds no Call Activity: joins after Calls are their own clause of `PC-CF-04`, and no witness of this family calibrates selection beside a called child;
6. at the Program level, every `expectedJoinInput` is the join input its branch reaches and the expected inputs of one split are exactly its join's inputs (`IGR-BIND-01`); at the checked level, each join's `pairedGatewayId` is the split that rule 2's pairing finds.

Measured closure bursts of the witnesses, by the composition of the [nested scope-control class](NESTED-EMBEDDED-SCOPE-CONTROL-SPEC.md#admission): the account opening's largest is the resumption after *Assess applicant*, 8 steps (body End, `completeScope`, split, `enterScope` and child arming of *Enhanced due diligence*, and three branch armings); the event booking's largest is the resumption after *Quote event*, 8 steps (fork, venue, split, catering, inner fork, projector, technician, attendee list). Both sit at `semanticProcessClosureLimit = 8`; one more branch or step refuses them.

Nearest wrong algorithms, each with a separating witness below:

1. synchronizing every join input, which strands the one-true and default journeys;
2. releasing the join at the first selected arrival;
3. selecting only the first true candidate, as `choose` does;
4. trusting a Program's `expectedJoinInput` values without checking them against its own control places;
5. pairing by key alone, so that an Inclusive split structurally closed by a Parallel join is admitted;
6. admitting a region in a Sub-Process body, where a condition misses the body's frame;
7. treating an unconditioned output as false, or admitting a default-less split that can select nothing, or a defaulted split whose default no state reaches;
8. widening the exact Inclusive profile, or admitting regions under another profile.
