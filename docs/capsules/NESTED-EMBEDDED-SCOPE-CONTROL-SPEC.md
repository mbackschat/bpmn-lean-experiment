# Nested embedded scope control specification

## Status

Lifecycle: implemented
Review: closure-approved

## Question and delivery boundary

Can the engine admit ordinary embedded Sub-Processes nested to a definition depth of at most three below the root, whose bodies compose User Tasks through paired Parallel fork/join blocks and terminal unjoined forks to separate None Ends, so that every scope completes exactly at its owned quiescence, continues exactly once at its own parent, and leaves concurrent work outside it untouched?

This is the second batch of the embedded and called scope family in [PLAN](../PLAN.md#exact-resume-point) and serves the control clauses of `PC-SCOPE-01` and the human-branch, nested-region and separate-End clauses of `PC-CF-03` in the [coverage checklist](../PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list). It does not close either row: mixed automated activities need concurrent-effect hosting that [host admission](../../packages/temporal-adapter/protocol/src/host-admission.ts) refuses for any program combining a token split with an effect or Timer wait, and selected Exclusive decisions inside scopes need a data and expression binding this profile lacks. Both stay named later increments.

Depth counts enclosing Sub-Processes: the root body has depth zero and a Sub-Process declared there owns a depth-one body, the convention of the [nested scope-data capsule](NESTED-EMBEDDED-SCOPE-DATA-SPEC.md#required-optional-and-excluded-scope).

Profile family: the owner direction of 2026-10-14 grows one cumulative profile per Practical CIB7 family, and the [checklist legend](../PRACTICAL-CIB7-COVERAGE-TARGET.md#contract-dependency-key-and-retained-evidence) separates `DATA` (PC-DATA-01–09) from `SCOPE` (PC-SCOPE-01–07 and PC-MI-01–12). The nested scope-data capsule served the `DATA` rows, so its profile stays that family's cumulative profile. `PC-SCOPE-01` names the [embedded owner](EMBEDDED-SUBPROCESS-COMPLETION-SPEC.md) as its row owner, so the `SCOPE` family grows that capsule's profile. The two lanes converge only at the concurrent owners of `PC-DATA-04`, where scope-local data meets concurrency. The data profile cannot absorb this increment anyway: its admission walk, Start capacity journey and frame commutation charge all assume no token split. Narrowing to User Tasks removes both blockers PLAN carried. Without Start data or Service effects, Start capacity reduces to the static task bound below, and no effect wait reaches host admission.

## Normative basis and CIB classification

BPMN 2.0.2 Clause 10.3.5 defines the embedded Sub-Process as a scope containing Flow Elements. Clause 13.3.4 instantiates it when a token arrives, executes its contents as a normal Process, and completes it only when no token remains inside and no contained Activity is active, then continues through its outgoing Sequence Flow. Clause 10.6.4 defines the Parallel Gateway, and Clause 13.4.1 with Table 13.1 activates it once at least one token is on each incoming flow, consuming exactly one token from each incoming flow and producing one on each outgoing flow. A None End consumes its token without completing anything else. Consult the [external reading copy](../reference/bpmn-2.0.2/README.md#reading-workflow).

The standard settles every selected behavior, so no new CIB relationship is required. The profile keeps naming [`CIB-AGR-0007`](../CIB-BPMN-RELATION-REGISTER.md#cib-agr-0007--ordinary-embedded-sub-process-quiescent-completion), still bound only to its one-level fixture; the new schedules are standards-only, and a CIB probe of one nested model is optional calibration, not acceptance.

## Required, optional and excluded scope

Required: one root Process with one None Start and one None End; finite acyclic flow; complete ownership and same-scope Sequence Flow closure; every embedded Sub-Process has exactly one incoming and one outgoing flow and a child body with one None Start; definition depth at most three below the root; at least one User Task or Sub-Process in every scope body, and on every Parallel branch every path reaches a User Task or Sub-Process before any join or End; at most 128 User Tasks per definition, the concurrent-wait ceiling of the existing [parallel Multi-Instance capacity account](../../packages/semantic-core/src/parallel-scope-program-capacity.ts); and ordinary User Tasks with one incoming and one outgoing flow whose completion accepts only an empty patch.

Optional: further User Tasks and Sub-Processes within those bounds; paired Parallel blocks of two or more branches, nested in any order inside branches and Sub-Process bodies; and, in a child body only, terminal unjoined Parallel forks whose branches each reach their own None End, in any arrangement that contraction rule 3 below reduces. A branch may contain a Sub-Process, so work outside a scope can run concurrently with it.

Excluded from the structural class, while the pre-existing multiset class keeps its exact one-level topologies: Exclusive, Inclusive, Event-Based or mixed gateways; unpaired, crossing or cross-scope blocks; more than one End at the root or a terminal fork there; implicit Activity fan-in or fan-out; Service, Script, Send, Receive or other Tasks; data mappings, scope-local data and completion values; boundary and intermediate Events; Event Sub-Processes, Terminate Ends, Calls, Multi-Instance, loops, Transactions and Compensation; and a new public command or observation field.

Acyclicity and element uniqueness mean each Sub-Process activates at most once per instance, so the element-identifier task identity of the [embedded specification](EMBEDDED-SUBPROCESS-COMPLETION-SPEC.md#runtime-state-identity-and-ownership) stays unique for the shapes this capsule admits. The [concurrent embedded activations specification](CONCURRENT-EMBEDDED-ACTIVATIONS-SPEC.md) adds, in the same profile, merge-target Sub-Processes with concurrently live occurrences, whose User Tasks are distinguished by activation. The restrictions narrow admission only: later increments add gateways, tasks or data without reinterpreting an admitted model.

## Representation and runtime ownership

Lowering reuses the existing operations: `initiate`, `awaitUserTask`, `duplicate`, `synchronize`, `enterScope`, `reachNoneEnd` and `completeScope`. There is no new opcode, Program field, runtime collection or synthetic occurrence. Tokens, User Task occurrences and child scope occurrences keep their owner links, so a `synchronize` consumes only tokens of its own scope occurrence, and a `completeScope` removes only its occurrence and places the single continuation token at that occurrence's parent output. Because each definition scope has at most one live occurrence, place-based token counting and occurrence-based ownership coincide here; the checkpoint must verify that both languages count join tokens per owning occurrence rather than per place.

Several internal operations can be enabled in one closure. Lean and the core already execute such a state as one batch under the INTERNAL-COMMUTATION rule of [`prepareInternalTransitionBatch`](../../packages/semantic-core/src/internal-transition-batch.ts): each member is prepared in its owner-scoped family, alternatives are unique, and every pair has independent footprints; otherwise the result is `ambiguousInternalChoice`. The branch condition fixes which batches this admission can reach. A closure starts from one Start or one task completion and so follows one token path until a fork. Every path from a fork then reaches a User Task or Sub-Process before any join or End, and every newly entered body arms a task before reaching either. A multiple-enabled state therefore contains only User Task arming (`Arming`), `enterScope` (`ScopeCreation`) and `duplicate` (`LocalControl`) in any owner, such as a nested fork beside a sibling branch's arming. `reachNoneEnd`, `synchronize` and `completeScope` are always the only enabled operation, because each is reached by a single token path. Both languages witness the Arming–Arming, Arming–ScopeCreation and ScopeCreation–ScopeCreation batches on the retained journeys; the nested-fork batch of `duplicate` beside a sibling arming is witnessed in TypeScript only. An `ambiguousInternalChoice` on any retained journey fails acceptance.

## Admission

Admission stays [profile-parameterized](../PROFILE-PARAMETERIZED-ADMISSION-SPEC.md): generic scoped-graph validation plus one structural capability, not a list of model predicates. It reuses the reviewed structured-body owner rather than writing a second contraction: [`StructuredParallelBodyAdmission`](../../BpmnSemantics/SemanticProcess/StructuredParallelBodyAdmission.lean) in Lean and [`structured-parallel-body-analysis.ts`](../../packages/semantic-core/src/structured-parallel-body-analysis.ts) with [`parallel-body-burst-analysis.ts`](../../packages/semantic-core/src/parallel-body-burst-analysis.ts) in TypeScript, which already back `SMIS-ADMIT-01` and `PMIS-ADMIT-01`. Each scope body is projected to that owner's vertices, and a Sub-Process appears in its parent body as a one-in, one-out `task` vertex. `structureOrder`, `paired`, `contractAt` and `structureOrder_certificate` then apply per body unchanged:

1. a User Task or Sub-Process vertex with one incoming and one outgoing edge becomes an edge;
2. a Parallel fork and join become one edge when every fork output leads directly to the join, these are exactly the join's two or more inputs, and the join has one output;
3. a fork whose outputs lead to distinct None Ends with no other input becomes a single End, an analysis sink and never a runtime join or first-End completion rule; this rule is refused in the root body.

A body admits when its contraction reaches Start, one edge and End; `structureOrder` already requires at least one task vertex, which here means a User Task or Sub-Process. Only the branch condition is new: every path from a fork output reaches a User Task or Sub-Process before any join or End. Both languages decide admission independently from their own graph and refuse leftovers, bypasses, crossings and cross-scope edges. The nearest wrong algorithm treats a terminal fork's first End as completing its scope. The second nearest joins at the wrong scope level and lets a nested completion satisfy an outer join.

The exact reuse gap is the burst bound. `close` charges a task vertex one step and stops its branch there. A Sub-Process vertex also charges one step, for `enterScope`, but its child's entry burst runs in the same closure, and the child's completion continues in its parent. One new composition owner per language therefore evaluates `close` and `afterTask` per body, unchanged, and composes the results over the scope tree:

- entry of a body: its `close` steps plus the child entry of every Sub-Process vertex the scan reaches;
- resumption after a User Task: its `afterTask` steps plus the child entries reached. When that closure leaves no wait in its body, the body may be complete, so it adds one `completeScope` step and the parent's `afterTask` resumption from the Sub-Process vertex, recursively up to the root.

Treating a closure with no remaining wait as possibly completing is conservative under a terminal fork, so the bound is sound without exact quiescence tracking. The root entry adds the existing Initiate charge, and a definition whose largest bound exceeds `semanticProcessClosureLimit = 8` (`scenarioClosureLimit` in Lean) is refused before Workflow start. The Multi-Instance consumers of the reused owner keep their exact behavior.

### Admission additivity correction

Implementation corrected one premise of the approved text, which replaced the exact multisets by the structural capability. The retained frontier tests admit one-level variants under this profile that the structural class refuses: a task-free child branch, a root terminal fork and a fork straight to an End. Replacing the multisets would narrow the profile, which the cumulative profile rule forbids without a new identity. Admission is therefore the legacy exact multiset or the structural class, in Program, checked source and Lean alike, and the variants keep their exact meaning. Source projection also widens Parallel Gateway arity from exactly two to two or more for this profile, as the Multi-Instance profiles already allow, so a fork of five tasks is admissible. Because the exact shape no longer bounds what this profile admits, the quantified cardinality law [`profile_operationCardinality_zero`](../../BpmnSemantics/SemanticProcess/TransactionCompensationProfileDomains.lean) and its Compensation and repeated-scope wrappers now exclude this profile by premise; every consumer names another profile. The semantic-checkpoint review must confirm this correction.

## Stable rules

- `NSC-ADMIT-01`: the structural class accepts exactly the structurally contracting definitions above within the depth, task and closure bounds and refuses every excluded construct before Workflow start; profile admission is that class or the pre-existing exact multiset class.
- `NSC-ENTER-01`: a token reaching a Sub-Process creates one child occurrence owned by the current occurrence and one entry token in it.
- `NSC-END-01`: a None End in a child body consumes only its branch's token; it completes nothing while the occurrence owns other work.
- `NSC-QUIESCE-01`: a child occurrence completes exactly when it owns no token, User Task or child occurrence, and the completion emits one token at that occurrence's parent output.
- `NSC-JOIN-01`: a join continues once, only after a token from every incoming flow in its own occurrence has arrived; a completion inside a nested scope cannot satisfy an outer join early.
- `NSC-OUTSIDE-01`: completing or progressing work in one branch leaves every sibling task, token and child occurrence unchanged.
- `NSC-REFUSE-01`: a command for a completed or absent task occurrence is rejected with the committed state preserved.

## Separating witnesses

All differ at the public boundary of open User Tasks and Process status.

- An onboarding model: a root fork with *Order equipment* on one branch and *Confirm start date* followed by *Workplace setup* on the other, then a root join and *Welcome meeting*. Setup's terminal fork ends *Assign desk* and *Accounts* at separate Ends, and *Accounts*, a second-level Sub-Process, ends *Create mailbox* and *Grant VPN* at separate Ends. After *Create mailbox* completes, *Grant VPN*, *Assign desk* and *Order equipment* stay open and *Welcome meeting* is absent; it appears only after all four complete, in every tested order. A first-End mutant drops *Grant VPN* or opens *Welcome meeting* early. Its largest closure, completing *Confirm start date*, is seven steps (two entries, two forks, three armings).
- An audit model at the maximum depth: the root runs *Audit* (depth one) and then *Close audit*; *Audit* runs *Fieldwork* (depth two) and then *Sign off*; *Fieldwork* runs *Plan fieldwork*, forks into the depth-three Sub-Processes *Sampling* (*Draw sample*) and *Interviews* (*Interview staff*), joins, and runs *Review findings*. Completing *Plan fieldwork* enters both depth-three scopes in one closure. Completing one of their tasks completes only its own scope and leaves the join waiting; *Review findings* appears only after both complete. Completing *Review findings* continues inside *Audit* and opens *Sign off*. A wrong-parent mutant puts that continuation at the root and opens *Close audit* while *Sign off* is unarmed. Its largest closure, completing *Plan fieldwork*, is five steps.
- Stale and early commands (`NSC-REFUSE-01`): completing *Review findings* before the join fires, and completing *Draw sample* again after *Sampling* has completed, are both rejected with the committed state unchanged.
- Reversed completion orders of each journey end in the same final observation.
- Refusals: the audit model with a fourth nesting level, crossing blocks whose joins pair inputs of different forks, a fork branch with no task, a join fed from two scopes (generic cross-scope validation in TypeScript, the checked analysis in Lean), a terminal fork at the root outside the multiset class, an Exclusive Gateway, a Service Task and a burst over the closure limit are each refused before start.

## Targeted preservation gate

Over every retained journey prefix in both completion orders, the core gate establishes that:

- every stable running state exposes at least one User Task or has completed;
- no reached closure yields `ambiguousInternalChoice`, and each closure stays within its computed bound, which the longest retained closure reaches ([bound check](../../packages/bpmn-source/test/nested-scope-control-source-admission.test.ts));

These are capsule-local executable claims, not a theorem for every admitted topology. The exact rewrite of a scope completion, which removes only its occurrence and emits one parent-output token, is the quantified `completeScopeState_selected_update`, not a gate check.

## Temporal hosting and refinement preflight

Ingress stays Start and User Task Update; waits are concurrent passive User Tasks, which [host admission](../../packages/temporal-adapter/protocol/src/host-admission.ts) already admits for token splits without effect or Timer waits. Nested ownership stays Workflow state interpreted by the pure core, never Child Workflows. There is no new Timer, Activity, Signal, cancellation or projection mechanism, so the increment adds no hosting mechanism and needs no separate refinement witness: the complete pipeline's Temporal target, with its isolation run and history replay, covers the new schedules. The preserved state relation is the [embedded owner's](EMBEDDED-SUBPROCESS-COMPLETION-SPEC.md#temporal-hosting-and-refinement-preflight), extended from one child occurrence to every nested occurrence and its owner link. It preserves definition identity, Process instance identity, every scope occurrence and its parent, exact User Task occurrences, token ownership, Process status, command-result classification and canonical trace, while Workflow, Run, Update and history identities stay host facts. The 128-task bound caps every reachable open-task set at the concurrent-wait ceiling that hosting already carries for parallel Multi-Instance bodies. The 128-task bound limits task count, not bytes. The [host-capability rule](../PROJECT-DESIGN.md#semantic-increment-preservation-gate) governs the reachable wait-set combination, and host admission's predicate decides it before Workflow start. Byte budgets stay with the existing owners, as for the one-level fixture and the Parallel fork/join profile. The pre-start [capacity envelope](../../packages/temporal-adapter/protocol/src/start-capacity-envelope.ts) exists because one admitted root value is copied into every hosted artifact, and its journey runs serial chains only. This profile admits no values, so its bytes are fixed by the admitted definition. Query responses page within the 192 KiB ceiling of the [lifecycle specification](../TEMPORAL-PROCESS-LIFECYCLE-SPEC.md), and the terminal envelope fails closed with the typed capacity failure. The checkpoint measures the largest retained model's publication and terminal envelope against those ceilings. Extending the envelope to concurrent waits is excluded here and would need its own journey and all-open estimator. Risks are ordering and deduplication of concurrent completions, which existing per-occurrence Update identity already decides.

## Epistemic closure

Established: under `cibseven-2.2.0-embedded-subprocess-completion-draft`, admission is the retained exact multiset class or the structural class of ordinary embedded Sub-Processes nested at most three deep, whose bodies compose User Tasks through paired and, below the root, terminal Parallel forks within the task and closure bounds. Both languages decide that class independently and refuse every listed exclusion before Workflow start. On the onboarding and audit journeys, both completion orders and the early and stale commands, a terminal-fork End completes nothing while its occurrence owns work, a scope completes only at quiescence and continues once at its own parent, a join waits for every branch of its own occurrence, and sibling tasks stay unchanged. The Lean conformance theorems and the TypeScript core agree on these schedules; the complete pipeline across Lean, core and Temporal carries both onboarding orders and the audit's early and stale journey, while the audit's reversed scope order is witnessed by Lean and the core only, and each closure stays within its computed bound, which the longest closure of each journey reaches.

Nearest unsupported claim: that every admitted definition completes under every completion order with sibling frames preserved. It rests on finite witnesses; the if half of `NSC-QUIESCE-01` and `NSC-END-01` have no quantified law, and token and occurrence frames are not observed by the conformance theorems. Mixed automated activities, decisions inside scopes, repeated activation (`PC-SCOPE-02`) and a CIB calibration of any nested model stay outside.

Common mode: the Worker, the pipeline's core target and the bound check share the TypeScript core, so hosted agreement is a refinement check; the Lean theorems decide admission and journeys from their own definitions. The two languages could agree on a shared misreading of the structured-body owner they both reuse, whose quantified certificate is per body; the scope-tree composition is the new code in each language, and its bound is separately checked against the journeys. The cumulative union exposed one shared assumption that no scenario could reach: the quantified cardinality law read this profile's exact shape as its whole admission, which only the Lean gate caught.
