# Serial business task composition proposal

## Status

Lifecycle: draft
Review: pending

## Question and boundary

Can a reusable serial Process alternate human work and named automated business operations, carry current Process data into each Service Task, and apply only its declared results before continuing? This is the first mixed-task increment under [Practical CIB7 Coverage](../PRACTICAL-CIB7-COVERAGE-TARGET.md). It does not close that target's branching, rework, business-failure, incident, structured-value or Multi-Instance obligations.

The retained [CIB experiment](../experiments/BUSINESS-EFFECT-DATA-EXPERIMENT.md) distinguishes outer-scope inputs from input-local chaining and local-result precedence from parent fallback. Existing effects already carry descriptors, arguments and typed results, but current admission selects calibration operations and literal inputs. The required outcome is a business-independent composition contract, not another hard-coded invoice profile. Private semantics precede the separately deferred live-host and public-registration evidence.

## Basis and layer ownership

BPMN 2.0.2 §§13.2, 13.3.2 and 13.3.3 supply sequential progression, Activity completion and User/Service Task lifecycle. The [Markdown-first reference route](../reference/bpmn-2.0.2/README.md) owns access; the standard does not prescribe CIB variable APIs or `camunda:inputOutput`.

The [relationship register](../CIB-BPMN-RELATION-REGISTER.md) and [compatibility scope](../CIB-SEVEN-COMPATIBILITY-SCOPE-PROPOSAL.md) separate these layers. Inherit the string/null public start/completion behavior classified by `CIB-EXT-0005` and `CIB-EXT-0006`, and the stable effect-identity separation of the [effect specification](SERVICE-TASK-EFFECT-SPEC.md). The new outer-input/local-output exact-token mapping is a bounded CIB extension. Record its own reviewed relationship and verifier coverage before production implementation; the experiment is its current evidence, not a registered profile. A durable intent followed by a separately committed result is a project operational realization, not a claim that CIB commits an in-flight delegate interval. Do not relabel the predecessor CIB `2.0.0` mapped-service evidence as `2.2.0` evidence.

This proposal expressly selects the exact-token extension below. It does not adopt JUEL, beans or Java execution inside Lean/core. Broader expression/script execution and a public handler registry remain governed by the compatibility proposal. The consumer here is a real project-owned invoice-validation journey using the existing caller-supplied effect Activity interface; no new dependency, registry abstraction or execution language is required.

## Scope

Required: one executable root Process, one None Start, one None End, a nonempty serial chain containing at least one User Task and one Service Task, unique source identities, and one incoming/outgoing flow per task. Every node and flow belongs to that chain; reject cycles, duplicate edges, disconnected material, implicit splits/merges and extra starts/ends. IDs and optional display names do not determine admission.

Optional: any finite number of either task, repeated use of the same named business operation at distinct elements, zero or more input/output mappings, literal inputs, shared input sources and shared output sources. Existing source and transport byte limits remain in force. Start and human completion carry canonical string/null Process bindings under the inherited merge contract; neither deletes bindings. Unlike the standard data-association composition profile, these human tasks use the selected CIB-style public completion map. No general standard Data Association support is inferred.

Excluded: gateways, cycles, nested scopes, Calls, boundary/events, Multi-Instance, Compensation/Transactions, other Task kinds, human form/assignment metadata, standard `ioSpecification`/Data Associations, new scalar or structured values, arbitrary expressions, Java delegate interoperability, output fallback to parent variables, scripts/listeners, new business Error routing, semantic incidents/retry/cancellation, and new public observation or stimulus fields. Existing profiles retain their exact contracts. Later profiles can add these behaviors without changing the meaning of an admitted serial model.

## Public contract

The private profile is `cibseven-2.2.0-serial-business-tasks-draft`. Compilation requires an existing content-bound [source overlay](../../packages/bpmn-source/src/source-overlay.ts) whose profile matches exactly. Each Service Task's exact `(implementation, delegateExpression)` pair must match exactly one overlay binding. No built-in probe fallback is available. Permit absent implementation or the exact `urn:bpmn-lean:effect-protocol:activity-v1` URI only when that precise pair is declared. Require `camunda:asyncBefore="true"` and an exact `${identifier}` delegate token; reject other execution bindings, asynchronous-after and executable extensions. The overlay descriptor has that Activity protocol and an operation name exactly equal to the delegate token's identifier (at most 1,024 characters). Thus `${validateInvoice}` binds operation `validateInvoice`; source aliases with a different operation name reject. This lets both semantic accounts derive the handler-shadowing exclusion from their own declared operations without trusting a compiler-supplied exclusion list. Operation names are business-handler identity, not executable code; preserve them unchanged in checked data, IL, waits and transport. Reject inert-attribute declarations in this profile rather than allowing an overlay to suppress executable semantics.

The existing Worker contract remains `executeBpmnEffect(request)`, where the request contains protocol, operation, committed arguments and its content-bound idempotency key. The configured implementation dispatches the operation name; it cannot alter definition identity or mappings. Unknown operation handling fails explicitly and must never fall back to the probe handler. Runtime qualification must use a business implementation outside the test-probe dispatcher before public coverage can be claimed.

Add one closed mapping-expression arm, `{ kind: "enclosingVariable", name: string }`, alongside the unchanged literal and local-reference arms. For this root-only profile, the enclosing context is the root Process. The name denotes a read in the containing context before the Activity's own input bindings exist; it never denotes a chained read of earlier inputs. This explicit scope meaning permits later nested admission without reinterpreting the arm as a root-global lookup.

Input source text is either one nonempty literal string without `${` or `#{`, or exactly `${identifier}` with identifier grammar `[A-Za-z_][A-Za-z0-9_]*` excluding `null`, `true`, `false`, `empty`, `div`, `mod`, `not`, `and`, `or`, `le`, `lt`, `eq`, `ne`, `ge`, `gt` and `instanceof` (the pinned JUEL `Scanner` keyword table). An exact token lowers to `enclosingVariable`; it is not evaluated as JUEL. Empty or whitespace-only parameter text and leading/trailing whitespace reject; CIB `BpmnParseUtil.parseParamValueProvider` trims text and treats empty text as null, so it cannot be represented as an empty string literal. Mixed text, whitespace around an expression, property/member access, calls, operators, nested XML values, maps/lists and scripts reject. Output text must be exactly `${identifier}` and lowers to the existing `localVariable`. Every mapping target is a nonempty identifier under that same grammar. Input targets are unique; output targets are unique. Input and output namespaces may overlap. Repeated source names are permitted and have no evaluation side effect. Canonical target ordering preserves this selected account; no such equivalence is claimed for general CIB mappings.

The pinned `VariableScopeElResolver` gives special meaning to engine-context names. Exclude `execution`, `caseExecution`, `task`, `externalTask` and `authenticatedUserId` from this profile's mapping identifiers and all supplied bindings. Also exclude every selected delegate-token identifier from input/output targets, reference names, start data, human patches and effect patches: a CIB variable can otherwise shadow the configured delegate bean. These exclusions belong to the CIB profile, not the generic wire vocabulary. Exact-token equivalence is conditional on present scalar variables, this closed name policy and the pristine selected CIB resolver/configuration; it is not a general JUEL theorem. Retain reserved-word, engine-context and handler-shadowing negatives alongside the ordinary lookup probe.

An effect result uses the existing success arm with a canonical patch containing exactly the distinct output-source names, each once, with string/null values. A source used by two output mappings requires one patch entry and writes both targets. Missing, extra, duplicate, wrongly typed or noncanonical entries refuse atomically. An output source must be supplied explicitly even when a same-named input or parent binding exists. No output mapping means exactly an empty result patch. Business Error results are unsupported in this profile and cannot enter the success route.

## Admission and execution rules

| Rule | Required decision and transition | Separating witness |
|---|---|---|
| `SBT-CHAIN-01` | Checked graph and IL independently admit the complete unique serial chain and exact lowering. Reuse generic graph validation and existing start/task/effect/end/scope operations; no serialized chain or new opcode. | Renamed/reordered declarations admit; a disconnected task, duplicate identity, back-edge or second outgoing flow rejects before start. |
| `SBT-AVAILABLE-01` | Scan the chain with a set of definitely produced Service Task output targets. Every enclosing input read absent from that set becomes a required start binding. Human patches do not promise writes. Start requires all such bindings; null counts as present. All accepted writes preserve binding presence. | A read after an earlier Service output needs no initial value; a read supplied only by potential human input still requires initialization. Missing start input refuses without starting a Process. |
| `SBT-INPUT-01` | Before activation, evaluate all inputs from one immutable enclosing binding set. Allocate one complete effect-occurrence-owned local scope and one wait carrying exactly those arguments. Missing/duplicate source bindings or duplicate owners yield no transition. | Root payload differs from mapped local payload: a later input reads root payload in either declaration order. Two Process instances and two task elements remain distinct. |
| `SBT-SNAPSHOT-01` | Arguments are committed at activation and retained through observation, export and transport. Lifecycle validation checks the exact wait/local-owner/definition join and canonical argument shape, never reevaluates a dynamic input against a later Process context. Literal positions still equal their declared values. | Change an unrelated or subsequently changed Process binding in a raw-state discriminator: projection must not fabricate new arguments. Missing/duplicate local owner or mismatched wait arguments rejects. |
| `SBT-RESULT-01` | Validate full effect occurrence and exact typed patch first; evaluate all outputs against that completed local result; atomically write declared Process targets, clear only this effect wait/local owner, and enable its sole successor. | Parent/result-name collision, fan-out from one local source, input/result overlap, null, private extra result and wrong target-name submission distinguish local precedence, frame and exact patch rules. |
| `SBT-HUMAN-01` | Only the exact live User Task accepts the inherited canonical string/null Process patch; merge happens before arming the next task. No caller chooses an occurrence or writes an effect-local scope. | Review changes an initialized request, Service sees the updated value, then Finalize sees its mapped decision; stale human completion preserves every predecessor field. |
| `SBT-REFUSE-01` | Wrong/stale effect, descriptor or owner association, malformed result, unsupported Error and commands from excluded families produce no successor or partial Process write. Technical handler failures remain host failures under the inherited transport contract, not BPMN Errors or successful task completion. | Replay one accepted completion, submit another task's occurrence, omit one of two outputs, and fail a handler after an external call; no fabricated normal continuation is observable. |
| `SBT-PROGRESS-01` | One control unit is pending, runnable, waiting for one human/effect result, or complete. Each accepted resumption reaches its next wait or completion within the existing internal limit. No multiple-enabled scheduling choice is reachable. | Human→Service→Service→Human, leading/trailing Service Tasks, empty mappings and long chains reach every expected wait; malformed stranded states fail validity. |

The input-availability restriction excludes some valid CIB executions whose first human task creates previously absent data. It is a conservative profile admission decision, not CIB behavior: the host may initialize required values with explicit null. Extending to runtime missing-input failure or later ingress requires its own semantics; this capsule does not silently turn CIB's failed job into an empty value.

The [scoped-data account](SCOPED-DATA-SPEC.md) remains the runtime representation. No new collection or synthetic occurrence is introduced. Static definition maps, dynamic arguments, local result patches and Process outputs remain separate. Existing effect identities, monotonic activation counters, local-owner discrimination, canonical variable ordering, deep immutability and E1/E2 occurrence publication remain mandatory.

## Lean assurance lane

Lane shape: proved

Evidence: extend the independent [data evaluator](../../BpmnSemantics/SemanticProcess/Data.lean), [effect relation](../../BpmnSemantics/SemanticProcess/EffectCompletion.lean) and [execution assembly](../../BpmnSemantics/SemanticProcess/Execution.lean). The selected laws must concern actual reachable serial execution and precise mapping premises, not evaluator equality as a substitute for meaning.

Prove input lookup uses the enclosing context and preserves it; snapshot argument/local-scope equality; exact output-target writes and preservation of other Process bindings/owners; state preservation on refused commands; and, from independently admitted exact lowering plus an accepted start, required input availability, one exact task/effect lifetime and bounded successful closure after every accepted completion. A successful transition's soundness bridge must expose the lookup, identity, patch, output and continuation premises. Do not assume the desired successor, successful preparation, input availability or an already completable wait to prove those facts.

Keep the new proof effort within three focused owners, each below 800 nonblank lines and the existing one-CPU/3-GiB/no-additional-swap limit: mapping/frame laws, reachable serial lifetime/data laws, and scheduled progress. Reuse existing algebraic and preparation laws; the structured-User-only composition theorem does not automatically cover effects. Reassess before adding another proof owner or changing representation. A required proposition that exceeds this bound remains explicitly unresolved; no silent downgrade or universal all-BPMN proof programme is authorized.

Finite checked fixtures and independent TypeScript assertions cover every rule's negative and positive witness, zero/multiple mappings, repeated source fan-out, string/null, renamed source identities and complete serial execution. The nearest non-laws are local input chaining, parent-output fallback, recomputed argument snapshots and continuation before complete result validation. Source parsing, general CIB expression equivalence, universal liveness/fairness, TypeScript correctness and Temporal refinement are not proved by these laws.

## Temporal hosting and refinement preflight

Durable start and human completion reuse content-bound Updates; one committed effect wait produces one existing `executeBpmnEffect` Activity request, with the exact definition/occurrence/descriptor/argument binding. Successful result admission precedes internal continuation and publication. Existing transport retries reuse the committed request and idempotency key; a repeated external call may occur, so the business handler must honor that key. Exactly-once external effects are not claimed. A wrong or incomplete result cannot produce a Process write or E1/E2 completion fact.

There are no timers, subscriptions, nested host lifecycles or concurrent semantic waits in this profile. Technical failure uses the existing explicit adapter failure boundary; this increment supplies no semantic incident/retry command. No semantic cancellation is admitted. Host interruption, Worker replacement and continuation must retain the exact committed wait and arguments; Workflow termination must not synthesize BPMN output. Input sampling happens at semantic activation, not on Worker dispatch or replay. The state relation pairs one semantic wait/local owner with its committed durable request and eventual admitted result, and pairs Process writes and lifecycle facts only after commit.

Before any Workflow starts, host admission rejects this private profile with `serialBusinessTaskQualificationUnavailable` in the existing rejected arm. Remove that refusal only with the deferred live witness: review an invoice, activate validation, force rollover while the effect is pending, replace the Worker, recover the same request/result, reach Finalize with the mapped decision, complete and replay every Run. Distinct subsequent Service Tasks must get distinct effect keys. A bypass mutation changing arguments, result target or occurrence must fail public state/publication assertions. This preflight establishes feasibility, not hosted support.

## Versioning consequences

Use two project-owned whole models: invoice Review→Validate→Finalize and a chain that validates then classifies an invoice before human completion. Both use real named operations through the existing configurable Activity contract, never a business-ID branch in the semantic core. Retain answer-free Lean/core schedules with independent expected identities, bindings and terminal state. CIB evidence observes delegate arguments and committed output/continuation through public APIs; generated CIB IDs and the async-before scheduler remain host facts. Retain the exact source/profile/overlay identity and distinguish source-backed calibration from full profile equivalence.

## Review and closure

Independent cold proposal approval precedes production semantic code. The first complete green source/Lean/core/protocol checkpoint requires its own cold review before live hosting or public registration. Live qualification remains owner-deferred. Closure requires rule-by-rule reconciliation across normative, CIB, Lean, independent TypeScript, differential and Temporal evidence, truthful capability/absence records, retained whole-model journeys, and independent closure approval. A private checkpoint is useful progress but cannot satisfy practical coverage acceptance.

Common-mode risks are a shared source normalization error, a profile guard accidentally widening an old mapped profile, a projection that reevaluates arguments, and a CIB observation that confuses transaction timing with durable effect identity. Independent raw argument observations, old-profile negatives, exact source-token tests, snapshot mutations and explicit host-relation evidence address different risks. The nearest unsupported claim is mixed branching or uninitialized human-created input, followed by business Error/incident handling and structured values.

Record baseline-to-closure code/document churn in the [cost ledger](../CAPSULE-COST-LEDGER.md), comparing scoped data and structured composition. Keep unknown authoring time unknown. Reassess after the mapping frame and serial reachable-lifetime guarantees; preserve the required guarantee if a smaller representation is needed rather than adding case-specific profile exceptions.
