# BPM platform

This tree contains product 2, the MIT BPM platform. [The implementation architecture](../docs/ARCHITECTURE.md) owns its modular-monolith layout and dependency direction; [the platform proposal](../docs/BPM-PLATFORM-PROPOSAL.md) owns product scope; [`implementation-status-owner:BPM-PLATFORM`](../docs/BPM-PLATFORM-IMPLEMENTATION-MAP.md#current-boundary) owns exact current status.

Directories here are ownership boundaries, not deployment-service claims. M1 is implemented through the engine gateway, artifact store, public contracts, definition deployment and exact-version start workflows, public definition routes, Node server composition root, HTTP-only definition workspace, and the separate executable showcase. M2 additionally instantiates the `operate` module for an exact confirmed-start Process-instance index and search service. M3 includes the strict Work contract, durable confirmed-Process registration, exact fake identity policy, append-only audit store, fresh all-or-error Work aggregation, actor filtering, typed task detail, retry-safe claim/release/completion mutations, durable audit-outbox delivery, strict HTTP routes, the CSS-Modules React Human Work panel, and live Temporal plus Chromium acceptance. M4 extends Operate with exact confirmed-instance locators, fresh all-or-error current-incident aggregation, authorized content-bound Retry and Cancel actions, durable action and audit-outbox state, a separate incident audit store, strict HTTP routes, the full-width Operations workspace, and isolated live plus 1280/1600 functional Chromium evidence. M5 E1 adds a representation-free committed-execution gateway, durable contiguous projection, authorized page and canonical-export routes, and fail-closed Process-instance Overview, semantic History, multi-position Diagram, and exact JSON download. Its operator-history increment adds one Operations-authorized canonical export over independently ordered Work and incident-action audit snapshots, with separate heads, restart convergence, independent execution/audit availability, and an accessible two-table Process-instance view. The Product 2 presentation increment adds source-first BPMN DI resolution, digest-bound generated sidecars, exact task, incident, token, and active-wait highlighting, and complete derived BPMN downloads without changing Product 1 source or semantics. Direct dependencies belong in their owning package manifest, exact resolution belongs in the committed pnpm lockfile, pnpm reports the production closure, and [`license-policy.json`](license-policy.json) owns only the permitted licences and exact non-standard exceptions.

Horizon 1 adds one complete shared storage mode without replacing local development mode. Shared API replicas use only PostgreSQL adapters at schema epoch 9, and the separate recovery-worker application owns the eleven bounded lifecycle, audit, and projection families. The explicit migration application applies the fixed checksum-bound catalog before either runtime starts. Shared requests read bounded-freshness projections and perform no population-wide Product 1 Query fan-out; local mode retains filesystem artifacts, SQLite, and its single-node startup behavior. Real PostgreSQL 18 evidence remains in the separate opt-in gate so ordinary package, platform, browser, and Product 1 loops stay database-free.
