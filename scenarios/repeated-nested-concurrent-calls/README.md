# Repeated, nested and concurrent Call sources

This directory contains two exact BPMN 2.0.2 sources for the [repeated, nested and concurrent Calls proposal](../../docs/capsules/REPEATED-NESTED-CONCURRENT-CALLS-PROPOSAL.md): the [supplier onboarding source](supplier-onboarding.bpmn) for Stage A and the [guarantor loan source](guarantor-loan.bpmn) for Stage B. Clause 10.3.6 makes each Call Activity activation transfer control to its called element, and Clause 13.3.4 gives the called Process the instantiation and completion semantics of a Sub-Process, so every activation creates its own called instance and the Call Activity completes when that instance completes. That is the mechanism this source witnesses.

The entry Process registers a supplier and forks into collecting tax documents followed by the Tax approval Call, and collecting bank details followed by the Bank approval Call. Both Calls run Four-eyes approval (Prepare approval, then Approve). After the join, Review risk calls Supplier risk review, which assesses the risk and then reaches the nested Check compliance Call of Compliance check (Screen sanctions). Final approval then calls Four-eyes approval a third time.

- Repeated and concurrent: the three Four-eyes approval instances have distinct called identities, and their User Task activations count per element across all instances in commit order. A completion order never routes a return to another instance's caller, including an instance of the same definition.
- Nested: the nested call keeps the outer called root live. Supplier risk review holds no task of its own and is not completed while Screen sanctions waits, so the inner return precedes the outer return.

A called instance's tasks carry that instance's own `processInstanceId`, derived deterministically from the caller instance, the Call element and the Call activation, for example `call:10:Instance_1:24:CallActivity_TaxApproval:1` for the Tax approval instance of `Instance_1`. The scenarios address called tasks by these literal identities.

The focused [runtime test](../../packages/bpmn-source/test/repeated-nested-concurrent-calls-runtime.test.ts) drives both completion orders and the nested return through the semantic core.

Two answer-free schedules are registered as standards-only [pipeline cases](../../packages/differential/test/repeated-nested-concurrent-calls-pipeline-cases.ts), each with one seeded mutation:

- [Natural order](natural-order.scenario.json) completes every task in the order the instances were invoked, tax approval before bank approval, then risk review, sanctions screening and final approval, to Process completion. Its mutation completes the outer called root while its nested call is live, which would open Final approval's Prepare approval beside Screen sanctions.
- [Reverse order with stale and cross-addressed completions](reverse-order-stale-and-cross-addressed.scenario.json) finishes the bank approval instance before the tax approval instance, so the bank instance returns into its own branch and the join keeps waiting for the tax instance. While the bank instance's Approve task is live, it completes that task addressed first with the tax instance's identity and then with the caller's, so only the exact instance tells them apart; after the tax instance has returned it completes the tax instance's Approve task again. All three are rejected with the state unchanged. Its mutation retires the tax instance at the bank return, as a return selected by the called definition or by the first-invoked record would.

## Guarantor loan (Stage B)

The [guarantor loan](guarantor-loan.bpmn) with its [handler](guarantor-loan-overlay.json) registers a loan application, verifies the applicant through a mapped root-path Call of Identity verification (Collect identity document, then Record verdict), and then enters a Guarantor review Sub-Process that declares `guarantorVerdict`. Inside it, a second mapped Call of the same definition verifies the guarantor into that local; a reviewer confirms it, and the Sub-Process publishes it to the Process on completion. The second Call's inputs read and its outputs write along the Guarantor review's chain (`CALLN-FRAME-01`), its called instance has its own identity, and its first task carries activation 2.

The focused [runtime test](../../packages/bpmn-source/test/embedded-mapped-calls-runtime.test.ts) reads the frames in committed core state. Two answer-free schedules are registered as standards-only [pipeline cases](../../packages/differential/test/embedded-mapped-calls-pipeline-cases.ts), each with one seeded mutation; the [registration controls](../../packages/differential/test/embedded-mapped-calls-pipeline-cases.test.ts) run every named mutation:

- [Verified guarantor](guarantor-verified.scenario.json) returns the applicant's verdict to the Process, then, while the guarantor instance is live, completes the returned applicant instance's Record verdict again, addresses the guarantor's Collect identity document with the applicant instance's identity and with the caller's, and all three are rejected unchanged. The guarantor's verdict lands in the Guarantor review frame, so the Process holds no `guarantorVerdict` at the Confirm guarantor wait and receives it only when the review completes. Its mutation writes the output from the hosting root.
- [Absent guarantor](guarantor-absent.scenario.json) starts without `guarantor`, so the second Call copies a present null; the guarantor's approval reaches the Guarantor review frame and never the applicant's `applicantVerdict`. Its mutation applies the first invocation's mappings to the second call, as selection by called definition would.
