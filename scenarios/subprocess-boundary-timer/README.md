# Interrupting Sub-Process boundary Timer scenarios

This directory contains one exact BPMN 2.0.2 source and two answer-free scenarios for the [interrupting Sub-Process boundary Timer capsule](../../docs/capsules/SUBPROCESS-BOUNDARY-TIMER-SPEC.md). The [scope-completes scenario](scope-completes.scenario.json) completes the child User Task so the child scope reaches quiescence before its deadline, then completes the After Scope follow-on. The [deadline-wins scenario](deadline-wins.scenario.json) fires the exact `PT1S` deadline while the child task is still live, then completes the Escalation Task that the boundary route reaches instead. One embedded Sub-Process containing a single child User Task owns one interrupting `PT1S` Timer Boundary Event, and each route reaches its own follow-on User Task — After Scope on the quiescent-completion route, the Escalation Task on the deadline route — which is what makes the route choice observable at the public boundary. The two distinct root None End Events are structural symmetry only and are not a discriminator, because the canonical observation exposes no terminal element identity.

`cancelActivity` is deliberately omitted from the source rather than written as `true`. The XSD and CMOF default it to `true`, so omission is the admissible interrupting form; lexical `false` is a separate proposition and is rejected at admission. `triggeredByEvent` is likewise omitted, and `triggeredByEvent="true"` is rejected: an Event Sub-Process is not a boundary host under this profile.

Two witnesses are deliberately **not** registered as scenarios, and the two limits are distinct rather than one scheduling choice. A pre-due firing cannot be presented to any target, because the Temporal host derives its firing instant from the wait's own committed `deadlineMs`; it lives in the quantified Lean refusal law and [the focused semantic-core test](../../packages/semantic-core/test/subprocess-boundary-timer.test.ts) instead. A post-victory stale refusal is excluded for a second reason: only `completeUserTaskInstance` stimuli are delivered to Temporal, so a stale `fireTimer` would reach no host at all, and a stale child completion after the deadline races the host's own derived firing rather than observing a settled refusal. Both stale directions are covered in Lean and the focused core test, where the order is exact. Target inputs added here must carry no winner annotation and no expected result.

Lean, the independently implemented TypeScript semantic core, and the Temporal adapter all execute this source and agree on both scenarios. No CIB Seven boundary-Timer relationship, target, or retained evidence is selected for this profile; the pinned corpus was used for scheduling and calibration only.
