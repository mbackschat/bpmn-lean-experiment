# Fulfillment journey: one parcel process called by concurrent orders

Answer-free population schedules for [PC-JOURNEY-02](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list): two customer orders run side by side, each calling one parcel-fulfillment process repeatedly, which itself calls an address check, so one called definition serves different callers, nested and repeated. The schedules return normally, return through a business Error from either Call level and cancel one caller while its Calls are open, and each pairs an ordinary path with the nearest wrong-owner, wrong-order, lost-data or stale-command case. The [scopes](../../../docs/kernel/semantics/SCOPES-SEMANTICS-SPEC.md#pc-scope-06-exceptional-call-return-and-propagated-cancellation), [work](../../../docs/kernel/semantics/WORK-SEMANTICS-SPEC.md), [propagation](../../../docs/kernel/semantics/PROPAGATION-SEMANTICS-SPEC.md) and [population](../../../docs/kernel/semantics/POPULATION-SEMANTICS-SPEC.md) semantics own the meaning; the schedules only exercise it, and the retained CIB Seven `2.2.0` answer is the target. The profile is `cibseven-2.2.0` with no source overlay, and every task is a Human Task, so no named handler is involved.

No CIB evidence is retained yet. The schedules name the pinned revision because every construct they use has retained CIB evidence in its own witness ([call-exceptional-return](../call-exceptional-return/README.md), [error-called-child](../error-called-child/README.md), [repeated-nested-concurrent-calls](../../repeated-nested-concurrent-calls/README.md)), and the hosted evidence batch produces the answer.

## Model

[fulfillment.bpmn](fulfillment.bpmn) holds three processes in one document, the first being the root.

| Process | What it holds |
|---|---|
| `Process_Order` | Starts with the String `orderId`, the Map `address` (`street`, `city`, `country`) and the List `lines` of Maps (`sku`, `quantity`). The Call `ShipParcel` of `Process_Fulfil` maps `orderId`, `address` and `lines` in and `trackingId` out. Interrupting boundaries on it: the Error `OUT_OF_STOCK` to the Human Task `ResolveShortage`, the Error `ADDRESS_REJECTED` to `HoldOrder`, and the Timer `CustomerGaveUp` (`P2D`) to `NotifyCancellation`. Normal return leads to the Human Task `ReviewShipment` (candidate group `dispatchers`) and an Exclusive Gateway that returns to `ShipParcel` on `${moreParcels == true}` and otherwise ends in *Order shipped*, so one order calls the same process once per parcel. |
| `Process_Fulfil` | The Human Task `PickParcel` writes `outcome` and `pickNote`; `short` ends in the Error End `OUT_OF_STOCK`, anything else continues to the Call `CheckAddress` of `Process_AddressCheck` (in `address`, out `addressVerified`), then the Human Task `HandOver`, which writes `trackingId` and `carrierNote`. |
| `Process_AddressCheck` | The Human Task `VerifyAddress` writes `addressVerified` and `checkNote`; `false` ends in the Error End `ADDRESS_REJECTED`, anything else in a normal End. |

Only `trackingId` crosses back to an order, so `outcome`, `pickNote`, `addressVerified`, `checkNote` and `carrierNote` are the child locals the callers must never hold. The two orders are `Order_1` (`orderId` `A-1`, Berlin, two lines) and `Order_2` (`B-2`, Lyon, one line); both start at logical time 0, so each window Timer is due at 172,800,000 ms from its Call's activation.

## Schedules

Each schedule names the acceptance clause of PC-JOURNEY-02 it witnesses. Every command in a failing schedule that is not the refused one is the valid continuation, so a refusal that leaves the state unchanged is told from one that does not.

| Schedule | Clause witnessed | Case it separates |
|---|---|---|
| [concurrent-orders-reverse-return](concurrent-orders-reverse-return.population-scenario.json) | Repeated, nested Calls reuse one child across concurrent orders; normal return; wrong caller receives no output; child locals never leak | Both orders start. The second order's whole chain, nested address check included, returns before the first order's, then the first order ends while the second calls the parcel process again and returns. `Order_1` ends with its own tracking identifier and `Order_2` with the second parcel's; neither holds a child local. |
| [cross-addressed-and-stale-commands](cross-addressed-and-stale-commands.population-scenario.json) | Wrong caller receives no output; stale previous-child command | While both parcels are open, the address check of `Order_2` is completed under `Order_1`, under the caller's identity and under the parcel's identity, and `HandOver` is completed before the address check returned. After `Order_1`'s return the address check is completed again, and after its second Call begins the first parcel's `HandOver` and `PickParcel` are addressed again. Each is refused and the valid continuation then completes both orders. |
| [out-of-stock-in-one-caller](out-of-stock-in-one-caller.population-scenario.json) | Exceptional (Error) return; one child's failure does not finish the other caller | `Order_2`'s parcel is picked, then `Order_1`'s reports `short`: the Error reaches `Order_1`'s boundary, the failed parcel is addressed again and refused, and `Order_2`'s nested check, hand-over and review complete afterwards. `Order_1` ends through `ResolveShortage` without its `trackingId`, and holds no child local. |
| [address-rejected-two-levels-down](address-rejected-two-levels-down.population-scenario.json) | Exceptional (Error) return from the nested Call; one child's failure does not finish the other caller | `Order_1`'s address check reports `false` while `Order_2`'s nested check of the same definition is open. The Error crosses the parcel process, which has no boundary, to `Order_1`'s `ADDRESS_REJECTED` boundary; the rejected parcel's `HandOver` is refused, `Order_2` completes its parcel, and `HoldOrder` ends `Order_1`. |
| [out-of-stock-on-second-parcel](out-of-stock-on-second-parcel.population-scenario.json) | Exceptional return after a normal one; lost data | `Order_1`'s first parcel returns its tracking identifier, the order calls the process again and the second parcel is out of stock. | [cancel-one-caller-mid-nested-call](cancel-one-caller-mid-nested-call.population-scenario.json) | Cancellation of one caller; wrong caller receives no output; stale previous-child command | Both parcels are open at the nested address check. `Order_2`'s window is fired an hour before it is due and is refused, then fired at 172,800,000: the interruption removes its parcel and nested check and leaves `NotifyCancellation`. The removed address check and parcel are addressed late and refused, `Order_1`, whose own window Timer is due at the same instant and never fired, completes its parcel, and the notice ends `Order_2`. |
| [cancel-during-second-parcel](cancel-during-second-parcel.population-scenario.json) | Cancellation of one caller during a repeated Call; lost data; stale firing | `Order_1` returns its first parcel and calls the process again; the first parcel's window is fired after its Call returned and is refused, then the second parcel's window, the boundary's second activation, is fired. The first return's `trackingId` survives, the second parcel's subtree is removed, and the removed address check and the first parcel's `HandOver` are refused. `Order_2` completes beside it. |

Notes for the target runners:

- A called instance is addressed by the kernel's derived identity, `call:` followed by the byte-length-prefixed caller instance, Call element and activation, nested for the address check under its parcel (`call:30:call:7:Order_1:10:ShipParcel:1:12:CheckAddress:1` for the first). Each traversal of the order's loop is a new activation of `ShipParcel`, a new parcel instance and a new activation of its window Timer, which is addressed as `CustomerGaveUp` activation 2 in the second traversal.
- `ReviewShipment` counts its activations per order, so the second review of an order is activation 2.
- The user task completions install their submitted values by name ([CIB-EXT-0005](../../../docs/CIB-BPMN-RELATION-REGISTER.md#cib-ext-0005--public-user-task-completion-installs-submitted-process-variables)) at the root of the instance that holds the task, so `outcome`, `pickNote` and `carrierNote` live in the parcel instance and `checkNote` in the address-check instance.
- The schedules fire Timers and address tasks that a refused command would leave open, so the refusals are part of the schedule rather than harness mistakes.
- The schedules carry no expected route, open wait, variable or Process state; the retained CIB evidence is the answer.
