# Multi-Instance Activity input mapping scope

Neutral inputs for the mapping-scope part of [PC-MI-10](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list) (body data of a Multi-Instance Activity). They classify the variable scope in which CIB Seven `2.2.0` evaluates a `camunda:inputOutput` input mapping declared on a Multi-Instance Activity, and whether loop-level `camunda:asyncBefore` changes that scope or only moves the point where a failure surfaces into the job. They are answer-free: the CIB Seven `2.2.0` evidence run supplies every expected result, and no schedule states one. Every scenario uses the `cibseven-2.2.0` profile with the neutral delegate-expression effect handler of the [Service Task effect scenario](../../service-task-effect/README.md).

The mapping scope is a CIB fact the [Multi-Instance Service Task witnesses](../multi-instance-service-task/README.md) must avoid, so those models carry the loop's item the standard way and declare no mapping. These models declare one on purpose. `IoParameter#execute` evaluates an input mapping against the parent variable scope, and `BpmnParse#parseActivityInputOutput` does not make a Multi-Instance inner Activity a scope; the mapped expression `${loopCounter}` names a variable local to the inner instance, so the first body's effect is the discriminator.

## Models

Each model is one sequential Service Task `ServiceTask_Notify`, generated by `loopCardinality` `${count}`, with the input mapping `position` = `${loopCounter}` declared on the Activity, followed by the User Task `UserTask_Close` so that the outer Activity's return is a visible wait.

| Model | Loop-level `camunda:asyncBefore` | Separates |
|---|---|---|
| [sequential-loop-counter](sequential-loop-counter.bpmn) | absent | where a mapping failure surfaces when the body runs inside the command that reaches the Activity |
| [sequential-loop-counter-async](sequential-loop-counter-async.bpmn) | `true` | where a mapping failure surfaces when the body runs in its own job |

## Schedules

Both schedules run the same journey: `count = 2`, a successful effect result for each of the two bodies in generation order, then the close task. A synchronous Service Task consumes its effect results inside the command that reaches it; an asynchronous one waits for each result.

| Schedule | Model | Journey | Row |
|---|---|---|---|
| [sequential-loop-counter](sequential-loop-counter.scenario.json) | sequential-loop-counter | `count = 2`; results for the first and second body, then the close task | PC-MI-10 |
| [sequential-loop-counter-async](sequential-loop-counter-async.scenario.json) | sequential-loop-counter-async | the same journey with each effect a wait answered by an `effectResult` stimulus | PC-MI-10 |
