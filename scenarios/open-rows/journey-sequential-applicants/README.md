# Sequential applicants journey: applicant Sub-Process bodies with human and automated work

Answer-free schedules for [PC-JOURNEY-03](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list): a case screens its applicants one after the other, each body a Human Task interview followed by an automated credit check, and an underwriter decides the case afterwards. A sequential Multi-Instance Sub-Process, a completion predicate that a declined credit result satisfies and an outer deadline give the empty, ordinary, early-completion and outer-interruption cases, and each schedule pairs an ordinary path with the nearest wrong-order, lost-data or stale-command case. The [Multi-Instance](../../../docs/kernel/semantics/MULTI-INSTANCE-SEMANTICS-SPEC.md), [work](../../../docs/kernel/semantics/WORK-SEMANTICS-SPEC.md) and [data](../../../docs/kernel/semantics/DATA-SEMANTICS-SPEC.md) semantics own the meaning; the schedules only exercise it. The profile is `cibseven-2.2.0`.

The credit check is a named business handler, `checkCredit`, that the exact [source overlay](sequential-screening-overlay.json) binds to a neutral effect descriptor; the model carries no probe handler and no scenario names a model identity, so a host binds the same name through its own configuration (PC-AUTO-01). Every schedule therefore names no CIB revision (`cibRevision` is `not-applicable`): the CIB runner registers only the three delegate tokens of `CibSevenScriptedEffect.HANDLER_BEANS`, so it cannot run a model whose handler carries this name. Retained CIB evidence for this journey needs a runner that registers the token, or a calibration probe that registers it as a delegate bean; the constructs it combines have their own CIB witnesses ([multi-instance-sub-process](../multi-instance-sub-process/README.md) for the sequential bodies and their outer Timer, [multi-instance-instance-sites](../multi-instance-instance-sites/README.md) for the item and counters inside a body).

## Model

| File | What it holds |
|---|---|
| [sequential-screening.bpmn](sequential-screening.bpmn) | The start variables are the String `caseId`, the List `applicants` of Maps (`name`, `incomeCents`), the Integers `screened`, `scoreSum` and `declines` at 0 and the Strings `lastScreened`, `lastBand`, `lastVerdict` and `lastNote` at `none`. The Sub-Process *Screen one applicant* loops sequentially over `applicants`, one body per item (the item is `applicant`), declares the body locals `verdict` and `interviewNote`, and ends its loop when `${declines >= 1}`. A body runs the Human Task *Interview the applicant* (candidate group `screeners`, publishing the applicant's name, declared income and position) and then the Service Task *Check the applicant's credit* (named handler `checkCredit`, asynchronous before), which takes the name, the income and the interview's `verdict` and `interviewNote` and returns `result`, a Map with an Integer `score` and a String `band`. Its output mappings write at the Process: `screened` plus one, `scoreSum` plus the score, `declines` plus one when the band is `decline`, and `lastScreened`, `lastBand`, `lastVerdict` and `lastNote` from the body. An interrupting Timer boundary *Screening window closes* (`P3D`) on the Sub-Process leads to the Human Task *Close the expired case* (`underwriters`). Normal completion of the Sub-Process leads to the Human Task *Decide the case* (`underwriters`). Both tasks publish the counters and the `last` values, so the surviving writes are visible at the outer return. |
| [sequential-screening-overlay.json](sequential-screening-overlay.json) | The exact source overlay binding the delegate token to the neutral operation `checkCredit`. |

The applicants the schedules use are `Mara Berger` (420,000 cents), `Tomas Okafor` (310,000), `Ines Vidal` (265,000) and `Noor Haddad` (198,000). The window is due 259,200,000 ms after the case starts at logical time 0.

## Schedules

Each schedule names the acceptance clause of PC-JOURNEY-03 it witnesses. Every command in a failing schedule that is not the refused one is the valid continuation, so a refusal that leaves the state unchanged is told from one that does not.

| Schedule | Clause witnessed | Case it separates |
|---|---|---|
| [empty-applicants](empty-applicants.scenario.json) | Empty case; wrong iteration count fails | No applicant: the Sub-Process completes at once, so *Decide the case* is open after the start, the window was never armed and its firing is refused, and an interview and a credit result for a body that does not exist are refused. Every counter stays 0. |
| [ordinary-three-applicants](ordinary-three-applicants.scenario.json) | Ordinary case; completed writes survive; wrong iteration data and count fail | Three bodies run in item order, human then automated, and the third item equals the first: it gets its own body, its own interview and its own credit result, so `screened` is 3, `scoreSum` sums three different results and the `last` values belong to the third body. |
| [wrong-iteration-commands](wrong-iteration-commands.scenario.json) | Wrong iteration data and count fail | While the first interview is open a credit result for it, an interview for the second body and a credit result for the second body are refused; after the interview a repeated interview, an interview for the second body and, after the first body ended, a repeated credit result (a decline that would have ended the loop) and a repeated interview are refused; an interview for a third body beyond the collection is refused; the valid continuation then decides the case. |
| [early-completion-on-decline](early-completion-on-decline.scenario.json) | Early completion; completed writes survive; surviving cancelled work fails | Four applicants; the second body's credit result is a decline, which ends the loop with the third and fourth items never begun. *Decide the case* is refused while that result is open, then offered with both bodies' writes (`screened` 2, `scoreSum` 1,190, `declines` 1); the window, the interviews and the credit result of bodies that never began are refused. |
| [window-closes-while-credit-is-open](window-closes-while-credit-is-open.scenario.json) | Outer interruption; completed writes survive; surviving cancelled work fails | The first body finishes and the second waits for its credit result. The window fired an hour early is refused, then fired at 259,200,000 it removes the open effect and leaves *Close the expired case* with the first body's writes. The removed credit result, the removed and never begun interviews, *Decide the case* and a second firing are refused. |
| [window-closes-during-first-interview](window-closes-during-first-interview.scenario.json) | Outer interruption; surviving cancelled work fails | The window closes with the first interview open and nothing written: the expired case shows the start values, and the interview and credit result of the removed body are refused. |
| [window-fired-after-the-loop-completed](window-fired-after-the-loop-completed.scenario.json) | Ordinary completion withdraws the outer window; stale firing fails | Both bodies finish; a firing of the window, a repeated credit result and *Close the expired case* are refused, and *Decide the case* completes the Process. |

Notes for the target runners:

- Inner tasks and effects are addressed by activation, counted per begun occurrence of the element in the Process instance. A sequential body begins only after the previous body ended, so the interview and the credit check of applicant k are both activation k.
- Every effect result is a scenario `effectResult` stimulus, so no handler runs: the host supplies `checkCredit` through its own configuration, and the stimulus carries each result.
- The interview submits `verdict` and `interviewNote` by name. The Sub-Process holds both as body locals, so the submission lands in that body's own scope ([CIB-EXT-0005](../../../docs/CIB-BPMN-RELATION-REGISTER.md#cib-ext-0005--public-user-task-completion-installs-submitted-process-variables)) and reaches the Process only through the credit check's output mappings.
- The schedules fire the window and address bodies that a refused command would leave unchanged, so the refusals are part of the schedule rather than harness mistakes.
- The schedules carry no expected route, open wait, variable or Process state.
