# Multi-Instance User Task bodies

Neutral inputs for [PC-MI-01](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list) (User Task bodies, both modes, collection and cardinality generation) and the User Task parts of PC-MI-08 (mutable collection), PC-MI-09 (completion predicates), PC-MI-10 (body data) and PC-MI-12 (outer Timer). They complement the standards-only [sequential](../../sequential-multi-instance/README.md) and [parallel](../../parallel-multi-instance/README.md) scenarios with the CIB attribute forms. They are answer-free: the CIB Seven `2.2.0` evidence run supplies every expected result.

## Models

Each model is one User Task `UserTask_Review` with Multi-Instance loop characteristics between a Start Event and the User Task `UserTask_Publish`, so that the outer Activity's return is a visible wait. The task's input mappings publish the body's context at its start: `subject` is the element variable `item`, `position` is `loopCounter`, and `instances`, `active` and `completed` are `nrOfInstances`, `nrOfActiveInstances` and `nrOfCompletedInstances`. Task completions write Process variables through the `verdict` result and, in the halting models, through the body-local names `status` and `note`. Under `cibseven-2.2.0` a looping User Task's own input mapping that reads the item or a counter is CIB-LIM-0019's refusal, so the models above, but for their zero-instance schedules, witness that refusal rather than agreement. The `quorum` models and `parallel-output-collection` read nothing of the instance in an own mapping: they are the agreeing, non-refused witnesses of a User Task body itself, whose counters are observable only through the completion condition (the item and the counters at a mapped site are observed on a nested task in [multi-instance-instance-sites](../multi-instance-instance-sites/README.md)).
