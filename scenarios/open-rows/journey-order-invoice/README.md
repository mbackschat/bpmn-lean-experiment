# Order invoice journey: structured data, a decision, human and automated branches, a notice and rework

Answer-free schedules for [PC-JOURNEY-01](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list): one supplier invoice with typed structured business data that a clerk enters, a Business Rule Task grades, an approver reviews on the manual branch, an invoice-posting Service Task books on both branches and a Send Task announces, with a rework loop back to the entry. The [work](../../../docs/kernel/semantics/WORK-SEMANTICS-SPEC.md), [data](../../../docs/kernel/semantics/DATA-SEMANTICS-SPEC.md) and [decision](../../../docs/kernel/semantics/DECISION-SEMANTICS-SPEC.md) semantics own the meaning; the schedules only exercise it. The profile is `cibseven-2.2.0`.

Both automated steps are named business handlers, `postInvoice` and `sendPostingNotice`, that the exact [source overlay](order-invoice-overlay.json) binds to neutral effect descriptors; the model carries no probe handler and no scenario names a model identity, so a host binds the same names through its own configuration (PC-AUTO-01). The CIB runner binds them the same way: it registers every token the overlay declares as its one scripted effect, which answers from the schedule's `effectResult` stimuli. No CIB evidence is retained yet. The schedules name the pinned revision because every construct they use has retained CIB evidence in its own witness ([business-rule-routing](../business-rule-routing/README.md), [send-task-configured-send](../send-task-configured-send/README.md), [automation-handler-reuse](../automation-handler-reuse/README.md)), and the hosted evidence batch produces the answer.

## Model

| File | What it holds |
|---|---|
| [order-invoice.bpmn](order-invoice.bpmn) | The start variable `invoice` is a Map: its `number`, a `supplier` Map (`name`, `country`, `contactEmail` and a present-Null `iban`), `lines`, a List of Maps with a Decimal `unitPrice` and repeated equal lines, an Integer `amountCents`, a Decimal `vatRate` and a present-Null `note`. The User Task *Enter the invoice* publishes the draft, declares the form field `enteredBy` and writes the corrected `invoice` and `clerk`. The Business Rule Task *Classify the invoice* maps `amountCents` and `supplierCountry` from `invoice`, evaluates `gradeDecision` and writes `grade` and `approver` from the two outputs. An Exclusive Gateway routes `A` to the Service Task *Post the invoice* and everything else to the User Task *Approve the invoice* (candidate group `approvers`, form fields `verdict` and `note`, written to `review` and `approvalNote`). Its second Exclusive Gateway sends `rework` back to *Enter the invoice* and otherwise joins the automatic branch at *Post the invoice*, which captures `invoice` and `grade` and writes the structured `receipt`. The Send Task *Send the posting notice* takes the supplier's `contactEmail`, the invoice `number` and the receipt's `ledgerEntry`, and the Process ends. |
| [grade-decision.dmn](grade-decision.dmn) | The UNIQUE decision `gradeDecision` over the Integer `amountCents` and the String `supplierCountry`: up to 50,000 cents from a `DE` supplier is grade `A` with approver `none`, up to 50,000 cents from any other supplier is `B` with `clerk`, and above 50,000 cents is `B` with `manager`. |
| [order-invoice-overlay.json](order-invoice-overlay.json) | The exact source overlay binding the two delegate tokens to the neutral operations `postInvoice` and `sendPostingNotice`. |

The invoices the schedules use: the large invoice (supplier in `DE`, amount 114,000 cents with a freight line, no IBAN) is graded `B` with `manager`; the corrected entry adds the IBAN and keeps the amount; the split entry bills the freight separately and falls to 9,000 cents, which grades `A`; the small invoice (9,000 cents, IBAN present) grades `A` at once.

## Schedules

Each schedule names the acceptance clause of PC-JOURNEY-01 it witnesses. The decisive wrong-order, lost-field and stale-occurrence cases follow an ordinary success path, and every later command in a failing schedule is the valid continuation, so the schedule also separates a refusal that leaves the state unchanged from one that does not.

| Schedule | Clause witnessed | Case it separates |
|---|---|---|
| [automatic-success](automatic-success.scenario.json) | Preserve all declared writes and the common continuation | The small invoice is entered, graded `A`, posted and noticed without the approver; `review` and `approvalNote` are never written, and the Process still ends at the common notice. |
| [manual-rework-success](manual-rework-success.scenario.json) | Preserve all declared writes and the common continuation; human branching and rework | The large invoice is graded `B`, the approver sends it back (`rework`), the corrected entry is a second activation of *Enter the invoice*, the second approval posts it and the notice follows; every structured field, the Decimals, the equal lines and the present Nulls reach the posting and the receipt. |
| [rework-reclassified-automatic](rework-reclassified-automatic.scenario.json) | Rework; the decision reads the current data | The approver sends the large invoice back, the split entry grades `A` on re-evaluation, and the invoice posts without a second approval. A stale `grade` would open a second *Approve the invoice*. |
| [wrong-order-automatic-branch](wrong-order-automatic-branch.scenario.json) | Wrong-order branch fails | On the automatic branch a completion of *Approve the invoice*, which was never offered, and a result for *Send the posting notice* before the posting are refused; the posting and the notice then complete. |
| [wrong-order-manual-branch](wrong-order-manual-branch.scenario.json) | Wrong-order branch fails | On the manual branch results for *Post the invoice* and *Send the posting notice* before the approval are refused; the approval, the posting and the notice then complete. |
| [lost-field-approval-note](lost-field-approval-note.scenario.json) | Lost field fails | The approval is submitted with its `verdict` and without the declared `note`: CIB's own answer for a completion that omits a declared field, [claim-missing-result](../human-task-result-identity/claim-missing-result.scenario.json), commits it and the output mapping reads the task-local default, so `approvalNote` is the default `none` and the approver's note is lost. |
| [lost-write-rework-entry](lost-write-rework-entry.scenario.json) | Lost field fails | After a rework the second entry submits `enteredBy` and leaves out the corrected `invoice`: the earlier `invoice` stays, the IBAN is still missing and the second approval sees the uncorrected invoice. |
| [stale-rework-occurrence](stale-rework-occurrence.scenario.json) | Stale rework occurrence fails | After the first rework a repeated completion of the first *Enter the invoice* activation, a completion naming another instance and a repeated completion of the first approval are refused; after the second entry completes, a completion of the first approval activation is refused while the second approval is open, and the second approval then completes. |

Notes for the target runners:

- Every effect result is a scenario `effectResult` stimulus, so no handler runs: the host supplies `postInvoice` and `sendPostingNotice` through its own configuration, and the stimulus carries each result.
- The decision reads the Integer `amountCents` and the String `supplierCountry` through task-local input mappings of the Business Rule Task, so the Map-valued `invoice` never reaches the decision as an input.
- The Decimal values are written in canonical spelling: with a scale above zero the coefficient does not end in a zero digit, so 4.50 is `45` with scale 1 and 1,140.00 is `114000` with scale 0.
- The corrected `invoice` is no input of *Enter the invoice*, which publishes the draft as `draft`, so the completion installs it by name at the Process root under the profile's submission rule ([CIB-EXT-0005](../../../docs/CIB-BPMN-RELATION-REGISTER.md)); `enteredBy`, `verdict` and `note` are each a form field and a task-local input, so they end with their task and reach the Process only through the output mappings.
- The schedules carry no expected route, open wait, variable or Process state.
