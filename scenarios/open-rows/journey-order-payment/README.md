# Order payment journey: correlated payment, withdrawal and repeated status updates

Answer-free population schedules for [PC-JOURNEY-06](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list): two orders each wait for a correlated payment Message while a withdrawal Message can cancel the settlement and status Messages with a payload can arrive repeatedly beside it. Success and cancellation both end the order, and each schedule pairs an ordinary path with the nearest wrong-owner, consumed-sibling or after-expiry case. The [subscriptions](../../../docs/kernel/semantics/SUBSCRIPTIONS-SEMANTICS-SPEC.md#messages) and [population](../../../docs/kernel/semantics/POPULATION-SEMANTICS-SPEC.md#message-key-correlation) semantics own the meaning; the schedules only exercise it, and the retained CIB Seven `2.2.0` answer is the target. The profile is `cibseven-2.2.0` with no source overlay, and every task is a Human Task, so no named handler is involved.

Every publication addresses its Message by name and reaches an order only through the existing [API criteria protocol](../../../docs/CIB-BPMN-RELATION-REGISTER.md#cib-ext-0025--message-correlation-by-api-criteria-and-delivered-variables): a typed match on the Process variable `orderId`, which the order published at its start. No schedule names an occurrence, an instance identifier or a subscription, and the started orders are the only instances a publication can reach (the mode is `executionsOnly`, and the model has no Message Start).

CIB evidence is retained for every schedule but `kernel-publication-retry` (Verify run 43370273960). The schedules name the pinned revision because every construct they use has retained CIB evidence in its own witness ([message-correlation-criteria](../message-correlation-criteria/README.md), [message-boundary-interrupting](../message-boundary-interrupting/README.md), [message-boundary-repeated](../message-boundary-repeated/README.md)), and the hosted evidence batch produces the answer. The two schedules that deliver a status payload differ from it at the Process Property that receives the payload, which CIB leaves unwritten ([CIB-LIM-0013](../../../docs/CIB-BPMN-RELATION-REGISTER.md#cib-lim-0013-pinned-cib-ignores-the-data-input-and-output-associations-of-an-activity-or-a-catch-event)): the CIB runner sends no payload, since CIB's Message carries only variables. The [kernel-publication-retry](kernel-publication-retry.population-scenario.json) schedule names no CIB revision (`cibRevision` is `not-applicable`), since CIB keeps no command ledger.

## Model

[order-payment.bpmn](order-payment.bpmn) starts with the String `orderId`, the String `customer` and the Integer `amountCents`, then enters the Sub-Process *Settle the order*. Inside it the Message catch *Await payment* (`payment-received`) leads to the Human Task *Record the payment* (candidate group `accounting`). After the Sub-Process the Human Task *Ship the order* (`warehouse`) ends in *Order shipped*. Two boundaries hang on the Sub-Process:

| Boundary | Behavior |
|---|---|
| *Customer withdraws* (`order-withdrawn`) | Interrupting. It removes the settlement with its payment catch and open task, and leads to the Human Task *Cancel the order* (`sales`) and *Order cancelled*. |
| *Status update arrives* (`order-status`) | Non-interrupting and repeatable. Its Data Output fills the Process Property `Property_StatusNote` with the String payload, and each delivery starts its own Human Task *Note the status update* (`sales`). |

The two orders are `Order_1` (`orderId` `A-1`) and `Order_2` (`B-2`); the catch and both boundaries of each wait on the same three Message names, so only the criteria tell them apart.

## Schedules

Each schedule names the acceptance clause of PC-JOURNEY-06 it witnesses. Every publication in a failing schedule that is not the refused one is the valid continuation, so a publication that reaches nobody is told from one that changes state.

| Schedule | Clause witnessed | Case it separates |
|---|---|---|
| [correlated-payment-success](correlated-payment-success.population-scenario.json) | Two orders receive correlated payment; success is public; consumed sibling subscription fails | Payment for `B-2` reaches `Order_2` alone, which records it and ships while `Order_1` still waits; the same payment is published again and finds no subscription, since the delivery consumed it; the payment for `A-1` then reaches `Order_1`, so the sibling's subscription was not consumed. |
| [wrong-owner-publications](wrong-owner-publications.population-scenario.json) | Wrong order or owner fails | While both orders wait, a payment without criteria, one for an order no instance holds, one by a local `orderId` the waiting scope does not hold, one by a business key neither order has and one on another Message name are each refused; the payments for `B-2` and `A-1` then settle their own orders. |
| [withdrawal-interrupts-one-order](withdrawal-interrupts-one-order.population-scenario.json) | Interrupting withdrawal; cancellation is public; delivery after scope expiry fails | The withdrawal for `A-1` interrupts `Order_1`'s settlement and leaves *Cancel the order*; the payment, a status update and a second withdrawal for `A-1` then find no subscription, `Order_2` is untouched and settles and ships, and `Order_1` ends through the cancellation task. |
| [status-updates-repeat-with-payload](status-updates-repeat-with-payload.population-scenario.json) | Repeated non-interrupting status work with payload; wrong order or owner fails; delivery after scope expiry fails | Two status updates for `A-1` start two handlers beside the waiting payment and one for `B-2` starts its own; the handlers complete in reverse order of their start; after `Order_1`'s payment is recorded a status update and a withdrawal for `A-1` find no subscription, because the Sub-Process that armed them has completed. |
| [withdrawal-after-payment-and-beside-a-handler](withdrawal-after-payment-and-beside-a-handler.population-scenario.json) | Delivery after scope expiry fails; cancellation is public; success is public | `Order_1` pays, records and then receives a withdrawal, which finds no subscription, and ships. `Order_2` receives a status update, whose handler opens, then the withdrawal, which interrupts the settlement and leaves the handler open; its payment and a further status update then find nothing, and the handler and the cancellation task end the order. |
| [kernel-publication-retry](kernel-publication-retry.population-scenario.json) | None of the row's clauses: a kernel-only witness of publication idempotence | Kernel-only twin. The payment for `B-2` is published, then repeated under the same command identifier and content, which answers the recorded delivery and consumes nothing again; a new identifier for the same payment finds no subscription; the first identifier with the payment for `A-1` is refused as other content under a settled identifier, and the payment for `A-1` under a new identifier then settles `Order_1`. |

Notes for the target runners:

- A non-interrupting boundary keeps its identity after a delivery, so every delivery of `order-status` names the boundary's first activation; a handler is addressed by the activation of its Human Task, counted per begun occurrence.
- The payload of a status update is delivered to the boundary's Data Output, which the kernel writes into `Property_StatusNote`; each delivery replaces the earlier value.
- The status boundary and the withdrawal boundary arm with their host and leave with it, so a delivery after the Sub-Process completed or was interrupted finds no subscription, and the schedules record the refusal as a publication that changes no state.
- The schedules carry no expected resolution, open wait, variable or Process state; the retained CIB evidence is the answer. `kernel-publication-retry` carries none either, and the differential compares the Lean kernel with the TypeScript kernel on it.
