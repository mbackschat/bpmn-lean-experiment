# Scheduled case journey: a date, duration or cycle start, reminders and a deadline escalation

Answer-free schedules for [PC-JOURNEY-05](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list): a case that starts on a date, after a duration or on a cycle, sends reminders while its review stays open and either completes the review or reaches its deadline, which escalates the overdue case to a manager. The [subscriptions semantics](../../../docs/kernel/semantics/SUBSCRIPTIONS-SEMANTICS-SPEC.md) own the Timer and Escalation meaning; the schedules only exercise it, and the retained CIB Seven `2.2.0` answer is the target. The Start takes each form of the root Timer Start row ([PC-TIMER-04](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list)), a date, a duration and a cycle, in three models that differ only in the Start's Timer; the reminders are a finite cycle and the deadline a duration. The profile is `cibseven-2.2.0` with no source overlay, and every task is a Human Task, so no named handler is involved.

CIB evidence is retained for every schedule of the date model (Verify run 43370273960), and the hosted evidence batch produces it for the duration and cycle schedules; `duplicate-reminder` and `late-firing-keeps-cadence` differ after the third reminder fires at its deadline, where CIB leaves a fourth reminder job due at that instant ([CIB-DEV-0006](../../../docs/CIB-BPMN-RELATION-REGISTER.md#cib-dev-0006--the-last-firing-of-a-finite-cycle-starts-an-endless-chain-at-its-deadline)). The schedules name the pinned revision because every construct they use has retained CIB evidence in its own witness ([timer-start-forms](../timer-start-forms/README.md), [timer-recurrence](../timer-recurrence/README.md), [escalation-boundary-hosts](../escalation-boundary-hosts/README.md)), and the hosted evidence batch produces the answer.

## Model

[scheduled-case.bpmn](scheduled-case.bpmn) holds a root Timer Start *On the case date* (`timeDate` `1970-01-01T08:00:00Z`) that leads to the Sub-Process *Review the case*. Inside it the User Task *Review the case* (candidate group `reviewers`) carries a non-interrupting Timer boundary *Reminder due* (`timeCycle` `R3/PT4H`) to the User Task *Follow up with the reviewer* and an interrupting Timer boundary *Deadline passed* (`timeDuration` `P2D`) to an Escalation End Event *Raise the overdue escalation* (code `OVERDUE`). An interrupting Escalation boundary *Overdue* on the Sub-Process leads to the User Task *Handle the overdue case* and the End Event *Case escalated*; normal completion of the Sub-Process leads to *Case closed*.

The model is deployed at logical time zero, the Start fires at the case date and the Timers inside the Sub-Process are armed at that instant: the date is 28,800,000 ms, the reminders are due at 43,200,000, 57,600,000 and 72,000,000, and the deadline at 201,600,000. A follow-up task is open per reminder, so the Sub-Process cannot complete before each one does.

[scheduled-case-duration.bpmn](scheduled-case-duration.bpmn) (`Process_ScheduledCaseByDuration`) replaces the Start with *Eight hours after intake* (`timeDuration` `PT8H`), due eight hours after the deployment at zero, at 28,800,000 ms, so every later instant is the date model's. [scheduled-case-cycle.bpmn](scheduled-case-cycle.bpmn) (`Process_ScheduledCaseByCycle`) replaces it with *Every eight hours* (`timeCycle` `R/PT8H`), whose occurrences are due at 28,800,000, 57,600,000 and every eight hours after; each occurrence starts a case of its own, whose Timers count from that case's start, so the second case's reminders are due at 72,000,000, 86,400,000 and 100,800,000 and its deadline at 230,400,000.

The first case gets two reminders and its review completes, which withdraws its reminder Timer; its third reminder, due at the instant the second case's first is, is then fired and refused, the second case's own fires, and the first case's last follow-up completes it. The second case gets two reminders and reaches its deadline, which interrupts it with both follow-ups open; completing a follow-up is refused and *Handle the overdue case* ends the case as escalated. |

Notes for the target runners:

- A Timer's activation is counted per begun occurrence of its element: the first reminder is activation 1 and each successor of the finite cycle the next, so the fourth firing of `R3/PT4H` names an occurrence no Timer holds.
- A case the cycle Start begins has the engine's derived identity `timer:<len>:<deploymentId>:<len>:<startEvent>:<dueMs>` ([population semantics](../../../docs/kernel/semantics/POPULATION-SEMANTICS-SPEC.md#timer-starts)), so the cycle schedule addresses its cases as `timer:1:1:13:CaseScheduled:28800000` and `timer:1:1:13:CaseScheduled:57600000`.
- A firing names the occurrence and the Timer's deadline in `logicalTimeMs`; `late-firing-keeps-cadence` states a later logical time in `at`, as a host that wakes late does.
- The schedules fire Timers that a refused firing would leave open, so the refusals are part of the schedule rather than harness mistakes.
- The schedules carry no expected route, open wait, variable or Process state; the retained CIB evidence is the answer.
