# Multi-Instance Sub-Process bodies

Neutral inputs for [PC-MI-04](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list) (collection-driven sequential Sub-Process), PC-MI-05 (collection-driven parallel Sub-Process and its 16-body capacity) and PC-MI-06 (cardinality-driven Sub-Process bodies), and the Sub-Process parts of PC-MI-07 (cardinality domain), PC-MI-09 (completion predicates), PC-MI-10 (body data) and PC-MI-12 (outer Timer). They are answer-free: the CIB Seven `2.2.0` evidence run supplies every expected result.

## Models

Every model wraps one embedded Sub-Process `SubProcess_Item` in Multi-Instance loop characteristics between a Start Event and the User Task `UserTask_Publish`, so that the outer Activity's return is a visible wait.

| Model | Mode | Generation | Body and extras |
|---|---|---|---|
| [sequential](sequential.bpmn), [parallel](parallel.bpmn) | sequential, parallel | collection `invoices`, element `invoice`; completion condition `${nrOfCompletedInstances >= quorum}` | Parallel Gateway into the User Task `UserTask_Commercial` and the chain `UserTask_Compliance`, async effect `ServiceTask_Validate`, ending at separate End Events. The Sub-Process declares body-local inputs `status` (`pending`), `note` (`${note}`, a String or present null) and `decision` (`unset`); the effect maps its result to `decision` (body-local name) and `summary` (not declared locally). Both user tasks publish `seenInvoice`, `seenStatus`, `seenNote` and `position`. |
| [parallel-simple](parallel-simple.bpmn) | parallel | collection `items`; the same completion condition | one User Task `UserTask_Inspect`; the capacity vehicle |

| [parallel-beside-branch](parallel-beside-branch.bpmn) | parallel | collection `items`, element `item` | A Parallel Gateway whose first Sequence Flow reaches `SubProcess_Lot`, the body of `parallel-entry-read`, and whose second reaches `Task_Flag`, which writes `last` from `fresh`, then the User Task `UserTask_Sibling`. |

| [parallel-inner-boundary](parallel-inner-boundary.bpmn) | parallel | collection `items`, element `item` | the body is `UserTask_Inspect` (publishing `subject` and `position`) with an interrupting `PT5S` Timer Boundary Event `BoundaryTimer_Inspect` on that inner task, routed to the inner `UserTask_Escalation`, which ends at `EndEvent_Escalated`. The Timer interrupts one instance's task, not the loop. |

Three further models are standards-profile witnesses for the racing instances of a parallel Multi-Instance Sub-Process ([#72](https://github.com/mbackschat/bpmn-lean-experiment/issues/72), `multiInstance.concurrentInstances`): they use the `bpmn-2.0.2` profile and the Data Association binding, with no Multi-Instance counters or CIB attributes. CIB's retained answer commits each race in its instance order, where the standards profile refuses it at admission ([CIB-OP-0016](../../../docs/CIB-BPMN-RELATION-REGISTER.md#cib-op-0016--a-splits-branches-run-in-declaration-order-each-to-its-next-wait-join-or-end)). Each is `Start_Race → SubProcess_Lot → End_Race`, where `SubProcess_Lot` loops in parallel over the Property `items` (the input data item `item`, no output data item) with a body that never waits, and the Process holds the Property `x` where one is written. A parallel loop whose instances meet at a write or at a completion condition has no order among them under BPMN 2.0.2 §13.3.7, so the standards reading refuses the loop.

| Model | Body | Race |
|---|---|---|
| [concurrent-condition-race](concurrent-condition-race.bpmn) | `Lot_Start → Lot_End` | the Simple Boolean completion condition `stringEquals(item,"b")` may hold in the closure that begins an instance, so which instances it cancels depends on the order |
| [concurrent-write-race](concurrent-write-race.bpmn) | `Lot_Start → SubProcess_Inner → Lot_End`; `SubProcess_Inner` is `Inner_Start → Inner_End` | its Data Output Association writes `x` from `item` before any wait, so the last instance's item is the one left |
| [concurrent-write-race-call](concurrent-write-race-call.bpmn) | `Lot_Start → Call_Q → Lot_End` | `Call_Q` takes `din` from `item` and writes `x` from `din`; it calls the process `Q` (`QS → QE`) in the same definitions |

The three schedules `parallel-entry-reads-earlier-instance`, `parallel-first-instance-completes-early` and `parallel-body-above-sibling-branch` separate the begin order of [CIB-OP-0016](../../../docs/CIB-BPMN-RELATION-REGISTER.md#cib-op-0016--a-splits-branches-run-in-declaration-order-each-to-its-next-wait-join-or-end) from one that begins every instance at entry; their retained CIB answers agree with the kernel's declaration-order, depth-first begin.

The Timer is one outer deadline over the whole body, so its occurrence is addressed as `BoundaryTimer_Item` activation 1 throughout. The `parallel-sixteen-bodies-*` schedules carry sixteen completion commands each.
