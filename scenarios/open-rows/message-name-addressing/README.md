# Message names, source identifiers and Operations

Answer-free schedules for [PC-MESSAGE-01](../../../docs/PRACTICAL-CIB7-COVERAGE-TARGET.md#delivery-task-list): whether a Message's `name` or its source identifier addresses a Message wait in CIB Seven `2.2.0`, Message names given by an expression at a running catch and at a root start, two Messages of one name (two boundaries of one host, two Event Sub-Process starts, an Event-Based Gateway's arms, a Receive Task and its own boundary, and the same pairs split across a Multi-Instance body's and an instance's scope), a Message without a name, and Operations that are consistent, foreign, shared between two waits or unresolved, and whether CIB matches them. The [subscriptions semantics](../../../docs/kernel/semantics/SUBSCRIPTIONS-SEMANTICS-SPEC.md) own the meaning; the retained CIB Seven `2.2.0` answer is the target. A delivery states the channel the target runner publishes for the wait (the Message identifier, and the Interface and Operation when the wait declares one). The models are project-authored MIT source for the `cibseven-2.2.0` profile with no source overlay.

| [two-handlers-one-name.bpmn](two-handlers-one-name.bpmn) | A None Start and the Human Task `Prepare_Order`, with two non-interrupting Message Event Sub-Processes `ESP_CancelA` and `ESP_CancelB` in the process scope, whose starts wait on `Message_CancelA` and `Message_CancelB`, two Messages that share the name `order-cancelled`. |
| [subprocess-boundary-and-handler.bpmn](subprocess-boundary-and-handler.bpmn) | A None Start and the Sub-Process `Region` around the Human Task `Serve_Customer`. `Region` has the interrupting Message boundary `Call_Boundary` on `Message_CallBoundary` and holds the non-interrupting Message Event Sub-Process `ESP_CallHandler` on `Message_CallHandler`; both Messages are named `customer-call`. |
| [mi-subprocess-boundary-and-handler.bpmn](mi-subprocess-boundary-and-handler.bpmn) | The same model with `Region` looping in parallel over the collection `items`, element `item`: the boundary belongs to the Multi-Instance body, the Event Sub-Process to each instance, so the two `customer-call` subscriptions lie in different scopes. |

| [receive-task-own-boundary.bpmn](receive-task-own-boundary.bpmn) | A None Start and the Receive Task `Receive_Approval` on `Message_Approval`, with the non-interrupting Message boundary `Approval_Reminder` on `Message_ApprovalReminder`; both Messages are named `approval`. |
| [mi-receive-task-own-boundary.bpmn](mi-receive-task-own-boundary.bpmn) | The same model with `Receive_Approval` looping in parallel over `items`, element `item`: the boundary belongs to the body, each instance's Message wait to the instance, so the two `approval` subscriptions lie in different scopes. |

## Notes for the target runners

- A schedule over a model CIB may refuse at deployment (`twin-same-scope`, `unresolved-operation`, `unnamed-message`, `start-expression`) carries the stimuli that would separate the readings if it is accepted; a refused deployment ends the run at it.
- A channel that differs from the one the runner publishes for the addressed wait (another Message identifier, or another Operation of the same Message) is rejected by the runner's channel equality before CIB is called, so those controls need the runner to state them as deliveries to CIB's name-addressed API.
- `wire` is the String Process variable that `Message_Expr` reads when `Catch_Expr` is reached, which is the start command.
- `unnamed-receive` carries the delivery that would separate the readings if the engine accepts the model, like `unnamed-message`; `esp-root-name-from-start-variable` carries a delivery that a start the engine rolls back never reaches, and the three other new schedules end at the start, where the name is resolved or refused.
- The six schedules from `two-handlers-one-name` on end at the start, where the engine either deploys the model or refuses it for a repeated Message name; the refusal is the case the kernel's `message.duplicateName` admission claims for each shape, and the two Multi-Instance models are its controls, which keep the repeated name in two scopes.

The schedules carry no expected route, open wait, variable or Process state; the retained CIB evidence is the answer.
